# [severity-3] [bug-00115] `fscnpy::npy2mri` byte-swaps 8-byte doubles using the 4-byte float helper

> [!bug] Synopsis
> ```cpp
> /* utils/fscnpy.cpp:119-128 */
> if (__archendian != __endian)
> {
>   // swap bytes
>   if (__dtype_len == 2)
>     byteswapbufshort(buf, bytes_per_slice);
>   if (__dtype_len == 4)
>     byteswapbuffloat(buf, bytes_per_slice);
>   if (__dtype_len == 8)
>     byteswapbuffloat(buf, bytes_per_slice);   /* :127 — should be byteswapbufdouble */
> }
> ```
>
> The dispatcher uses `byteswapbuffloat`
> for both 4-byte and 8-byte cases. The
> 4-byte helper iterates with stride 4
> and swaps `byte[0]↔byte[3],
> byte[1]↔byte[2]`; the 8-byte helper
> `byteswapbufdouble`
> ([`utils/bfileio.cpp:51-78`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/bfileio.cpp#L51-L78))
> iterates with stride 8 and swaps
> `byte[0]↔byte[7], byte[1]↔byte[6],
> byte[2]↔byte[5], byte[3]↔byte[4]`.
>
> For a double-precision value with bytes
> `[A B C D E F G H]`:
>
> | path                       | result            |
> |----------------------------|-------------------|
> | correct byteswapbufdouble  | `[H G F E D C B A]` |
> | bug: byteswapbuffloat (4-byte stride) | `[D C B A H G F E]` |
>
> The buggy result reverses each 4-byte
> half but doesn't exchange the halves.
> The reinterpreted double has a
> completely different mantissa /
> exponent layout — it's not a small
> precision loss, it's an unrelated
> floating-point value.
>
> The disabled `#else` branch at
> `:134-159` has the same bug at
> `:153-154`.

  `recon-all`. NPY input is opt-in.
- **Triggering configuration:** all of

  1. Input is a `.npy` file.

  3. The npy file's recorded
     endianness differs from the host's
     architecture (typically: a
     big-endian npy read on x86 little-
     endian, or vice versa).
- **FreeSurfer version(s):** confirmed
  in `$FREESURFER_VERSION` (commit
  `d932c45b79`).

## Detailed Description

### Why it's not just a precision issue

The byte-swap in floating-point IO is a
binary-level operation, not a numerical
one. A correct 8-byte swap reverses the
endianness of the IEEE-754 double's
sign, exponent, and mantissa bits in
one go. A 4-byte swap on each half
mangles the relationship between the
upper and lower 32 bits.

Concrete example: the double
`1.0` (IEEE-754 = `0x3FF0000000000000`)
in little-endian byte order is
`[00 00 00 00 00 00 F0 3F]`. In
big-endian it's `[3F F0 00 00 00 00 00 00]`.

If a big-endian npy file containing
`1.0` is read on x86 little-endian:

| step                  | bytes                     | as little-endian double |
|-----------------------|---------------------------|-------------------------|
| from disk             | `[3F F0 00 00 00 00 00 00]` | (read as LE: nonsense, very large) |
| correct swap          | `[00 00 00 00 00 00 F0 3F]` | `1.0` ✓ |
| buggy swap (4-byte ×2)| `[00 00 F0 3F 00 00 00 00]` | `~6.94e-310` (subnormal nonsense) |

So instead of `1.0` the user gets
`6.94e-310`. Every voxel of the volume
is similarly corrupted.

### Same bug in the disabled branch

The file has a `#if 1 ... #else ... #endif`
block. The disabled `#else` branch at
[`:134-159`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/fscnpy.cpp#L134-L159)
contains the same dispatch with the same
bug at `:153-154`. If the build flag is
ever flipped, the bug remains.

### Why the bug went undetected

Modern systems are predominantly
little-endian (x86, ARM in default
mode), and numpy by default writes in
the host's native endianness. So most
npy files read on x86 are also
little-endian, and the
`__archendian != __endian` branch is
never taken — the swap path is dormant.

The bug only fires when:

- A user sources an npy file from a
  big-endian system (e.g., older Sun /
  IBM / SGI systems) and reads it on
  x86, OR
- A user explicitly forces big-endian
  encoding in numpy (e.g.,
  `np.array(..., dtype='>f8').tofile`)
  and reads on x86.

Both are rare paths, but the corruption
is total when triggered.

## Root Cause

Copy-paste of the 4-byte case to the
8-byte case without updating the
function name. The function
`byteswapbufdouble` exists in the
codebase at `bfileio.cpp:51`, declared
in
[`include/bfileio.h`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/include/bfileio.h)
— so the fix is a one-line edit.

## Impact

- **`mri_convert`/`freeview` reading a
  big-endian `float64` `.npy` file on
  x86:** every voxel is corrupted; the
  loaded MRI is garbage.
- **Default `recon-all`:** unaffected
  (no NPY input).
- **Severity:** 3 — niche path, but the
  failure mode is total data corruption
  rather than a small numerical
  perturbation.

## Recommended Fix

```diff
--- a/utils/fscnpy.cpp
+++ b/utils/fscnpy.cpp
@@ -123,8 +123,8 @@ MRI* fscnpy::npy2mri(const char *npy, bool verbose)
           if (__dtype_len == 2)
             byteswapbufshort(buf, bytes_per_slice);
           if (__dtype_len == 4)
             byteswapbuffloat(buf, bytes_per_slice);
           if (__dtype_len == 8)
-            byteswapbuffloat(buf, bytes_per_slice);
+            byteswapbufdouble(buf, bytes_per_slice);
         }
@@ -149,8 +149,8 @@ MRI* fscnpy::npy2mri(const char *npy, bool verbose)
           if (__dtype_len == 2)
             byteswapbufshort(buf, bytes_per_col);
           if (__dtype_len == 4)
             byteswapbuffloat(buf, bytes_per_col);
           if (__dtype_len == 8)
-            byteswapbuffloat(buf, bytes_per_col);
+            byteswapbufdouble(buf, bytes_per_col);
         }
```

`byteswapbufdouble` is already
declared in `include/bfileio.h`. Adding
the include if missing and using the
correct function is a one-line fix per
branch (active and disabled).

## Workarounds

For users who need to load a big-endian
`float64` `.npy` file on x86: convert
to native endianness first, e.g. in
Python:
```python
import numpy as np
arr = np.load("input.npy")
np.save("input_native.npy", arr.astype(arr.dtype.newbyteorder('=')))
```
