# [severity-3] [bug-00117] `MRIsampleVolumeDerivativeScale` divides unweighted `len` sum by kernel weight sum; directional gradient is under-estimated by ~3x

> [!bug] Synopsis
> ```cpp
> /* utils/mri.cpp:11003-11049 */
> int MRIsampleVolumeDerivativeScale(MRI *mri, double x, double y, double z,
>                                    double dx, double dy, double dz,
>                                    double *pmag, double sigma)
> {
>   ...
>   step_size = MAX(.25, sigma / 5.0);
>   for (ktotal = 0.0, n = 0, len = vp1 = vm1 = 0.0, dist = step_size;
>        dist <= MAX(2 * sigma, step_size);
>        dist += step_size, n++) {
>     if (FZERO(sigma)) k = 1.0;
>     else              k = exp(-dist * dist / (2 * sigma * sigma));
>     ktotal += k;
>     len += dist;                              /* :11029 — bug: unweighted */
>
>     /* sample at +dist along (dx, dy, dz) */
>     MRIsampleVolume(mri, x + dist*dx, y + dist*dy, z + dist*dz, &val);
>     vp1 += k * val;                           /* :11034 — weighted */
>
>     /* sample at -dist */
>     MRIsampleVolume(mri, x - dist*dx, y - dist*dy, z - dist*dz, &val);
>     vm1 += k * val;                           /* :11040 — weighted */
>   }
>   vm1 /= ktotal;                              /* :11043 — divide by kernel sum */
>   vp1 /= ktotal;                              /* :11044 — divide by kernel sum */
>   len /= ktotal;                              /* :11045 — bug: divide unweighted-sum by kernel-sum */
>   *pmag = (vp1 - vm1) / (2.0 * len);
> }
> ```
>
> `vp1` and `vm1` are kernel-weighted
> averages of the volume samples at
> `±dist`. The effective "centre-of-mass"
> distance of these averages is the
> **weighted mean of distances**:
>
> `len_correct = sum(k_i · dist_i) / ktotal`
>
> but the code computes
>
> `len_buggy = sum(dist_i) / ktotal`
>
> which has no consistent
> interpretation: it divides an
> unweighted-distance-sum by a
> kernel-weight-sum.
>
> For the typical iteration with
> sigma = 0.5, step_size = 0.25, and
> 4 steps at dist = 0.25, 0.5, 0.75,
> 1.0:
>
> | quantity      | value        |
> |---------------|--------------|
> | dist          | 0.25, 0.5, 0.75, 1.0 |
> | k (exp(-d²/2σ²)) | 0.882, 0.607, 0.325, 0.135 |
> | ktotal        | 1.949        |
> | sum(dist)     | 2.5          |
> | sum(k·dist)   | 0.882·0.25 + 0.607·0.5 + 0.325·0.75 + 0.135·1.0 = 0.903 |
> | correct len   | 0.903 / 1.949 ≈ 0.463 |
> | buggy len     | 2.5 / 1.949 ≈ 1.283   |
> | bug factor    | 2.77x too large |
>
> The reported gradient magnitude is
> therefore **~2.77x too small** for this
> configuration. For larger sigma, the
> factor approaches 1 (more samples
> closer to the centre dominate, weights
> become similar), but never matches.

## Detailed Description

### The mathematical issue

A two-sided finite-difference
derivative formula needs the
"effective spacing" between the +
and - sample averages. When sample
values are kernel-weighted:

```
v̄_+ = Σ k_i · v(x + d_i · u) / Σ k_i
v̄_- = Σ k_i · v(x - d_i · u) / Σ k_i
```

If `v` is smooth (Taylor-expanded
along `u`):
`v(x + d·u) ≈ v(x) + d · (∇v · u) + O(d²)`

then
`v̄_+ ≈ v(x) + (∇v · u) · Σ k_i d_i / Σ k_i`

and the derivative recovers as
`(v̄_+ - v̄_-) / (2 · ⟨d⟩_k)` where
`⟨d⟩_k = Σ k_i d_i / Σ k_i` — the
**kernel-weighted mean** of the
distances.

The code instead computes
`Σ d_i / Σ k_i` for "len". This
mixes apples (a kernel-independent
distance sum) with oranges (a
kernel-dependent normaliser).

### Why the bug is plausibly missed

The sister function
`MRIsampleVolumeDerivative` (no
sigma scaling) at
[`:11077-11093`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L11077-L11093)
divides everything by `n` and is
consistent (unweighted). The bug
exists only in the kernel-weighted
variant, where the accumulator
types diverged.

The bug under-estimates gradient
magnitudes uniformly, which any
threshold tuned empirically would
compensate for. Tools like
`mri_watershed` use the gradient
for edge detection; thresholds in
the watershed algorithm have been
calibrated against the buggy
output, so the algorithm "works" in
practice — but the absolute
gradient values reported are
wrong.

### Impact magnitude

| sigma | step | iterations | bug factor (buggy / correct) |
|-------|------|------------|------------------------------|
| 0.5   | 0.25 | 4          | ~2.77                        |
| 1.0   | 0.25 | 8          | ~2.04                        |

| 5.0   | 1.0  | 10         | ~1.25                        |

the bug factor is ~2.8x.

## Root Cause

The function was likely
refactored from the unweighted
variant (which uses `n` as the
divisor and unweighted `len` sum)
to a kernel-weighted variant. The
accumulators for `vp1`/`vm1` were
updated to use `k*val`, and the
divisor was changed from `n` to
`ktotal`. But the `len`
accumulator (which represents
the distance scale) was left as
`+= dist` (unweighted) — yet its
divisor was changed to `ktotal`
along with the others. Either:

- both should be unweighted
  (`len += dist`, `len /= n`),
- or both should be weighted
  (`len += k*dist`, `len /= ktotal`).

The proper fix is the
kernel-weighted version (option
2) since the sample-value
accumulators are already
weighted.

## Recommended Fix

```diff
--- a/utils/mri.cpp
+++ b/utils/mri.cpp
@@ -11026,7 +11026,7 @@ int MRIsampleVolumeDerivativeScale(...)
       k = exp(-dist * dist / (2 * sigma * sigma));
     ktotal += k;
-    len += dist;
+    len += k * dist;
     xp1 = x + dist * dx;
```

Single-line change: weight the
`len` accumulator by `k` so it's
consistent with the
sample-value accumulators. The
divisor by `ktotal` is then
correct.

A more conservative fix
(preserving backwards
compatibility for tools that
have been calibrated to the
buggy behaviour) is to gate
the fix behind an environment
variable or new function
variant.

## Workarounds

Tools relying on
`MRIsampleVolumeDerivativeScale`
have been calibrated to the
buggy output, so applying the
fix may shift their behaviour.
Users who want correct
absolute gradient magnitudes
should:

- Use
  `MRIsampleVolumeDerivative`
  (unweighted, correct).
- Or compute the gradient
  externally with their own
  weighting.
