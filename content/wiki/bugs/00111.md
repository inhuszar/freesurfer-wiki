# [severity-3] [bug-00111] `JHISTOfindBin` omits the `(val − min)` shift; bins collapse toward the upper edge for volumes with non-zero minimum

> [!bug] Synopsis
> ```cpp
> /* utils/joint_histo.cpp:156-168 */
> int JHISTOfindBin(JOINT_HISTOGRAM *jhisto, double val1, double val2)
> {
>   int bins1 = jhisto->nbins_1;
>   int bins2 = jhisto->nbins_2;
>
>   int i = (int)((val1 * bins1) / (jhisto->max - jhisto->min));
>   int j = (int)((val2 * bins2) / (jhisto->max - jhisto->min));
>   /* clamp */
>   i = max(min(i, bins1 - 1), 0);
>   j = max(min(j, bins2 - 1), 0);
>   return (i * bins2 + j);
> }
> ```
>
> The bin formula scales `val` by
> `bins / (max − min)` but never
> subtracts `min`. The standard
> linear-binning formula is
>
> `bin = (int)((val − min) · bins / (max − min))`
>
> which maps `min → 0` and `max → bins`
> (clamped to `bins − 1`).
>
> The code's formula maps `val · bins / range`,
> so:
>
> | `val`             | correct bin | code's bin |
> |-------------------|-------------|------------|
> | `min`             | 0           | `(int)(min · bins / range)` |
> | `min + range/2`   | `bins/2`    | `(int)((min + range/2) · bins / range)` |
> | `max`             | `bins − 1`  | `(int)(max · bins / range)` |
>
> For a typical anatomical volume with
> `min = 0.0`, the formula coincidentally
> reduces to the correct one. For a volume
> with `min > 0` (most floating-point or
> normalised volumes, and any input where
> the minimum is a positive intensity), the
> bin index is shifted upward by
> `min · bins / range`. After clamping to
> `bins − 1`, many distinct values get
> collapsed into the top bin.

## Affected Artefacts

- **Tool:** [[mri_mi]] — only in-tree
  caller. Computes pairwise mutual
  information between two volumes via
  marginal and joint entropies.
- **Pipeline stage(s):** none in default
  `recon-all`. Standalone CLI / scripting
  use.
- **Triggering configuration:** any
  `mri_mi` invocation where either input's
  minimum value is non-zero. `JHISTOfill`
  uses the **joint** min/max
  (`flmin(min1, min2)`,
  [`utils/joint_histo.cpp:186-187`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/joint_histo.cpp#L186-L187)),
  so the bug fires whenever the joint
  minimum is non-zero.
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION` (commit
  `d932c45b79`).

## Detailed Description

### Concrete example

Consider two volumes with intensity range
`[5, 10]`, `bins = 100`,
`range = max − min = 5`:

| `val` | correct bin | code's bin (pre-clamp) | post-clamp |
|-------|-------------|------------------------|------------|
| 5.0   | 0           | `(int)(5 · 100 / 5)` = 100 | 99 (max) |
| 6.0   | 20          | `(int)(6 · 100 / 5)` = 120 | 99 |
| 7.5   | 50          | `(int)(7.5 · 100 / 5)` = 150 | 99 |
| 8.0   | 60          | `(int)(8 · 100 / 5)` = 160 | 99 |
| 9.0   | 80          | `(int)(9 · 100 / 5)` = 180 | 99 |
| 10.0  | 99          | `(int)(10 · 100 / 5)` = 200 | 99 |

Every value collapses into the top bin.
Joint entropy = 0. Mutual information
becomes `marginalentropy1 +
marginalentropy2 − 0`, which
overestimates dependence.

### Less extreme: when range > min

For `min = 5, max = 100`,
`range = 95`, `bins = 100`:

| `val` | correct bin | code's bin |
|-------|-------------|------------|
| 5.0   | 0           | `(int)(5 · 100 / 95)` = 5 |
| 50.0  | 47          | `(int)(50 · 100 / 95)` = 52 |
| 100.0 | 99          | `(int)(100 · 100 / 95)` = 105 → 99 |

The shift is by `min · bins / range`,
roughly 5 bins here. The top
`(min · bins / range)` bins are
artificially over-populated (because
many values clamp to `bins-1`), and the
bottom `(min · bins / range)` bins are
empty.

### Effect on mutual information

`mri_mi` computes:

```
MI = H(X) + H(Y) − H(X,Y)
```

where `H(X)` and `H(Y)` use 1D
histograms (computed by `HISTOcount`,
which is a different code path — see
[`utils/histo.cpp`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/histo.cpp)
— and is **not** affected by this bug)
and `H(X,Y)` uses the buggy
`JHISTOfindBin`.

Because the joint histogram collapses
toward `(bins-1, bins-1)`, joint entropy
is **underestimated**. Therefore MI is
**overestimated**.

Marginal entropies are computed
correctly (different histogram code),
so the MI score is biased upward by an
amount proportional to how much
`min / range` deviates from zero.

### `JHISTOfill`'s `flmin/flmax` choice

`JHISTOfill`
([`:170-204`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/joint_histo.cpp#L170-L204))
sets `jhisto->min = flmin(min1, min2)`
and `jhisto->max = flmax(max1, max2)` —
the joint range across both volumes.
A value at the lower end of one volume
that's above the joint min still gets
shifted, because `JHISTOfindBin` uses
the joint `min` (which it doesn't
actually subtract).

## Root Cause

The author wrote the bin formula as if
`min == 0` were assumed, then divided by
the range to scale to `[0, bins]`. The
proper linear binning formula
`(val − min) · bins / (max − min)` was
abbreviated to `val · bins / range` —
correct only when `min = 0`.

The companion 1D `HISTOcount` routine in
`utils/histo.cpp` does the
`(val − min)` shift correctly, so the
inconsistency between the two histogram
implementations may have masked the bug
during development.

## Impact

- **`mri_mi` on volumes with non-zero
  joint minimum:** MI score is biased
  upward (joint entropy
  underestimated).
- **Magnitude:** depends on
  `min / range` ratio. For
  conformed-T1 data with intensities in
  `[0, 255]`, `min ≈ 0` typically and
  the bug is largely latent. For
  fMRI / PET data with positive
  baseline, the effect can be
  significant.
- **Severity:** 3 — standalone tool, not
  in default `recon-all`; latent for
  the typical `min == 0` case but real
  for non-zero-min inputs.

## Recommended Fix

```diff
--- a/utils/joint_histo.cpp
+++ b/utils/joint_histo.cpp
@@ -158,8 +158,8 @@ int JHISTOfindBin(JOINT_HISTOGRAM *jhisto, double val1, double val2)
   int bins1 = jhisto->nbins_1;
   int bins2 = jhisto->nbins_2;
 
-  int i = (int)((val1 * bins1) / (jhisto->max - jhisto->min));
-  int j = (int)((val2 * bins2) / (jhisto->max - jhisto->min));
+  int i = (int)(((val1 - jhisto->min) * bins1) / (jhisto->max - jhisto->min));
+  int j = (int)(((val2 - jhisto->min) * bins2) / (jhisto->max - jhisto->min));
   // insure they are in range
   i = max(min(i, bins1 - 1), 0);
   j = max(min(j, bins2 - 1), 0);
```

## Workarounds

For users running `mri_mi` who need
correct MI now: pre-shift inputs to have
zero minimum (e.g.
`mri_concat in.mgz --add -<min> --o
in_shifted.mgz`).

## Provenance and Discovery

- **Discovered:** 2026-05-10 by agent
  (audit of small utility files in
  `utils/`).
- **Evidence:**
  - The bin formula at `:161-162`
    multiplies `val * bins` and divides
    by `(max - min)` — but `val` is
    not shifted by `min`.
  - For `val = min`, the formula yields
    `(int)(min * bins / range)` instead
    of 0.
  - For `val = max`, yields
    `(int)(max * bins / range)`, which
    overflows `bins-1` when `min > 0`
    and clamps to `bins-1` (correct
    bound, wrong distribution).
  - 1D companion `HISTOcount` in
    `utils/histo.cpp` does the
    `(val − min)` shift, so the joint
    case is the outlier.
