# MRIsincSampleVolume / MRIsincSampleVolumeFrame — MRI_SHORT clamp uses unsigned range [0, 65535] instead of signed [−32768, 32767]

> [!bug] Synopsis
> The two sinc-interpolation primitives in `utils/mri.cpp`
> post-clamp the accumulated `sum_z` into the output voxel's
> representable range. The `MRI_SHORT` branch clamps as if
> `short` were **unsigned**: negatives are snapped to `0` and
> large positives are capped at `65535`. FreeSurfer's `MRI_SHORT`
> is a signed `int16_t` with legal range `[-32768, 32767]`, so
> the clamp destroys legitimate negative values (e.g., bipolar
> fMRI intensities) and permits values up to `65535` — past the
> true signed maximum of `32767` — to escape unbounded,
> producing wrap-around when the double is subsequently stored
> into a `short` voxel. The `MRI_USHRT` branch has the matching
> semantics it was meant for, but it is not wired into the
> clamping ladder at all. `MRI_INT` is also unclamped.

## Affected Artefacts

- **Tool(s):** every caller of `SAMPLE_SINC` interpolation.
  - [[mri_convert]] via
    [`mri_convert/mri_convert.cpp:3418`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_convert/mri_convert.cpp#L3418)

  - [[mri_vol2vol]] through `MRIresample` at
    [`utils/mri.cpp:12236`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L12236).
  - Any tool that calls `MRIsampleVolumeType(..., SAMPLE_SINC)`

- **Pipeline stage(s):** _N/A_ for default [[recon-all]]. The

- **Platforms:** all — purely arithmetic.
- **Triggering configuration:** any sinc-interpolation call on a
  source volume whose `type == MRI_SHORT`. The defect bites
  twice: negatives are clamped to `0` (destroys signed data),
  and values in `(32767, 65535]` escape the clamp and then
  wrap on the SHORT store.

## Detailed Description

FreeSurfer distinguishes two 16-bit integer voxel types:

- `MRI_SHORT` — signed `int16_t`, range `[-32768, 32767]`. Used
  for data that can legitimately be negative (e.g., centred BOLD,
  signed distance transforms, some DTI outputs).
- `MRI_USHRT` — unsigned `uint16_t`, range `[0, 65535]`. Used
  for data that is non-negative and needs > 255 dynamic range.

The post-clamping ladder at the end of `MRIsincSampleVolume`
(and `MRIsincSampleVolumeFrame`) reads:

```cpp
if ((mri->type == MRI_UCHAR || mri->type == MRI_SHORT) && sum_z < 0.0)
  *pval = 0.0;                                    // ← clamps SHORT negatives to 0
else if (mri->type == MRI_UCHAR && sum_z > 255.0)
  *pval = 255.0;
else if (mri->type == MRI_SHORT && sum_z > 65535.0)
  *pval = 65535.0;                                // ← 65535 is USHRT_MAX, not SHORT_MAX
else
  *pval = sum_z;
```

The `65535` constant makes the intent transparent: the author
was typing the clamp ladder for the unsigned 16-bit type but
wrote `MRI_SHORT` where they should have written `MRI_USHRT`.
As a result the signed `MRI_SHORT` case ends up with
asymmetric bounds of `[0, 65535]`, and the actual `MRI_USHRT`
case is entirely missing from the clamping ladder.

### Expected Behaviour

Clamp each integer type to its own representable range:

| Type       | Range            |
|------------|------------------|
| MRI_UCHAR  | `[0, 255]`       |
| MRI_SHORT  | `[-32768, 32767]`|
| MRI_USHRT  | `[0, 65535]`     |
| MRI_INT    | `[INT_MIN, INT_MAX]` |
| MRI_LONG   | `[LONG_MIN, LONG_MAX]` |

`MRI_FLOAT` and `MRI_LONG` typically don't need clamping inside
sinc since the double `sum_z` already fits their range.

### Observed Behaviour

For an `MRI_SHORT` source:

- A valid interpolated value of `-20000` is clamped to `0`,
  destroying the magnitude and sign of the signed datum.
- A valid interpolated value of `40000` (outside SHORT range but
  inside the code's spurious `[0, 65535]` window) passes
  through unclamped. If the caller then writes `*pval` into a
  `MRI_SHORT` voxel, the C signed conversion wraps (usually to
  `-25536`), corrupting the pixel silently.

For an `MRI_USHRT` source: no branch of the clamping ladder
matches, so the final `else *pval = sum_z;` runs. That's
numerically fine (USHRT's natural range fits inside a double),
but negatives are also not clamped — if sinc lobing produces
`sum_z = -3.5` (it can in principle), the subsequent store into
a `uint16_t` voxel wraps to `65533`.

For `MRI_INT`: no clamp; no risk in practice because `sum_z`
from a sinc over `MRI_INT` rarely exceeds INT_MAX, but the
absence of a guard is worth noting.

`MRI_SHORT` by mistake.

## Root Cause

The author of the clamping ladder misidentified the two 16-bit
enum values. `MRI_SHORT` is signed `int16_t` (range
`[SHORT_MIN, SHORT_MAX] = [-32768, 32767]`); `MRI_USHRT` is
unsigned `uint16_t` (range `[0, USHRT_MAX] = [0, 65535]`). The
constant `65535` was paired with `MRI_SHORT` rather than
`MRI_USHRT`, and the implicit "negatives clamp to 0" logic was
extended to `MRI_SHORT` in the same error. `MRI_USHRT`, the
type that actually matches the clamp, is not mentioned in the
ladder at all.

## Impact

- **`mri_convert --resample_type sinc`** on a signed 16-bit
  volume silently zeroes out legitimate negative voxels and
  permits `sum_z > SHORT_MAX` to escape, wrapping on the
  subsequent store.
- **`mri_vol2vol --interp sinc`** when the source is
  `MRI_SHORT`: same.
- **Standard [[recon-all]]** is unaffected — recon-all's
  primary sampling paths use trilinear interpolation, and the
  volumes most likely to be `MRI_SHORT` in the pipeline (e.g.,
  certain atlas probability maps) are not sinc-resampled in
  the default flow.
- **fMRI / diffusion side-paths** that store signed 16-bit
  data and opt for sinc resampling hit the defect directly.

## Recommended Fix

Replace the `MRI_SHORT` clamp with its correct signed bounds
and add an explicit `MRI_USHRT` clamp with the unsigned
bounds. Also add an `MRI_INT` clamp for completeness:

```diff
-  if ((mri->type == MRI_UCHAR || mri->type == MRI_SHORT) && sum_z < 0.0)
-    *pval = 0.0;
-  else if (mri->type == MRI_UCHAR && sum_z > 255.0)
-    *pval = 255.0;
-  else if (mri->type == MRI_SHORT && sum_z > 65535.0)
-    *pval = 65535.0;
-  else
-    *pval = sum_z;
+  switch (mri->type) {
+    case MRI_UCHAR:
+      *pval = (sum_z < 0.0)     ? 0.0
+            : (sum_z > 255.0)   ? 255.0
+            : sum_z;
+      break;
+    case MRI_SHORT:
+      *pval = (sum_z < -32768.0) ? -32768.0
+            : (sum_z >  32767.0) ?  32767.0
+            : sum_z;
+      break;
+    case MRI_USHRT:
+      *pval = (sum_z < 0.0)      ? 0.0
+            : (sum_z > 65535.0)  ? 65535.0
+            : sum_z;
+      break;
+    case MRI_INT:
+      *pval = (sum_z < (double)INT_MIN) ? (double)INT_MIN
+            : (sum_z > (double)INT_MAX) ? (double)INT_MAX
+            : sum_z;
+      break;
+    default:
+      *pval = sum_z;
+      break;
+  }
```

Apply the same patch to `MRIsincSampleVolumeFrame` at
[`utils/mri.cpp:10790–10797`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L10790-L10797).

### Alternative Fixes Considered

Delegate the clamp to the caller by always returning the raw
`sum_z` and relying on the store site to saturate. That keeps
the sinc routines purely mathematical, but requires touching
every store site and is riskier than the targeted clamp fix
above.

## Workarounds (If Any)

Users with signed 16-bit volumes should convert to `MRI_FLOAT`
before sinc resampling (`mri_convert in.mgz -odt float
tmp.mgz`), then resample, then convert back at the end if
necessary.
