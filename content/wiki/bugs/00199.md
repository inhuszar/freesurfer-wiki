# [severity-4] [bug-00199] `fem core` — Element3d interpolation cache is never invalidated; the untangler's corrected node displacements are ignored for elements that were already queried

> [!bug] Synopsis
> `Element3d` (the tetrahedral element of the FEM core behind [[surf2vol]])
> turns its four node displacements into a per-element affine displacement
> field on first use and keeps that result behind a flag
> (`m_isInterpolUpdated`) that is set to `true` once and never reset. In every
> surf2vol FEM step the element containing each constraint point is queried
> (and therefore cached) right after the linear solve; the topology
> ("untangling") solver then rewrites the node displacements to repair folded
> elements, but the cached elements keep interpolating the **old**
> displacements. The deformation exported at the end of the step
> (`convert_to_delta`, `update_bc_container`) is therefore assembled from a
> mixture of pre-repair (cached) and post-repair (never-queried, e.g. folded)
> elements — a non-conforming, discontinuous field exactly where folds were
> repaired. This sits on the default [[mri_cvs_register]] path
> (`-topology_old -compress`), on every FEM step whose log prints
> `solving topology problems`.

## Affected Artefacts

- **Tool(s):** [[surf2vol]] (FEM core: `fem_elastic/fem_3d.cpp`, `mesh.h`, `solver.h`);
  the morph it writes is consumed by [[exportGcam]] and [[mri_cvs_register]]'s later stages.
- **Pipeline stage(s):** [[mri_cvs_register]] elastic (surface-driven) stage, i.e. the
  `surf2vol … -topology_old -compress …` call at
  [`mri_cvs_register/mri_cvs_register:389-403`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_cvs_register/mri_cvs_register#L389-L403) followed by `exportGcam`.
- **FreeSurfer version(s):** confirmed in 8.2.0; the cache flag and its
  one-way set date from the 2008-03-14 import of the `fem_elastic` sources
  (commit `4b881dc775f`) — no version in the tree ever resets it.
- **Platforms:** all
- **Triggering configuration:** any surf2vol step in which (a) at least one
  element containing a constraint point (BC point) is queried before the
  untangler runs — always true, see below — and (b) the mesh contains an
  orientation problem (a folded/inverted tetrahedron) so that the topology
  solver changes node displacements. With the CVS options this is
  the case for every step whose log contains `orientation_pbs` /
  `solving topology problems`; steps with `NO ORIENTATION PBs FOUND !!!`
  are not affected.

## Detailed Description

`Element3d` stores, for each tetrahedron, the coefficients of the shape
functions (`m_ca…m_cd`, a function of the **node coordinates** only) and the
coefficients of the interpolated **displacement** field (`m_int_a…m_int_d`,
a function of the **node displacements**):

```cpp
  mutable tCoords m_int_a, m_int_b, m_int_c, m_int_d;
  void update_interpol_coefs() const;
  mutable bool m_isInterpolUpdated;
```

The displacement coefficients are computed lazily by
`update_interpol_coefs()`, which reads the current node deltas and finally
sets the "valid" flag:

```cpp
void
Element3d::update_interpol_coefs() const
{
  assert(m_vpNodes.size()==size_t(4));

  if ( !m_isShapeUpdated )
    update_coefs();

  m_int_a.set(0.0);
  m_int_b.set(0.0);
  m_int_c.set(0.0);
  m_int_d.set(0.0);

  for (int i=0; i<4; ++i)
  {
    const Coords3d& delta = m_vpNodes[i]->delta();
    m_int_a += m_ca(i) * delta;
    m_int_b += m_cb(i) * delta;
    m_int_c += m_cc(i) * delta;
    m_int_d += m_cd(i) * delta;
  }
  m_isInterpolUpdated = true;
}
```

The flag is initialised to `false` in the constructor
([`fem_elastic/fem_3d.cpp:111-115`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fem_3d.cpp#L111-L115)) and assigned `true` at
[`fem_elastic/fem_3d.cpp:366`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fem_3d.cpp#L366); a search of the whole `fem_elastic/` tree
shows no other writer — there is no invalidation hook and `TNode::set_delta()`
([`fem_elastic/node.h:26-29`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/node.h#L26-L29))
does not reach the elements. Both consumers of the cache test the flag:

```cpp
tDblCoords
Element3d::dir_img(const tDblCoords& src_coords) const
{
  if ( !m_isInterpolUpdated )
    update_interpol_coefs();

  return src_coords + m_int_a
         + src_coords(0) * m_int_b
         + src_coords(1) * m_int_c
         + src_coords(2) * m_int_d;

}
```

(`inv_img` has the same guard at [`fem_elastic/fem_3d.cpp:394-395`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fem_3d.cpp#L394-L395).)

`TMesh::dir_img` is where the stale and the fresh elements meet:

```cpp
TMesh<Cstr,n>::dir_img(const tCoords& c_src,
                       bool signalTopology) const /*throw(gmpErr) */
{
  tCoords img;
  const tElement* pelt = this->element_at_point( c_src );

  if ( !pelt )
    img.status() = cOutOfBounds;
  else if ( pelt->orientation_pb() )
    img.invalidate();
  else
    img = pelt->dir_img( c_src );

  return img;
}
```

A folded element (`orientation_pb()` reads the node deltas **directly**, via
`dst_coords()`, so it is evaluated against the *new* geometry) is never
cached before the repair, because during the earlier queries (items 1 and 2 above) it was reported
invalid and skipped ([`fem_elastic/mesh.h:1249-1250`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/mesh.h#L1249-L1250)). After the repair it is valid and gets
fresh coefficients on its first post-repair query. Its cached neighbours —
precisely the elements that contain BC points, i.e. those around the
cortical surfaces — keep interpolating the
pre-repair displacements.

### Expected Behaviour

After the topology solver has rewritten node displacements, every
subsequent `Element3d::dir_img` / `inv_img` must interpolate the **current**
node displacements, so that the exported transform is the continuous,
piecewise-linear field defined by the repaired nodes (this is also what
`orientation_pb()` — which is evaluated on the repaired nodes — implicitly
assumes).

### Observed Behaviour

Elements queried before the repair continue to return the pre-repair
displacement; elements first queried after it return the repaired one. The
two fields disagree at every shared face between a stale and a fresh element,
so the exported displacement field is discontinuous (non-conforming) around
repaired folds, the folded elements use the *new* displacements while their
cached neighbours use the *old* ones, and the transform used to re-place the
BC points for the next step (`update_bc_container`) is evaluated in exactly the
(cached) elements that contain those points. The failure is silent: there is
no warning, and the topology check (`orientation_pb`) cannot reveal the
inconsistency because it reads the node deltas, not the cache.

## Root Cause

The element caches a quantity derived from **mutable** state (the node
displacements) but exposes no invalidation path: the flag
`m_isInterpolUpdated` is `mutable`, set to `true` once in
`update_interpol_coefs()`, and nothing — neither `TNode::set_delta()`, nor the
two topology solvers that call it, nor `TSolver::comm_solution()` — clears it.
The cache presumably assumes that displacements are set exactly once per
mesh (no comment documents the assumption); the untangler, added to surf2vol
a month after the sources were imported (2008-04-18, `9761aeb9b6b`), is a
second, post-query writer of the same nodes.
The shape-function cache `m_isShapeUpdated` (a function of the immutable
`coords()`) is correct to leave valid; the interpolation cache shares the same
"compute once" pattern but depends on data that does change.

## Impact

- **Output affected:** the `.tm3d` morph (and therefore the `exportGcam` m3z)
  written by surf2vol at the end of every FEM step that needed untangling.
  The error is silent.
- **Where:** discontinuities (old vs repaired displacement) on the faces
  between cached BC-containing elements and repaired neighbours. The BC points
  come from the cortical surfaces, so the cached elements are those around
  them; which fraction of repaired folds touches such elements has not been
  measured. The constraint points used to start the next step are moved
  through the same stale elements.
- **Default path:** every [[mri_cvs_register]] run (default template
  `cvs_avg35`) executes this code (17 FEM steps); the bug fires on each step
  that prints `solving topology problems`.
- **Why 4 and not 5:** the bug straddles the two top tiers. By reach it is on
  the default [[mri_cvs_register]] path, which argues for 5; but
  [[mri_cvs_register]] is not one of the schema's listed critical pipelines,
  the effect is confined to elements near repaired folds, its magnitude on real data is unquantified (see the gap above),
  and the later volumetric `mri_nl_align` stages of `mri_cvs_register`
  refine the alignment. Per the schema's tie-breaker the lower score is
  recorded. The same reasoning is used for [[00195]].
- **Related:** with the `-ksp_type preonly -pc_type jacobi` CVS options the
  linear solve itself is not converged ([[00200]]), and the element stiffness
  omits the volume factor ([[00207]]); those defects change *how often* folds
  occur but are independent of this one.

## Recommended Fix

Never serve interpolation coefficients that were computed from different
node displacements. The smallest, safest change is to recompute them on each
call (a few dozen multiply-adds; verified with the element-level reproducer to return
`0.5 0.5 0.5` in the example above):

```diff
--- a/fem_elastic/fem_3d.cpp
+++ b/fem_elastic/fem_3d.cpp
@@ Element3d::inv_img(const tDblCoords& c) const
 {
-  if ( !m_isInterpolUpdated )
```

### Alternative Fixes Considered

- **Explicit invalidation.** Add `void Element3d::invalidate_interpol() { m_isInterpolUpdated = false; }`
  (virtual hook on `TElement`) and call it for every element of the mesh at the
  end of `solve_topology_problems()` / `TopologySolver()` (and from
  `TSolver::comm_solution()`). This keeps the cache — useful because
  `convert_to_delta` calls `dir_img` about 16.8 million times per step
  (256³ voxels) — at the cost of having to find every writer of node
  displacements; the recompute-on-call variant above is more robust, and the
  per-call overhead has not been measured.
- Make `TNode::set_delta()` notify the elements that contain the node (they
  are already tracked by id: `get_elt_citer`).

A regression test should build a one-element mesh as in the Reproducer,
mutate a node displacement after the first `dir_img`, and assert that the
second call reflects it; an end-to-end check can compare a surf2vol step
containing orientation problems before and after the fix.

## Workarounds (If Any)

None at the user level: the cache is internal to every surf2vol FEM step and
both topology solvers (`-topology_old` or not) write node displacements after
the cache has been filled.
