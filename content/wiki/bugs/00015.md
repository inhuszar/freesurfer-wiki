# MRIxfmCRS2XYZ — shear gate tests only the positive side; negative shears are silently dropped

> [!bug] Synopsis
> `MRIxfmCRS2XYZ` in `utils/mri.cpp` is the primitive that builds
> the voxel-to-RAS matrix from a `VOL_GEOM`. When the caller opts
> in with `useshear = true`, the function is supposed to compose
> the shear components `s_r, s_a, s_s` into the output matrix.
> The gate that decides whether to do so is
> `mri->s_r > 1e-5 || mri->s_a > 1e-5 || mri->s_s > 1e-5` — a
> one-sided threshold that only fires for **positive** shear values.
> Any volume whose shear vector lies below the positive threshold —
> including any volume with negative shear of any magnitude — flows
> through the function as if it had zero shear, even when the
> caller explicitly asked for the shear-aware transform. The
> returned `voxel → RAS` matrix is then silently wrong.

## Affected Artefacts

- **Tool(s):** Every caller that passes `useshear = true` to
  `MRIxfmCRS2XYZ`, `VOL_GEOM::get_Vox2RAS`, or
  `VOL_GEOM::get_RAS2Vox`. In-tree callers with `useshear = true`
  at the audited commit:
  - [`utils/warpfield.cpp:70–73`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/warpfield.cpp#L70-L73)
    — warp-field construction for `mgz`-intent warp volumes
    (comment explicitly says "pre-calculated transform matrix
    taking shears into consideration").
  - [`utils/warpfield.cpp:451–453`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/warpfield.cpp#L451-L453)
    — the same for GCAM warp conversion.
  - [`include/mri.h:628`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/include/mri.h#L628)
    — `MRIsetRasXform` / voxel-to-RAS recovery.
  - All non-explicit callers use the default `useshear = false`
    and are unaffected.
- **Pipeline stage(s):** _N/A_ for standard [[recon-all]]. The
  defect lives on the warp-conversion path used by
  [[mri_warp_convert]] and by GCAMORPH-based warp pipelines that
  serialize through `warpfield.cpp`. recon-all's own M3Z path
  does not route through `warpfield.cpp` at this commit.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit
  `d932c45b79`.
- **Platforms:** all — purely arithmetic.
- **Triggering configuration:** any `VOL_GEOM` whose shear
  components are negative (or whose non-zero positive shear is
  below `1e-5`) combined with a caller that has opted into the
  shear-aware transform. Standard scanner-acquired MRI has zero
  shear, so most inputs pass unaffected; inputs with shear —
  manufactured test volumes, derived DTI outputs, or volumes
  whose shear was reconstructed from an affine LTA — are at risk.

## Detailed Description

A 4×4 voxel-to-RAS transform with non-zero shear is built as
`V2R = T · (Mdc · D · S) · [0 0 0 1]` (simplified) where `S` is
an upper-triangular identity matrix whose off-diagonals carry the
shear components. FreeSurfer stores `s_r, s_a, s_s` in
`VOL_GEOM` and applies them via an explicit `matshear` matrix
that multiplies the direction-cosines-and-scaling block.

The gate that decides whether this multiplication happens is a
one-sided magnitude check:

```cpp
if (useshear && (mri->s_r > 1e-5 || mri->s_a > 1e-5 || mri->s_s > 1e-5))
{
  MATRIX *matshear = MatrixIdentity(4, NULL);
  *MATRIX_RELT(matshear, 1, 2) = (MRIxfmCRS2XYZPrecision)mri->s_r;
  *MATRIX_RELT(matshear, 1, 3) = (MRIxfmCRS2XYZPrecision)mri->s_a;
  *MATRIX_RELT(matshear, 2, 3) = (MRIxfmCRS2XYZPrecision)mri->s_s;
  ...
  m = MatrixMultiplyD(m, matshear, NULL);
}
```

The condition is `x > 1e-5`, not `|x| > 1e-5`. A shear of
`s_r = -0.1` (a plausible value for legitimately-sheared inputs)
satisfies `-0.1 > 1e-5` as **false**, so the whole branch is
skipped and the returned matrix contains no shear.

### Expected Behaviour

When `useshear == true` and any shear component is non-negligible
in **either** sign, the shear matrix should be composed into the
output. The obvious test is
`fabs(mri->s_r) > 1e-5 || fabs(mri->s_a) > 1e-5 || fabs(mri->s_s) > 1e-5`.

### Observed Behaviour

For any `VOL_GEOM` with only negative shears (or mixed shears
where none is `> 1e-5` but some are `< -1e-5`), the returned
matrix omits the shear component entirely. Subsequent voxel ↔ RAS
conversions using that matrix place voxels at the wrong spatial
locations by an amount proportional to the dropped shear times
the voxel coordinate.

For a voxel at `(col, row, slc) = (128, 128, 128)` with dropped
`s_r = -0.1`, the R coordinate is off by
`0.1 × (row + slc) = 25.6 mm` relative to a correctly-composed
transform — not a small error for a transform the caller asked
for with `useshear = true`.

### Reproducer

> [!gap] Reproducer not yet constructed
> A direct demonstration:
>
> 1. Build a synthetic `VOL_GEOM` with
>    `xsize = ysize = zsize = 1`, direction cosines RAS,
>    `s_r = -0.1`, `s_a = s_s = 0`.
> 2. Call `mri->get_Vox2RAS(0, true)`.
> 3. Inspect the `(1, 2)` element of the returned 4×4. With the
>    bug present, it equals `mri->y_r * mri->ysize` (shear-free);
>    with the fix, it equals `mri->y_r * mri->ysize +
>    mri->s_r` (shear added).

## Root Cause

The gate was written as a "skip the shear branch if the shear is
numerically negligible" check, but without applying `fabs`. The
positive-side test silently drops any negative shear regardless
of magnitude, which is the opposite of "negligible". Shear
off-diagonals are legitimately signed, so the gate must be a
magnitude test.

## Impact

- **Warp-field construction** (`utils/warpfield.cpp`). The
  "pre-calculated transform matrix taking shears into
  consideration" comment at line 69 makes the intent explicit.
  On any input warp whose source or atlas `VOL_GEOM` carries a
  negative shear, the pre-calculated `srcVox2RAS` and
  `dstVox2RAS` matrices are shear-free. Any subsequent
  `rasSrc → voxSrc → warp → voxDst → rasDst` lookup misplaces
  the sampled point by the dropped shear times the voxel
  coordinate.
- **Standard [[recon-all]]** is not affected because its active
  primitives read voxel-to-RAS via the default `useshear = false`
  path (see `extract_i_to_r` in `utils/mri.cpp:719–724`), and
  conformed MRI volumes have zero shear. The defect lives on
  the warp-conversion side of the codebase.
- **Any downstream tool** that links `libutils` and calls
  `MRIxfmCRS2XYZ(vol, base, true)` — the number of such tools is
  small today but the primitive is widely exported, so a
  low-level defect here has latent reach.

## Recommended Fix

Replace the one-sided gate with a magnitude test:

```diff
-  if (useshear && (mri->s_r > 1e-5 || mri->s_a > 1e-5 || mri->s_s > 1e-5))
+  if (useshear && (fabs(mri->s_r) > 1e-5 ||
+                   fabs(mri->s_a) > 1e-5 ||
+                   fabs(mri->s_s) > 1e-5))
   {
```

The fix changes the gate's semantics to "apply the shear matrix
if any component's magnitude exceeds the epsilon". On zero-shear
inputs the branch still does not fire (matching existing
behaviour). On positive-shear inputs above the threshold it
still fires (matching existing behaviour). On negative-shear
inputs below `-1e-5`, it now fires — correcting the defect.

### Alternative Fixes Considered

Simply drop the gate and always apply `matshear` when
`useshear == true`. The matshear matrix reduces to the identity
when all shear components are zero, so composing it has no
effect other than the cost of one 4×4 multiply. The `1e-5`
threshold exists purely as an optimisation; a correct fix does
not need it. Preserving the threshold via `fabs` is the minimal
change.

## Workarounds (If Any)

Users can bypass the defect by constructing the shear-aware
transform by hand (compose `matshear` with the existing
`useshear = false` result) whenever they have a volume with
negative shear. There is no user-facing flag that papers over
the defect.
