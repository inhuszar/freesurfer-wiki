# [severity-4] [bug-00123] `GTMrbv` zeros `nhits` every frame, dividing `rbvsegmean` by zero for multi-frame PET

> [!bug] Synopsis
> ```cpp
> /* utils/gtm.cpp:1287-1370 (excerpt) */
> for (f = 0; f < gtm->nframes; f++) {
>     ...
>     nhits = MatrixAlloc(gtm->beta->rows, 1, MATRIX_REAL);  /* :1321 — bug */
>     for (c = 0; c < gtm->rbvseg->width; c++) {
>       for (r = 0; r < gtm->rbvseg->height; r++) {
>         for (s = 0; s < gtm->rbvseg->depth; s++) {
>           segid = MRIgetVoxVal(gtm->rbvseg, c, r, s, 0);
>           if (segid < 0.5) continue;
>           ...
>           for (nthseg = 0; nthseg < gtm->nsegs; nthseg++)
>             if (gtm->segidlist[nthseg] == segid) break;
>           if (f == 0) nhits->rptr[nthseg + 1][1]++;  /* :1336 — only counts on f=0 */
>           ...
>           v2 = MRIgetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f);
>           MRIsetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f, v2 + val);
>         }
>       }
>     }
>   }  /* :1353 — end of for(f) */
>   ...
>   for (nthseg = 0; nthseg < gtm->nsegs; nthseg++) {
>     for (f = 0; f < gtm->nframes; f++) {
>       val = MRIgetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f)
>           / nhits->rptr[nthseg + 1][1];                /* :1366 — div by zero */
>       MRIsetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f, val);
>     }
>   }
>   MatrixFree(&nhits);
> ```
>
> `nhits` is a per-seg voxel
> count used to normalise the
> running per-seg-per-frame
> sum into a mean. It is
> allocated inside the
> per-frame `for(f)` loop, so
> each frame iteration
> overwrites the pointer with
> a fresh **zero-filled**
> matrix (leaking the previous
> one). The increment is
> guarded by `if (f == 0)`,
> which was the developer's
> intent: count only once.
>
> But because the allocation
> is also inside the loop,
> the counts populated during
> `f == 0` are immediately
> lost when `f` advances to
> 1. By the time the loop
> ends, `nhits` is the
> freshly-zero allocation
> from `f == nframes - 1`.
> The post-loop division at
> `:1366` is then `rbvsegmean
> / 0`, producing Inf for
> positive accumulators and
> NaN for zero accumulators.
>
> The output file
> `aux/rbv.segmean.nii.gz` is
> therefore silently
> corrupted for any run with
> `nframes > 1`.

  the RBV "segment-mean" QA
  volume that records the

  any `mri_gtmpvc --rbv …
  --i <multi-frame-PET>` run

  not depend on `nhits` —

## Detailed Description

### Frame-by-frame behaviour

| frame `f` | what happens to `nhits` |
|-----------|------------------------|
| f = 0 | `MatrixAlloc(...)` — fresh zero matrix. Inner voxel loop runs `nhits[nthseg+1][1]++` for each in-mask voxel. End of iteration: real counts. |
| f = 1 | `MatrixAlloc(...)` — pointer **overwritten** with a fresh zero matrix; the previous (correctly populated) matrix is **leaked**. Inner voxel loop runs, but `if (f == 0)` is false so no increment. End of iteration: all zeros. |
| f = 2 … n-1 | Same as f=1. |

After the `for(f)` loop closes
at `:1353`, `nhits` points to
the fresh allocation from the
final iteration: **all zeros**.

### The post-loop divide

```cpp
/* :1364-1369 */
for (nthseg = 0; nthseg < gtm->nsegs; nthseg++) {
    for (f = 0; f < gtm->nframes; f++) {
      val = MRIgetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f)
          / nhits->rptr[nthseg + 1][1];
      MRIsetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f, val);
    }
}
```

For every `(nthseg, f)` pair,
`nhits[nthseg+1][1]` is 0.

`val / 0`:
- `val > 0` → `+Inf`
- `val < 0` → `-Inf`
- `val == 0` → `NaN`

The `MRIsetVoxVal` writes
these into `rbvsegmean`.

`mri_gtmpvc.cpp:1177` then
calls
`MRIwrite(gtm->rbvsegmean,
"…/aux/rbv.segmean.nii.gz")`
without sanity-checking.
The on-disk file contains
`Inf`/`NaN` voxels.

### Why nframes==1 works

For `nframes == 1`, the
`for(f)` loop executes
exactly once with `f == 0`.
The single `nhits`
allocation **is** the one
that gets populated, and
survives to the post-loop
divide. Static-PET use cases
(single-frame FDG, amyloid,
or tau imaging) — by far
the most common — are
unaffected.

### Why this is severity 4

- **Silently wrong QA output**
  for every dynamic PET run
  (multi-frame PET, used in
  TAC analysis, kinetic
  modeling, Logan
  graphical analysis).
- **No warning or error**;
  tool reports success.
- **Downstream consequence**:
  any script that loads
  `rbv.segmean.nii.gz` for
  per-seg time-activity-curve
  extraction gets Inf/NaN.
- **Reachable**: triggered
  by the documented `--rbv`
  flag plus any multi-frame
  PET input.
- **Reviewer attestation in
  comment**: docstring at
  `:1196-1207` confirms
  `GTMrbv` was a "re-write
  of `GTMrbv0()` which did
  not manage memory very
  well" — the bug arose
  during this refactor.

### Comparison with the
correct `GTMrbv0`

The earlier
[`GTMrbv0`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/gtm.cpp#L1420-L1523)
has the correct structure:

```cpp
/* :1488 — nhits allocated OUTSIDE per-frame loop */
nhits = MatrixAlloc(gtm->beta->rows, 1, MATRIX_REAL);
for (s = 0; s < gtm->anatseg->depth; s++) {
    for (c = 0; c < gtm->anatseg->width; c++) {
      for (r = 0; r < gtm->anatseg->height; r++) {
        ...
        nhits->rptr[nthseg + 1][1]++;  /* unconditional */
        for (f = 0; f < gtm->yvol->nframes; f++) {
          ...
        }
      }
    }
}
```

`GTMrbv0` keeps the per-voxel
loop outer and the per-frame
loop inner. `nhits` allocated
once, counts incremented
once per voxel,
unconditionally. The
post-loop divide works.

When the developer rewrote
`GTMrbv0` → `GTMrbv` to
swap the loop order (so
frame-sized intermediates
`yhat0seg`, `yhatseg`,
`yseg` can be allocated
once and reused per frame
instead of held in nframes-deep
volumes simultaneously),
they correctly added the
`if (f == 0)` guard to the
increment — but did not
move the `nhits` allocation
out of the new outer loop.

## Root Cause

Refactoring error: when
`GTMrbv0` was rewritten as
`GTMrbv` to interchange the
voxel and frame loops (for
memory efficiency), the
`nhits` allocation was kept
inside what became the
outer (per-frame) loop. The
`if (f == 0)` increment
guard was added to avoid
double-counting, but is
self-defeating because the
matrix is reallocated to
zero on every subsequent
frame iteration.

Secondary defect: each
per-frame `MatrixAlloc`
leaks the previous matrix
(no `MatrixFree` between
iterations). For a 30-frame
PET acquisition this leaks
~29 small matrices per RBV
call.

## Impact

- **Static PET (nframes=1):**
  unaffected.
- **Dynamic PET (nframes
  ≥ 2):** `aux/rbv.segmean.nii.gz`
  contains `Inf` / `NaN`
  values for **every** segment
  in **every** frame. The
  main `rbv.nii.gz` output is
  correct.
- **Downstream:** scripts
  that extract per-segment
  time-activity curves from
  `rbv.segmean.nii.gz`
  receive Inf/NaN.
- **Severity:** 4 — silent,
  reproducible, affects real
  research workflow
  (dynamic PET PVC + RBV).

Moves the `MatrixAlloc` out
of the `for(f)` loop. The
existing `if (f == 0)`
guard at `:1336` then
correctly increments
`nhits` exactly once per
voxel, and the counts
survive into the post-loop
divide. Also eliminates the
per-frame memory leak.

## Workarounds

For users running dynamic
PET with RBV: the main
`rbv.nii.gz` voxel-wise
output is unaffected. To
compute per-segment means
manually, post-process
`rbv.nii.gz` against
`seg.rbv.nii.gz` (the
saved RBV segmentation
volume), e.g.:

```
mri_segstats --seg seg.rbv.nii.gz \
             --i rbv.nii.gz \
             --avgwf rbv_per_seg.dat
```

This bypasses
`rbv.segmean.nii.gz`
entirely.

## Provenance and Discovery

- **Discovered:** 2026-05-11
  by agent (audit of GTM
  PVC code paths in
  `utils/gtm.cpp`).
- **Evidence:**
  - `MatrixAlloc` of
    `nhits` is on the line
    immediately preceding
    the per-voxel inner
    loop, inside the outer
    `for(f)` loop.
  - `MatrixAlloc` (via
    `MatrixAlloc → calloc`)
    returns a zero-filled
    matrix.
  - Increment is guarded
    by `if (f == 0)`.
  - Sister function
    `GTMrbv0` (line 1420)
    has the same logic but
    correctly allocates
    `nhits` outside the
    voxel-then-frame loop
    structure, and
    increments
    unconditionally.
  - Post-loop divide at
    `:1366` divides by the
    matrix entry directly,
    no guard against zero.

## Verification Checklist

- [x] `nhits = MatrixAlloc(...)`
      is inside the `for(f)`
      loop body.
- [x] Increment is gated by
      `if (f == 0)`.
- [x] No `MatrixFree` between
      iterations (leak).
- [x] Post-loop divide
      directly references
      `nhits->rptr[…][1]`
      with no zero-check.
- [x] `MatrixAlloc` →
      `calloc` → zero-filled.
- [x] `for(f)` iterates
