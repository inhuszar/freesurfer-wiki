# [severity-3] [bug-00203] `mri_cvs_register` — the surf2vol affine cache `$outdir/transform.txt` is never invalidated: it is reused across hemispheres, templates and `--clean*` reruns

> [!bug] Synopsis
> [[mri_cvs_register]] passes `-cache_transform $outdir/transform.txt` to
> [[surf2vol]] in both its two-hemisphere and its single-hemisphere call. The
> file name carries no template, hemisphere or subject key, and nothing in the
> script ever deletes it — not `--cleansurfreg`, `--cleanelreg`, `--cleanall`,
> and not the end-of-run cleanup. surf2vol reads the file unconditionally when
> it parses (the 12 numbers are taken as the affine without checking that
> they belong to the current surfaces) and only runs its Powell affine fit
> when the file is absent. A rerun in the same output directory therefore
> silently reuses a stale affine: `--hemi lh` then `--hemi rh` (the right
> hemisphere gets the left's affine), a second template, or `--cleanall` /
> `--cleansurfreg` after the moving subject was re-processed. The FEM stage has
> to absorb the wrong linear alignment and the morph and `-out_affine`
> output contain the wrong affine.

## Affected Artefacts

- **Tool(s):** [[mri_cvs_register]] (the script), [[surf2vol]] (cache read/write)
- **Pipeline stage(s):** `mri_cvs_register` step 2, elastic registration
  ([`mri_cvs_register/mri_cvs_register:388-444`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_cvs_register/mri_cvs_register#L388-L444))
- **FreeSurfer version(s):** confirmed in 8.2.0; the cached-transform call
  has been there since the script began calling surf2vol directly in
  2011-05-04 (commit `c5f9b595100`, "eliminated calling the perl script in step2"); the cache option in
  surf2vol is from the 2008-04-18 import.
- **Platforms:** all
- **Triggering configuration:** re-entering the elastic stage with an
  existing `$outdir/transform.txt` whose affine no longer matches the
  current moving/template surfaces. The default single run into a fresh
  `$SUBJECTS_DIR/<mov>/cvs` is unaffected (the file does not yet exist, Powell
  runs and writes it).

`CleanSurfReg` only forces regeneration of the `?h.resample.*` surfaces
([`mri_cvs_register/mri_cvs_register:295-308`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_cvs_register/mri_cvs_register#L295-L308)), `CleanElReg` only forces the surf2vol call at

`el_reg_to<template>.tm3d` (unless `--keepelreg`) — but not
`transform.txt`. Because the `.tm3d` is deleted at the end of every normal run,
every rerun re-enters surf2vol and finds the old `transform.txt`.

### Expected Behaviour

A cached affine may only be reused if it was computed for the same moving
surfaces, template and hemisphere configuration; `--cleansurfreg`,
`--cleanelreg` and `--cleanall` should force it to be recomputed.

### Observed Behaviour

The cached 12 numbers are used as is. Failing scenarios (from reading the
script):

1. `--hemi lh` and then `--hemi rh` into the same `--outdir` (or the default
   `…/cvs`): the second call finds the left-hemisphere affine (the single-hemisphere
   fit uses only that hemisphere's two surfaces) and applies it to the right
   hemisphere; the same applies between a both-hemisphere run and a single-hemisphere run.
2. `--cleanall` / `--cleansurfreg` after the moving subject was re-edited
   and re-processed with `recon-all`: the `resample` surfaces are rebuilt
   but the affine from the old surfaces survives.
3. A second `--template` into the same `--outdir` with `--cleansurfreg`
   (the resample file names do not contain the template either).

In each case the output is silently wrong: the log shows only
`trying to read transform from …/transform.txt` and no Powell fit.

### Reproducer

> [!gap] Script-level reproducer not constructed
> No end-to-end `mri_cvs_register` rerun with a stale `transform.txt` was
> executed (it needs two full CVS runs on prepared subjects). The defect is
> established from the script and from the following surf2vol-level
> experiment, which exercises exactly the code the script reaches.

The cache is honoured without any check (installed 8.2.0 `surf2vol`,
fixed = moving = `cvs_avg35` `mri/norm.mgz`, `-fixed_surf lh.white`,
`-moving_surf` = the same `lh.white` translated by +3.0 mm in x, CVS-style
options):

```bash
echo "1 0 0 0 1 0 0 0 1 0 0 0" > transform.txt      # stale / foreign affine: identity
surf2vol … -cache_transform transform.txt …           # log: " trying to read transform from transform.txt"
                                                      #      "linear transform = 1 0 0 / 0 1 0 / 0 0 1 / 0 0 0" (identity, no Powell)
rm transform.txt
surf2vol … -cache_transform transform.txt …           # log: "reading transform failed -> applying Powell",
                                                      #      "energy before calling Powell = 3", "energy after Powell = 7.91105e-06",
                                                      #      "writing transform to cache file transform.txt"
cat transform.txt                                     # 1 0 0 9.45902e-08 1 0 1.4788e-07 0 1 2.99993 0 0   (translation of 3 mm in x)
```

With the stale file the 3 mm shift is left for the FEM stage (the same two
inputs give an identity affine instead of the correct translation).

## Root Cause

The cache appears to be a speed-up for the Powell affine fit (expensive, and
deterministic given the surfaces) but has no cache key. The file lives in a
directory that is shared by successive runs and its name encodes none of the
inputs it depends on (moving surfaces, template, hemisphere set), and neither
the script's `Clean*` flags nor its cleanup blocks know about it.
surf2vol trusts any parseable file.

## Impact

- **Output affected:** the affine (`inv_t`) that pre-transforms the moving
  surfaces and is appended to the morph, so the `el_reg*.tm3d`, the exported
  `.m3z`, and the `-out_affine` volume all carry the wrong linear part. The FEM
  stage must absorb the error; with the limited convergence of the CVS options
  ([[00200]] analyses that the elastic system is not truly solved) some residual
  may survive into the final morph, though the later volumetric
  `mri_nl_align` stages refine it. The magnitude depends on how different the
  stale and the correct affines are.
- **Silent:** no error or warning.
- **Why 3:** wrong output gated behind a specific usage pattern (rerun in a
  shared `--outdir`: another hemisphere, another template, or
  `--clean*` after changing inputs); the default single run into a fresh
  directory is unaffected, and the flawed affine is partially compensated by
  the elastic and nonlinear stages. It is not severity 4 or 5 because it needs
  a rerun scenario, not just the default invocation.

## Recommended Fix

Key the cache file by what it depends on and remove it whenever the
corresponding stage is forced:

```diff
--- a/mri_cvs_register/mri_cvs_register
+++ b/mri_cvs_register/mri_cvs_register
@@ (before the elastic-registration block, line 388)
+# the cached affine depends on the template, the hemisphere set and the moving surfaces
+if ($BothHemis) then
+  set affinecache = $outdir/transform.${templateid}.both.txt
+else
+  set affinecache = $outdir/transform.${templateid}.${hemiReq}.txt
+endif
+if ($CleanSurfReg || $CleanElReg) then
+  rm -f $affinecache
+endif
 if (!(-e $outdir/$elasticmorph) || $CleanElReg) then
@@ line 402 and line 429
-                      $elasticoptions -cache_transform $outdir/transform.txt \
+                      $elasticoptions -cache_transform $affinecache \
```

(`--cleansurfreg` regenerates the resampled surfaces the affine is fitted
to, so it must drop the cache as well.) This diff was not executed against the
script.

### Alternative Fixes Considered

- Make surf2vol verify the cache: write a header (surface file names and
  modification times, or a hash of the moving/fixed vertex coordinates) and
  recompute when it does not match. More robust (it also covers a re-edited
  subject without `--clean*`) but touches the C++ file format and
  [[00204]]'s reader.
- Delete the cache at the end of every successful run (like the `.tm3d`).

## Workarounds (If Any)

Delete `$outdir/transform.txt` manually before every rerun, or give each
template/hemisphere/rerun its own `--outdir`.
