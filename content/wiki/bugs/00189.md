# [severity-2] [bug-00189] make_folding_atlas — --account sets FS_BATCH_ACCOUNT but sbatch reads FS_SBATCH_ACCOUNT, so the account is never applied

> [!bug] Synopsis
> `make_folding_atlas` lets the user choose the Slurm account for the
> cluster jobs it submits, via `--account <name>` (or, per its own help,
> the `FS_BATCH_ACCOUNT` environment variable). The `--account` handler
> stores the value in `FS_BATCH_ACCOUNT`, but the `sbatch` submission
> command is built with `--account=$FS_SBATCH_ACCOUNT` — a *different*
> environment variable (`SBATCH` vs `BATCH`). The user's account is
> therefore never passed to `sbatch`. Worse, the script unconditionally
> sets `FS_SBATCH_ACCOUNT` to the hard-coded value `fsm` just before
> reading it, so every submitted job runs under account `fsm` regardless
> of `--account` or any `FS_BATCH_ACCOUNT` the user exported.

## Affected Artefacts

- **Tool(s):** [[make_folding_atlas]]
- **Pipeline stage(s):** _N/A_ — a cluster-orchestration driver that
  iteratively builds a cortical folding atlas by submitting
  `make_average_subject` / `surfreg` / `xhemireg` jobs.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** Slurm clusters (the `sbatch` branch, taken when
  `squeue` is on `PATH`). The `pbsubmit` branch does not use either
  variable.
- **Triggering configuration:** running `make_folding_atlas` on an
  sbatch cluster with `--account myacct` (or `setenv FS_BATCH_ACCOUNT
  myacct`). The supplied account is silently ignored; jobs go to `fsm`.

## Detailed Description

When `squeue` is found, the script selects the sbatch submitter and
builds the submission command
([`scripts/make_folding_atlas:68-78`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/make_folding_atlas#L68-L78)):

```tcsh
set SubmitType = "sbatch"
setenv FS_SBATCH_ACCOUNT fsm                 # :71 — hard-codes the account
if($?FS_SBATCH_ACCOUNT == 0) then            # :72 — can never be true now
  echo "ERROR: no account set, must set env var FS_SBATCH_ACCOUNT"
  exit 1
endif
set submitcmd = (sbatch --partition=basic --nodes=1  \
  --account=$FS_SBATCH_ACCOUNT --ntasks-per-node=1 \   # :77 — reads FS_SBATCH_ACCOUNT
  --cpus-per-task=$OMP_NUM_THREADS --mem=7G --time=0-10:00)
```

The `--account` command-line handler, however, writes a different
variable ([`scripts/make_folding_atlas:534-537`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/make_folding_atlas#L534-L537)):

```tcsh
case "--account":
  if($#argv < 1) goto arg1err;
  setenv FS_BATCH_ACCOUNT $argv[1]; shift;   # :536 — sets FS_BATCH_ACCOUNT (not FS_SBATCH_ACCOUNT)
  breaksw
```

`parse_args` runs before the cluster-detection block (the script does
`goto parse_args` at
[`scripts/make_folding_atlas:39`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/make_folding_atlas#L39),
returning before line 68). So any `--account` value lands in
`FS_BATCH_ACCOUNT`, and is then overwritten-as-irrelevant when line 71
hard-sets `FS_SBATCH_ACCOUNT=fsm`, which line 77 actually uses.

The usage text and BEGINHELP both document the intended variable as
`FS_BATCH_ACCOUNT`
([`scripts/make_folding_atlas:641`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/make_folding_atlas#L641),
[`scripts/make_folding_atlas:673-674`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/make_folding_atlas#L673-L674)),
confirming the submission line's `FS_SBATCH_ACCOUNT` is the inconsistent
spelling.

### Expected Behaviour

`--account myacct` (or `setenv FS_BATCH_ACCOUNT myacct`) should cause the
submitted `sbatch` jobs to carry `--account=myacct`. With no account
supplied, the script should error out as its message says
("no account set, must set env var FS_BATCH_ACCOUNT").

### Observed Behaviour

- `--account myacct` sets `FS_BATCH_ACCOUNT=myacct`; the submission line
  uses `FS_SBATCH_ACCOUNT`, which line 71 has forced to `fsm`. Jobs are
  submitted with `--account=fsm`. The user's account is ignored.
- `setenv FS_BATCH_ACCOUNT myacct` before running has the same null
  effect.
- The guard at line 72 (`if($?FS_SBATCH_ACCOUNT == 0)`) is dead: line 71
  always defines `FS_SBATCH_ACCOUNT`, so the "no account set" error can
  never fire.

### Reproducer

> [!gap] Reproducer not yet constructed
> Requires an sbatch cluster (or an `sbatch`/`squeue` shim) and a valid
> subject list. The defect is evident from the code and the echoed
> command line:
>
> 1. On a host where `squeue` is on `PATH`, run
>    `make_folding_atlas --account myacct --b base --nmax 1 --s subj`
>    (with `--dont-run` to avoid real submission).
> 2. Inspect the echoed `$submitcmd` in the log: it contains
>    `--account=fsm`, not `--account=myacct`.

## Root Cause

Inconsistent environment-variable name between the `--account` handler
(`FS_BATCH_ACCOUNT`) and the consumer (`FS_SBATCH_ACCOUNT`). The
documentation matches the handler (`FS_BATCH_ACCOUNT`), so the consumer's
name is the odd one out. The bug is compounded by the unconditional
`setenv FS_SBATCH_ACCOUNT fsm` on the line above the consumer, which both
hard-codes a site-specific default and makes the adjacent "no account
set" guard unreachable — so a user who supplies no account is not warned
and is silently placed on `fsm`.

## Impact

- Cluster orchestration only; produces no scientific output itself, so a
  wrong/absent account does not corrupt data — hence severity 2.
- On any Slurm site where `fsm` is not a valid account (i.e. anywhere
  outside the MGH/Martinos environment this default encodes), every
  submitted job is rejected by the scheduler, and `--account` /
  `FS_BATCH_ACCOUNT` provide no way to fix it short of editing the
  script. The atlas build cannot proceed.
- Even where `fsm` is valid, users who intend to bill a different
  account cannot, and get no indication their `--account` was ignored.

## Recommended Fix

Make the consumer read the same variable the handler and docs use, and
turn the hard-coded `fsm` into a fallback default rather than an
override, so the "no account set" guard can actually fire:

```diff
   set SubmitType = "sbatch"
-  setenv FS_SBATCH_ACCOUNT fsm
-  if($?FS_SBATCH_ACCOUNT == 0) then
+  if(! $?FS_BATCH_ACCOUNT) then
     echo "ERROR: no account set, must set env var FS_BATCH_ACCOUNT"
     exit 1
   endif
   set submitcmd = (sbatch --partition=basic --nodes=1  \
-    --account=$FS_SBATCH_ACCOUNT --ntasks-per-node=1 \
+    --account=$FS_BATCH_ACCOUNT --ntasks-per-node=1 \
     --cpus-per-task=$OMP_NUM_THREADS --mem=7G --time=0-10:00)
```

(Note the original `if($?FS_SBATCH_ACCOUNT == 0)` form is itself
non-idiomatic for tcsh existence testing; `if(! $?FS_BATCH_ACCOUNT)` is
the correct "is this variable unset" check.)

### Alternative Fixes Considered

If preserving `fsm` as a site default is desired, keep it but apply it
only when the user supplied nothing:
`if(! $?FS_BATCH_ACCOUNT) setenv FS_BATCH_ACCOUNT fsm`, and read
`FS_BATCH_ACCOUNT` in the submission line. This keeps the current
out-of-the-box behaviour on the MGH cluster while letting `--account`
take effect elsewhere. Either way, the consumer must read the same name
the handler writes.

## Workarounds (If Any)

Until patched, the only way to change the account is to edit the
`setenv FS_SBATCH_ACCOUNT fsm` statement at
[`scripts/make_folding_atlas:71`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/make_folding_atlas#L71)
to the desired account, or to export `FS_SBATCH_ACCOUNT` *and*
delete/neutralise that same statement (exporting it alone does not help,
because [`scripts/make_folding_atlas:71`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/make_folding_atlas#L71)
overwrites it). Neither `--account` nor `FS_BATCH_ACCOUNT` works as
documented.
