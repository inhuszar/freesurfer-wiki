# [severity-2] [bug-00088] `CMAtotalClaims` — uninitialised top slot and wrong weight on diagonal neighbours

> [!bug] Synopsis
> The CMA outline-claim resolver
> ([`utils/cma.cpp:294-340`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/cma.cpp#L294-L340))
> aggregates per-pixel label claims from a 3×3
> neighbourhood and returns the highest-scoring
> label. Two independent defects:
>
> **Defect 1 — off-by-one in the init loop.**
>
> ```cpp
> float claim_totals[MAX_CMA_LABEL + 1];                /* :296 — sized N+1 */
> ...
> for (i = 0; i < MAX_CMA_LABEL; i++)                   /* :307 — only zeroes 0..N-1 */
>   claim_totals[i] = 0.0;
> ...
> for (i = 1; i <= MAX_CMA_LABEL; i++) {                /* :331 — reads up to N */
>   if (claim_totals[i] > best_claim) { ... }
> }
> ```
>
> `claim_totals[MAX_CMA_LABEL]` is read by the
> winner-search but never initialised. If no
> neighbour writes to that slot via
> `CMAaddWeightedTotals`
> ([`:285`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/cma.cpp#L285)),
> it stays at whatever the stack happened to
> contain — typically a leftover from a previous
> call to `CMAtotalClaims` (the function is
> invoked once per pixel from `CMAassignLabels`),
> which on Linux glibc is often the *previous*
> pixel's `claim_totals[MAX_CMA_LABEL]` slot.
>
> **Defect 2 — diagonal neighbours use the side
> weight.**
>
> ```cpp
> /* immediately adjoining points */
> if (x - 1 >= 0)            CMAaddWeightedTotals(..., OTL_CLAIM_WEIGHT_SIDE, ...);   /* :313 */
> if (x + 1 < field->width)  CMAaddWeightedTotals(..., OTL_CLAIM_WEIGHT_SIDE, ...);
> if (y - 1 >= 0)            CMAaddWeightedTotals(..., OTL_CLAIM_WEIGHT_SIDE, ...);
> if (y + 1 < field->height) CMAaddWeightedTotals(..., OTL_CLAIM_WEIGHT_SIDE, ...);
>
> /* diagonally adjoining points */
> if (x - 1 >= 0 && y - 1 >= 0)
>   CMAaddWeightedTotals(..., OTL_CLAIM_WEIGHT_SIDE, ...);                            /* :320 — should be DIAGONAL */
> if (x - 1 >= 0 && y + 1 < field->height)
>   CMAaddWeightedTotals(..., OTL_CLAIM_WEIGHT_SIDE, ...);                            /* :322 — should be DIAGONAL */
> if (x + 1 < field->width && y - 1 >= 0)
>   CMAaddWeightedTotals(..., OTL_CLAIM_WEIGHT_SIDE, ...);                            /* :324 — should be DIAGONAL */
> if (x + 1 < field->width && y + 1 < field->height)
>   CMAaddWeightedTotals(..., OTL_CLAIM_WEIGHT_SIDE, ...);                            /* :326 — should be DIAGONAL */
> ```
>
> `OTL_CLAIM_WEIGHT_DIAGONAL` is defined in
> [`include/cma.h:619`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/include/cma.h#L619)
> as `0.707` (≈ `1/√2`) — the obvious
> distance-weighted choice — but the constant is
> never referenced anywhere in the tree. All
> eight neighbours instead share the *side*
> weight `0.500`, so the function effectively
> ignores the geometric distinction between
> orthogonal and diagonal neighbours.

## Detailed Description

### Defect 1: undefined read of `claim_totals[MAX_CMA_LABEL]`

`MAX_CMA_LABEL` is defined as `MAX_LABEL`
([`include/cma.h:515`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/include/cma.h#L515)).
Whatever its concrete value, the array is sized
`MAX_CMA_LABEL + 1` and indexed `0..MAX_CMA_LABEL`.
The init loop runs only to `MAX_CMA_LABEL - 1`,
leaving the final slot indeterminate. The
winner-search reads it with `<=`, so on every
call the comparison `claim_totals[MAX_CMA_LABEL]
> best_claim` is against unspecified memory.

`CMAaddWeightedTotals` *can* write to that slot
(for any neighbour whose claim list contains
`MAX_CMA_LABEL`), but a slot may remain
uninitialised for the entire pixel if no
neighbouring claim covers that label. In that
case the winner-search either:

- declares `MAX_CMA_LABEL` the winner because
  the garbage happens to be larger than every
  legitimate total, or
- silently ignores it.

Both outcomes are unspecified. The bug fires
once per pixel in the OTL ingestion path.

### Defect 2: ignored `OTL_CLAIM_WEIGHT_DIAGONAL`

The header defines three weights:

```c
/* include/cma.h:617-619 */
#define OTL_CLAIM_WEIGHT_CENTER   1.000
#define OTL_CLAIM_WEIGHT_SIDE     0.500
#define OTL_CLAIM_WEIGHT_DIAGONAL 0.707
```

The diagonal weight is `1/√2` — the inverse of
the geometric distance from the centre pixel —
which is the standard "soft 3×3 stencil"
weighting in image processing. The
implementation never references the constant; a
repo-wide grep
(`grep -rn OTL_CLAIM_WEIGHT_DIAGONAL`) returns
the header definition only.

Diagonals therefore contribute the same `0.500`
weight as orthogonal neighbours, slightly
biasing the boundary towards labels that
dominate the diagonals over those that dominate
the orthogonal sides — and producing a
non-isotropic score field on the OTL grid.

## Root Cause

- **Defect 1:** classic `<` vs `<=` mistake. The
  array is sized `MAX_CMA_LABEL + 1` to allow
  inclusive indexing, but the init loop uses the
  exclusive `<` convention by mistake.
- **Defect 2:** copy-paste from the orthogonal
  block. The diagonal block was written with the
  same call signature as the side block, but
  the constant was never updated. The fact that
  `OTL_CLAIM_WEIGHT_DIAGONAL` is defined in the
  header indicates the original design intent
  was to use it.

## Impact

- **Defect 1:** unspecified behaviour at the
  upper label index in every pixel of an OTL
  read. Most often masked because the slot is
  re-touched by neighbour claims, but reliably
  reads uninitialised memory in pixels where no
  neighbour claims `MAX_CMA_LABEL`.
- **Defect 2:** anisotropic 3×3 stencil — the
  resolved label boundary is shifted relative
  to a true distance-weighted vote. The effect
  is small (≈30% over-weighting of diagonals
  relative to the intended ratio), but it
  accumulates along long diagonal boundaries.
- **Severity:** 2 — OTL ingestion is a legacy
  path not in default `recon-all`; both defects
  are observable but bounded.

## Workarounds

None within the OTL workflow. To avoid Defect 1
specifically, statically replace the
declaration with `float claim_totals[MAX_CMA_LABEL
+ 1] = {0};` (C99-compatible) so the entire
array is zero-initialised regardless of the
loop bound.
