# [severity-3] [bug-00110] `CMATwrite` omits whitespace between consecutive weight values; round-tripped CMAT files have corrupted weights

> [!bug] Synopsis
> ```cpp
> /* utils/cmat.cpp:95-98 — CMATwrite */
> for (i = 0; i < cmat->nlabels - 1; i++) {
>   for (j = i + 1; j < cmat->nlabels; j++)
>     fprintf(fp, "%f", cmat->weights[i][j]);   /* no separator */
>   fprintf(fp, "\n");
> }
>
> /* utils/cmat.cpp:54-63 — CMATread */
> for (i = 0; i < cmat->nlabels - 1; i++) {
>   for (j = i + 1; j < cmat->nlabels; j++) {
>     if (fscanf(fp, "%lf", &cmat->weights[i][j]) != 1) ...
>   }
>   if (fscanf(fp, "\n") != 1) ...
> }
> ```
>
> `fprintf(fp, "%f", v)` writes a single
> floating-point value at default 6-decimal
> precision (e.g. `1.000000`). Consecutive
> calls on the same row concatenate the
> outputs with no delimiter:
>
> | row weights | written output    |
> |-------------|-------------------|
> | `[1.0, 2.0]`| `1.0000002.000000\n` |
> | `[0.5, 1.5]`| `0.5000001.500000\n` |
> | `[0.1, 0.2, 0.3]` | `0.1000000.2000000.300000\n` |
>
> `fscanf("%lf", …)` parses the longest
> valid float prefix at the current
> position. For input `1.0000002.000000`:
>
> - reads `1`, `.`, `0000002` (all valid
>   fractional digits)
> - sees the second `.` — invalid (only one
>   decimal point allowed) — stops
> - first read = `1.0000002`
>
> The next `fscanf` call resumes at `.`,
> reads `.000000` = `0.0`. So the original
> `[1.0, 2.0]` round-trips as
> `[1.0000002, 0.0]`.
>
> The corruption is silent: `fscanf`
> returns 1 (one item parsed successfully)
> for both reads, no error indication.

## Detailed Description

### Why the corruption is silent

`fscanf("%lf", …)` is permissive: it
accepts any string that begins with a
valid float and stops at the first
character that would invalidate the
extended-precision parse (here, the
second `.`). It never errors on the
"too many digits" case — it simply
absorbs them.

Because the original value `1.0` was
written with six trailing zeros
(`1.000000`), and the next value `2.0`
starts with the digit `2`, the
concatenated input
`1.0000002.000000` looks like a
single 7-decimal number followed by a
second number. `fscanf` reads it as
such and returns success.

### When does the bug NOT corrupt data?

If consecutive values happen to have
specific properties, the parse may
recover the right boundary by accident:

- **Negative second value:** `1.000000-2.000000`.
  `fscanf` parses `1.000000`, stops at `-`
  (invalid in middle of float), next reads
  `-2.000000`. Round-trip OK.
- **Exponent in second value:** rare with
  default `%f` formatting (which never
  emits scientific notation).
- **Integer overflow length:** if the
  combined string exceeds the maximum
  representable double, the second `.`
  effectively bounds the parse — but
  intermediate digits are still mis-attributed.

For the typical case of two adjacent
positive non-negative floats with default
6-decimal `%f` formatting, the corruption
is deterministic and complete.

### Reader's row-end handling

`CMATread` ends each row with
`fscanf(fp, "\n")` (line 60). This expects
a literal `\n`. After reading `n - i - 1`
weights from a row, the parser should be
positioned at the trailing newline. With
the missing-whitespace bug, after the last
weight on the row, the next character is
`\n` (correct), so the row-end fscanf
succeeds. The bug is purely about
inter-value boundaries, not row boundaries.

### Magnitude on real data

A CMAT for a typical aparc+aseg with ~70
labels has on the order of 70²/2 ≈ 2500
weights stored in upper-triangular form.
With ~70 weights per row, the corruption
cascades — each parse position depends on
the previous, so a single mis-parse can
shift the entire row's interpretation.

The end result is that round-tripped CMAT
files contain weights that bear no
systematic relationship to the originals.
Visualization in freeview will show
nonsensical patterns; downstream analysis
(if any) operates on garbage.

## Root Cause

`fprintf` was used as if it produced
delimited output (e.g. like Python's
`print(*values)` which adds spaces
automatically). C's `printf` family does
not add separators between successive
calls — the author needs to write them
explicitly.

The matching reader `CMATread` was
written assuming whitespace-delimited
input (which `fscanf("%lf")` relies on),
but the writer never produces that
whitespace. Either both endpoints would
need to agree on a different delimiter
(e.g. comma, fixed-width field), or the
writer needs a space.

This pair of functions has no integration
test — round-trip testing would have
caught the bug immediately.

## Impact

- **Round-trip CMAT files corrupt every
  multi-weight row.** Single-weight rows
  (last row, where j=i+1=i+1, only one
  iteration) are unaffected.
- **Silent corruption:** no error
  message, no parse failure, no warning.
  `fscanf` reports success because it
  parses *some* float at each call.
- **Downstream:** freeview displays
  nonsense; `mri_transform` propagates
  garbage to its output; analyses run on
  the corrupted CMAT yield meaningless
  results.
- **Severity:** 3 — outside default
  `recon-all`; affects an active
  connectome / tractography path; effect
  is total corruption when triggered, but
  the path is opt-in.

## Recommended Fix

```diff
--- a/utils/cmat.cpp
+++ b/utils/cmat.cpp
@@ -94,7 +94,7 @@ int CMATwrite(CMAT *cmat, const char *fname)
   for (i = 0; i < cmat->nlabels - 1; i++) {
-    for (j = i + 1; j < cmat->nlabels; j++) fprintf(fp, "%f", cmat->weights[i][j]);
+    for (j = i + 1; j < cmat->nlabels; j++) fprintf(fp, "%f ", cmat->weights[i][j]);
     fprintf(fp, "\n");
   }
```

A trailing space inside the format
string ensures the next value starts on
a clean boundary. The reader is
unchanged — `fscanf("%lf")` skips
leading whitespace by default.

For long-term robustness, consider
adding a unit test that writes and
reads a CMAT and verifies bit-exact
weight equality.

## Workarounds

- For users with already-written CMAT
  files: regenerate them (or
  post-process by inserting spaces
  between every two consecutive 8-char
  fields if the original code used
  exactly `%f`).
- For users invoking the affected tools:
  pipe through a one-line sed that
  inserts spaces every 8 characters in
  weight rows.

## Verification Checklist

- [x] `CMATwrite` uses `fprintf("%f", ...)`
      with no separator.
- [x] `CMATread` uses `fscanf("%lf", ...)`
      which depends on whitespace
      delimiters.
- [x] Default `%f` format emits 6 decimal
      digits and no whitespace.
- [x] `%lf` parser reads as many
      consecutive valid float characters
      as possible, stopping only at an
      invalid character (e.g. second `.`).
- [x] No integration test for CMAT
      round-trip exists in the repo.
