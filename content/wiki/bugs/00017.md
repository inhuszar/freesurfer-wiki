# [severity-2] [bug-00017] MRIchangeType — histogram-trim src_max uses the just-overwritten src_min as its base

> [!bug] Synopsis
> `MRIchangeType` in `utils/mri.cpp` offers an optional
> histogram-based intensity trim before rescaling voxels to a new
> type: `f_low` trims the low tail and `f_high` trims the high tail.
> The function computes the new `src_min` by walking the histogram
> from the bottom, then the new `src_max` by walking it from the
> top. Both computations are supposed to anchor on the **original**
> `src_min`. But the code overwrites `src_min` in place with the
> new value on line `11909`, and the `src_max` computation on line
> `11913` then uses that already-overwritten `src_min` as its anchor.
> When `f_low > 0` and `f_high < 1` are both active, the returned
> `src_max` is inflated by exactly the amount of the low-trim
> (`new_src_min − old_src_min`), which skews the subsequent
> `scale = (dest_max − dest_min) / (src_max − src_min)` and
> therefore every voxel that gets rescaled. Typical in-tree
> callers pass `f_low = 0` (which makes the trim a no-op on the low
> side and hides the defect); any caller that actually uses a
> non-zero `f_low` exercises the bug.

## Affected Artefacts

- **Tool(s):** Every consumer of `MRIchangeType` with a non-zero
  `f_low` and an `f_high < 1` simultaneously. In the audited tree
  most call sites pass `f_low = 0` (e.g., `mri_fill`,
  `mri_watershed`, `mri_conform`, `mrinorm`, `gcamorph`) so the
  low-trim loop exits immediately at `bin = 0` and the defect is
  dormant. The documented general-purpose API takes `f_low`
  seriously, so any downstream tool that links `libutils` and
  uses the trimming feature as advertised hits the bug.
- **Pipeline stage(s):** _N/A_ for standard [[wiki/pipelines/recon-all|recon-all]].
  recon-all's `MRIchangeType` invocations (via `mri_convert`,
  `mri_conform`, `mri_fill`, etc.) all pass `f_low = 0`.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit
  `d932c45b79`.
- **Platforms:** all.
- **Triggering configuration:** `MRIchangeType(src, dest_type,
  f_low, f_high, no_scale = 0)` with both `0 < f_low < 1` and
  `0 ≤ f_high < 1`, when the histogram branch fires (i.e., the
  no-scale short-circuits above do not apply).

## Detailed Description

The trimming block builds a 256-bin histogram of source voxels,
walks it from the low bin until `f_low * N_voxels` have been
counted, and records that bin as the new low cutoff:

```cpp
nth = (int)(f_low * src->width * src->height * src->depth);
for (n_passed = 0, bin = 0; n_passed < nth && bin < N_HIST_BINS; bin++)
  n_passed += hist_bins[bin];
src_min = (float)bin * bin_size + src_min;     // line 11909
```

The right-hand side correctly uses the original `src_min` (the
bin base), but writes the result back into the same variable.
Immediately after that write, the equivalent walk from the top
is performed and the new `src_max` is computed as

```cpp
nth = (int)((1.0 - f_high) * nonzero);
for (n_passed = 0, bin = N_HIST_BINS - 1; n_passed < nth && bin > 0; bin--)
  n_passed += hist_bins[bin];
src_max = (float)bin * bin_size + src_min;     // line 11913
```

By this point `src_min` is the **new** low cutoff, not the
histogram base. The correct expression would be
`src_max = (float)bin * bin_size + original_src_min`.

### Expected Behaviour

Both the new `src_min` and the new `src_max` should be expressed
relative to the histogram base (the original `src_min`):

```
new_src_min = old_src_min + bin_low  * bin_size
new_src_max = old_src_min + bin_high * bin_size
```

so the trimmed interval `[new_src_min, new_src_max]` sits inside
the original intensity range, and `src_max − src_min =
(bin_high − bin_low) * bin_size`.

### Observed Behaviour

```
new_src_min = old_src_min + bin_low  * bin_size
new_src_max = new_src_min + bin_high * bin_size      // because src_min was already overwritten
            = old_src_min + (bin_low + bin_high) * bin_size
```

The returned `src_max` is inflated by `bin_low * bin_size` —
exactly the amount of the low-trim. The width of the trimmed
interval is preserved (`new_src_max − new_src_min =
bin_high * bin_size`) but the whole interval is shifted upward.

The downstream `scale = (dest_max − dest_min) / (src_max − src_min)`
is therefore **correct in magnitude but applied around the wrong
offset**. The subsequent voxel-by-voxel rescale

```
dest_voxel = (src_voxel - src_min) * scale + dest_min
```

uses the correct `src_min` (fine) and the wrong `src_max` only
through the scale denominator — which is `(new_src_max −
new_src_min) = bin_high * bin_size`, the intended width. So the
slope is right, but `src_max` itself is reported wrong to any
caller that reads it out (the function doesn't expose it, but
internal consistency assumptions break). Worse, a subsequent
edit that reads `src_max` assuming the stated semantics will be
subtly off.

Worked example. `old_src_min = 0`, `old_src_max = 100`,
`N_HIST_BINS = 100`, `bin_size = 1`, `f_low = 0.10`,
`f_high = 0.90`. After the low-trim loop, `bin = 10` and
`new_src_min = 0 + 10 = 10`. After the high-trim loop,
`bin = 90` and the intended `new_src_max = 0 + 90 = 90`. The
code computes `new_src_max = new_src_min + 90 = 100`, so the
clipped interval `[10, 100]` is 10 mm too wide on the top and
misses the tail-trim by exactly the low-trim amount.

> 2. Call `MRIchangeType(src, MRI_UCHAR, 0.1, 0.9, 0)`.
> 3. Compare the output against a hand-rolled reference that

## Code Reference (Unambiguous)

- **File:** `utils/mri.cpp`
- **Function:** `MRIchangeType()`
- **Lines:** `11806–11972` (full function); defect at
  `11907–11913`
- **Commit:** `d932c45b79`

```cpp
    nth = (int)(f_low * src->width * src->height * src->depth);
    for (n_passed = 0, bin = 0; n_passed < nth && bin < N_HIST_BINS; bin++) n_passed += hist_bins[bin];
    src_min = (float)bin * bin_size + src_min;                      // ← overwrites src_min

    nth = (int)((1.0 - f_high) * nonzero);
    for (n_passed = 0, bin = N_HIST_BINS - 1; n_passed < nth && bin > 0; bin--) n_passed += hist_bins[bin];
    src_max = (float)bin * bin_size + src_min;                      // ← uses overwritten src_min
```

The symmetry of the two walks (`src_min = bin * bin_size + src_min`
and `src_max = bin * bin_size + src_min`) makes the intent
explicit: both should anchor on the histogram base. The author
did not preserve the original `src_min` before overwriting it.

## Root Cause

The author wrote the two anchor updates as parallel statements
in the form `src_X = (float)bin * bin_size + src_min;`, but
forgot that the first assignment mutates the RHS of the second.
A local snapshot of the original `src_min` before the first
update (or writing the new low as a temporary) would have
preserved the intended invariant.

## Impact

- `src_max` is inflated by `bin_low * bin_size`; the subsequent
  `scale = (dest_max − dest_min) / (src_max − src_min)` is
  mathematically unchanged (the two errors in `src_min` and
  `src_max` cancel because their difference is what matters),
  **but** `src_max` itself is incorrect for any subsequent use.
- The per-voxel rescale
  `dest = (src_voxel − src_min) * scale + dest_min` uses the
  (correct) new `src_min` and the (correct) `scale`, so voxels
  below the new `src_min` get clamped and voxels above the new
  `src_max` would get clamped — except that the upper clamp
  reads `src_max` which is now wrong, so the upper clamp is
  ineffective in proportion to `bin_low * bin_size`.
- No current in-tree caller exercises the bug: `mri_fill`,
  `mri_watershed`, `mri_conform`, and `mrinorm` all pass
  `f_low = 0`, which makes the low-trim loop exit at `bin = 0`
  with `src_min` unchanged. The defect only manifests for
  callers (including downstream tools linking `libutils`) that
  use the trimming feature as documented.

## Recommended Fix

Save the original `src_min` before overwriting it:

```diff
+    float const src_min_orig = src_min;
+
     nth = (int)(f_low * src->width * src->height * src->depth);
     for (n_passed = 0, bin = 0; n_passed < nth && bin < N_HIST_BINS; bin++) n_passed += hist_bins[bin];
-    src_min = (float)bin * bin_size + src_min;
+    src_min = (float)bin * bin_size + src_min_orig;

     nth = (int)((1.0 - f_high) * nonzero);
     for (n_passed = 0, bin = N_HIST_BINS - 1; n_passed < nth && bin > 0; bin--) n_passed += hist_bins[bin];
-    src_max = (float)bin * bin_size + src_min;
+    src_max = (float)bin * bin_size + src_min_orig;
```

The patch is symmetric and matches the intuitive semantics of
"both cutoffs are bin indices times bin width, plus the histogram
base".

### Alternative Fixes Considered

Compute `src_max` before overwriting `src_min`:

```c
float new_src_min = (float)bin_low  * bin_size + src_min;
src_max           = (float)bin_high * bin_size + src_min;
src_min           = new_src_min;
```

Functionally equivalent; picking between the two is a style
preference.

## Workarounds (If Any)

Until the fix lands, callers that want documented-style trim
semantics can perform the histogram trim externally (e.g.,
`MRIhistogram` + manual bin walking) and pass `f_low = 0,
f_high = 1` to `MRIchangeType`, forcing it into the unclipped
rescale path.
