# [severity-2] [bug-00166] vlrmerge-mni — --no-mni152 still sets DoMNI152=1 (custom-target path dead); custom white surface mis-set to sphere.reg

> [!bug] Synopsis
> `scripts/vlrmerge-mni` has two defects on its custom-target (non-MNI152)
> path. First, both the `--mni152` and `--no-mni152` flag handlers set
> `DoMNI152 = 1`, so there is no way to turn MNI152 mode off — the
> custom-target code path is unreachable, and `--no-mni152` either does
> nothing or trips the "cannot spec --s and --mni152" guard. Second, even if
> that path were reached, it mis-sets the white-surface variable to
> `$hemi.sphere.reg` instead of `$hemi.white`, so `mri_surf2vol --so` would
> be handed the spherical registration surface in place of the white surface
> and map the overlay onto meaningless coordinates.

## Affected Artefacts

- **Tool(s):** [[vlrmerge-mni]] — merges left/right surface overlays and a
  subcortical-GM volume into a single volume map (for figures of group PET
  or FSFAST results).
- **Pipeline stage(s):** _N/A_ — standalone figure-making helper; not on the
  default [[wiki/pipelines/recon-all|recon-all]] path.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`;
  earliest known: _unknown_.
- **Platforms:** all — pure tcsh control flow.
- **Triggering configuration:** any attempt to use a custom target subject
  via `--no-mni152 --s <subject>` (the documented non-MNI152 mode). Both
  defects live entirely on that opt-in path; the default MNI152 mode is
  unaffected.

## Detailed Description

`vlrmerge-mni` defaults to MNI152 mode (`DoMNI152 = 1` at
[`scripts/vlrmerge-mni:20`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/vlrmerge-mni#L20))
but documents a `--no-mni152` escape hatch that, together with `--s
<targetsubject>`, lets the user merge into a custom subject's space
([`scripts/vlrmerge-mni:450-451`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/vlrmerge-mni#L450-L451)).
Two defects make that path non-functional.

**Defect 1 — `--no-mni152` does not clear `DoMNI152`.** Both flag handlers
assign `1`:

```tcsh
    case "--no-mni152":
     set DoMNI152 = 1
     breaksw

    case "--mni152":
     set DoMNI152 = 1
     breaksw
```

`DoMNI152` therefore can never become 0 from the command line. The
consequences in `check_params`:

- If the user runs `--no-mni152` **alone**, `DoMNI152` stays 1, the script
  forces `targetsubject = fsmni152`
  ([`scripts/vlrmerge-mni:400-405`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/vlrmerge-mni#L400-L405)),
  and silently runs MNI152 mode — the opposite of the request.
- If the user runs `--no-mni152 --s subj` (the documented combination), the
  guard at
  [`scripts/vlrmerge-mni:396-399`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/vlrmerge-mni#L396-L399)
  (`$#targetsubject != 0 && $DoMNI152 != 0`) fires and the script aborts with
  "ERROR: cannot spec --s and --mni152". The custom-target branch
  (`else` of the `targetsubject == fsmni152` tests at
  [`scripts/vlrmerge-mni:155-156`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/vlrmerge-mni#L155-L156))
  is unreachable.

**Defect 2 — custom white surface mis-set to `sphere.reg`.** In the surface
mapping loop, the white surface and ribbon are chosen per target. The
`fsmni152` branch is correct; the custom (`else`) branch is not:

```tcsh
    if($targetsubject == fsmni152) then
      set white  = $FREESURFER/subjects/fsmni152/surf/$hemi.white
      set ribbon = $FREESURFER/subjects/fsmni152/mri/ribbon.mgz
    else
      set white = $SUBJECTS_DIR/$targetsubject/surf/$hemi.sphere.reg
      set ribbon = $SUBJECTS_DIR/$targetsubject/mri/ribbon.mgz
    endif
```

The `else` branch sets `white` to `$hemi.sphere.reg` — the spherical
registration surface — instead of `$hemi.white`. This `white` is then passed
to `mri_surf2vol --so $white ...` at
[`scripts/vlrmerge-mni:158-159`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/vlrmerge-mni#L158-L159).
`--so` (surf-overlay) expects an anatomical surface whose vertices live in
the subject's volume space; `sphere.reg` vertices live on the unit sphere, so
the overlay would be painted at nonsensical coordinates relative to the
ribbon. The `fsmni152` branch one line up uses `$hemi.white`, confirming the
intended value.

### Expected Behaviour

- `--no-mni152 --s subj` should set `DoMNI152 = 0` and merge the overlays
  into `subj`'s native space using `subj`'s `?h.white` surface and ribbon.

### Observed Behaviour

- `--no-mni152` cannot clear `DoMNI152`; the custom-target path is dead
  (either silently runs MNI152, or aborts when `--s` is also given).
- The custom-target branch, were it reachable, would feed
  `?h.sphere.reg` to `mri_surf2vol --so`, producing a wrong overlay-to-volume
  mapping.

### Reproducer

```bash
# Defect 1: --no-mni152 leaves DoMNI152 = 1 (verbatim case bodies):
cat > /tmp/repro.csh <<'CSH'
#!/bin/tcsh -f
set DoMNI152 = 1
set flag = "--no-mni152"
switch($flag)
  case "--no-mni152":
   set DoMNI152 = 1
   breaksw
  case "--mni152":
   set DoMNI152 = 1
   breaksw
endsw
echo "DoMNI152 = $DoMNI152   <-- still 1; custom-target path unreachable"
CSH
tcsh -f /tmp/repro.csh
# prints: DoMNI152 = 1
```

A real `--no-mni152 --s subj ...` invocation aborts in `check_params` with
"ERROR: cannot spec --s and --mni152" (from
[`scripts/vlrmerge-mni:396-399`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/vlrmerge-mni#L396-L399)),
which is the externally observable symptom of defect 1.

## Root Cause

- **Defect 1:** copy-paste — the `--no-mni152` case body was duplicated from
  `--mni152` and the `0` was never substituted for `1`.
- **Defect 2:** wrong surface name in the custom branch — `sphere.reg`
  instead of `white`, contradicting the parallel `fsmni152` branch one line
  above and the semantics of `mri_surf2vol --so`.

## Impact

- The documented `--no-mni152` custom-target workflow is unusable: it either
  silently reverts to MNI152 or aborts. A user who wants to merge into a
  non-MNI152 subject cannot do so.
- Default MNI152 mode (the overwhelmingly common usage, and the only mode the
  shipped `fsmni152` data supports) is **unaffected** — it goes through the
  correct `fsmni152` branches for both `DoMNI152` and `white`.
- Severity is **2 (low)**: both defects are confined to an opt-in,
  non-default code path that is currently unreachable; the tool's primary
  (MNI152) output is correct. Defect 1 fails loudly (abort) in the
  `--s`-combined case, and defect 2 is masked because the path that would
  trigger it cannot be reached.

## Recommended Fix

Fix both sites:

```diff
     case "--no-mni152":
-     set DoMNI152 = 1
+     set DoMNI152 = 0
      breaksw

     case "--mni152":
      set DoMNI152 = 1
      breaksw
```

```diff
     else
-      set white = $SUBJECTS_DIR/$targetsubject/surf/$hemi.sphere.reg
+      set white = $SUBJECTS_DIR/$targetsubject/surf/$hemi.white
       set ribbon = $SUBJECTS_DIR/$targetsubject/mri/ribbon.mgz
     endif
```

After the first change, `--no-mni152` clears `DoMNI152`, so `--no-mni152 --s
subj` passes the `check_params` guards and reaches the custom-target branch.
After the second change, that branch hands `mri_surf2vol` the correct white
surface.

### Alternative Fixes Considered

None required; both are single-token corrections matching the existing
`--mni152` / `fsmni152` patterns.

## Workarounds (If Any)

There is no way to use a custom (non-MNI152) target with the current code.
Users must operate in MNI152 mode, or patch the two lines locally.
