# [severity-3] [bug-00103] `MRIlaplacian` mixes frame-0 centre with frame-`f` neighbours for `f >= 1`

> [!bug] Synopsis
> `MRIlaplacian`
> ([`utils/mrifilter.cpp:947-973`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrifilter.cpp#L947-L973))
> implements the 6-connected discrete
> Laplacian
> `Δu = (Σ_neighbours u) − 6·u_centre` per
> frame. The body is:
>
> ```cpp
> for (f = 0; f < mri_src->nframes; f++)
>   for (x = 0; x < mri_src->width; x++) {
>     for (y = 0; y < mri_src->height; y++) {
>       for (z = 0; z < mri_src->depth; z++) {
>         lap  = -6 * MRIgetVoxVal(mri_src, x, y, z, 0);                       /* :960 — frame 0 */
>         lap += MRIgetVoxVal(mri_src, mri_src->xi[x - 1], y, z, f);            /* :961 — frame f */
>         lap += MRIgetVoxVal(mri_src, mri_src->xi[x + 1], y, z, f);            /* :962 */
>         lap += MRIgetVoxVal(mri_src, x, mri_src->yi[y - 1], z, f);            /* :963 */
>         lap += MRIgetVoxVal(mri_src, x, mri_src->yi[y + 1], z, f);            /* :964 */
>         lap += MRIgetVoxVal(mri_src, x, y, mri_src->zi[z - 1], f);            /* :965 */
>         lap += MRIgetVoxVal(mri_src, x, y, mri_src->zi[z + 1], f);            /* :966 */
>         MRIsetVoxVal(mri_laplacian, x, y, z, f, lap);
>       }
>     }
>   }
> ```
>
> The centre coefficient at line `:960` reads
> from frame **0**, but the six neighbour
> reads use the loop frame variable `f`. For
> single-frame inputs (`f` is always 0) the
> formula is correct. For multi-frame inputs,
> the Laplacian written to frame `f >= 1` of
> the destination is
> `(Σ neighbours @ frame f) − 6·(centre @
> frame 0)` — a frame-mixing nonsense.

## Detailed Description

For `f == 0`:
- centre uses frame 0 (line `:960` writes
  literal 0).
- neighbours use frame `f == 0`.
- result: `Σ@0 − 6·u@0` — correct discrete
  Laplacian of frame 0.

For `f == 1` (and similar for `f == 2`):
- centre still uses frame 0.
- neighbours use frame 1.
- result: `Σ_nbr@1 − 6·u_centre@0` —
  ill-defined; mixes information from two
  frames.

The Laplacian destination at frame `f` is
therefore wrong for any `f >= 1`. For
`gcamorph`'s warp the dy and dz Laplacian
frames are corrupted; only the dx frame is
correct.

A naïve viewer of `mri_tmp` from
`gcamorph.cpp:6184` will see a sensible-looking
dx-Laplacian and visually-plausible-but-wrong
dy/dz-Laplacians (the `−6 · dx_centre` term
biases dy and dz toward dx's average
intensity).

## Root Cause

Typo / oversight when the function was
generalised from single-frame to multi-frame.
The outer loop adds the `f` dimension and the
six neighbour reads were updated to use `f`,
but the centre read was left at the literal
`0`.

## Impact

- **`gcamorph` Laplacian regularisation:** the
  3-frame warp Laplacian is wrong on dy and dz
  frames. This affects the warp regulariser
  in non-linear registration. Frame 0 (dx) is
  correct.
- **Other multi-frame consumers:** any caller
  passing `nframes > 1` gets nonsense for
  `f >= 1`.
- **Severity:** 3 — wrong output gated on
  multi-frame input; affects `mri_ca_register`
  in default `recon-all`.

Single-character substitution.

## Workarounds

For multi-frame inputs, split the volume into
single-frame volumes via `MRIcopyFrame`,
compute the Laplacian on each, and recombine.
