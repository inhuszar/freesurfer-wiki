# [severity-2] [bug-00220] `applyMorph` `sprobe`/`snormals` — NULL dereference when the morph lacks valid geometry

> [!bug] Synopsis
> `SurfaceProbeFilter::LoadInputData()` checks that the morph carries valid
> fixed and moving volume geometries. If it does not, it prints "Morph
> doesn't have valid geometries" and plain `return`s, leaving both surface
> pointers NULL. Its callers, `SurfaceProbeFilter::Execute` and
> `SurfaceNormalsProbeFilter::Execute`, do not check and immediately
> dereference the NULL surfaces: the program dies with a segmentation fault
> (exit status 139) instead of a clean error. A morph without geometry is
> exactly what `createMorph` writes when `--template`/`--subject` are omitted.

## Affected Artefacts

- **Tool(s):** [[applyMorph]] (items `sprobe` and `snormals`); the geometry-less morph comes from [[createMorph]] ([[00216]])
- **Pipeline stage(s):** _N/A_
- **FreeSurfer version(s):** confirmed in 8.2.0; lines date from the 2008 import (commit `4b881dc775f`)
- **Platforms:** all (observed on Linux)
- **Triggering configuration:** `applyMorph ... snormals|sprobe ...` with a `.tm3d` whose stored fixed or moving geometry is flagged invalid: a `createMorph` output made without `--template`/`--subject`, or a legacy `.nm3d` without geometry tags.

## Detailed Description

The probe filters convert both surfaces to voxel space using the volume
geometries stored in the morph (`vgFixed()` for the template surface,
`vgMoving()` for the subject surface). `VolumeMorph` initialises both to the
library default flagged `valid = 0`; a morph file without geometry records
keeps that state. `LoadInputData()` guards against this case, but the guard
is a `return` in a `void` function, whereas the failure paths below it use
`throw`, which `main()` turns into a diagnostic and `exit(1)`.

### Expected Behaviour

A clean failure: the message "Morph doesn't have valid geometries" followed
by exit status 1 (as for the other load failures in the same function, which
`throw` a `const char*` caught in `main()`).

### Observed Behaviour

The message is printed, the member pointers `m_mrisTemplate` and
`m_mrisSubject` (initialised to NULL in the constructor) stay NULL, and the
caller dereferences them: segmentation fault, exit status 139, no output file.

### Reproducer

Synthetic: `lh.white` of a FreeSurfer subject (135 546 vertices) as template
surface, a copy shifted by 2 mm as subject surface, a 32^3 template volume
`tmpl.mgz`, and a morph created with the real `createMorph` from a text file
with the 12 numbers of a `+3` voxel x-translation, once **without** and once
**with** geometry.

```bash
echo "1 0 0 0 1 0 0 0 1 3 0 0" > aff3.txt
createMorph --in affine aff3.txt --out <W>/cm_nogeom.tm3d                       # rc 0, no geometry stored
createMorph --in affine aff3.txt --out <W>/cm_geom.tm3d \
            --template tmpl.mgz --subject tmpl.mgz                               # geometry stored

applyMorph --template tmpl.mgz --transform <W>/cm_nogeom.tm3d \
           snormals lh.white lh.white.shift <W>/lh.cm_sn.curv ; echo rc=$?
applyMorph --template tmpl.mgz --transform <W>/cm_geom.tm3d \
           snormals lh.white lh.white.shift <W>/lh.cm_sn_ok.curv ; echo rc=$?

# SurfaceProbeFilter (reachable only when the template surface file is literally
# named "sprobe" in the current directory, see 00211)
cp lh.white sprobe
applyMorph --template tmpl.mgz --transform <W>/cm_nogeom.tm3d \
           sprobe sprobe lh.white.shift <W>/lh.cm_sp.curv ; echo rc=$?
```

Observed with the installed 8.2.0 binaries:

| Run | Output | Exit |
|-----|--------|------|
| `snormals` with `cm_nogeom.tm3d` | ` Morph doesn't have valid geometries`, then `Segmentation fault` | 139 |
| `snormals` with `cm_geom.tm3d` | normal output file | 0 |
| `sprobe` (file named `sprobe`) with `cm_nogeom.tm3d` | same message, `Segmentation fault` | 139 |

A hand-built `.tm3d` lacking the geometry records gave the same result for
both items. Which of the two dereferences faults first in
`SurfaceNormalsProbeFilter::Execute` (the NULL `m_mrisSubject` passed to
`MRIScomputeNormals`, or the NULL `m_mrisTemplate` indexed at
`vertices[0]`) was not determined with a debugger; both operate on NULL.

## Root Cause

`LoadInputData()` reports an invalid-geometry condition by returning, but
`Execute()` has no way to tell that the load did not happen: the function
returns `void` and the members it was supposed to fill remain NULL (set in the
constructor). The sibling error paths (unreadable surface, vertex-count
mismatch) correctly `throw`, which `main()` catches
([`fem_elastic/fapplyMorph.cpp:273-278`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fapplyMorph.cpp#L273-L278));
this one was left as a `return`.

## Impact

- **Crash, not corruption.** The process dies with SIGSEGV and writes no
  output (no stale or wrong file is produced); the diagnostic printed just
  before it names the cause. Only users of `sprobe`/`snormals` with a
  geometry-less morph are affected.
- **Severity 2, not 3.** The trigger is an input that no caller exercises:
  a morph created without geometry (a degenerate `createMorph` use, see
  [[00216]]), fed to a rarely used item keyword with no in-tree caller. The
  failure is loud (crash plus a diagnostic naming the cause) and leaves no
  wrong data behind, which fits the schema's "latent under typical
  conditions" tier. It would be a 3 only if the probe items were part of a
  routine workflow.
- Once [[00211]] is fixed, `sprobe` reaches the same crash through its own
  filter; today only the file-named-`sprobe` trick reaches it.

## Recommended Fix

Throw instead of returning, like the other failure paths:

```diff
   if ( !this->pmorph->vgFixed().valid ||
        !this->pmorph->vgMoving().valid )
   {
-    std::cerr << " Morph doesn't have valid geometries \n";
-    return;
+    throw "SurfaceProbeFilter - morph doesn't have valid geometries ";
   }
```

`main()` already catches `const char*` around the filter loop and exits with
status 1. A regression test is the geometry-less reproducer above: expect
exit status 1 and the message, not 139.

## Workarounds (If Any)

Create the morph with `createMorph --template <fixed.mgz> --subject
<moving.mgz>` so that valid geometries are stored (see [[createMorph]]).
