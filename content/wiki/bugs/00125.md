# [severity-3] [bug-00125] `MRIgetEqualizeHistoRegion` cumulative histogram starts at index 0 instead of `low`

> [!bug] Synopsis
> ```cpp
> /* utils/mrihisto.cpp:514-559 */
> HISTOGRAM *MRIgetEqualizeHistoRegion(MRI *mri, HISTOGRAM *histo_eq, int low, MRI_REGION *region, int norm)
> {
>   ...
>   histo = MRIhistogramRegion(mri, 0, NULL, region);
>   nbins = histo->nbins;
>   ...
>
>   /* :543 — total over wrong range */
>   for (pc = &histo->counts[0], total_pix = 0, i = low; i < nbins; i++)
>       total_pix += *pc++;
>
>   if (total_pix) {
>     /* :546-547 — cumulative output starts at index 0 */
>     pc = &histo->counts[0];
>     pdst = &histo_eq->counts[0];
>
>     for (total = 0, i = low; i < nbins; i++) {
>       total += *pc++;
>       if (norm)
>         *pdst++ = nint(255.0f * (float)total / (float)total_pix);
>       else
>         *pdst++ = total;
>     }
>   }
>   ...
> }
> ```
>
> The loop counter `i` starts
> at `low` and runs to
> `nbins-1` (`nbins - low`
> iterations), but the byte
> pointer `pc` starts at
> `&counts[0]` and advances
> once per iteration. So
> `pc` traverses
> `counts[0..nbins-low-1]`,
> not `counts[low..nbins-1]`.
>
> Compare the sister
> function which is
> structurally correct
> ([`utils/mrihisto.cpp:568-601`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrihisto.cpp#L568-L601)):
>
> ```cpp
> /* MRIgetEqualizeHisto — indexed access */
> for (total_pix = 0, i = low; i <= high; i++)
>     total_pix += histo->counts[i];
>
> for (i = 0; i < low; i++) {
>     histo_eq->counts[i] = 0;
>     histo_eq->bins[i] = i;
> }
> for (total = 0, i = low; i <= high; i++) {
>     total += histo->counts[i];
>     if (norm)
>       histo_eq->counts[i] = nint(255.0f * (float)total / (float)total_pix);
>     else
>       histo_eq->counts[i] = total;
>     histo->bins[i] = i;
> }
> ```
>
> This version uses indexed
> access (`histo->counts[i]`,
> `histo_eq->counts[i]`)
> and correctly writes to
> the slice `[low..high]`.

## Detailed Description

### What pc traverses vs what i indexes

For `low = 30`, `nbins = 256`
(UCHAR — the function
explicitly rejects non-
UCHAR input at `:528-529`):

| iteration k | `i` | `pc` (offset) | `*pc++` reads |
|-------------|-----|---------------|---------------|
| 0           | 30  | `counts[0]`   | counts[0]     |
| 1           | 31  | `counts[1]`   | counts[1]     |
| 2           | 32  | `counts[2]`   | counts[2]     |
| …           | …   | …             | …             |
| 225         | 255 | `counts[225]` | counts[225]   |

`total_pix` becomes
`counts[0] + counts[1] +
… + counts[225]` — i.e.,
the cumulative count over
the **first 226** bins,
not the last 226. The
intended sum is
`counts[30] + counts[31] +
… + counts[255]`.

For typical brain MRI
with UCHAR intensities,
counts[0..29] is
dominated by air /
background voxels, while
counts[30..255] is the
brain/skull/soft-tissue
distribution. The
`low=30` choice exists
precisely to skip the
background and equalize
only the brain
intensities.

The bug computes
total_pix over
`counts[0..225]` which
**includes the
background** (counts[0..29])
and **excludes part of
the brain tail**
(counts[226..255]).

### Second loop: cumulative output also offset

```cpp
pc = &histo->counts[0];
pdst = &histo_eq->counts[0];
for (total = 0, i = low; i < nbins; i++) {
    total += *pc++;
    *pdst++ = nint(255.0f * (float)total / (float)total_pix);  /* norm == 1 */
}
```

Same shift applies:
- `pc` reads
  `counts[0..225]` (226
  values).
- `pdst` writes
  `histo_eq->counts[0..225]`
  (226 entries).
- `histo_eq->counts[226..255]`
  is never written; the
  `HISTOclear` at
  `:540` left them at 0.
- `histo_eq->counts[0..29]`
  receives cumulative
  sums starting from
  `counts[0]` — but the
  intent was for these
  to be 0 (or undefined,
  since they're below
  `low`).

### Numerical impact

For a typical brain
intensity histogram with
total background voxels
≈ 30% of total, the bug
gives:

| quantity     | intended (correct) | actual (bug)       |
|--------------|--------------------|--------------------|
| total_pix    | sum over brain (70% of voxels) | sum over [0..225] (≈ all voxels) |
| histo_eq[0]  | 0 (background sentinel) | nint(255 * counts[0] / total) — likely large |
| histo_eq[30] | nint(255 * Σcounts[30..30] / brain_total) | nint(255 * Σcounts[0..0] / total) |
| histo_eq[225]| nint(255 * Σcounts[30..225] / brain_total) | nint(255 * Σcounts[0..225] / total) |
| histo_eq[226..255] | maps for high intensities | **0** (uninitialised) |

The mapping table is
shifted by `low` bins
in indexing and the
high-intensity tail is
zeroed. Applied via
`MRIapplyHistogramToRegion`,
this produces:
- Background voxels (input
  intensity 0..29) get
  mapped to non-zero
  values (instead of 0).
- High-intensity voxels
  (input intensity
  226..255) get mapped to
  0 (instead of their
  equalized values).
- Mid-range voxels get
  mapped using the wrong
  cumulative.

### Why this is severity 3

- **Reachable**: the only
  in-tree caller
  (`mri_histo_eq
  --adaptive-normalize`)
  passes `low=30` —
  guaranteed to trigger
  the bug.
- **Silent**: tool runs
  to completion, no
  warning.
- **Visibly wrong
  output**: histogram-
  equalized intensities
  are mis-mapped,
  especially in
  background and high-
  intensity regions.
- **Below severity 4**
  because:
  - `mri_histo_eq` is a
    stand-alone utility,
    not part of default
    `recon-all`.
  - The non-adaptive
    path (default
    `MRIhistoNormalize`)
    works correctly.
  - Adaptive
    normalization is a
    niche workflow.

## Root Cause

The author intended to
mirror the indexed-access
logic of `MRIgetEqualizeHisto`
but partially converted
it to pointer arithmetic
without offsetting the
pointer. The loop counter
was correctly set to start
at `low`, but the pointer
was left at `&counts[0]`.

In the same function, the
output pointer `pdst` is
also at `&histo_eq->counts[0]`
instead of
`&histo_eq->counts[low]`.

## Impact

- **`mri_histo_eq
  --adaptive-normalize`**:
  the equalized output
  has shifted mapping —
  background pixels (in
  the [0..low-1] range)
  receive non-zero
  equalized values, and
  high-intensity pixels
  (in the [nbins-low..nbins-1]
  range) receive 0
  instead of their
  equalized values.
- **Default
  (non-adaptive)
  `mri_histo_eq`**:
  unaffected (uses
  `MRIgetEqualizeHisto`).
- **`recon-all`**:
  unaffected.
- **Severity:** 3 —
  silent, reachable, but
  in a niche tool.

```diff

-    pc = &histo->counts[0];

-    for (total = 0, i = low; i < nbins; i++) {
-      total += *pc++;

+      total += histo->counts[i];

-        *pdst++ = nint(255.0f * (float)total / (float)total_pix);

```

Converts the loops from
pointer arithmetic to
indexed access, matching
the structure of the
correct `MRIgetEqualizeHisto`
function. Also explicitly
zeros the `[0..low-1]`
range of histo_eq.

## Workarounds

For users who need
adaptive histogram
equalization: pass
`low=0` to disable the
background skip. This
avoids triggering the
indexing mismatch (since
the pointer starts at
index 0 anyway, and with
`low=0` that's also
what the loop counter
should start at). The
trade-off is that
background voxels are
included in the
equalization — but this
is usually acceptable
for brain MRI where
background is small.

Or: use the non-adaptive
`mri_histo_eq` (default
mode without
`--adaptive-normalize`),
which uses the correct
`MRIgetEqualizeHisto`
path.
