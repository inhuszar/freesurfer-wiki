# [severity-4] [bug-00121] `readFSL2` negates all three warp frames when only frame 0 should be flipped

> [!bug] Synopsis
> ```cpp
> /* mri_warp_convert/mri_warp_convert.cpp:127-193 */
> GCAM* readFSL2(const string& warp_file, const string& src_geom)
> {
>   ...
>   double det = MatrixDeterminant(vox2ras);
>   ...
>   for(c=0; c < warp->width; c++){
>     for(r=0; r < warp->height; r++){
>       for(s=0; s < warp->depth; s++){
>         ...
>         fslras = MatrixMultiply(vox2fslras_warp,crs,fslras);
>         for(int k=0; k<3; k++) {
>           double w = MRIgetVoxVal(warp, c,r,s,k);
>           // 2026-02-17 YJH: it looks like it flips every frame not just the first one
>           // readFSL() flips only the first frame
>           if(det > 0) w *= -1;  /* :166 — bug: applies to k=0, 1, AND 2 */
>           fslras->rptr[k+1][1] += w;
>         }
>         ...
>       }
>     }
>   }
> }
> ```
>
> The FSL warp-file convention is that
> when the source image has positive
> Jacobian determinant (non-radiological
> orientation), the **x-component**
> (frame 0) of the displacement must
> be negated to convert to FSL's
> internal radiological frame. The
> sister function `readFSL`
> ([`:195-…`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_warp_convert/mri_warp_convert.cpp#L195))
> implements this correctly: only
> frame 0 is negated.
>
> `readFSL2` (the newer version that
> handles arbitrary voxel sizes) puts
> the `if(det > 0) w *= -1;`
> negation **inside** the per-frame
> loop, so it applies to all three
> displacement components (x, y, z).
>
> The comment at `:164-165`
> (added 2026-02-17 by author YJH)
> explicitly acknowledges the
> discrepancy:
> *"it looks like it flips every
> frame not just the first one,
> readFSL() flips only the first
> frame"*
>
> But the fix has not been applied;
> the bug remains.

## Detailed Description

### What FSL warps look like

An FSL warp `.nii.gz` is a 4D
displacement field where each
voxel stores a 3-vector `(dx, dy,
dz)` in FSL-RAS coordinates. FSL's
internal coordinate convention is
radiological: when the source
image has POSITIVE Jacobian
determinant, FSL has implicitly
flipped the x-axis. To consume
such a warp in a "normal"
(non-FSL) tool, you must un-flip
the x-axis by negating the
x-component of the displacement.

So the correct conversion is:
- if det > 0: negate dx only.
- if det ≤ 0: pass through.

`readFSL` (the original function)
implements this correctly by
treating the three frames
separately
([`:229-234`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_warp_convert/mri_warp_convert.cpp#L229-L234)):

```cpp
v = MRIgetVoxVal(mri, c,r,s,0) / mri->xsize;
if (MatrixDeterminant(m) > 0)
  MRIsetVoxVal(mri2, c, r, s, 0, -v);    // negate only frame 0
else
  MRIsetVoxVal(mri2, c, r, s, 0,  v);

v = MRIgetVoxVal(mri, c,r,s,1) / mri->ysize;
// ... no flip for frame 1 ...

v = MRIgetVoxVal(mri, c,r,s,2) / mri->zsize;
// ... no flip for frame 2 ...
```

`readFSL2` (the newer
voxel-size-aware version)
processes all three frames in
the same `for k` loop, with the
negation inside the loop:

```cpp
for(int k=0; k<3; k++) {
  double w = MRIgetVoxVal(warp, c,r,s,k);
  if(det > 0) w *= -1;     /* negates k=0, 1, AND 2 */
  fslras->rptr[k+1][1] += w;
}
```

So for det > 0, all three
displacements are negated. The
resulting warp transforms points
to mirrored positions in y and z
that should not have been
mirrored.

### Concrete impact

For a typical (det > 0) FSL warp
that transforms `subject → MNI`:

- **Correct:** apply x-flip, end
  up with correct subject-to-MNI
  warp.
- **Buggy:** apply x-flip AND
  y-flip AND z-flip — the
  resulting "warp" maps points to
  approximately point-mirrored
  positions instead of MNI.

When the converted GCAM is
subsequently used by
`mri_vol2vol --m3z` or similar,
the output volume is severely
distorted — left/right is
correctly mirrored back, but
anterior/posterior and
inferior/superior are now also
mirrored relative to expected.

### Why the bug went undetected (until 2026-02-17)

The author YJH discovered the
issue during a code-review of
GCAM warp readers and added the
acknowledging comment, but did
not commit the fix. The
function is called only by
users who explicitly pass
`--in_src_geom`, which is a
non-default opt-in path. Default
FSL-warp conversion uses
`readFSL` (the correct version)
which is selected when
`in_src_geom` is empty
([`:616`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_warp_convert/mri_warp_convert.cpp#L616)).

### Why use readFSL2 vs readFSL

`readFSL2` was added because
`readFSL` "assumes a standard
siemens image orientation" and
"isotropic voxels" (per comments
in readFSL). For modern
multi-vendor datasets with
anisotropic or non-standard
orientations, users are pushed
toward `readFSL2`. But
`readFSL2`'s flip bug means
those modern users get a worse
result than the old code-path.

## Root Cause

When `readFSL2` was written
(later than `readFSL`), the
author put the flip logic inside
the per-frame loop for code
brevity, not realizing that the
flip should only apply to frame
0. The 2026-02-17 review caught
the discrepancy but a fix was
not committed.

## Impact

- **`mri_warp_convert
  --in_src_geom`:** any FSL warp
  with positive Jacobian
  determinant produces a
  fundamentally wrong GCAM. The
  resulting warp mirrors all
  three axes when it should
  mirror only x.
- **Downstream:** all tools
  consuming the converted
  `.m3z` (e.g.
  `mri_vol2vol`,
  `mri_label2label --regmethod
  m3z`, `mris_resample`) produce
  visually-wrong outputs.
- **Severity:** 4 — opt-in code
  path (`--in_src_geom`), but
  results are silently and
  catastrophically wrong when
  triggered.

## Recommended Fix

```diff
--- a/mri_warp_convert/mri_warp_convert.cpp
+++ b/mri_warp_convert/mri_warp_convert.cpp
@@ -160,12 +160,13 @@ GCAM* readFSL2(const string& warp_file, const string& src_geom)
         fslras = MatrixMultiply(vox2fslras_warp,crs,fslras);
         // Add the warp value at this voxel to get the FSL RAS in the source space
         for(int k=0; k<3; k++) {
           double w = MRIgetVoxVal(warp, c,r,s,k);
-          // 2026-02-17 YJH: it looks like it flips every frame not just the first one
-          // readFSL() flips only the first frame
-          if(det > 0) w *= -1; // only flip first frame (by negating relative shifts)
+          // FSL convention: when det > 0 (non-radiological source),
+          // FSL has internally flipped x. We undo that by negating
+          // only the x-component (frame 0).
+          if(det > 0 && k == 0) w *= -1;
           fslras->rptr[k+1][1] += w;
         }
```

Add `&& k == 0` to the flip
condition so it applies only to
the x-component, matching
`readFSL`'s behaviour and the
FSL convention.

## Workarounds

For users converting FSL warps
right now: use the older
`readFSL` path by omitting
`--in_src_geom`:

```
mri_warp_convert --infswarp \
    <fsl_warp.nii.gz> \
    --outfswarp <out.m3z>
```

(But this only works for
isotropic voxel inputs.)

Alternatively, pre-flip the y
and z components of the FSL
warp before feeding to
`readFSL2`, to compensate for
the bug.
