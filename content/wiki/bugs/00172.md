# [severity-2] [bug-00172] bbmask — --npad N pads the bounding box by N+1 voxels (off-by-one)

> [!bug] Synopsis
> `bbmask` lets the user expand the cropping bounding box by `--npad N`
> voxels. Before calling `mri_mask -bb`, the script computes
> `@ npad2 = $npad + 1` and passes `npad2` (not `npad`) as the
> `mri_mask -bb` padding argument. Because `mri_mask -bb K` expands the
> box by exactly `K` voxels in each direction, the user-requested
> `--npad N` actually yields a pad of `N + 1` voxels on every face. A
> request of `--npad 0` still pads by 1 voxel, and `--npad 3` pads by 4.
> The output field of view is one voxel larger than documented in every
> direction.

## Affected Artefacts

- **Tool(s):** [[bbmask]] — the `--npad` option.
- **Pipeline stage(s):** _N/A_ — `bbmask` is a standalone field-of-view
  reduction utility; it is not invoked by
  [[wiki/pipelines/recon-all|recon-all]].
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all — purely arithmetic in the tcsh script.
- **Triggering configuration:** always on. Every invocation adds 1 to
  the requested pad before cropping the mask
  ([`scripts/bbmask:76-77`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/bbmask#L76-L77))
  and every `--src` volume
  ([`scripts/bbmask:87`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/bbmask#L87)).

## Detailed Description

`bbmask` builds a tight bounding box around the non-zero voxels of an
input mask and crops the mask (and any `--src` volumes) to that box,
optionally expanded by a user-specified pad. The help text states:

> "The bounding box can be expanded by npad number of voxels."

The cropping is delegated to `mri_mask -bb <npad>`. In `mri_mask`, the
`-bb` option sets all six face-pads `nPadBB[0..5]` to its single integer
argument
([`mri_mask/mri_mask.cpp:522-533`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_mask/mri_mask.cpp#L522-L533)),
and `REGIONgetBoundingBoxM` then moves the box start to `cmin - npad[0]`
and grows its size by `npad[0] + npad[1]`
([`utils/region.cpp:324-329`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/region.cpp#L324-L329)).
So `mri_mask -bb K` expands the box by exactly `K` voxels toward 0 and
`K` voxels toward the far edge — i.e. `K` voxels on each face, matching
its own help ("expanded by npad voxels in each direction").

`bbmask` does **not** pass `--npad` straight through. It first does:

```tcsh
@ npad2 = $npad + 1
set cmd = (mri_mask -T .01 -bb $npad2 ...)
```

The `+ 1` means the effective pad is always one greater than the value
the user asked for. The user-facing contract ("expanded by npad voxels")
is therefore violated by exactly one voxel per face.

### Expected Behaviour

`bbmask --npad N ...` should crop to a bounding box expanded by `N`
voxels in each direction, matching the documented "expanded by npad
number of voxels". `--npad 0` should give a tight box with no padding.

### Observed Behaviour

The box is expanded by `N + 1` voxels in each direction. `--npad 0`
pads by 1 voxel; `--npad 3` pads by 4. The `mri_mask` console line that
`bbmask` echoes confirms the inflated value: with `--npad 3` it prints
`cropping npad = 4` and `Computing bounding box, npad = 4, 4, 4, 4, 4, 4`.

### Reproducer

```bash
# npad2 = npad + 1 is visible directly in the echoed mri_mask command.
# Create a small mask with a single non-zero voxel block and crop it:
mri_mask -T .01 -bb 3 mask.mgz mask.mgz out_npad3.mgz   # 3-voxel pad
# vs. what bbmask actually runs for --npad 3:
bbmask --mask mask.mgz out.mgz --npad 3
#   -> echoes: cropping npad = 4   (bbmask added 1)
#   -> out.mgz is one voxel larger per face than out_npad3.mgz
```

The off-by-one is also provable by inspection without data: `bbmask`
echoes its `mri_mask` command line, and the `npad` value printed there
is always `$npad + 1`.

## Root Cause

`bbmask` adds a spurious `+ 1` to the user's pad before handing it to
`mri_mask -bb`
([`scripts/bbmask:76`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/bbmask#L76)).
The most likely intent was to guarantee at least one voxel of padding so
the box never clips the mask (the `mri_mask` help for `-crop`/`-bbm`
recommends "npad should be at least 1 to avoid clipping"). But the
script implements this as an unconditional `npad + 1` rather than a
floor (`max(npad, 1)`), so it over-pads for *every* value of `--npad`,
not just `--npad 0`. The documented "expanded by npad voxels" contract
is broken by one voxel per face in all cases.

## Impact

- **Latent, low severity.** The output is still a valid cropped volume;
  it is simply one voxel larger per face than requested. No data is
  lost (the extra voxel is on the padding side, away from the mask), so
  the masked content is intact.
- The accompanying header-based registration
  ([`scripts/bbmask:95-98`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/bbmask#L95-L98))
  is derived from the *actual* cropped geometry, so it stays internally
  consistent — the registration is not wrong, only the field of view is
  larger than the user dialled in.
- Users who rely on `--npad 0` to produce a *tight* box (no padding)
  will instead get a 1-voxel border, which may matter for exact-FoV
  comparisons or downstream size assertions.
- `bbmask` is not in any default pipeline, so no standard recon-all /
  trac-all output is affected — hence severity 2 rather than 3.

## Recommended Fix

If the goal is to honour `--npad N` literally, pass `$npad` through
unchanged:

```diff
 # Mask the mask down to the bouning box. 
-@ npad2 = $npad + 1
-set cmd = (mri_mask -T .01 -bb $npad2 $inmask $inmask $outmask)
+set cmd = (mri_mask -T .01 -bb $npad $inmask $inmask $outmask)
```

```diff
-  set cmd = (mri_mask -T .01 -bb $npad2 $src $inmask $trg)
+  set cmd = (mri_mask -T .01 -bb $npad $src $inmask $trg)
```

### Alternative Fixes Considered

If a minimum of one voxel of padding is genuinely desired (to avoid
clipping, per the `mri_mask` guidance), enforce a floor instead of an
unconditional increment, so that values `N >= 1` are honoured exactly
and only `N = 0` is bumped to `1`:

```tcsh
@ npad2 = $npad
if($npad2 < 1) @ npad2 = 1
```

This preserves the no-clip safety net without over-padding every
non-zero `--npad`. The choice between the two fixes depends on whether
the documented contract ("expanded by npad voxels") or the no-clip
safety was the intended behaviour — see Confidence and Gaps.

## Workarounds (If Any)

Pass `--npad N-1` to obtain a pad of `N` voxels (e.g. `--npad 2` for a
3-voxel border). To get a genuinely tight box you cannot reach
`--npad 0` semantics through this tool; call
`mri_mask -T .01 -bb 0 in in out` directly instead.

## Confidence and Gaps

> [!gap] Was the +1 a deliberate no-clip floor?
> The `+ 1` may have been intended only to ensure a minimum 1-voxel
> margin (the `mri_mask` help warns that npad "should be at least 1 to
> avoid clipping"). If so, the *intent* is partially served but the
> *implementation* over-pads for every `--npad >= 1`. A developer should
> confirm whether the literal `--npad N` contract or a no-clip floor was
> meant, and pick the corresponding fix above. Either way the current
> behaviour disagrees with the documented "expanded by npad voxels".
