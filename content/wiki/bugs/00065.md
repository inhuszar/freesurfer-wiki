# [severity-1] [bug-00065] `mrisurf_vals.cpp` — six source-acknowledged float→double precision sites

> [!bug] Synopsis
> The surface-distance accumulation primitives at
> [`utils/mrisurf_vals.cpp:3717`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_vals.cpp#L3717),
> [`:3738`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_vals.cpp#L3738),
> [`:3786`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_vals.cpp#L3786),
> [`:3811`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_vals.cpp#L3811),
> [`:3987`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_vals.cpp#L3987),
> all accumulate vertex-pair distances `dist =
> sqrt(xd*xd + yd*yd + zd*zd) + neighbour_dist`
> using `float` for `xd`, `yd`, `zd`, `dist`. Each
> site carries the comment:
>
> ```cpp
> // BUG - THESE SHOULD BE double!  NOT CHANGED TO AVOID RESULTS CHANGING.
> ```
>
> The promotion to `double` was deferred to preserve
> bit-for-bit numerical-result stability on the
> author's regression test set. The pattern is
> visible technical debt rather than a hidden defect,
> but the author labelled it `BUG` so it merits a
> wiki entry for traceability.

## Affected Artefacts

- **Functions affected:** `MRISdistanceTransform`,
  `MRISexpandDistances`, and similar
  surface-vertex-pair distance utilities in
  `utils/mrisurf_vals.cpp` (the six annotated sites
  span both functions).
- **Pipeline stage(s):** surface integration (cortex
  ribbon / sphere normalisation) — affects float
  precision in distance-transform fields used as
  smoothing / energy inputs.
- **Triggering configuration:** any call that
  invokes the surface-distance primitives. In
  practice, recon-all surface stages do.
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION`.

## Detailed Description

```cpp
// :3717
// BUG - THESE SHOULD BE double!  NOT CHANGED TO AVOID RESULTS CHANGING.
//
float xd = vn2->x - vn->x;
float yd = vn2->y - vn->y;
float zd = vn2->z - vn->z;
float dist = sqrt(xd * xd + yd * yd + zd * zd);
#if !MULTI_DIST_SCALING
if (nbhd_size > 1) {
  dist /= dist_scale;
}
dist += vn2->d;
#else
dist = (dist + vn2->d * distance_scale[vn2->marked]) / distance_scale[vn2->marked + 1];
#endif
```

The float accumulation is fine for short-range
distances but loses precision when many small
distances are summed. The comment is consistent
across all six sites, so the pattern is intentional.

## Root Cause

Documented technical debt. A historical regression-
test cohort produced `float`-precision distance
fields, and changing the type to `double` would
shift bit-level results enough to fail the test
diff. The author preferred to leave the precision
defect in place rather than rebaseline.

## Impact

- **Numerical:** small precision loss in surface
  distance fields. Visible only at sub-bit-precision
  level; consumers that compare distances (e.g.,
  `MRISsmoothMRI`) accumulate the same minor error.
- **Practical:** below the noise floor of typical
  recon-all results.

## Recommended Fix

Promote the four locals (`xd`, `yd`, `zd`, `dist`)
to `double` at all six sites and rebaseline the
test cohort. Single-token type change × 4 lines × 6
sites.

## Workarounds

None — sub-bit-precision impact.
