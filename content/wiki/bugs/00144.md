>
> Nine `MRIsetVoxVal` calls. No `for` loop over the cube interior. The output is a synthetic volume containing only 9 marked voxels at the locations described above; every other voxel is zero (from the `MRIconst(…, 0, …)` initialisation at the top of the branch).
>
> For comparison, the sister PDFs in the same cascade do fill regions:
>
> - `--sphere` at [`:236-245`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_volsynth/mri_volsynth.cpp#L236-L245) calls `MRIsphereMask(...)` which fills all voxels within `voxradius` of `spherecenter`.
> - `--boundingbox` at [`:338-343`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_volsynth/mri_volsynth.cpp#L338-L343) calls `MRIsetBoundingBox(...)` which fills the box interior with `ValueA` (and outside with `ValueB`).
> - `--grid` at [`:350-360`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_volsynth/mri_volsynth.cpp#L350-L360) calls `MRIgrid(...)` which fills a periodic grid.
>
> Only `--cube` writes a sparse fiducial pattern.

## Detailed Description

`mri_volsynth` is a phantom / synthetic-volume generator that supports many probability density functions (PDFs) and geometric shapes via the `--<pdf>` family of flags. The `--cube cubeedgemm` flag exists alongside `--sphere`, `--boundingbox`, `--grid`, etc., and the naming convention `--cube` strongly implies "fill a cube". The code instead marks 9 voxels (the volume center plus the cube's 8 corner voxels) and leaves all other voxels at zero.

### Expected Behaviour

`--cube cubeedgemm` should fill a cube of side `cubeedgemm` mm centered in the volume with `ValueA`, leaving the rest of the volume at `ValueB` (or zero). This is analogous to `--boundingbox`, which already does the same job for an axis-aligned box defined explicitly.

### Observed Behaviour

The output volume has 9 voxels set to `ValueA` (center + 8 corners) and all other voxels at zero. No cube interior is filled.

### Reproducer

```bash
# Volume: 256³ at 1mm; ValueA = 100; cube edge = 40 mm
mri_volsynth \
    --dim 256 256 256 1 \
    --res 1 1 1 1 \
    --pdf cube \
    --cube 40 \
    --val-a 100 \
    --o cube.mgz

# Expected: a 40×40×40-voxel cube of 100s centered at (128,128,128).
# Observed:
mri_segstats --i cube.mgz --sum cube.stats
#   Number of voxels with value 100: 9   (instead of 64000)
```

> [!gap] Reproducer not yet executed end-to-end
> The static read of the code is unambiguous: nine `MRIsetVoxVal` calls, no loop over the cube interior. An A/B run against a patched version that uses `MRIsetBoundingBox` (or an explicit `for c, for r, for s` loop) would confirm the 64000 vs 9 voxel-count discrepancy.

## Root Cause

Either the implementation is incomplete (the author wrote the corner computation and the fiducial set, intending to follow up with the interior fill but never did) or the option name is wrong (the author intended fiducial markers, not a solid cube, and chose a misleading name). The behaviour matches neither the natural reading of `--cube` nor any other documented use case in the file.

## Impact

- **Synthetic phantom users get wrong output.** Anyone who reaches for `mri_volsynth --cube N` to make a solid cube phantom (e.g., for PVE calibration, registration validation, kinetic-modelling test) gets a 9-voxel fiducial pattern that doesn't behave like a cube under partial-volume effects, smoothing, or volume-of-interest stats.
- **No `recon-all` impact.** `mri_volsynth` is not on the default `recon-all` path.
- **Silent.** The CLI does not warn that the output is fiducial-only; the printed message at [`:372`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_volsynth/mri_volsynth.cpp#L372) just dumps the 8 corner coords.

## Recommended Fix

Two plausible fixes, depending on intent:

### Fix A — fill the cube interior (preferred if name is to stay `--cube`)

```diff
-  MRIsetVoxVal(mri,c0,r0,s0,0,ValueA);
-  MRIsetVoxVal(mri,c1,r1,s1,0,ValueA);
-  MRIsetVoxVal(mri,c1,r1,s2,0,ValueA);
-  MRIsetVoxVal(mri,c1,r2,s1,0,ValueA);
-  MRIsetVoxVal(mri,c1,r2,s2,0,ValueA);
-  MRIsetVoxVal(mri,c2,r1,s1,0,ValueA);
-  MRIsetVoxVal(mri,c2,r1,s2,0,ValueA);
-  MRIsetVoxVal(mri,c2,r2,s1,0,ValueA);
-  MRIsetVoxVal(mri,c2,r2,s2,0,ValueA);
+  for (int cc = c1; cc <= c2; cc++)
+    for (int rr = r1; rr <= r2; rr++)
+      for (int ss = s1; ss <= s2; ss++)
+        MRIsetVoxVal(mri, cc, rr, ss, 0, ValueA);
```

Alternatively, replace the whole block with a call to `MRIsetBoundingBox`, which already implements axis-aligned box filling and is the existing convention in this file (used by `--boundingbox` at [`:338-343`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_volsynth/mri_volsynth.cpp#L338-L343)).

### Fix B — rename the option and document fiducial intent (if 9-voxel fiducial is the intended behaviour)

Add a `--cube-fiducial` (or `--cube-corners`) flag that triggers the existing code, and reject `--cube N` with an error pointing users to one of the supported alternatives. Add help text to the existing XML / usage docs.

The choice between A and B requires confirmation from the original author; the static reading cannot disambiguate intent.

## Workarounds (If Any)

- Use `--boundingbox c0 r0 s0 c1 r1 s1 ValueA ValueB` to manually specify cube corners — this works correctly.
- Use `--sphere voxradius` with `voxradius = cubeedgemm/2` for a sphere phantom (different geometry but at least a filled solid).
- Pre-build the cube as a `.mgz` with another tool (e.g., `mri_binarize --i <empty_template> --match … --o cube.mgz`) and load via `--temp`.
