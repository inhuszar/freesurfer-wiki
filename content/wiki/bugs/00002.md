# [severity-3] [bug-00002] MRISfindExpansionRegions — neighbour ripflag test uses central vertex

> [!bug] Synopsis
> Inside the neighbour loop of `MRISfindExpansionRegions`, the ripflag
> check is written against the central vertex `v` rather than the
> neighbour `vn`. Because the outer loop already guarantees
> `v->ripflag == 0` whenever control reaches the neighbour loop, the
> intended guard never fires, and ripped neighbouring vertices are still
> counted in the long-distance statistics that seed the surface
> "expansion region" mask used during white/pial placement.

## Affected Artefacts

- **Tool(s):** [[mris_place_surface]] (modern placement driver;
  [`mris_make_surfaces/mris_place_surface.cpp:730`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mris_make_surfaces/mris_place_surface.cpp#L730)) and
  [[mris_make_surfaces]] via the shared `MRISfindExpansionRegions`
  library call. The legacy attic copy in
  `attic/mris_longitudinal_surfaces/mris_longitudinal_surfaces.cpp` has
  an independent in-tree copy with the same pattern.
- **Pipeline stage(s):** `autorecon2` / surface placement; the function
  runs after the intensity-gradient search that populates `v->d`.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit
  `d932c45b79`.
- **Platforms:** all — purely logical.
- **Triggering configuration:** always-on for any run that reaches the
  white-matter surface deformation call chain.

## Detailed Description

`MRISfindExpansionRegions` flags vertices whose distance-to-max-gradient
(`v->d`) exceeds `mean + 2 sigma` and which have more than 25% of their
immediate neighbours also beyond that threshold. Those vertices are
zeroed out in `v->curv` (and otherwise set to `|v->d|`) to down-weight
them in subsequent surface relaxation.

The outer loop already rejects ripped vertices and vertices with non-
positive `val` before reaching the neighbour loop. Inside the neighbour
loop, the intent is clearly to skip ripped **neighbours** so they are
not counted in the denominator `num` or the long-distance count
`num_long`. Instead, the code tests the central vertex's own
`ripflag` — a value that is always zero at that point — so the guard is
dead and ripped neighbours contribute to the statistic.

### Expected Behaviour

When enumerating the first-ring neighbours of `v`, skip any neighbour
`vn` whose `ripflag` is set (i.e., that has been marked inactive). The
central vertex is already known to be live by construction.

### Observed Behaviour

The neighbour-loop guard reads `v->ripflag` instead of `vn->ripflag`.
Because `v->ripflag` has just been filtered to `0`, the guard never
fires; ripped neighbours pass through the `val <= 0` test only if their
`val` happens to be non-positive. Ripped neighbours whose `val` is still
positive (possible whenever `MRISripVertices` or related routines flip
`ripflag` without zeroing `val`) are therefore counted in both `num`
and, if `|vn->d| >= mean + 2*std`, in `num_long`, biasing the ratio that
decides whether the central vertex is marked as an expansion region.

### Reproducer

> [!gap] Reproducer not yet constructed
> Verifying the impact requires a surface on which some neighbours of an
> expansion candidate are ripped but still carry a positive `val`. Such
> surfaces arise during `mris_place_surface` after partial deformation
> steps; a targeted unit-style exercise — rip a subset of neighbours,
> set their `d` and `val` by hand, and call `MRISfindExpansionRegions` —
> would demonstrate the miscount directly.

## Root Cause

A copy-paste of the central-vertex guard into the neighbour loop without
renaming the pointer. The condition should read `vn->ripflag`; as
written, `v->ripflag` is statically known to be zero at that line, so
the clause is dead code.

## Impact

- Ripped neighbours whose `val` remains positive are counted, slightly
  inflating both the denominator `num` and (when their `d` is large) the
  numerator `num_long`. The resulting ratio may cross the 25% threshold
  in edge cases it should not.
- The function is called from `mris_place_surface` (modern driver) and
  historically from `mris_make_surfaces`/`mris_refine_surfaces`, inside
  the white-surface placement loop in [[wiki/pipelines/recon-all|recon-all]]. Effects on the
  final surface are expected to be small and confined to ripped-neighbour
  boundaries, but the fix is free.
- A related variance formula one line above
  (`std = sqrt(dsq/num - mean*mean)`) is susceptible to catastrophic
  cancellation but is a separate, much milder concern; it is not part of
  this bug report.

## Recommended Fix

```diff
     for (num_long = num = 1, n = 0 ; n < vt->vnum ; n++)
     {
       VERTEX const * const vn = &mris->vertices[vt->v[n]] ;
-      if (vn->val <= 0 || v->ripflag) continue ;
+      if (vn->val <= 0 || vn->ripflag) continue ;
       if (fabs(vn->d) >= mean+2*std)
         num_long++ ;
       num++ ;
     }
```

Apply the same one-character fix to the near-duplicate body in
`attic/mris_longitudinal_surfaces/mris_longitudinal_surfaces.cpp` if
that file is still compiled in any configuration.

## Workarounds (If Any)

None needed at the user level; the defect biases the heuristic rather
than crashing or corrupting output.
