# [severity-2] [bug-00175] fs_update — selective update appends to rsync_cmd without resetting the base, building a malformed command for 2+ paths

> [!bug] Synopsis
> `fs_update <path1> <path2> ...` is meant to rsync each named path from
> the FreeSurfer patch server into `$FREESURFER_HOME`, one path per
> iteration. The loop appends `"/<path> $FREESURFER_HOME/<path>"` to the
> shared `rsync_cmd` string with `+=` but never resets `rsync_cmd` to its
> base prefix between iterations. After the first path, `rsync_cmd`
> already contains a complete command; the second path is concatenated
> onto the end of it, so the resulting rsync has the wrong source and a
> mangled destination (the second source path is glued onto the first
> destination path). Every path after the first is mis-synced. With a
> single path argument the command is correct, so the bug is latent until
> a user passes two or more paths.

## Affected Artefacts

- **Tool(s):** [[fs_update]] — the selective-update branch
  ([`scripts/fs_update:67-73`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs_update#L67-L73)).
- **Pipeline stage(s):** _N/A_ — `fs_update` is a manual installation
  helper that downloads tutorial patches; it is not part of any analysis
  pipeline.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all (bash script).
- **Triggering configuration:** `fs_update <path1> <path2> [...]` with
  two or more path arguments, answering `y` at the prompt. A single path
  argument is unaffected.

## Detailed Description

`fs_update` constructs an rsync base command once, into `rsync_cmd`
([`scripts/fs_update:55`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs_update#L55)):

```bash
rsync_cmd="rsync -zbrlv --progress --suffix=.`date +%s`_bak rsync://surfer.nmr.mgh.harvard.edu/pub/dist/freesurfer/patches/${build}"
```

When the user passes explicit paths, it loops over them and *appends* the
source/destination pair to `rsync_cmd` with `+=`
([`scripts/fs_update:67-73`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs_update#L67-L73)):

```bash
    else
      for update_file in "$@"; do
        rsync_cmd+="/${update_file} $FREESURFER_HOME/${update_file}"
        echo "$rsync_cmd"
        $rsync_cmd
      done
    fi
```

The base prefix is never re-established inside the loop. On the **first**
iteration, `rsync_cmd` becomes:

```
rsync ... patches/<build>/<path1> $FREESURFER_HOME/<path1>
```

which is a correct two-operand rsync. On the **second** iteration the
loop appends to *that already-complete string*, producing:

```
rsync ... patches/<build>/<path1> $FREESURFER_HOME/<path1>/<path2> $FREESURFER_HOME/<path2>
```

Now the command has the wrong shape: rsync interprets the trailing
argument as the destination and everything before it as sources, so the
**source** is `patches/<build>/<path1>` (the *first* path's URL — the
intended second-path source `patches/<build>/<path2>` is missing), and
the **destination** is `$FREESURFER_HOME/<path1>/<path2>` (the second
path name glued onto the first path's destination directory). The real
`$FREESURFER_HOME/<path2>` becomes a second source rather than the
destination. Every subsequent iteration compounds the corruption.

### Expected Behaviour

Each iteration should run an independent, well-formed rsync:

```
rsync ... patches/<build>/<pathN>  $FREESURFER_HOME/<pathN>
```

i.e. the per-path source/destination must be appended to a *fresh* copy
of the base prefix on every iteration.

### Observed Behaviour

Only the first path syncs correctly. From the second path onward, the
command is malformed: the prior path's source URL is reused, and the new
path name is appended onto the prior destination, so files land in the
wrong place (or rsync errors).

### Reproducer

```bash
# Stub rsync to print its argv; stub FREESURFER_HOME and build-stamp.
mkdir -p home bin
echo "fake-build" > home/build-stamp.txt
cat > bin/rsync <<'EOF'
#!/bin/sh
echo "ARGC=$#"; for a in "$@"; do echo "  ARG: $a"; done
EOF
chmod +x bin/rsync
FREESURFER_HOME="$PWD/home" PATH="$PWD/bin:$PATH" \
  bash -c 'printf "y\n" | fs_update bin/mri_convert bin/mri_info'

# Iteration 1 (correct, 5 args):
#   rsync ... patches/fake-build/bin/mri_convert  $FH/bin/mri_convert
# Iteration 2 (malformed, 6 args):
#   rsync ... patches/fake-build/bin/mri_convert  $FH/bin/mri_convert/bin/mri_info  $FH/bin/mri_info
#                                                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ destination corrupted;
#                                                  source for mri_info is missing.
```

Executed against the installed `/usr/local/freesurfer/8.2.0/bin/fs_update`;
the second iteration produced the 6-argument malformed command shown
(source `.../patches/fake-build/bin/mri_convert`, destination
`$FREESURFER_HOME/bin/mri_convert/bin/mri_info`).

```bash
if [[ $REPLY =~ ^[Yy]$ ]]; then
    if [ "$#" -eq 0 ]; then
      rsync_cmd+="/* $FREESURFER_HOME"
      echo "$rsync_cmd"
      $rsync_cmd
    else

        rsync_cmd+="/${update_file} $FREESURFER_HOME/${update_file}"
        echo "$rsync_cmd"
        $rsync_cmd
      done
    fi
```

(The no-argument branch at line 64 appends once and runs once, so it is
not affected; the defect is specific to the multi-path loop.)

## Root Cause

`rsync_cmd` is treated as if it were reset to the base on each iteration,
but it is a single accumulating string. The `+=` operator concatenates
the per-path operands onto whatever `rsync_cmd` already holds — which,
after iteration 1, is a full command. Nothing inside the loop restores
the base prefix, so the operands stack up and the command shape degrades
after the first path.

## Impact

- **Latent, low severity.** The default usage `fs_update` (no path
  arguments) and single-path usage `fs_update bin/mri_convert` are
  correct; only multi-path invocations are affected. `fs_update` is a
  manual tutorial-installation helper, not part of any pipeline, and the
  patch server it targets is rarely used.
- When triggered, the consequence is a wrong rsync: from the second path
  onward, files are fetched from the wrong source URL and/or written to a
  nested wrong destination (e.g. `bin/mri_convert/bin/mri_info`), or rsync
  errors out. Because rsync runs once per loop iteration with the
  *cumulative* string, the script can silently update the wrong location
  rather than failing loudly.
- The post-loop `if [ "$?" -eq 0 ]` check
  ([`scripts/fs_update:74`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs_update#L74))
  only inspects the status of the *last* rsync, so partial corruption on
  earlier iterations is not detected.

## Recommended Fix

Build each iteration's command from a fresh copy of the base prefix
rather than mutating the shared string. Keep the base in a separate
variable and concatenate into a local per-iteration command:

```diff
     else
       for update_file in "$@"; do
-        rsync_cmd+="/${update_file} $FREESURFER_HOME/${update_file}"
-        echo "$rsync_cmd"
-        $rsync_cmd
+        this_cmd="${rsync_cmd}/${update_file} $FREESURFER_HOME/${update_file}"
+        echo "$this_cmd"
+        $this_cmd
       done
     fi
```

Here `rsync_cmd` keeps holding only the base prefix, and each iteration
derives an independent `this_cmd`.

### Alternative Fixes Considered

Save and restore the base inside the loop:

```bash
base="$rsync_cmd"
for update_file in "$@"; do
  rsync_cmd="${base}/${update_file} $FREESURFER_HOME/${update_file}"
  echo "$rsync_cmd"
  $rsync_cmd
done
```

Functionally equivalent; the local-variable version above is cleaner.
(Both leave the unrelated word-splitting reliance on `$rsync_cmd` intact;
that is a separate style concern, not this defect.)

## Workarounds (If Any)

Invoke `fs_update` once per path so each run starts from the base
prefix:

```bash
fs_update bin/mri_convert
fs_update bin/mri_info
```

A single path per invocation is always well-formed.
