# [severity-2] [bug-00176] check_subject — vertex-count check writes /tmp/chsubj.$$.dat but reads /tmp/chsubj.dat, so the check is dead/unreliable

> [!bug] Synopsis
> `check_subject` runs a per-surface vertex-count consistency check: it
> calls `mris_info <file> --o /tmp/chsubj.$$.dat --nvertices` (writing the
> info to a **PID-suffixed** temp file), but then reads the count back
> from `/tmp/chsubj.dat` (**no PID suffix**). Because the file it reads
> is not the file it wrote, the read normally fails, `$nvertices` becomes
> `undef`, and the "inconsistent number of vertices" warning can never
> fire. The check is effectively dead — it silently passes every subject,
> and on a shared `/tmp` it could read a stale `/tmp/chsubj.dat` left by
> another run/process, yielding a wrong result.

## Affected Artefacts

- **Tool(s):** [[check_subject]] — the vertex-count loop
  ([`scripts/check_subject:52-87`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/check_subject#L52-L87)).
- **Pipeline stage(s):** _N/A_ — `check_subject` is a standalone QA
  helper that sanity-checks a recon-all subject's `surf/` directory; it
  is not invoked by [[wiki/pipelines/recon-all|recon-all]] itself.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all (Perl script). The stale-read race is most likely on
  multi-user hosts that share `/tmp`.
- **Triggering configuration:** always on — every run writes and reads
  mismatched paths. The check's *failure to fire* is unconditional; the
  stale-read variant depends on another `/tmp/chsubj.dat` existing.

## Detailed Description

For each hemisphere, `check_subject` iterates over the surface files
`smoothwm, inflated, white, sphere, pial, sphere.reg` and verifies they
all report the same vertex count. It obtains the count by running
`mris_info ... --nvertices` and parsing its output file
([`scripts/check_subject:58-69`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/check_subject#L58-L69)):

```perl
    # Get numer of vertices
    $tmpfile = "/tmp/chsubj.$$.dat";
    #printf "$tmpfile $file\n";
    system("mris_info $file --o $tmpfile --nvertices > /dev/null 2>&1");
    open(nvtxfp,"/tmp/chsubj.dat");
    $line = <nvtxfp>;
    close(nvtxfp);
    system("rm $tmpfile");
```

`mris_info` writes its info dump (which contains the `nvertices` line) to
`--o $tmpfile`, i.e. `/tmp/chsubj.$$.dat`, where `$$` is the script's PID.
The very next line opens `/tmp/chsubj.dat` — a **different** filename,
without the PID. The data that was just written is never read; the
PID-suffixed file is then deleted by `rm $tmpfile`.

The `open` has no `or die`/error check, so when `/tmp/chsubj.dat` does
not exist the `open` fails silently, `$line = <nvtxfp>` returns `undef`,
`@a = split(" ", undef)` yields an empty list, and
`$nvertices = @a[1]` is `undef`
([`scripts/check_subject:67-69`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/check_subject#L67-L69)).
The script lacks `use warnings`, so the uninitialized-value uses are
silent. On the first surface `$nvertices0` is set to `undef`; thereafter
every comparison `$nvertices0 != $nvertices`
([`scripts/check_subject:71`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/check_subject#L71))
compares `undef != undef`, which in numeric context is `0 != 0` → false.
The `WARN: inconsistent number of vertices` branch therefore never
executes.

### Expected Behaviour

For each hemisphere, the vertex count of every listed surface should be
read and compared; if any surface's vertex count differs from the first,
`check_subject` should emit `WARN: inconsistent number of vertices ...`
and increment `$status`.

### Observed Behaviour

The check is inert. The vertex count is read from the wrong file
(`/tmp/chsubj.dat`), which is normally absent, so `$nvertices` is `undef`
for every surface and no mismatch is ever reported — even when the
surfaces genuinely differ. On a shared `/tmp`, if some other process or a
prior tool left a `/tmp/chsubj.dat`, the script reads *that* file's first
line instead, producing a vertex count unrelated to the surface under
test (false positives or wrong values).

### Reproducer

```bash
# 1. Confirm the path mismatch directly: mris_info writes to the --o path,
#    and /tmp/chsubj.dat (no PID) is never created.
rm -f /tmp/chsubj.dat /tmp/chsubj.*.dat
mris_info $SUBJECTS_DIR/bert/surf/lh.white --o /tmp/chsubj.demo.dat --nvertices >/dev/null 2>&1
grep nvertices /tmp/chsubj.demo.dat     #  -> nvertices   135546   (written to the PID-style path)
ls /tmp/chsubj.dat                       #  -> No such file or directory (the path it READS)

# 2. Run the tool; no vertex warnings appear and /tmp/chsubj.dat is never made.
check_subject bert 2>&1 | grep -c "inconsistent number of vertices"   #  -> 0
ls /tmp/chsubj.dat                       #  -> No such file or directory
```

Executed against the installed `/usr/local/freesurfer/8.2.0/bin/check_subject`
and `mris_info` on subject `bert`: `mris_info` wrote the `nvertices` line
to the `--o` path; `/tmp/chsubj.dat` was never created; `check_subject`
emitted zero "inconsistent number of vertices" warnings.

## Code Reference (Unambiguous)

- **File:** `scripts/check_subject`
- **Function:** main hemisphere loop (vertex-count block)
- **Lines:** `58-69`
- **Commit:** `d932c45`

```perl
    # Get numer of vertices
    $tmpfile = "/tmp/chsubj.$$.dat";
    #printf "$tmpfile $file\n";
    system("mris_info $file --o $tmpfile --nvertices > /dev/null 2>&1");
    open(nvtxfp,"/tmp/chsubj.dat");
    $line = <nvtxfp>;
    close(nvtxfp);
    system("rm $tmpfile");

    @a = split(" ",$line);
    $nvertices = @a[1];
    if($nvertices0 < 0) {$nvertices0 = $nvertices;}

    if( $nvertices0 != $nvertices ){
	warn "WARN: inconsistent number of vertices between $hemi.smoothwm and $file\n";  
        $status++;
    }
```

The write target (`$tmpfile = /tmp/chsubj.$$.dat`) and the read target
(`/tmp/chsubj.dat`) differ by the `$$` PID component.

## Root Cause

The `open` reads a hard-coded `/tmp/chsubj.dat` while the write target is
the PID-suffixed `/tmp/chsubj.$$.dat`. The PID suffix was almost certainly
added to the *write* path (to avoid collisions between concurrent runs)
without updating the matching *read* path, so the two diverged. The
absent `or die` on the `open`, combined with the lack of `use warnings`,
hides the failure: the broken read degrades silently to `undef` rather
than erroring.

## Impact

- **Latent, low severity — a QA check that silently does nothing.** No
  pipeline output is affected; `check_subject` only *reports* on a
  subject. The harm is a false sense of safety: the vertex-count
  consistency check that this tool advertises will pass a subject whose
  surfaces actually have mismatched vertex counts (e.g. a corrupted or
  partially-regenerated `?h.pial`), because the comparison is always
  `undef != undef`.
- The script's other checks (file presence, modification-time ordering,
  curv/sulc/thickness size equality, qsphere-vs-orig size) still work, so
  `check_subject` is not entirely broken — only the vertex-count arm is
  dead. The tool's exit `$status` therefore omits any contribution from
  vertex mismatches.
- **Cross-run stale-read risk.** Because the read path is a fixed,
  un-PID'd name in shared `/tmp`, a leftover `/tmp/chsubj.dat` from
  another user or an unrelated tool would be read and parsed, producing a
  vertex count unrelated to the surface being checked — an
  unreliable/non-deterministic result rather than a guaranteed no-op.

## Recommended Fix

Read back the same PID-suffixed file that was written:

```diff
     # Get numer of vertices
     $tmpfile = "/tmp/chsubj.$$.dat";
     #printf "$tmpfile $file\n";
     system("mris_info $file --o $tmpfile --nvertices > /dev/null 2>&1");
-    open(nvtxfp,"/tmp/chsubj.dat");
+    open(nvtxfp,"$tmpfile") or warn "WARN: cannot read $tmpfile for $file\n";
     $line = <nvtxfp>;
     close(nvtxfp);
     system("rm $tmpfile");
```

Using `$tmpfile` for both the write and the read guarantees the count
parsed belongs to the surface just measured, and the added `or warn`
surfaces any future read failure instead of silently yielding `undef`.

### Alternative Fixes Considered

- Parse `mris_info` directly rather than via a temp file
  (`$line = (grep /^nvertices/, \`mris_info $file --nvertices\`)[0]`),
  eliminating the temp file (and the collision surface) entirely. Larger
  change; the minimal one-line path fix above is sufficient.
- Add `use strict; use warnings;` at the top so the uninitialized-value
  propagation that masked this defect would have been reported; advisable
  as a follow-up but orthogonal to the path fix.

## Workarounds (If Any)

No user-side workaround restores the vertex-count check without editing
the script. Users who need to confirm vertex-count consistency across a
subject's surfaces can run `mris_info <surf> --nvertices` on each surface
manually and compare. The remainder of `check_subject`'s checks remain
usable.
