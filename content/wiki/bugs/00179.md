# [severity-2] [bug-00179] wmedits2surf / bmedits2surf — freshness loop overwrites `$UpdateNeeded` each pass instead of OR-accumulating, so only the last output file decides whether to recompute

> [!bug] Synopsis
> `wmedits2surf` and `bmedits2surf` both decide whether to redo their
> work by looping over every output overlay and asking the helper
> `UpdateNeeded` whether that output is older than the inputs. The
> intent is "recompute if **any** output is stale". But each loop
> iteration writes `set UpdateNeeded = \`UpdateNeeded ...\`` —
> overwriting the accumulator instead of OR-ing into it
> (`set UpdateNeeded = ($UpdateNeeded || ...)`). Only the result for the
> **last** file in the loop (rh fill / rh clone) survives the loop. If
> that last file is up to date but an earlier file (e.g. an lh overlay)
> is stale or missing, the scripts wrongly report "update not needed"
> and skip the regeneration, leaving stale or absent overlays in place.

## Affected Artefacts

- **Tool(s):** [[wmedits2surf]] and [[bmedits2surf]] — both compute
  per-hemisphere binary edit-location overlays and gate recomputation
  on the same kind of freshness loop. The defect is the same logic
  error realised in two scripts.
- **Pipeline stage(s):** _N/A_ — both are standalone QA/analysis
  wrappers run manually after WM / brainmask edits; neither is on the
  default [[wiki/pipelines/recon-all|recon-all]] path.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all — tcsh control-flow logic.
- **Triggering configuration:** the freshness loop runs whenever the
  script is invoked **without** `--overwrite`. The defect changes the
  outcome only when the set of output overlays is in a mixed state —
  the last-checked overlay fresh while an earlier one is stale or
  missing.

## Detailed Description

Both scripts begin (when `--overwrite` is not set) by computing a
single boolean `$UpdateNeeded`. The helper script `scripts/UpdateNeeded`
returns `1` when an output file is missing or older than any of the
listed input files, `0` otherwise. The loop walks over every output
overlay (two edit types × the hemisphere list) and is meant to set the
accumulator true if **any** overlay needs refreshing.

The accumulator is initialised to `0`, but inside the loop it is
**assigned** the per-file result rather than OR-ed with it. After the
loop, `$UpdateNeeded` therefore reflects only the final iteration —
the last `(edit, hemi)` pair — discarding the verdict for every earlier
overlay.

### Expected Behaviour

"Recompute if any output is stale." For the default both-hemisphere run
the four checked overlays are, e.g. for `wmedits2surf` with `--fsa`:

```
lh.wmerase.fsa.mgh   rh.wmerase.fsa.mgh
lh.wmfill.fsa.mgh    rh.wmfill.fsa.mgh
```

If **any** of these is missing or older than `wm.mgz`, the script
should proceed to regenerate the overlays. Only if **all four** are
fresh should it print "update not needed" and exit early.

### Observed Behaviour

`$UpdateNeeded` is overwritten on every pass, so after the loop it
equals the freshness verdict of only the **last** overlay visited —
`rh.wmfill[.fsa].mgh` for `wmedits2surf`, `rh.bmclone[.fsa].mgh` for
`bmedits2surf` (the last `edit` value crossed with the last `hemi`).

Consequences:

- If the last overlay is **fresh** but an earlier overlay is **stale or
  missing**, the loop ends with `$UpdateNeeded = 0`, the script prints
  `update not needed`, and exits **without** regenerating the stale /
  missing earlier overlays.
- If the last overlay is stale, the script does recompute — and because
  the body unconditionally rebuilds *all* overlays, the earlier stale
  files happen to get fixed. So the bug only bites when the **last**
  file is the fresh one.
- With `--lh` or `--rh` the loop has a single hemi but still two edit
  types, so the `erase` verdict is overwritten by the `fill` (or
  `bmerase` by `bmclone`) verdict — the same class of miss.

The failure is silent: no error, just a skipped recomputation that
leaves the user with stale or partial overlays they believe are current.

### Reproducer

```bash
# Illustrate the overwrite-vs-OR bug in isolation. Stand in for
# UpdateNeeded with: 1 = stale, 0 = fresh. Suppose lh is stale (1)
# and rh is fresh (0):
tcsh -f -c 'set UpdateNeeded = 0
foreach v (1 0)          # 1 = an earlier stale file, 0 = last fresh file
  set UpdateNeeded = $v  # <-- the bug: assign, not OR
end
echo "final UpdateNeeded = $UpdateNeeded"   # prints 0 → "not needed"'
# Correct accumulation would print 1 (recompute), because an earlier
# file was stale.
```

End-to-end: run `wmedits2surf --s SUBJ` once to create all overlays,
then `touch` only `surf/lh.wmerase.fsa.mgh`'s **inputs** (or delete
`surf/lh.wmerase.fsa.mgh`) so that an lh overlay is stale while
`rh.wmfill.fsa.mgh` stays fresh, and re-run without `--overwrite`: the
script reports "update not needed for SUBJ" and does not rebuild the
stale lh overlay.

## Root Cause

The accumulator pattern is half-implemented: `$UpdateNeeded` is
initialised to `0` before the loop (correct for an OR-fold) but the
loop body uses plain assignment (`set UpdateNeeded = \`...\``) instead
of folding (`set UpdateNeeded = ($UpdateNeeded || \`...\`)`). Each pass
clobbers the running result, so the fold collapses to "value of the
last iteration". The `set UpdateNeeded = 0` initialisation is a strong
tell that an OR-fold was intended — otherwise it would be dead.

## Impact

- **Stale / missing overlays silently retained.** When the last
  overlay in iteration order is up to date but an earlier one is not,
  both scripts skip regeneration and leave the user with overlays that
  do not reflect the current `wm.mgz` / `brainmask.mgz` edits. Any
  downstream averaging of these overlays across a cohort then mixes
  fresh and stale maps without warning.
- **Not a default-pipeline defect.** Both tools are manual QA wrappers
  outside [[wiki/pipelines/recon-all|recon-all]], and the failure is
  gated on the no-`--overwrite` freshness path with a mixed-staleness
  file set — hence severity 2 (latent under typical use, QA-only
  output), not a higher score.
- **Easy to mask.** Passing `--overwrite` bypasses the loop entirely and
  always recomputes, so users who habitually force overwrite never see
  the bug.

## Recommended Fix

OR-accumulate the per-file result into the running flag in both scripts:

```diff
# scripts/wmedits2surf
-      set UpdateNeeded = `UpdateNeeded $fname $wm`
+      set UpdateNeeded = ($UpdateNeeded || `UpdateNeeded $fname $wm`)
```

```diff
# scripts/bmedits2surf
-      set UpdateNeeded = `UpdateNeeded $bmeditsurf $bm $bma`
+      set UpdateNeeded = ($UpdateNeeded || `UpdateNeeded $bmeditsurf $bm $bma`)
```

With the OR-fold, `$UpdateNeeded` becomes true as soon as **any**
overlay is stale or missing and stays true for the rest of the loop, so
the early-exit only fires when every overlay is fresh.

### Alternative Fixes Considered

Equivalent: short-circuit out of the loop the first time a stale file is
found, e.g. `if(\`UpdateNeeded ...\`) set UpdateNeeded = 1`. Functionally
identical to the OR-fold; the OR-fold keeps the existing one-line shape
and is the smaller diff.

## Workarounds (If Any)

Run with `--overwrite`, which skips the freshness check and always
regenerates all overlays. This trades a small amount of recomputation
for guaranteed-fresh output.

> [!gap] `UpdateNeeded` return convention
> The fix assumes `scripts/UpdateNeeded` prints `1` for "needs update"
> and `0` otherwise, which is how the `if(! $UpdateNeeded)` consumer and
> the `set UpdateNeeded = 0` initialiser both read it. If that helper's
> convention were inverted the early-exit polarity would already be
> wrong independently of this bug; the OR-fold fix preserves whatever
> convention the helper uses.
