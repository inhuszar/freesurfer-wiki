# [severity-3] [bug-00086] `MRIvol2VolTLKernel` leaks a full-volume `kernel` allocation and returns the wrong type

> [!bug] Synopsis
> `MRIvol2VolTLKernel`
> ([`utils/mri2.cpp:1233-1291`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri2.cpp#L1233-L1291))
> declares
>
> ```cpp
> MRI *MRIvol2VolTLKernel(MRI *src, MRI *targ, MATRIX *Vt2s)
> {
>   ...
>   MRI *kernel;
>   kernel = MRIallocSequence(targ->width, targ->height, targ->depth, MRI_FLOAT, 8);  /* :1243 */
>   if (kernel == NULL) return (NULL);
>   MRIcopyHeader(targ, kernel);                                                       /* :1245 */
>   ...
>   MRIsetVoxVal(targ, ct, rt, st, f, kvect[f]);                                       /* :1276 — writes to targ */
>   ...
>   return (0);                                                                        /* :1290 — wrong type / wrong target */
> }
> ```
>
> Three intertwined defects:
>
> 1. **`kernel` is allocated and never used.** The
>    8-frame, target-sized `MRI_FLOAT` volume is
>    written to once (`MRIcopyHeader` at `:1245`)
>    and then ignored. The actual results are
>    written to the caller's `targ` parameter at
>    `:1276`.
> 2. **`kernel` is leaked.** No `MRIfree(&kernel)`
>    on any control-flow path.
> 3. **Return type mismatch.** The function
>    signature is `MRI *`, but `return (0);`
>    returns `NULL`. The caller
>    [`mri_vol2vol/mri_vol2vol.cpp:972`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_vol2vol/mri_vol2vol.cpp#L972)
>    ignores the return value, so the contract
>    violation is silent.

## Affected Artefacts

- **Tool:** [[mri_vol2vol]] when invoked with
  `--kernel` (the only caller).
- **Pipeline stage(s):** none in default
  `recon-all`. `mri_vol2vol --kernel` is a
  diagnostic mode.
- **Triggering configuration:**
  `mri_vol2vol --kernel ...` — fires
  unconditionally inside the `--kernel`
  branch of
  [`mri_vol2vol.cpp:969-972`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_vol2vol/mri_vol2vol.cpp#L969-L972).
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION` (commit `d932c45b79`).

## Detailed Description


Caller side
([`mri_vol2vol/mri_vol2vol.cpp:969-972`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_vol2vol/mri_vol2vol.cpp#L969-L972)):

```cpp
if(DoKernel) {
  out = MRIcloneBySpace(mri_template, MRI_FLOAT, 8);
  printf("Computing Trilinear Kernel\n");
  MRIvol2VolTLKernel(in, out, vox2vox);   /* return value ignored */

```

The caller pre-allocates `out` and passes it as
`targ`, which is what the function actually
writes to. The function-local `kernel` is
leaked. For a typical resampling target volume
(say, 256×256×256 × 8 frames × 4 bytes ≈ 512 MB),
the leak is substantial — but it fires once per
`mri_vol2vol --kernel` invocation, so the
process exits soon after and the kernel is
reclaimed by the OS. Cumulative for in-process
harnesses.

## Root Cause

The function appears to have been refactored
from "allocate-and-return" semantics to
"in-place into caller's `targ`" without
removing the now-orphaned allocation. The
mismatched `return (0)` was the original
author's signal that the return is unused —
but a `MRI *` function returning `0` is a
contract violation that future static analysers
(and the type system) will flag. The leaked
`kernel` is the real cost.

## Impact

- **Memory:** ~`width × height × depth × 8 ×
  sizeof(float)` bytes leaked per call. For
  256³, that's ~512 MB; the process usually
  exits soon after, so the OS reclaims it.
- **Output correctness:** unaffected — the
  caller-provided `targ` is correctly
  populated.
- **Static analysis / contract:** `return (0)`
  for a `MRI *` function will raise warnings on
  any strict tooling.
- **Severity:** 3 — the bug fires only when the
  user opts into `--kernel`, so it sits behind
  a specific flag. Latent leak; bounded effect.

## Recommended Fix

Either delete the dead `kernel` allocation
(simplest) or wire the function to actually use
it. The simpler, behaviour-preserving fix:

```diff

   ...
@@ -1288,7 +1282,7 @@ MRI *MRIvol2VolTLKernel(MRI *src, MRI *targ, MATRIX *Vt2s)

```

If the original intent was to *return* a
freshly-allocated 8-frame kernel volume rather
than write through `targ`, the fix is the
opposite refactor (write to `kernel`, free
nothing, return `kernel`, and update the
caller to use the return value instead of
passing `out`). That's a behaviour change and
should be approved separately.

## Workarounds

None required — output is correct. To avoid
the leak, callers can spawn a child process
per invocation (the OS reclaims on exit).
