# [severity-4] [bug-00013] mris_euler_number — post-patch hole count is double (2-eno vs. 1-eno/2)

> [!bug] Synopsis
> `mris_euler_number` prints the number of topological holes in two
> places (the stdout summary and the optional `-o` output file), and
> does so twice: once on the raw input surface and once, when `-p`
> is given, after `MRISremoveTopologicalDefects`. The first pair
> uses the correct formula `1 - eno/2 = g` (genus), but the
> second pair — the post-patch pair — uses `2 - eno = 2g`, so every
> reported post-patch hole count is exactly twice the true number
> of holes. A torus (g = 1, eno = 0) reports "2 holes"; a genus-2
> surface (g = 2, eno = −2) reports "4 holes".

## Affected Artefacts

- **Tool(s):** [[mris_euler_number]]. The pre-patch printout and
  the pre-patch file output (the `else` branch at
  `mris_euler_number/mris_euler_number.cpp:102–108`) use the
  correct formula; the post-patch printout at
  `mris_euler_number/mris_euler_number.cpp:117` and the post-patch
  file output at `mris_euler_number/mris_euler_number.cpp:136`
  both use `2 - eno`.
- **Pipeline stage(s):** _N/A_ — [[recon-all]] invokes
  `mris_euler_number` at `scripts/recon-all` line 3755 **without**
  `-p` or `-o`, so the buggy branches are not reached from a
  standard recon-all run. The defect appears only for users who
  pass `-p` (to request in-memory defect patching) or who combine
  `-p` with `-o` to write a patched-hole-count file.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit
  `d932c45b79`.
- **Platforms:** all — purely arithmetic.
- **Triggering configuration:** `mris_euler_number -p surface` or
  `mris_euler_number -p -o holes.txt surface`. Any surface that
  actually had holes before the patch will report a wrong count
  afterwards.

## Detailed Description

For a closed oriented surface the Euler characteristic `eno` is
related to the genus `g` by `eno = 2 − 2g`, so the number of
topological holes is

$$
g = \frac{2 - \mathit{eno}}{2} = 1 - \frac{\mathit{eno}}{2}.
$$

The tool's first printout and first file write evaluate the
right-hand side correctly. The post-patch printout and file write
emit `2 − eno`, which equals `2g` — the number of holes multiplied
by two.

### Expected Behaviour

For any closed input surface, both the pre-patch and post-patch
"number of holes" outputs should equal the genus `g`. A sphere
should report `0`, a torus `1`, a genus-2 surface `2`, etc., both
before and after patching.

### Observed Behaviour

- Pre-patch stdout: `"%d holes"` with `1 - eno/2`. ✓
- Pre-patch file (when `-o` and no `-p`): `%5d` with `1 - eno/2`.
  ✓
- Post-patch stdout (`-p`): `"%d holes"` with `2 - eno` — **twice
  the genus**.
- Post-patch file (`-p -o`): `%5d` with `2 - eno` — **twice the
  genus**.

Worked examples:

| Surface | eno | true g | pre-patch output | post-patch output |
|---------|-----|--------|------------------|-------------------|
| Sphere  |  2  |   0    |        0         |         0         |
| Torus   |  0  |   1    |        1         |         2         |
| Genus 2 | −2  |   2    |        2         |         4         |
| Genus 3 | −4  |   3    |        3         |         6         |

For a sphere the defect is invisible because `2g == g == 0`.

The two correct pre-patch writes (`1 - eno/2`) and the two defective
post-patch writes (`2 - eno`) make the inconsistency visible at a
glance; the identical comments above each file write (`// write out
number of holes`) confirm the intended semantics.

## Root Cause

Almost certainly a hand-written expression that confused two
related identities:

- `1 - eno/2 = g` (genus; number of holes).
- `2 - eno = 2g` (twice the genus; arises in the derivation but is
  not the "number of holes").

The pre-patch branch uses the first identity; the post-patch
branch accidentally uses the second. The printf format strings in
both branches end with `--> %d holes`, reinforcing the intent that
the printed value is the genus.

## Impact

- [[recon-all]] is unaffected: its `mris_euler_number` invocation
  at `scripts/recon-all:3755` passes neither `-p` nor `-o`, so
  only the pre-patch stdout block fires and it uses the correct
  formula.
- Users who invoke `mris_euler_number -p <surface>` to patch
  topology and then read the "N holes" line from stdout see the
  wrong count (twice the true genus) and may misclassify a
  successfully patched surface as "still has holes".
- Users who invoke `mris_euler_number -p -o holes.txt <surface>`
  and consume the file programmatically — for example, a
  downstream QC script that reads the file to decide whether to
  re-run topology correction — will make wrong decisions based on
  the inflated count.

## Recommended Fix

Replace `2 - eno` with `1 - eno/2` (or equivalently `(2 - eno)/2`)
in both post-patch sites so all four emissions use a single
formula:

```diff
       eno = MRIScomputeEulerNumber(mris, &nvertices, &nfaces, &nedges) ;
       fprintf(stdout, "euler # = v-e+f = 2g-2: %d - %d + %d = %d --> %d holes\n",
-              nvertices, nedges, nfaces, eno, 2-eno) ;
+              nvertices, nedges, nfaces, eno, 1-eno/2) ;
       /* ... */
       if(outfile){
         FILE *fp;
         fp = fopen(outfile,"w");
-        fprintf(fp,"%5d\n",2-eno);
+        fprintf(fp,"%5d\n",1-eno/2);
         fclose(fp);
       }
```

For a well-formed closed surface `eno` is always even, so the
integer division `eno/2` is exact.

### Alternative Fixes Considered

Extract a `holes(eno) -> int` helper and use it in all four
emissions. This prevents the two branches from drifting apart
again; the cost is one additional small inline function at the
top of the file. The minimal two-line fix above is sufficient
without restructuring.

## Workarounds (If Any)

When invoking `mris_euler_number -p` manually, divide the reported
"N holes" count by two to recover the true genus. Consumers of
the `-o` output file should do the same.

## Confidence and Gaps

> [!gap] Integer-division corner case
> For any non-closed surface where `eno` is odd, integer division
> `eno/2` truncates toward zero. The fix's correctness depends on
> `eno` being even, which is the case for the closed surfaces
> `mris_euler_number` is designed to operate on. A patched
> surface that somehow ends up non-closed (e.g., failed patch) is
> outside the tool's contract.
