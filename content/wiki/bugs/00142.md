# [severity-3] [bug-00142] `MRImatchIntensityRatio` peak-fallback is unconditionally overwritten — `h->bins[-1]` OOB read becomes the registration intensity rescale factor

> [!bug] Synopsis
> ```cpp
> /* utils/mri.cpp:16357-16367 */
> peak = HISTOfindHighestPeakInRegion(h, 0, h->nbins);
> if (peak < 0) {
>   printf("warning: MRImatchIntensityRatio could not find any peaks\n");
>   ratio = 1.0;                         /* :16360 — intended fallback         */
> }
> ratio = h->bins[peak];                 /* :16362 — runs unconditionally;     *
>                                         *          if peak == -1, this reads *
>                                         *          h->bins[-1] (OOB).        */
> printf("peak ratio at %2.3f\n", ratio);
> if (FZERO(ratio)) {
>   printf("warning: MRImatchIntensityRatio peak at 0 - disabling\n");
>   ratio = 1.0;
> }
> mri_matched = MRIscalarMul(mri_source, mri_matched, ratio);
> ```
>
> `HISTOfindHighestPeakInRegion` ([`utils/histo.cpp:891-916`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/histo.cpp#L891-L916)) returns `max_count_bin = -1` when every histogram bin has zero count — the documented "no peaks" condition. The if-block sets the intended fallback `ratio = 1.0`. The very next line then unconditionally reads `h->bins[peak]` and assigns it to `ratio`, blowing away the fallback. With `peak == -1`, `h->bins[-1]` is a read one slot before the bin array's first valid element — undefined behaviour. On glibc with default malloc this returns whatever happens to lie in the preceding heap chunk metadata or adjacent allocation; on hardened allocators (AddressSanitizer, scudo) it traps. The garbage value then propagates through `MRIscalarMul(mri_source, mri_matched, ratio)`, silently re-scaling the source volume by an arbitrary multiplier before the high-resolution registration consumes it.
>
> The secondary `FZERO(ratio)` guard at [`:16364`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L16364) only protects the case where the garbage happens to be exactly 0.0; any other value (even tiny `1e-30`, even `NaN`, even gigantic `1e+38`) passes the guard and is used as the multiplier.

The bug fires whenever the histogram has zero counts after the inner filter — i.e., when no voxel pair `(x,y,z)` simultaneously satisfies `val_source ∈ (100, 125]`, `val_target ∈ (100, 125]`, and `val_target / val_source ∈ [0.8, 1.2]` (the histogram filter at [`utils/mri.cpp:16342-16347`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L16342-L16347)).

## Detailed Description

`MRImatchIntensityRatio` is a histogram-mode-based intensity normaliser used as a pre-registration step in `mri_hires_register`. Per the function's design (and the call site's hardcoded thresholds), the typical input is a T1-weighted volume in which white-matter intensity falls in roughly `[100, 125]`; the function estimates the modal `target / source` intensity ratio across WM voxels and rescales the source so that its WM peak matches the target's. The intended fallback when no voxels match is "no rescaling": `ratio = 1.0`.

### Expected Behaviour

```cpp
peak = HISTOfindHighestPeakInRegion(h, 0, h->nbins);
if (peak < 0) {
  printf("warning: MRImatchIntensityRatio could not find any peaks\n");
  ratio = 1.0;
} else {
  ratio = h->bins[peak];
}
```

When `peak == -1`, leave `ratio` at the fallback value of 1.0; `MRIscalarMul(mri_source, mri_matched, 1.0)` is a no-op pass-through copy. Subsequent registration runs against the unmodified source.

### Observed Behaviour

The `else` is missing, so the assignment `ratio = h->bins[peak]` runs unconditionally — even when `peak == -1`. The C standard makes `h->bins[-1]` undefined behaviour (pointer arithmetic outside the bounds of the malloc'd `bins` array). Practically:

- glibc default allocator: returns whatever 4-byte float bit-pattern happens to lie in the previous heap chunk (likely the heap-chunk header's `prev_size` or `size` field, interpreted as `float`).
- jemalloc: similar — some adjacent allocation's bytes interpreted as `float`.
- Scudo / hardened allocators: may trap or return poisoned memory.
- AddressSanitizer: traps with `heap-buffer-overflow READ of size 4`.

Then `MRIscalarMul(mri_source, mri_matched, ratio)` rescales the entire source volume by that bit-pattern interpreted as `float`. Even if it happens to be a sane-looking value, the registration consumes a silently-corrupted moveable volume.

### Reproducer

```bash
# Synth a source/target pair where the WM range condition fails for every
# voxel: scale the source up by 10x so that source intensities > 125 mm
# (out of the hardcoded high_thresh).

# (i) Make two volumes from the same T1 with source rescaled by 10.
mri_convert orig.mgz src.mgz
mri_convert orig.mgz tgt.mgz
mri_concat src.mgz --mul 10 --o src_x10.mgz

# (ii) Run mri_hires_register with -match_peak. The hardcoded thresholds
# [100, 125] now exclude every voxel of src_x10 (all > 1000 in WM).
mri_hires_register \
    -match_peak \
    src_x10.mgz tgt.mgz out_xform.m3z

# Output: "warning: MRImatchIntensityRatio could not find any peaks"
# Then immediately: "peak ratio at <garbage value>"
# The registration proceeds with garbage-scaled source.
```

> The static read of the if/else is unambiguous (`peak = ...; if (peak < 0) { ratio = 1.0; } ratio = h->bins[peak];` — no `else`). I have not run `mri_hires_register` end-to-end with the synthetic over-scaled input above; the registration is computationally heavy and the bug's behaviour past the OOB read depends on the runtime allocator. ## Root Cause

A missing `else` (or missing early `return mri_matched`). The author wrote a fallback assignment inside the `if (peak < 0)` block but did not chain the subsequent assignment, so the fallback is immediately overwritten. The pattern is structurally analogous to the C anti-pattern `if (err) handle(); use_the_thing_anyway();`, where the error-handling branch sets a state that the following unconditional line then trashes.

## Impact

- **Silent registration corruption.** When triggered, `MRIscalarMul(mri_source, mri_matched, ratio)` rescales the entire moveable volume by a garbage multiplier. `mri_hires_register` then runs its non-linear morph against a wrongly-scaled source — the intensity-likelihood and likelihood-ratio terms of the optimisation are computed against a source that has been multiplied by junk. The resulting `.m3z` warp is silently wrong.
- **Undefined behaviour.** `h->bins[-1]` is OOB; on ASAN builds, the tool aborts (heap-buffer-overflow). On production glibc, the read silently returns adjacent heap memory.
- **`recon-all` impact: none on the default path.** `mri_hires_register` is not invoked by default `recon-all` / `recon-all -long` / `recon-all -base`. It is a standalone tool used for high-resolution non-linear registration (e.g., hippocampal subfield templates) and is invoked manually by hippo-subfield and exvivo workflows.
- **Reachability narrows the impact.** The user must (a) pass `-match_peak`, (b) provide source/target where no voxel pair satisfies the hardcoded `[100, 125]` and ratio `[0.8, 1.2]` filter. Re-scaled inputs (after `-scale_values N`), non-T1 modalities, or wildly intensity-mismatched pairs trigger it.
- **The first warning printf (`"could not find any peaks"`) is at least diagnostic** — the user sees that *something* is off, even if the subsequent `"peak ratio at <garbage>"` line prints a plausible-looking number.

## Recommended Fix

Add an `else` (or restructure as early return).

```diff
   peak = HISTOfindHighestPeakInRegion(h, 0, h->nbins);
-  if (peak < 0) {
-    printf("warning: MRImatchIntensityRatio could not find any peaks\n");
-    ratio = 1.0;
-  }
-  ratio = h->bins[peak];
+  if (peak < 0) {
+    printf("warning: MRImatchIntensityRatio could not find any peaks\n");
+    ratio = 1.0;
+  } else {
+    ratio = h->bins[peak];
+  }
   printf("peak ratio at %2.3f\n", ratio);
```

### Alternative Fixes Considered

- **Early return.** `if (peak < 0) { printf(...); HISTOfree(&h); return MRIscalarMul(mri_source, mri_matched, 1.0); }` — cleaner control flow but introduces a second exit point.
- **Defensive bounds check.** `ratio = (peak >= 0 && peak < h->nbins) ? h->bins[peak] : 1.0;` — works but the `if (peak < 0) ratio = 1.0;` block above it becomes dead code.

The minimal `else` patch matches the existing style of sister functions in `utils/histo.cpp`.

## Workarounds (If Any)

- **Don't pass `-match_peak`.** The default `match_mean_intensity = 1` path (lines [`:884-891`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_hires_register/mri_nl_align.cpp#L884-L891)) uses `MRImatchMeanIntensity` instead, which does not have this defect.
- **Pre-rescale source/target so WM intensity falls in `[100, 125]`.** Then the histogram is populated and `peak >= 0`. `mri_normalize` on both inputs produces FreeSurfer-conformed T1 intensity (WM ≈ 110), which fits.
- **Don't ignore the `warning: MRImatchIntensityRatio could not find any peaks` printf** — if you see it, the next line's `peak ratio at <…>` is garbage, regardless of how plausible the number looks.

## Confidence and Gaps

> [!gap] Real-world reach of `-match_peak`
> The bug only fires when `-match_peak` is passed. I have not surveyed how often that flag is used in published `mri_hires_register` pipelines; it is not in any `recon-all` default. The hippocampal subfield templates' registration scripts may or may not pass it.

> [!gap] Garbage-value distribution
> The OOB read at `h->bins[-1]` returns adjacent heap memory. On glibc with default malloc, the value is the previous chunk's `size` field interpreted as `float` — usually a moderately small positive integer reinterpreted as a denormal or small-magnitude float. `FZERO(ratio)` (the secondary guard) catches values within `1e-6` of zero, which lets through nearly all garbage. A statistical characterisation of the garbage distribution under typical allocator state is out of scope.
