# [severity-3] [bug-00127] `MRIvol2VolR` leaks one (3-frame) or two (9-frame) MATRIX allocations per voxel, scaling to GB-level on a typical DTI volume

> [!bug] Synopsis
> ```cpp
> /* utils/mri2.cpp:1053-1180 */
> int MRIvol2VolR(MRI *src, MRI *targ, MATRIX *Vt2s, int InterpCode, float param, MATRIX *RRot)
> {
>   ...
>   /* :1066-1071 — init: 6 matrices alloced, one immediately leaked */
>   RRotT     = MatrixIdentity(3, NULL);  /* :1066 */
>   Tensor    = MatrixIdentity(3, NULL);
>   RotTensor = MatrixIdentity(3, NULL);
>   RRotT     = MatrixTranspose(RRot, NULL);  /* :1069 — leaks :1066 RRotT */
>   Vector    = VectorAlloc(3, MATRIX_REAL);
>   RotVector = VectorAlloc(3, MATRIX_REAL);  /* never used directly */
>   ...
>   for (ct = 0; ct < targ->width; ct++) {
>     for (rt = 0; rt < targ->height; rt++) {
>       for (st = 0; st < targ->depth; st++) {
>         ...
>         if (nframes == 3) {
>           ...
>           RotVector = MatrixMultiply(RRot, Vector, NULL);  /* :1145 — leak per voxel */
>           for (col = 1; col <= 3; col++) MRIsetVoxVal(...);
>         }
>         else {  /* nframes == 9 */
>           ...
>           RotTensor = MatrixMultiply(RRot,
>                                      MatrixMultiply(Tensor, RRotT, NULL),  /* leak per voxel */
>                                      NULL);                                 /* :1158 — leak per voxel */
>           for (row, col) MRIsetVoxVal(...);
>         }
>       }
>     }
>   }
>
>   free(valvect);
>   if (FreeMats) {
>     MatrixFree(&V2Rsrc);
>     MatrixFree(&invV2Rsrc);
>     MatrixFree(&V2Rtarg);
>     MatrixFree(&Vt2s);
>   }
>   /* RRotT, Tensor, RotTensor, Vector, RotVector never freed */
>   return (0);
> }
> ```
>
> Each inner-loop iteration
> (one per voxel of the target
> volume) calls
> `MatrixMultiply(..., NULL)`
> which `MatrixAlloc`s a new
> MATRIX and returns it. The
> result is assigned to the
> same local that held the
> previous iteration's
> matrix — overwriting the
> pointer without `MatrixFree`.
>
> | branch        | leaks per voxel |
> |---------------|-----------------|
> | nframes == 3  | 1 vector (3×1) from line 1145 |
> | nframes == 9  | 1 intermediate (3×3) from inner `MatrixMultiply(Tensor, RRotT, NULL)` at `:1158` + 1 matrix (3×3) from outer assignment to `RotTensor` |
>
> Plus the init-time leak of
> the `:1066` `RRotT` identity,
> and the never-freed
> `Tensor`, `RotTensor`,
> `Vector`, `RotVector`,
> and final `RRotT` on
> function return.

## Affected Artefacts

- **Tool:** [[freeview]] — DTI
  tensor visualisation.
- **Caller:**
  [`freeview/FSVolume.cpp:1895`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/freeview/FSVolume.cpp#L1895),
  inside `FSVolume::ResampleCropToTarget`,
  invoked when a DTI tensor
  volume (`nframes ∈ {3, 9}`)
  is resampled with a
  registration matrix that
  contains a non-trivial
  rotation. The rotation
  needs to be applied to
  the tensor data itself
  (not just resampled), so
  the per-voxel matrix-
  multiply path is used.
- **Pipeline stage(s):**
  none in default
  `recon-all`. Triggers
  when a user loads a DTI
  tensor volume and a
  registration is applied
  in FreeView.
- **Triggering configuration:**
  Loading a DTI tensor
  volume (`*.mgz` or
  `*.nii.gz` with 3 or 9
  frames representing
  eigenvectors / full
  tensor) into FreeView
  with an associated
  registration. Each
  resample call leaks
  memory proportional to
  the volume size.
- **FreeSurfer version(s):**
  confirmed in `$FREESURFER_VERSION`
  (commit `d932c45b79`).

## Detailed Description

### Init-time leak

```cpp
/* :1066-1071 */
RRotT     = MatrixIdentity(3, NULL);   /* alloc #1 */
Tensor    = MatrixIdentity(3, NULL);   /* alloc #2 */
RotTensor = MatrixIdentity(3, NULL);   /* alloc #3 */
RRotT     = MatrixTranspose(RRot, NULL); /* alloc #4 — leaks #1 */
Vector    = VectorAlloc(3, MATRIX_REAL); /* alloc #5 */
RotVector = VectorAlloc(3, MATRIX_REAL); /* alloc #6 */
```

The identity matrix
allocated at `:1066`
is immediately discarded
at `:1069` when `RRotT`
is reassigned. Alloc #1
is leaked even before the
voxel loop starts.

### Per-voxel leaks

For each output voxel
`(ct, rt, st)`:

**nframes == 3** (eigenvector
volume):
```cpp
/* :1145 */
RotVector = MatrixMultiply(RRot, Vector, NULL);
```
- `RRot` is 3×3,
  `Vector` is 3×1.
- `MatrixMultiply(..., NULL)`
  allocates a new 3×1
  matrix.
- The previous
  `RotVector` (initialised
  at `:1071`, or the result
  from the previous
  iteration) is overwritten
  without `MatrixFree`.
- **1 vector leaked per
  voxel.**

**nframes == 9** (full
tensor volume):
```cpp
/* :1158 */
RotTensor = MatrixMultiply(RRot,
                           MatrixMultiply(Tensor, RRotT, NULL),
                           NULL);
```
- Inner
  `MatrixMultiply(Tensor,
  RRotT, NULL)` allocates
  a new 3×3 intermediate.
  The pointer to this
  intermediate is only
  used as a function
  argument; nothing holds
  a handle to it after
  the outer call returns,
  so it is **lost**.
- Outer
  `MatrixMultiply(RRot,
  …, NULL)` allocates a
  new 3×3 result and
  overwrites `RotTensor`.
  Previous `RotTensor`
  is leaked.
- **2 matrices leaked
  per voxel.**

### Quantitative impact

For a 256³ target volume
(typical conformed FS
volume):

| nframes | leaked allocations | bytes per matrix | total leak |
|---------|--------------------|------------------|------------|
| 3       | ~16.7 M vectors    | ~80 (struct + 3×4 data + rptr) | **~1.3 GB** |
| 9       | ~33 M matrices     | ~120 (struct + 9×4 data + rptr) | **~3.9 GB** |

(Actual sizeof depends on
`MATRIX` struct definition
+ `data` allocation +
`rptr` array; the totals
above are conservative.)

For a 128³ DTI volume
(more typical of clinical
diffusion):
- 3-frame:
  ~2.1 M leaks → ~170 MB.
- 9-frame:
  ~4.2 M leaks → ~500 MB.

Each invocation of
`MRIvol2VolR` (i.e., each
time a user adjusts the
registration / camera /
slice in FreeView while
displaying a DTI tensor
volume) leaks this much
memory.

### End-of-function
post-loop leaks

At `:1171-1177`, only
`valvect`, `V2Rsrc`,
`invV2Rsrc`, `V2Rtarg`,
and (if `FreeMats`)
`Vt2s` are freed. The
function exits with the
following local matrices
still allocated and
unreferenced:
- `RRotT` (final value
  from `:1069`)
- `Tensor`
- `RotTensor` (final
  voxel's allocation)
- `Vector`
- `RotVector` (final
  voxel's allocation)

These 5 small matrices
are leaked per call in
addition to the
per-voxel leaks.

### Why this is severity 3

- **Reachable**: triggered
  by routine DTI tensor
  loading + rotation in
  FreeView, a documented
  workflow.
- **Silent**: no warning,
  no crash on a single
  invocation. Memory
  pressure grows
  invisibly over a
  visualisation session.
- **GB-scale leak**:
  every interactive
  reorientation /
  registration update
  during DTI viewing
  leaks hundreds of MB
  to several GB.
- **Crash risk**: long
  FreeView sessions
  with DTI data can
  exhaust system memory
  → OS-level OOM kill
  or swap thrashing.
- **Bounded scope**:
  affects only DTI-tensor
  workflows; the
  non-rotation path
  (`MRIvol2Vol` at
  `:877-1052`) is not
  affected.
- **Not severity 4**
  because it doesn't
  silently produce
  WRONG voxel values
  (only leaks).

## Root Cause

`MatrixMultiply(M1, M2,
M3)` returns `M3` if
non-NULL (reused buffer)
or allocates a new
matrix if `M3 == NULL`.
The function passes
`NULL` for the destination
in the per-voxel hot
loop instead of reusing
a pre-allocated buffer.

The init at `:1066-1071`
preallocates buffers
(`RRotT`, `RotTensor`,
`RotVector`) presumably
to reuse — but the
inner loop ignores them
and allocates fresh
each iteration.

## Impact

- **FreeView with DTI
  tensor data**:
  GB-scale leak per
  resample call. Long
  visualisation
  sessions consume
  increasing memory
  until OS OOM kill or
  swap thrash.
- **Production
  `recon-all`**:
  unaffected (function
  not called).
- **Severity:** 3 —
  reproducible,
  user-visible
  performance
  degradation, can lead
  to crashes; but the
  computed voxel values
  themselves are
  correct (the
  rotation math is OK).

## Workarounds

For FreeView users
working with DTI tensor
data: avoid prolonged
visualisation sessions
on a single tensor
volume. Quit and restart
FreeView periodically
to reclaim leaked
memory. Or work with
3-frame eigenvector
data when possible
