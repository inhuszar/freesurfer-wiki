# [severity-3] [bug-00161] histo_register_block — MRIreplaceValues writes into wrong destination, overwriting the histology image with the block image

> [!bug] Synopsis
> Before registration, `histo_register_block` reserves intensity 0 for
> background in both inputs. The first call,
> `MRIreplaceValues(mri_histo, mri_histo, 0, 1)`, correctly remaps the
> histology image in place. The second call is written
> `MRIreplaceValues(mri_block, mri_histo, 0, 1)` — `mri_block` as source,
> `mri_histo` as **destination** — instead of `(mri_block, mri_block, …)`.
> Since `MRIreplaceValues(src, dst, …)` writes every voxel of `src` into
> `dst`, this overwrites the entire histology image with the block-face
> image (with 0→1 applied). If the two volumes differ in size (the common
> case — they are read from separate files and only resampled to a common
> grid *after* this call), the inner `MRIcheckVolDims` instead `ErrorExit`s
> and the program aborts. Either way the intended per-image background
> reservation of the block volume never happens and the histology data is
> lost or the run crashes.

## Affected Artefacts

- **Tool(s):** [[histo_register_block]]. The clobbered `mri_histo` is then
  resampled and passed to `align_block_to_histo`, so the alignment is
  computed block-against-block rather than block-against-histology.
- **Pipeline stage(s):** _N/A_ — standalone 2-D histology / block-face
  registration tool; not part of [[wiki/pipelines/recon-all|recon-all]].
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`;
  earliest known: _unknown_.
- **Platforms:** all — wrong destination argument; behaviour depends only
  on whether the two input volumes share dimensions.
- **Triggering configuration:** every default run
  (`histo_register_block block.mgz histo.mgz density out.xfm`). The
  background-reservation block is enabled unconditionally (`#if 1`), so the
  defect fires on the tool's default path; the user-visible manifestation
  depends on whether `block.mgz` and `histo.mgz` have equal dimensions.

## Detailed Description

`main()` reads the block-face image into `mri_block` (argv[1]) and the
histology image into `mri_histo` (argv[2]) from independent files, with no
resampling to a shared grid yet. After computing a segmentation mask it
runs an unconditional (`#if 1`) block that is meant to reserve value 0 as
background in **each** image before they are embedded into a common
template:

```c
MRIreplaceValues(mri_histo, mri_histo, 0, 1) ;  /* reserve 0 for background */
MRIreplaceValues(mri_block, mri_histo, 0, 1) ;  /* reserve 0 for background */
```

`MRIreplaceValues` has the signature
`MRI *MRIreplaceValues(MRI *mri_src, MRI *mri_dst, float in_val, float out_val)`
(`utils/mriset.cpp`). It iterates over **every** voxel of `mri_src`,
replaces `in_val` with `out_val`, and stores the result into the
corresponding voxel of `mri_dst` — it is a full copy of `src` into `dst`,
not a selective edit. The first line is the correct in-place form
(`src == dst == mri_histo`). The second line should likewise be in-place on
the block image, i.e. `MRIreplaceValues(mri_block, mri_block, 0, 1)`, but
instead names `mri_histo` as the destination.

There are two outcomes, depending on the input geometry:

1. **Different dimensions (typical).** Block-face photographs and
   histology slices are generally not the same pixel size; the code itself
   anticipates this by computing `max_width`/`max_height` and resampling
   both into a shared `mri_template` — but that resampling happens at lines
   *after* the buggy call. So at this point `mri_block` and `mri_histo`
   usually differ in width/height. `MRIreplaceValues` first calls
   `MRIcheckVolDims(mri_src, mri_dst)`, which `ErrorExit`s with
   `volume1 width=… != volume2 width=…` (or the height/depth analogue),
   aborting the program with a confusing error on what should be a valid
   run.

2. **Identical dimensions.** If the two inputs happen to share dimensions,
   the call succeeds and silently overwrites `mri_histo` with
   `mri_block`'s pixel data (0→1 applied). From here on, the variable named
   `mri_histo` actually holds the block image. It is resampled into the
   template and handed to `align_block_to_histo(mri_histo, mri_block, …)`,
   so the registration aligns the block image to a copy of itself — the
   optimiser sees two identical images and the resulting transform/aligned
   output is meaningless, with no error emitted.

### Expected Behaviour

Each input image should have its own zeros remapped to 1 in place,
independently: `MRIreplaceValues(mri_histo, mri_histo, 0, 1)` for the
histology and `MRIreplaceValues(mri_block, mri_block, 0, 1)` for the block.
After this, `mri_histo` still holds the histology image and `mri_block`
still holds the block image, both with background reserved, ready to be
embedded into the shared template and registered.

### Observed Behaviour

- Typical (differing sizes): the program aborts at the second
  `MRIreplaceValues` with an `MRIcheckVolDims` "width/height mismatch"
  `ErrorExit`.
- Equal sizes: `mri_histo` is silently replaced by `mri_block`; the
  subsequent alignment is block-vs-block and the written `.xfm` / aligned
  `.mgz` are invalid, with no warning.

### Reproducer

> [!gap] Reproducer not executed end-to-end
> A full run needs a block image, a histology image, and the matching
> `*_level0.den` density file (from [[histo_compute_joint_density]]). The
> defect is established by the function's documented semantics
> (`MRIreplaceValues(src, dst, …)` copies `src` into `dst`) plus the
> `MRIcheckVolDims` `ErrorExit` it performs first:
>
> - **Crash path:** supply `block.mgz` and `histo.mgz` of different pixel
>   dimensions; the run aborts at the second `MRIreplaceValues` with a
>   `volume1 … != volume2 …` error.
> - **Silent-clobber path:** supply two equal-dimension inputs and observe
>   (e.g. by dumping `mri_histo` after line 212, or noting a near-zero cost
>   from `align_block_to_histo` on identical images) that the histology
>   buffer now equals the block image.

## Root Cause

A copy-paste of the first (histology) line with only the source argument
updated to `mri_block`; the destination argument was left as `mri_histo`.
The two lines carry the identical comment "reserve 0 for background",
confirming the intent was the same in-place operation applied to each
image separately. Because `MRIreplaceValues` writes the whole source into
the destination, the mismatched destination either trips the
`MRIcheckVolDims` size guard (abort) or overwrites the histology buffer
(silent corruption).

## Impact

- On the **default invocation path** (`#if 1`, no flag required) the tool
  either aborts with a misleading dimension-mismatch error (typical,
  differently-sized inputs) or silently produces a meaningless
  block-against-block registration (equal-sized inputs). Both are serious
  for a tool whose sole job is block-to-histology alignment.
- Severity is held at **3 (medium)** rather than 4 because
  `histo_register_block` is a niche, non-pipeline histology tool that
  additionally **requires a precomputed `*_level0.den` density file to run
  at all**; it is not a routinely-run standalone utility, and it has no
  reach into [[wiki/pipelines/recon-all|recon-all]]. The crash variant is
  also self-announcing. Were this on a commonly-run standalone tool's
  default path it would rate 4.

## Recommended Fix

Make the block image's background reservation in-place, mirroring the
histology line:

```diff
   MRIreplaceValues(mri_histo, mri_histo, 0, 1) ;  /* reserve 0 for background */
-  MRIreplaceValues(mri_block, mri_histo, 0, 1) ;  /* reserve 0 for background */
+  MRIreplaceValues(mri_block, mri_block, 0, 1) ;  /* reserve 0 for background */
```

After the change each image keeps its own data with zeros remapped to 1,
and both are then embedded into the shared template as intended.

### Alternative Fixes Considered

None — the destination argument is unambiguously wrong; the one-token
correction restores the intended per-image operation.

## Workarounds (If Any)

No command-line workaround exists: the call is unconditional. A user can
only avoid the crash variant by pre-resampling both inputs to identical
dimensions, but that merely converts the abort into the silent
block-vs-block corruption — so there is no safe workaround. The source
fix is required.

## Confidence and Gaps

> [!gap] Manifestation depends on input geometry — confirmed wrong either way
> The audit did not run the tool end-to-end (it needs a `.den` density
> file and matched histology/block inputs). However, the defect is not
> merely suspected: `MRIreplaceValues(src, dst, …)` provably writes all of
> `src` into `dst`, so naming `mri_histo` as the destination of a
> `mri_block` source is wrong by the function's own contract. The only
> open question is *which* failure a given user hits — the
> `MRIcheckVolDims` abort (unequal dimensions) or the silent histology
> clobber (equal dimensions) — not whether the line is defective.
