# [severity-2] [bug-00040] MRItranslate (and MRIrotate) write output via UCHAR pointer regardless of voxel type — silent corruption for non-UCHAR inputs

> [!bug] Synopsis
> `MRItranslate` reads input voxels through the type-aware
> `MRIsampleVolume` (correct for any of MRI_UCHAR / FLOAT /
> SHORT / USHRT / INT / LONG) but writes the output through
> a `BUFTYPE *` (=`unsigned char *`) raw pointer obtained
> from `MRIvox(mri_dst, 0, y2, y3)` — *one byte per voxel*,
> regardless of `mri_dst->type`. The destination is allocated
> via `MRIclone(mri_src, NULL)` which preserves the source
> type, so when the input is non-UCHAR (e.g. MRI_FLOAT, the
> common case for unconformed T1 volumes), the loop writes a
> single byte at strides of one byte into a buffer that holds
> 4-byte floats. The output is junk: the first ~`width` bytes
> of each row are clipped-to-uchar values of the first
> `width/sizeof(T)` source voxels, and the remaining bytes of
> the row are left at the `MRIclear`-zeroed initial state.
> The downstream consumer reads it back through
> `MRIFvox`/`MRISvox` and sees mostly zeros (with garbage
> dotted in the low-byte positions of the first few voxels of
> each row). Sister function `MRIrotate` has the identical
> defect at `utils/mri.cpp:6648` (`mri_dst->slices[y3][y2][y1]
> = mri_src->slices[x3][x2][x1]`, which is byte-only). Fires
> in [[mri_average]], [[mri_em_register]], [[mri_deface]],
> [[mri_linear_register]] when the user passes the `-d` or
> `-r` flags with a non-UCHAR input volume and the
> conform-to-UCHAR step has been disabled (or the tool does
> not conform).

## Detailed Description

### Expected Behaviour

`MRItranslate(mri_src, mri_dst, dx, dy, dz)` is documented
("Translate the MRI image mri_src by the vector dx, dy, dz
and store the result in mri_dst") with no type restriction.
Sister geometric transforms in the same file —
`MRIscale` ([`utils/mri.cpp:6566`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L6566))
and `MRIlinearTransform` — handle every supported type
correctly via `MRIgetVoxVal` / `MRIsetVoxVal`. The natural
expectation is that `MRItranslate` should produce a
correctly-translated copy of the input, regardless of voxel
type.

### Observed Behaviour

The translation loop
([`utils/mri.cpp:6313-6348`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L6313-L6348)):

```cpp
MRI *MRItranslate(MRI *mri_src, MRI *mri_dst, double dx, double dy, double dz)
{
  int y1, y2, y3, width, height, depth;
  BUFTYPE *pdst;                                        /* uchar pointer */
  double x1, x2, x3, val;

  width  = mri_src->width;
  height = mri_src->height;
  depth  = mri_src->depth;
  if (!mri_dst) mri_dst = MRIclone(mri_src, NULL);      /* dst type = src type */
  else          MRIclear(mri_dst);                      /* zero the buffer */

  for (y3 = 0; y3 < depth; y3++) {
    x3 = (double)y3 - dz;
    if (x3 < 0 || x3 >= depth) continue;
    for (y2 = 0; y2 < height; y2++) {
      x2 = (double)y2 - dy;
      if (x2 < 0 || x2 >= height) continue;

      pdst = &MRIvox(mri_dst, 0, y2, y3);               /* (a) UCHAR-only address */
      for (y1 = 0; y1 < width; y1++, pdst++) {           /* (b) +1 byte per voxel */
        x1 = (double)y1 - dx;
        if (x1 >= 0 && x1 < width) {
          MRIsampleVolume(mri_src, x1, x2, x3, &val);    /* type-aware read */
          *pdst = (BUFTYPE)nint(val);                    /* (c) 1-byte write */
        }
      }
    }
  }
  /* … */
}
```

`MRIvox` is `(((BUFTYPE *)mri->slices[z][y])[x])`
([`include/mri.h:1480`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/include/mri.h#L1480));
it returns a `uchar` reference. For an MRI_FLOAT
`mri_dst`, the underlying row is `4 * width` bytes of float
storage, but step (b) advances `pdst` by 1 byte and step (c)
writes 1 byte — so after the inner loop, only the first
`width` bytes of the `4 * width`-byte row are touched. The
first `width / sizeof(float) = width/4` floats receive a
trashed value (one byte modified, three bytes left at the
`MRIclear`-zeroed `0x00`); floats from index `width/4`
onward are unchanged at zero. The
downstream consumer reading `MRIFvox(mri_dst, x, y, z)`
sees a strange spectrum of values close to zero from the
first quarter of each row, and pure zero from the rest.

`MRIrotate`
([`:6601-6661`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L6601-L6661))
has the identical defect at the inner copy:

```cpp
mri_dst->slices[y3][y2][y1] = mri_src->slices[x3][x2][x1];   /* :6648 — uchar-only */
```

`slices` is declared as `BUFTYPE ***`
([`include/mri.h:828`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/include/mri.h#L828)),
so this single-byte assignment loses the high bytes of any
non-UCHAR voxel.

The macro that makes the bug latent is
[`MRIvox`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/include/mri.h#L1480):

```cpp
#define MRIFvox(mri,x,y,z)  (((float *)(mri->slices[z][y]))[x])     /* type-aware float */
#define MRIvox(mri,x,y,z)   (((BUFTYPE *)mri->slices[z][y])[x])     /* uchar-only */
```

The same code paths in the type-correct sister `MRIscale`
([`:6566-6592`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L6566-L6592))
delegate to `MRIlinearTransform`, which uses `MRIgetVoxVal`
/ `MRIsetVoxVal` and is correct for every supported type.

## Root Cause

Both functions predate the introduction of multi-type MRI
volumes in FreeSurfer. The original implementation handled
only UCHAR via the legacy `MRIvox`/`slices[z][y][x]`
buffer-byte access patterns. When the codebase added
MRI_FLOAT, MRI_SHORT, MRI_INT, MRI_USHRT, MRI_LONG types, the
sister geometric transforms (`MRIscale`, `MRIlinearTransform`,
`MRIsampleVolume`) were rewritten in terms of
`MRIgetVoxVal`/`MRIsetVoxVal`, but `MRItranslate` and
`MRIrotate` were missed.

## Impact

- **`mri_em_register -d`, `mri_linear_register -d`,
  `mri_deface -d`, `mri_average -d`** with non-UCHAR inputs:
  the translated volume is replaced with a near-zero buffer
  containing only low-byte fragments of the first
  `width/sizeof(voxel-type)` voxels of each row. The
  registration/averaging proceeds with the corrupted volume
  silently — no warning is printed.
- **`mri_em_register -r`, `mri_linear_register -r`,
  `mri_deface -r`, `mri_average -r`** with non-UCHAR inputs:
  same defect via `MRIrotate`.
- **Latent for default [[wiki/pipelines/recon-all|recon-all]]**: the standard call
  to `mri_em_register` operates on `nu.mgz`, which is
  `mri_make_uchar`-converted to UCHAR before
  `mri_em_register` runs. The `-d`/`-r` flags are not used
  by default. So the standard pipeline is unaffected.
- **Active in user workflows that:** (a) feed a
  unconformed/un-converted FLOAT or SHORT volume to one of
  the four tools and (b) pass `-d` or `-r` (e.g.
  pre-aligning multi-acquisition T1s prior to averaging).

## Recommended Fix

Replace the legacy buffer access in both functions with
`MRIgetVoxVal` / `MRIsetVoxVal` (or equivalently, delegate to
`MRIlinearTransform` as `MRIscale` does).

```diff
   for (y3 = 0; y3 < depth; y3++) {
     x3 = (double)y3 - dz;
     if (x3 < 0 || x3 >= depth) continue;
     for (y2 = 0; y2 < height; y2++) {
       x2 = (double)y2 - dy;
       if (x2 < 0 || x2 >= height) continue;
-      pdst = &MRIvox(mri_dst, 0, y2, y3);
-      for (y1 = 0; y1 < width; y1++, pdst++) {
+      for (y1 = 0; y1 < width; y1++) {
         x1 = (double)y1 - dx;
         if (x1 >= 0 && x1 < width) {
           MRIsampleVolume(mri_src, x1, x2, x3, &val);
-          *pdst = (BUFTYPE)nint(val);
+          MRIsetVoxVal(mri_dst, y1, y2, y3, 0, val);
         }
       }
     }
   }
```

Same for `MRIrotate` line 6648:

```diff
-          mri_dst->slices[y3][y2][y1] = mri_src->slices[x3][x2][x1];
+          MRIsetVoxVal(mri_dst, y1, y2, y3, 0,
+                       MRIgetVoxVal(mri_src, x1, x2, x3, 0));
```

Both fixes preserve the existing nearest-neighbour behaviour
for `MRIrotate`; for `MRItranslate`, the source is already
sampled with `MRIsampleVolume` (trilinear), so the fix
simply finishes the type-aware pipeline.

### Alternative Fixes Considered

- **Type-check at function entry and `ErrorReturn` for
  non-UCHAR.** Less surprising than silent corruption, but a
  regression for any user who relied on the (broken) MRI_UCHAR
  case continuing to work. Not preferred.
- **Delegate to `MRIlinearTransform` (as `MRIscale` does).**
  `MRItranslate` already has all the information to build a
  4×4 translation matrix; this would also bring trilinear
  interpolation under user control. A larger but cleaner
  refactor.
- **Multi-frame support.** The current loop only translates
  frame 0 (the `MRIsampleVolume` at line 6339 doesn't iterate
  frames). Worth noting in any future rewrite, but not part
  of the minimum fix.

## Workarounds (If Any)

- Ensure the input is MRI_UCHAR before calling these tools.
  In `mri_average`, this means *not* passing `--noconform`
  (the default `MRIconform` path produces UCHAR output).
- For tools that don't conform, pre-convert with
  `mri_convert -odt uchar input.mgz input_uchar.mgz` (and
  scale into the 0-255 range first to avoid clipping).
- Apply the translation/rotation outside FreeSurfer using
  another tool (e.g. ITK / niimath) and feed the
  pre-translated volume in.

## Confidence and Gaps

> [!gap] Magnitude of the defect for FLOAT vs SHORT vs INT
> The fraction of the row that is corrupted depends on the
> sizeof(voxel-type): 1/4 for FLOAT/INT, 1/2 for SHORT/USHRT,
> 1/8 for LONG. The remaining fraction stays at zero from the
> `MRIclear` initialisation. The exact bit pattern of the
> corrupted voxels also depends on endianness — on
> little-endian (Linux/x86_64), the modified byte is the
> lowest-significance byte of the float, so the float values
> are in roughly the [0, 5e-43] range (zero plus subnormal
> noise). On big-endian, the modified byte is the highest
> byte of the float exponent — values can be very large or
> NaN. Either way the output is unusable.

> [!gap] Whether `MRIrotateZ_I` / `MRIrotateY` / `MRIrotateX`
> share the bug
> All three call `MRIrotate` (the buggy core function), so
> the bug propagates. `MRIscale` calls `MRIlinearTransform`
> instead and is unaffected.
