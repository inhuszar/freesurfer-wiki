# [severity-2] [bug-00107] `MRI::toITKImage` / `loadITKImage` drop origin and direction cosines

> [!bug] Synopsis
> `MRI::toITKImage`
> ([`utils/mri.cpp:17783-17823`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L17783-L17823))
> converts an MRI volume to an ITK image for
> use with ITK-based algorithms (denoising,
> N4 bias correction). It copies:
>
> - **Size** (width, height, depth) — yes
>   ([`:17793-17795`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L17793-L17795))
> - **Voxel spacing** (xsize, ysize, zsize) —
>   yes
>   ([`:17805-17807`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L17805-L17807))
> - **Pixel data** — yes
>   ([`:17812-17822`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L17812-L17822))
>
> But it does **not** copy:
>
> - **Origin** (`c_r`, `c_a`, `c_s` — RAS centre)
> - **Direction cosines**
>   (`x_r/x_a/x_s`, `y_r/y_a/y_s`, `z_r/z_a/z_s`)
>
> The resulting ITK image inherits ITK's
> defaults: `origin = (0, 0, 0)` and
> `direction = identity`. The companion
> `MRI::loadITKImage`
> ([`:17832-17853`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L17832-L17853))
> is symmetric — it copies pixels but ignores
> any orientation the ITK image may carry.
>
> For axis-aligned RAS-conformed FreeSurfer
> inputs (the typical case), the lost
> orientation matches the ITK default, so
> algorithms see a correct-by-coincidence
> spatial frame. For arbitrarily-oriented
> inputs (oblique acquisitions, non-conformed
> volumes) ITK computes in voxel-aligned space
> while the algorithm was designed for
> physical/RAS space.

## Detailed Description

```cpp
/* utils/mri.cpp:17783-17823 — toITKImage */
ITKImageType::Pointer MRI::toITKImage(int frame)
{
  ...
  ITKImageType::SpacingType spacing;
  spacing[0] = this->xsize;
  spacing[1] = this->ysize;
  spacing[2] = this->zsize;
  image->SetSpacing(spacing);
  /* NO SetOrigin() call */
  /* NO SetDirection() call */
  ...
  /* copy pixels */
}
```

ITK images have three spatial-metadata
slots: `Spacing`, `Origin`, `Direction`. The
function sets only `Spacing`. ITK's defaults
for the others are `Origin = (0, 0, 0)` and
`Direction = identity matrix`.

The MRI struct carries:

- `c_r/c_a/c_s`: the RAS coordinate of the
  centre voxel (used to compute the volume's
  origin in RAS).
- `x_r/x_a/x_s`: direction cosines of the
  column axis in RAS.
- `y_r/y_a/y_s`: direction cosines of the
  row axis.
- `z_r/z_a/z_s`: direction cosines of the
  slice axis.

Together these encode the vox→RAS transform.
The ITK round-trip drops everything except
spacing.

### When the bug fires

ITK algorithms typically iterate over voxel
indices but compute distances and physical-
space neighbourhoods using the image's
`spacing` and `direction`. With identity
direction the algorithm sees:

- column axis = +X (matches RAS R)
- row axis    = +Y (matches RAS A)
- slice axis  = +Z (matches RAS S)

For a conformed FreeSurfer MRI (LIA/RAS
orientation, isotropic voxels), this matches
the actual orientation closely enough that
N4 bias correction and ITK denoising produce
sensible-looking results. For an oblique
acquisition or a flipped-axis input, the ITK
algorithm runs in a frame mis-rotated from
the volume's true orientation — bias field
or denoising kernels are applied along
incorrect physical directions.

### Asymmetric vs symmetric round-trip

Because both `toITKImage` and `loadITKImage`
drop orientation, a `MRI → ITK → MRI`
round-trip preserves voxel data positions
correctly (no resampling occurs — both sides
use voxel-index-based pixel access). The
issue is only inside the ITK algorithm,
where physical-space computations use the
wrong frame.

## Root Cause

The bridge functions were written to "shuttle
pixels and basic shape" between MRI and ITK,
but the spatial metadata copy was incomplete.
The author probably tested on conformed
inputs where the identity direction matrix
matches the actual orientation, masking the
bug.

## Impact

- **Conformed FreeSurfer inputs:** none
  observable. Identity direction
  approximately matches RAS-conformed
  orientation.
- **Non-conformed / oblique inputs:** ITK
  algorithm operates in a wrong physical
  frame. N4 bias-field smoothness assumes
  the image's physical axes; with incorrect
  direction the smoothness term applies
  along voxel axes instead of RAS axes,
  yielding a slightly wrong bias field.
- **Severity:** 2 — latent under typical
  conformed-input usage; conceptually wrong
  for arbitrary orientations.

## Recommended Fix

```diff
--- a/utils/mri.cpp
+++ b/utils/mri.cpp
@@ -17806,6 +17806,28 @@ ITKImageType::Pointer MRI::toITKImage(int frame)
   spacing[1] = this->ysize;
   spacing[2] = this->zsize;
   image->SetSpacing(spacing);

+  // Set origin from RAS centre (c_r/c_a/c_s) corrected for the centre-voxel offset
+  ITKImageType::PointType origin;
+  // The MRI's c_r/c_a/c_s is at voxel (width/2, height/2, depth/2). Compute the
+  // RAS position of voxel (0,0,0).
+  double cx = this->width  / 2.0, cy = this->height / 2.0, cz = this->depth / 2.0;
+  origin[0] = this->c_r - (this->x_r * cx * this->xsize +
+                           this->y_r * cy * this->ysize +
+                           this->z_r * cz * this->zsize);
+  origin[1] = this->c_a - (this->x_a * cx * this->xsize +
+                           this->y_a * cy * this->ysize +
+                           this->z_a * cz * this->zsize);
+  origin[2] = this->c_s - (this->x_s * cx * this->xsize +
+                           this->y_s * cy * this->ysize +
+                           this->z_s * cz * this->zsize);
+  image->SetOrigin(origin);
+
+  // Set direction cosines
+  ITKImageType::DirectionType direction;
+  direction(0, 0) = this->x_r; direction(0, 1) = this->y_r; direction(0, 2) = this->z_r;
+  direction(1, 0) = this->x_a; direction(1, 1) = this->y_a; direction(1, 2) = this->z_a;
+  direction(2, 0) = this->x_s; direction(2, 1) = this->y_s; direction(2, 2) = this->z_s;
+  image->SetDirection(direction);
```

The companion `loadITKImage` should also
copy origin and direction back into the MRI
fields so a round-tripped MRI preserves its
spatial reference (the current implementation
overwrites pixels but the existing MRI
struct's metadata is preserved by virtue of
not touching it).

## Workarounds

For non-conformed inputs to AntsN4 / AntsDenoise,
manually conform the input first via
`mri_convert --conform`.

## Provenance and Discovery

- **Discovered:** 2026-05-10 by agent
  (ITK-bridge metadata audit).
- **Evidence:**
  - `image->SetSpacing(spacing)` at `:17808`
    is the only metadata setter.
  - No `SetOrigin` or `SetDirection` calls
    in either function.
  - ITK's defaults for these are zero origin
    and identity direction.
