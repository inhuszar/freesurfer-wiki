# [severity-3] [bug-00058] `LabelIntersect` — off-by-one allocation, OOB read/write at the max-vno entry

> [!bug] Synopsis
> `LabelIntersect`
> ([`utils/label.cpp:747-796`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/label.cpp#L747-L796))
> intersects two labels using a working array indexed
> by `vno - vmin`. The allocation is sized
> `vmax - vmin` ints
> ([`:776-777`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/label.cpp#L776-L777)):
>
> ```cpp
> vnum = vmax - vmin;                                /* :776 */
> isec = (int *)calloc(vnum, sizeof(int));           /* :777 */
> ```
>
> But the indexing range is `0..vmax-vmin`
> *inclusive* — `vmax - vmin + 1` distinct values:
>
> ```cpp
> for (n = 0; n < area1->n_points; n++) {
>   vno = area1->lv[n].vno - vmin;                    /* range [0, vmax-vmin] */
>   isec[vno] = n;                                    /* :785 — OOB if vno == vmax-vmin */
>   area1->lv[n].deleted = 1;
> }
> for (n = 0; n < area2->n_points; n++) {
>   vno = area2->lv[n].vno - vmin;
>   if (isec[vno] > -1) {                             /* :790 — OOB read symmetrically */
>     area1->lv[isec[vno]].deleted = 0;
>   }
> }
> ```
>
> Whenever the vertex with the maximum index across
> both labels actually appears in `area1` and/or
> `area2`, `isec[vmax - vmin]` writes / reads one past
> the allocated range. Heap corruption with
> non-deterministic downstream effect.

- **Sole caller in-tree:**

## Detailed Description

```cpp
int LabelIntersect(LABEL *area1, LABEL *area2)
{
  int n, vno;
  int vmin, vmax, vnum;
  int *isec;
  ...
  vmin = area1->lv[0].vno;
  vmax = area1->lv[0].vno;
  for (n = 0; n < area1->n_points; n++) {
    vno = area1->lv[n].vno;
    if (vno < vmin) vmin = vno;
    if (vno > vmax) vmax = vno;                       /* vmax is reached at some n */
  }
  for (n = 0; n < area2->n_points; n++) {
    vno = area2->lv[n].vno;
    if (vno < vmin) vmin = vno;
    if (vno > vmax) vmax = vno;
  }
  vnum = vmax - vmin;                                 /* (!) off-by-one */
  isec = (int *)calloc(vnum, sizeof(int));
  if (!isec) ErrorExit(...);
  for (n = 0; n < vnum; n++) isec[n] = -1;            /* zeroed up to vnum-1 only */

  for (n = 0; n < area1->n_points; n++) {
    vno = area1->lv[n].vno - vmin;                    /* vno ∈ [0, vmax-vmin] = [0, vnum] */
    isec[vno] = n;                                    /* writes isec[vnum] when vno == vmax-vmin */
    area1->lv[n].deleted = 1;
  }
  for (n = 0; n < area2->n_points; n++) {
    vno = area2->lv[n].vno - vmin;
    if (isec[vno] > -1) {                             /* reads isec[vnum] symmetrically */
      area1->lv[isec[vno]].deleted = 0;
    }
  }
  ...
}
```

The entry whose `vno == vmax` is the precise trigger:
its `vno - vmin` equals `vmax - vmin == vnum`, one
past the last legal index of `isec[]`.

The initialisation loop at `:780` (zero out `isec`)
writes `vnum` ints — also stops one short, leaving
`isec[vnum]` with whatever the `calloc` returned (zero
in practice, since `calloc` zeros memory — but
`isec[vnum]` is past the allocation, so the read at
`:790` is technically reading uninitialised /
adjacent-allocation memory).

Heap-allocator behaviour determines the operational
impact: typically the next 8-byte alignment slot is
unused padding within the same block, so the OOB
write may silently succeed; in tight allocators it
can clobber a header word and trigger a corruption
diagnostic on the next free.

## Root Cause

Classic off-by-one: the size of an inclusive index
range `[0..N]` is `N + 1`, not `N`. The code uses
`vmax - vmin` directly without the `+ 1`.

## Impact

- **Heap corruption / OOB read** at the exact entry
  whose vertex index equals `vmax`. Since `vmax` is
  derived from those very indices, the bug is
  triggered virtually every time the function is
  called.
- **Operational effect:** depends on heap allocator.
  On glibc with `MALLOC_CHECK_=3`, a write past a
  small chunk's payload triggers an abort. On default
  glibc (no checks), the write usually lands in
  inter-block padding and is silent — but the next
  allocator call may behave erratically.
- **Functional correctness:** the intersection result
  is correct *for every entry except* the one with
  `vno == vmax`. That entry's `area1->lv[i].deleted`
  is left at `1` (not cleared) because the
  `isec[vno]` lookup reads junk past the allocation.
  Effectively: `mris_label_calc intersect` may drop
  the highest-vno vertex from the intersection.
- **Severity:** medium. Heap-corruption potential on
  hardened systems; silent data loss of one vertex on
  default systems.

## Recommended Fix

```diff
--- a/utils/label.cpp
+++ b/utils/label.cpp
@@ -773,7 +773,7 @@ int LabelIntersect(LABEL *area1, LABEL *area2)
       vmax = vno;
     }
   }
-  vnum = vmax - vmin;
+  vnum = vmax - vmin + 1;

```

Single-token fix. The initialisation loop at `:779`
will now zero all `vnum` entries; the index range
`[0, vmax-vmin]` is fully covered.

## Workarounds

For the user: avoid `mris_label_calc intersect` on
labels where vertex indices span a tight range; or
patch and rebuild.
