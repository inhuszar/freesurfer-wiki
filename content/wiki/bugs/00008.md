# [severity-3] [bug-00008] gdfContrastDOSS — off-by-one writes past the contrast matrix and past wCovar

> [!bug] Synopsis
> `gdfContrastDOSS` in `utils/fsgdf.cpp` allocates a 1×(`nclasses +
> nvariables`) contrast matrix to match the DOSS design-matrix
> column count, but the covariate loop iterates `nvariables + 1`
> times instead of `nvariables`. The last iteration writes one
> column past the end of the matrix (column index `nclasses +
> nvariables + 1` when only `nclasses + nvariables` columns exist)
> and, when the optional `wCovar` array is supplied, reads
> `wCovar[nvariables]` — one past the caller-provided array. The
> function is exported via `include/fsgdf.h` but has no in-tree
> caller at the audited commit, so the defect is latent; any
> downstream GLM consumer that picks it up will hit both the
> out-of-bounds write and the out-of-bounds read on every call.

## Affected Artefacts

- **Tool(s):** None today — `gdfContrastDOSS` is declared in
  `include/fsgdf.h:136` and defined in `utils/fsgdf.cpp:1920` but
  has no in-tree caller. Companion
  [`gdfMatrixDOSS`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/fsgdf.cpp#L1196)
  (the design-matrix builder) is widely used; the contrast
  counterpart is a latent utility.
- **Pipeline stage(s):** _N/A_ — recon-all does not call this
  function directly. Catalogued as a latent trap because the
  function is exported as part of the FreeSurfer utility library
  and is available to any downstream consumer that links against it,
  including [[wiki/tools/mri_glmfit|mri_glmfit]]-style tools that build DOSS contrast
  matrices programmatically.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit
  `d932c45b79`.
- **Platforms:** all — purely C-level indexing.
- **Triggering configuration:** every call to `gdfContrastDOSS`
  fires the defect; the impact depends on what the overflowed byte
  corrupts (allocator metadata, the next matrix's data, or
  unmapped memory).

## Detailed Description

In the DOSS design (Different Offset, Same Slope), the design
matrix has `nclasses + nvariables` columns: the first `nclasses`
columns are per-class intercepts; the next `nvariables` columns are
global slopes shared across classes. This is the layout
established by `gdfMatrixDOSS`
(`utils/fsgdf.cpp:1196–1221`).

A contrast vector for that design must have exactly one entry per
column: `nclasses` class weights followed by `nvariables` covariate
weights.

`gdfContrastDOSS` allocates the correct number of columns:

```cpp
C = MatrixAlloc(1, fsgd->nvariables + fsgd->nclasses, MATRIX_REAL);
```

…but its covariate loop iterates one time too many and writes one
column past the end.

### Expected Behaviour

`gdfContrastDOSS(fsgd, wClass, wCovar)` should return a 1×(`nclasses
+ nvariables`) contrast matrix whose columns match the DOSS design
matrix column-by-column, reading at most `nclasses` weights from
`wClass` and at most `nvariables` weights from `wCovar`.

### Observed Behaviour

The covariate loop bound is `v < nvariables + 1`, so it runs
`nvariables + 1` iterations. In the final iteration:

- the write `C->rptr[1][n + 1]` targets column
  `nclasses + nvariables + 1`, which is one past the allocated
  column range of the 1×(`nclasses + nvariables`) matrix;
- the read `wCovar[v]` (when `wCovar != NULL`) accesses
  `wCovar[nvariables]`, one past the end of the caller's array.

Whether the write corrupts adjacent memory depends on the `MATRIX`
internal layout (a contiguous row/column store); at minimum the
value is written into memory the caller did not allocate for this
purpose, and the returned contrast vector has no entry for one of
its intended columns.

### Reproducer

> [!gap] Reproducer not yet constructed
> The function has no in-tree caller, so the defect is latent. A
> unit-style exercise that builds a minimal `FSGD` with
> `DesignMatMethod = "doss"`, `nclasses = 2`, `nvariables = 2`, and
> calls `gdfContrastDOSS(fsgd, wClass, wCovar)` with a 2-element
> `wCovar` would demonstrate both the out-of-bounds write and the
> read of `wCovar[2]` under an address sanitiser.

## Code Reference (Unambiguous)

- **File:** `utils/fsgdf.cpp`
- **Function:** `gdfContrastDOSS()`
- **Lines:** `1920–1948`
- **Commit:** `d932c45b79`

```cpp
MATRIX *gdfContrastDOSS(FSGD *fsgd, float *wClass, float *wCovar)
{
  MATRIX *C;
  float w;
  int c, v, n;

  if(strcasecmp(fsgd->DesignMatMethod,"doss") != 0){
    printf("ERROR: gdfContrastDOSS() cannot be used with %s\n",fsgd->DesignMatMethod);
    return(NULL);
  }

  /* Contrast matrix*/
  C = MatrixAlloc(1, fsgd->nvariables+fsgd->nclasses, MATRIX_REAL);

  n = 0;
  for (c=0; c < fsgd->nclasses; c++) {
    w = 1;
    if (wClass != NULL) w *= wClass[c];
    C->rptr[1][n+1] = w;
    n++;
  }
  for (v=0; v < fsgd->nvariables+1; v++) {     // ← one too many iterations
    w = 1;
    if (wCovar != NULL) w *= wCovar[v];        // ← reads wCovar[nvariables] on last iter
    C->rptr[1][n+1] = w;                       // ← writes past column nclasses+nvariables on last iter
    n++;
  }
  return(C);
}
```

For comparison, the DOSS design-matrix builder uses exactly
`nvariables` covariate columns:

- **File:** `utils/fsgdf.cpp`
- **Function:** `gdfMatrixDOSS()`
- **Lines:** `1196–1221`
- **Commit:** `d932c45b79`

```cpp
MATRIX *gdfMatrixDOSS(FSGD *gd, MATRIX *X) {
  /* ... */
  ncols = gd->nclasses + gd->nvariables;

  X = MatrixZero(nrows,ncols,X);
  /* ... */
  for (r=0; r<nrows; r++) {
    c = gd->subjclassno[r];
    X->rptr[r+1][c+1] = 1;

    for (v = 0; v < gd->nvariables; v++) {     // correct bound
      /* ... */
      c = v + gd->nclasses;
      X->rptr[r+1][c+1] = gd->varvals[r][v] - mn;
      /* ... */
    }
  }
  return(X);
}
```

The DODS contrast builder — which is used in-tree — iterates
`nvariables + 1` times because the DODS layout includes an offset
column for each variable, so `nvariables + 1` is the correct count
there:

- **File:** `utils/fsgdf.cpp`
- **Function:** `gdfContrastDODS()`
- **Lines:** `1884–1910`
- **Commit:** `d932c45b79`

The bug in `gdfContrastDOSS` is almost certainly a copy of the DODS
covariate-loop bound without the corresponding layout change: DOSS
has no per-variable offset column, so the `+1` is spurious.

## Root Cause

Almost certainly a copy-paste from `gdfContrastDODS`, whose
`nvariables + 1` bound is correct for its "Different Offset" layout
(one offset column per class + `nvariables` slope columns per
class). In the DOSS variant the `+1` has no corresponding column and
walks off both the matrix and the caller's `wCovar` array.

## Impact

- Currently **latent**: no in-tree caller at `d932c45b79`, so the
  defect does not affect any shipping FreeSurfer tool run today.
- Any downstream tool (outside the FreeSurfer tree) that links
  against `libutils` and uses `gdfContrastDOSS` to build a DOSS
  contrast will hit the out-of-bounds write on every call. The
  practical manifestation depends on the `MATRIX` memory layout and
  the allocator: silent corruption of a neighbouring allocation is
  most likely, occasional crashes under an allocator that places
  guard bytes, and sanitiser reports under AddressSanitizer or
  Valgrind.

## Recommended Fix

```diff
-  for (v=0; v < fsgd->nvariables+1; v++) {
+  for (v=0; v < fsgd->nvariables; v++) {
     w = 1;
     if (wCovar != NULL) w *= wCovar[v];
     C->rptr[1][n+1] = w;
     n++;
   }
```

The one-character change (`nvariables + 1` → `nvariables`)
simultaneously fixes the out-of-bounds write (the final column
no longer exists in the iteration) and the out-of-bounds read from
`wCovar` (the loop no longer accesses `wCovar[nvariables]`).

### Alternative Fixes Considered

If the author actually intended a contrast vector that includes a
global intercept term (making the contrast longer than the design
matrix), both this function and `gdfMatrixDOSS` would need changes.
That is unlikely: the existing call sites of `gdfMatrixDOSS` (via
`gdfMatrix`) give no hint of such an intercept, and the DOSS layout
was explicitly contrasted with DODS's "one offset per class" layout.
The simple loop-bound fix is the safe minimal change.

## Workarounds (If Any)

Build the DOSS contrast vector directly in caller code with
`MatrixAlloc(1, nclasses + nvariables, MATRIX_REAL)` and a manual
assignment loop.
