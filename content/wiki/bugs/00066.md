# [severity-4] [bug-00066] `mri_extract_label --out_like` only copies dimensions, not RAS

> [!bug] Synopsis
> `mri_extract_label`
> ([`mri_extract_label/mri_extract_label.cpp:99-113`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_extract_label/mri_extract_label.cpp#L99-L113))
> handles `--out-like <template>` (alias `-ol`) by:
>
> ```cpp
> if (out_like_fname) {
>   MRI *mri_tmp = MRIread(out_like_fname);
>   ...
>   mri_out = MRIalloc(mri_tmp->width,
>                      mri_tmp->height,
>                      mri_tmp->depth,
>                      mri_tmp->type);
>   /*    MRIcopyHeader(mri_tmp, mri_out) ;*/   /* :111 — commented out */
>   MRIfree(&mri_tmp);
> }
> ```
>
> The CLI handler at
> [`:185-189`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_extract_label/mri_extract_label.cpp#L185-L189)
> documents the option as "shaping output to be like
> <file>". The natural reading is that the output's
> dimensions, type, *and* RAS geometry match the
> template. The implementation copies dimensions and
> type but the `MRIcopyHeader` call that would also
> copy origin / direction-cosines / voxel size is
> commented out. The output is written with whatever
> `MRIalloc` defaults to (origin at zero, identity
> direction cosines, unit voxel size).

## Affected Artefacts

- **Tool:** [[mri_extract_label]] when invoked with
  `--out-like` / `-ol`.
- **Pipeline stage(s):** none in default
  `recon-all`. Affects user pipelines.
- **Triggering configuration:** any
  `mri_extract_label … --out-like <tmpl> …` where
  the template's RAS positioning differs from the
  default.
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION`.

## Detailed Description

`MRIalloc(w, h, d, t)` produces an MRI with default
header values: `c_r = c_a = c_s = 0`, identity
direction cosines, voxel sizes 1×1×1 mm. A typical
template (e.g. an aseg.mgz from a real subject)
has nontrivial origin and direction cosines.

`extract_labeled_image`
([`:290-309`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_extract_label/mri_extract_label.cpp#L290-L309))
operates voxel-wise via `MRIadd`. It does not check
or use `mri_dst`'s RAS coordinates — the data
written into `mri_out` corresponds to the input's
voxel positions, *interpreted* in `mri_out`'s default
RAS. When the user later loads the output volume
(e.g. in FreeView), the extracted labels appear at
the wrong RAS positions relative to the rest of the
subject's data.

## Root Cause

The `MRIcopyHeader` call was commented out at some
point — possibly to debug a geometry mismatch between
input and template — and never restored. Without
git-blame the original motivation is unclear.

## Impact

- **User-facing:** when the input and template have
  different RAS positioning, the extracted output
  volume is georeferenced incorrectly. Loading the
  output alongside the template / subject's
  coordinate system in FreeView shows the labels
  spatially offset.
- **Severity:** low. `mri_extract_label --out-like`
  is a niche option. Correct behaviour is easy to
  recover by post-processing the output with
  `mri_convert --like <tmpl>` or by avoiding
  `--out-like` and aligning manually.

## Recommended Fix

```diff
--- a/mri_extract_label/mri_extract_label.cpp
+++ b/mri_extract_label/mri_extract_label.cpp
@@ -108,7 +108,7 @@ int main(int argc, char *argv[]) {
                        mri_tmp->height,
                        mri_tmp->depth,
                        mri_tmp->type) ;
-    /*    MRIcopyHeader(mri_tmp, mri_out) ;*/
+    MRIcopyHeader(mri_tmp, mri_out) ;
     MRIfree(&mri_tmp) ;
   }
```

If there was a documented reason to disable the
header copy, restore it conditional on a CLI flag
(`--no-out-header`) so the default matches the user
expectation.

## Workarounds

After running `mri_extract_label … --out-like tmpl
out.mgz`, follow up with:

```bash
mri_convert --like tmpl out.mgz out.fixed.mgz
```

to inherit the template's RAS geometry.
