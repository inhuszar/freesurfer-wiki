# MRIvalRange family uses fixed ±10000 sentinel instead of first-sample initialisation

> [!bug] Synopsis
> `MRIvalRange`, `MRIvalRangeFrame`, `MRIvalRangeRegion`, and
> `MRInonzeroValRange` all initialise `fmin = 10000.0f` and
> `fmax = -10000.0f` and then update only via `val < fmin` / `val >
> fmax`. Any volume whose entire value range lies _above_ `10000`
> (realistic for `MRI_USHRT`, `MRI_INT`, scaled `MRI_SHORT`) silently
> receives `fmin = 10000` — an incorrect lower bound — and any volume
> whose range lies _below_ `−10000` receives `fmax = −10000`. Empty
> or fully-masked volumes return the paradoxical `fmin > fmax` with
> no error. The sister function `MRIlabelValRange` _does_ use a
> first-sample sentinel and is correct, demonstrating the intended
> idiom.

## Affected Artefacts

- **Tool(s):** any caller of `MRIvalRange` family. Thirty-plus
  in-tree call sites including:
  - `utils/density.cpp:45-46` (joint-density image pairs for
    [[mri_em_register]])
  - `utils/mrinorm.cpp:2377` ([[mri_normalize]])
  - `utils/mrisurf_sseTerms.cpp:1193, 1357, 2359, 2405`
    ([[mris_make_surfaces]] SSE / likelihood terms)
  - `utils/mrifilter.cpp:5410` (MRIcomputeClassStatistics —
    white/gray histograms for `mris_ca_label`)
  - `utils/mrimorph.cpp:6539, 6547, 6762, 6772, 7279, 7282`
    (label-morph energy terms)
  - `utils/mrihisto.cpp:192, 226, 732, 1342` (histogram
    construction — one with an explicit in-tree `// fmin = is
    wrong!` comment)
- **Pipeline stage(s):** latent under standard [[recon-all]] inputs
  (conformed `MRI_UCHAR`, values 0–255), but fires whenever a caller
  passes a `MRI_USHRT`/`MRI_INT` volume whose minimum exceeds 10000
  or whose maximum falls below −10000.
- **FreeSurfer version(s):** confirmed in `$FREESURFER_VERSION`;
  earliest known: _unknown_
- **Platforms:** all
- **Triggering configuration:**
  - Integer-typed volumes with all nonzero values > 10000 (e.g.,
    MRI_USHRT DICOMs with a scale offset).
  - All-negative float volumes with all values < −10000 (rare but
    possible, e.g., distance maps with reversed sign convention).
  - Empty volumes (all-zero, or all voxels outside the region):
    `fmin = 10000 > fmax = −10000` is returned with `NO_ERROR`; no
    caller checks for this inversion.

## Detailed Description

### Expected Behaviour

For a volume containing any data, `MRIvalRange(mri, &fmin, &fmax)`
should set `*fmin = min(voxel values)` and
`*fmax = max(voxel values)`, regardless of the numeric range of the
underlying type. For an empty volume the function should either
return a distinct error code or use sentinels drawn from the type's
extrema (e.g., `FLT_MAX`, `-FLT_MAX`) so the caller has a detectable
"no data" signal instead of a plausible-looking `[10000, −10000]`
interval.

The sibling function `MRIlabelValRange` at
[`utils/mri.cpp:2145-2176`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L2145-L2176)
uses a first-sample sentinel:

```cpp
int first = 1;
...
if (first) { first = 0; fmax = fmin = val; }
if (val < fmin) fmin = val;
if (val > fmax) fmax = val;
```

which correctly handles any numeric range.

### Observed Behaviour

With the `fmin = 10000 / fmax = -10000` initialisation:

- For a volume whose minimum is above 10000, `val < fmin` is never
  satisfied on the low side, so `fmin` is returned as `10000` —
  below the actual minimum.
- For a volume whose maximum is below −10000, `val > fmax` is never
  satisfied on the high side, so `fmax` is returned as `-10000` —
  above the actual maximum.
- For a volume that contributes no samples to the range
  computation (e.g., `MRInonzeroValRange` on an all-zero volume,
  or `MRIvalRangeFrame` on a frame index that matches no voxels),
  both sentinels are returned unchanged: `fmin = 10000 > fmax =
  -10000`. No error code signals this case.

Corroborating in-tree comment at
[`utils/mrihisto.cpp:732`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrihisto.cpp#L732)
where `MRIhistogram` calls `MRIvalRange`:

```cpp
MRIvalRange(mri, &fmin, &fmax);  // fmin = is wrong!
```

An author has already noted the symptom and tagged the call site.

### Reproducer

```c
// Minimal demonstration with an MRI_INT volume whose values are all > 10000:
MRI *mri = MRIalloc(2, 2, 2, MRI_INT);
for (int x = 0; x < 2; x++) for (int y = 0; y < 2; y++) for (int z = 0; z < 2; z++)

// Expected: fmin == 50000, fmax == 50000
// Observed: fmin == 10000, fmax == 50000
```

## Root Cause

The `±10000` sentinel assumes all FreeSurfer volumes have values
inside `(-10000, 10000)`. This assumption fails for several real
cases:

1. **Scaled 16-bit data.** `MRI_USHRT` is natively `[0, 65535]`;
   `MRI_SHORT` with a rescale is natively `[-32768, 32767]`. DICOM
   stack imports with a dynamic range in the tens of thousands are
   common.
2. **Integer posterior probabilities × scale.** GCA posterior
   volumes are often stored as `MRI_INT` with an integer-scaled
   probability.
3. **Distance / warp fields** with a convention that puts all
   values on one sign (rare, but the code has no guard).
4. **Empty / fully-masked volumes.** The return is `fmin = 10000,
   fmax = -10000` with `NO_ERROR`, so the caller cannot distinguish
   "empty volume" from "valid range [10000, -10000]".

`MRIlabelValRange` already uses the correct first-sample sentinel,
which is portable to any numeric type and handles the empty-label
case by returning the initial `10000, -10000` — still imperfect for
empty but at least consistent with the idiom elsewhere.

## Impact

- **`DensityHistogramEstimate`** at
  [`utils/density.cpp:45-58`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/density.cpp#L45-L58)
  stores `pdf->min_val1 = MRIvalRange(...)` and uses it as the left
  edge of the binning transform. If the true minimum exceeds 10000,
  the first `(true_min - 10000) / bin_size` bins are unused —
  wasted histogram resolution but not a correctness bug for the
  bins that _do_ receive data, because subsequent
  `bin = (val - fmin) / bin_size` stays in range.
- **`MRIhistogram`** at
  [`utils/mrihisto.cpp:732-752`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrihisto.cpp#L732-L752)
  is similar: wasted bins, shifted distribution.
- **`MRIcomputeClassStatistics`** at
  [`utils/mrifilter.cpp:5410-5412`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrifilter.cpp#L5410-L5412)
  overrides `min_val = 0` immediately after the call, so the
  low-side defect does not propagate; the `max_val = -10000` case
  would still allocate a tiny histogram. For normal T1 inputs this
  is not reached, but for a pathologically-empty `mri_T1` it would
  allocate `nbins = 1` and silently produce degenerate
  statistics.
- **`MRIcomputeLabelAccuracy`** at
  [`utils/mriset.cpp:3420-3434`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mriset.cpp#L3420-L3434)
  allocates `present = calloc(max_val + 1, sizeof(int))`. If the
  volume is empty, `max_val = -10000`, and `calloc(-10000 + 1, ...)`
  is called with a very large unsigned value — either a huge
  allocation or `NULL` return depending on `size_t` cast.
- **Silent.** `NO_ERROR` is returned even when no data was
  observed. A caller using `fmin`/`fmax` to allocate arrays or
  compute bin widths cannot detect the "empty" case without a
  separate `fmin <= fmax` check.
- **Standard [[recon-all]] is unaffected** because conformed
  inputs are UCHAR with values in `[0, 255]` — well inside the
  sentinel range.

## Recommended Fix

Mirror the `MRIlabelValRange` idiom. Initialise on the first
observed sample. Return an explicit error when no samples were
observed.

```diff
 int MRIvalRange(MRI *mri, float *pmin, float *pmax)
 {
-  fmin = 10000.0f;
-  fmax = -10000.0f;
+  int first = 1;
+  fmin = 0.0f;
+  fmax = 0.0f;
   switch (mri->type) {
     case MRI_FLOAT:
       for (frame = ...) { ... for (x = ...) {
         val = *pf++;
-        if (val < fmin) fmin = val;
-        if (val > fmax) fmax = val;
+        if (first) { first = 0; fmin = fmax = val; continue; }
+        if (val < fmin) fmin = val;
+        else if (val > fmax) fmax = val;
       }}
     /* repeat in other cases */
   }
+  if (first) {
+    /* no data observed */
+    *pmin = 0; *pmax = 0;
+    return (ERROR_BADPARM);
+  }
   *pmin = fmin;
   *pmax = fmax;
   return (NO_ERROR);
 }
```

Apply the same fix to `MRIvalRangeFrame`, `MRIvalRangeRegion`, and
`MRInonzeroValRange` (for the latter, the `first` flag should be
set only after the first _nonzero_ value is accepted).

### Alternative Fixes Considered

- **Use `FLT_MAX` / `-FLT_MAX` as sentinels.** Simpler patch (no
  `first` flag), but still loses the ability to detect "no data
  observed" — the caller would see `fmin = FLT_MAX`, `fmax =
  -FLT_MAX`, which is still an invalid range.
- **Derive the initial values from the source type's extrema**
  (e.g., `USHRT_MAX` for `MRI_USHRT`). Correct for each integer
  type but requires per-type code and still does not signal the
  empty case.

## Workarounds (If Any)

- Callers that know the data range can pass bounds explicitly via
  a caller-local pass, but this bypasses the primitive entirely.
- Adding `if (min_val > max_val) { /* empty */ }` in every caller
  catches the empty case but does not fix the under-range and
  over-range cases.

> [!gap] Historical choice of 10000
> The `10000` / `-10000` magic numbers suggest a design-era
> assumption (likely from UCHAR-era FreeSurfer when values were
> guaranteed `[0, 255]`) that has not been revisited as support
> for wider integer types was added. Confirming the earliest
> commit that introduced this sentinel would help date the
> regression but is not strictly necessary for the fix.
