# [severity-3] [bug-00213] `DeltaTransform3d::invert` — negates only the x displacement (frame 0)

> [!bug] Synopsis
> `DeltaTransform3d::invert()` (the `field` transform in a `.tm3d` morph,
> which is what `surf2vol -compress` writes) is implemented by negating the
> stored displacement field, but the loop reads and writes **frame 0 only**
> (`MRIsampleVolume` returns frame 0; `MRIsetVoxVal(..., 0, -val)`). Frames 1
> and 2 (y and z displacements) are left untouched. The only caller,
> `applyMorph point_list` / `tract_point_list` through
> `VolumeMorph::invert()`, therefore maps points through a hybrid
> "inverse x, forward y, forward z" transform, silently. (Even with all frames
> negated the result is only a first-order inverse.)

## Affected Artefacts

- **Tool(s):** [[applyMorph]] (point-list items, and anything placed after a point-list item, see [[00214]]); the defective method belongs to the morph library shared with [[surf2vol]] / [[exportGcam]] / [[createMorph]]
- **Pipeline stage(s):** _N/A_. The CVS default path of [[mri_cvs_register]] does not invert morphs (it uses `exportGcam` and `mri_vol2vol`), and in 8.2.0 no in-tree script calls `applyMorph` with point lists.
- **FreeSurfer version(s):** confirmed in 8.2.0; the method dates from commit `1caf672b1fa` (2010-10-27, "corrected morph inversion code")
- **Platforms:** all
- **Triggering configuration:** `applyMorph --transform <file.tm3d> point_list|tract_point_list ...` where the `.tm3d` contains a `field` (`DeltaTransform3d`) transform, i.e. morphs produced by `surf2vol -compress` (the setting `mri_cvs_register` uses) or by `createMorph --in volume <displacement volume>`.

## Detailed Description

A `.tm3d` morph is a chain of transforms (`affine`, `fem`, `id`, `field`).
`VolumeMorph::invert()` inverts the chain by calling `invert()` on every
transform and reversing their order. For the `affine` and `fem` types this
is an exact inversion. A `field` transform stores a 3-frame float volume
`u(p)` (displacement in x, y, z) and maps `p -> p + u(p)`
([`fem_elastic/morph.cpp:414-442`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L414-L442)).
Its `invert()` is meant to replace `u` by `-u`, which for a smooth field is
the usual first-order inverse approximation.

The loop that does this reads the value with `MRIsampleVolume(m_field, i, j, k,
&val)`, which for integer coordinates is a nearest-neighbour read of
**frame 0**, and writes it back with `MRIsetVoxVal(m_field, i, j, k, 0, -val)`,
again **frame 0**. The y and z frames are never touched, although the
constructor allocation, `doInput`, `doOutput` and `doOwnImg` all handle three
frames. `surf2vol -compress` converts each FEM step to such a field
(`FemTransform3d::convert_to_delta`, a 256^3 grid), so this defect affects
the morphs the default CVS registration produces.

### Expected Behaviour

After `VolumeMorph::invert()` the `field` transform must map `p + u(p)` back
to (approximately) `p`: all three displacement components must change sign
(and, for a faithful inverse, the field should be re-sampled on the target
grid and the validity mask moved with it).

### Observed Behaviour

Only the x component changes sign. For a constant displacement field
`u = (2, 3, 4)` the point `(10, 20, 30)` is carried forward to `(12, 23,
34)` (observed with `--dbg_coords`), and a point list passed through the
"inverted" morph returns `(8, 23, 34)` instead of `(8, 17, 26)`. No message
is printed. The mask (`m_mask`) is also left on the original sampling grid,
which is only correct for an exact point-wise negation.

### Reproducer

Synthetic: a `.tm3d` with one `field` transform holding a constant
displacement `(2, 3, 4)` on a 40^3 grid, no mask, with valid fixed and moving
geometry records. The file layout is: for each of tags 1 (fixed geometry)
and 2 (moving geometry) a record `int32 valid, int32 w,h,d, float32 voxel
size[3], float32 x_r[3], y_r[3], z_r[3], c_ras[3]`, then tag 3 per transform
(`zlib`-compressed `uint32 len`, description `"field|t"`, one byte for the
"has initial" flag, then the payload); each record is `int32 tag, int64
length, bytes` (all little-endian). The payload of `field` is `int32 w,h,d`,
the three frames as float32 in (frame, z, y, x) order, and one byte for
"has mask".

```python
import struct, zlib, numpy as np
def vg(n):  # valid=1, n^3, 1 mm, LIA-like direction cosines, c_ras = 0
    b = struct.pack('<i', 1) + struct.pack('<iii', n, n, n) + struct.pack('<fff', 1, 1, 1)
    for v in ((-1, 0, 0), (0, 0, 1), (0, -1, 0)): b += struct.pack('<fff', *v)
    return b + struct.pack('<fff', 0, 0, 0)
def rec(tag, data): return struct.pack('<i', tag) + struct.pack('<q', len(data)) + data
def tr(kind, payload):
    d = (kind + '|t').encode()
    return struct.pack('<I', len(d)) + d + b'\x00' + payload
n, u = 40, (2.0, 3.0, 4.0)
payload = struct.pack('<iii', n, n, n)
for f in range(3): payload += np.full(n**3, u[f], dtype='<f4').tobytes()
payload += b'\x00'
open('field234.tm3d', 'wb').write(rec(1, vg(n)) + rec(2, vg(n)) + rec(3, zlib.compress(tr('field', payload))))
```

## Root Cause

`MRIsampleVolume` has no frame argument and returns frame 0 only (for integer coordinates it is a nearest-neighbour read through `MRIFvox`, [`utils/mri.cpp:9694-9695`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L9694-L9695), [`utils/mri.cpp:9418-9419`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L9418-L9419)), and
`MRIsetVoxVal(..., 0, ...)` hard-codes frame 0 as well, so the nested loops
over `(i, j, k)` only ever touch the x displacement. The loop should iterate
over `m_field->nframes` (3) frames. `git blame` shows the loop was written
in commit `1caf672b1fa` (2010-10-27, "corrected morph inversion code") and
never extended. Two secondary shortcomings are in the same method: negating
`u` at the same grid point is only a first-order inverse (the exact inverse
at `p + u(p)` is `p - u(p)` only where `u` is constant to first order), and
`m_mask` is not re-targeted to the inverse's domain.

## Impact

- **Silent wrong output** of `applyMorph point_list` / `tract_point_list`
  for any morph whose chain contains a `field` transform: the x coordinate
  is mapped backward while y and z are mapped forward. Such morphs are exactly
  what `surf2vol -compress` writes, hence what the CVS elastic step produces
  (`-compress` is part of the `elasticoptions` of `mri_cvs_register`, [`mri_cvs_register/mri_cvs_register:389-392`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_cvs_register/mri_cvs_register#L389-L392)) when
  its `.tm3d` is kept (`--keepelreg`, see [[mri_cvs_register]]; the script
  deletes the file otherwise).
- **Also reached through item order.** Because `point_list` inverts the
  shared morph permanently ([[00214]]), the defective inversion also
  affects any `vol`/`surf` item that follows a point list in the same call.
- **Severity 3, not 4 or 5.** The wrong result is reached only through an
  opt-in data-item keyword of one tool and only for morphs containing a
  `field` transform, which is the "gated behind specific flags/inputs"
  criterion. No default pipeline step inverts a morph: `mri_cvs_register`
  (8.2.0) applies the morph through `exportGcam` + `mri_vol2vol` and has the
  `applyMorph` calls commented out, and no in-tree script uses
  `applyMorph point_list`. It is not scored 2 because the output of the
  requested operation is wrong for every point.
- **Conditions where it is harmless:** morphs consisting only of `affine`,
  `id` and `fem` transforms invert correctly.

## Recommended Fix

Negate every frame:

```diff
 void
 DeltaTransform3d::invert()
 { 
-  double val;
-  //  std::cout << "DeltaTransform3d: invert" << std::endl;
-  int i, j, k;
-  for (i = 0; i < m_field->width; i++)
-    for (j = 0; j < m_field->height; j++)
-      for (k = 0; k < m_field->depth; k++)
-	{
-	  MRIsampleVolume(m_field, i, j, k, &val);
-	  MRIsetVoxVal(m_field, i, j, k, 0, -val); 
-	}
+  if ( !m_field )
+    throw "DeltaTransform3d invert - NULL data";
+  for (int f = 0; f < m_field->nframes; f++)
+    for (int i = 0; i < m_field->width; i++)
+      for (int j = 0; j < m_field->height; j++)
+        for (int k = 0; k < m_field->depth; k++)
+          MRIsetVoxVal(m_field, i, j, k, f, -MRIgetVoxVal(m_field, i, j, k, f));
 }
```

A regression test is the constant-field experiment above (expect `(8, 17,
26)`), plus a round-trip test `p -> T(p) -> T^-1(T(p))` on a smooth non-constant
field with a tolerance reflecting the first-order approximation.

### Alternative Fixes Considered

A faithful inverse for non-constant fields: for each target grid point `q`
solve `p + u(p) = q` by fixed-point iteration `p <- q - u(p)` (a few
iterations suffice for the small, smooth displacement fields CVS produces),
and carry the validity mask to the inverse's domain. This changes the stored
field values and is a larger change than the one-line frame fix; it is the
right fix if `applyMorph` point lists are to be used on CVS morphs with
sub-voxel accuracy.

## Workarounds (If Any)

Do not use `applyMorph point_list`/`tract_point_list` with morphs containing a
`field` transform. For CVS results use the exported `.m3z`
([[exportGcam]] output, as `mri_cvs_register` does) with the tools that
accept GCAMs (for example `mri_vol2vol --m3z`).
