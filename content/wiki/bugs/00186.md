# [severity-2] [bug-00186] fs-eddy — eddy binary-name mismatch: existence check tests `eddy` while the default invocation runs `eddy_cpu`

> [!bug] Synopsis
> `fs-eddy` validates that FSL's eddy is installed with `which eddy` (the
> plain, generic name), but the command it actually invokes is built as
> `eddy$cpu`, and `$cpu` defaults to `_cpu` — so the default run executes
> `eddy_cpu`. The existence check and the invocation therefore reference
> **different binary names**. On a modern FSL install (6.0.4+) that ships
> `eddy_cpu` / `eddy_cuda<ver>` but no generic `eddy`, the `which eddy` gate
> fails and the script aborts ("ERROR: cannot find eddy") even though
> `eddy_cpu` is present; conversely, on an older FSL that ships only a generic
> `eddy`, the gate passes but the default `eddy_cpu` invocation fails to
> launch ("command not found"). Either way the guard does not match the call.

## Affected Artefacts

- **Tool(s):** [[fs-eddy]] — FreeSurfer frontend to FSL `eddy` for
  eddy-current / motion / B0 distortion correction of diffusion data.
- **Pipeline stage(s):** _N/A_ — standalone script (a sibling of
  [[fs-topup]]); not part of [[wiki/pipelines/recon-all|recon-all]].
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all; the failure surfaces depending on which FSL build's
  eddy binaries are on `PATH`.
- **Triggering configuration:** depends on the installed FSL eddy binary
  set:
  - FSL with `eddy_cpu` but **no** generic `eddy` (modern default): the
    `which eddy` gate fails → script aborts before doing anything.
  - FSL with a generic `eddy` but **no** `eddy_cpu`: the gate passes, but the
    default (`--cpu`) invocation `eddy_cpu` is not found → eddy step fails.

## Detailed Description

`fs-eddy` selects the eddy variant via a `$cpu` suffix appended to the
literal `eddy`. The default is `_cpu`
([`scripts/fs-eddy:24`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-eddy#L24)
`set cpu = _cpu`), which the help text documents as the default
("`--cpu : forces use of cpu (default)`",
[`scripts/fs-eddy:568`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-eddy#L568)).
`--gpu` sets `$cpu` to the empty string
([`scripts/fs-eddy:429`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-eddy#L429)).
The actual call is assembled at
[`scripts/fs-eddy:267`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-eddy#L267)
as `eddy$cpu ...`, so:

- default / `--cpu` → runs **`eddy_cpu`**
- `--gpu` → runs **`eddy`** (generic)

But the up-front installation check (and the log line) test only the generic
name `eddy`:

- [`scripts/fs-eddy:73`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-eddy#L73)
  `which eddy | tee -a $LF` (log)
- [`scripts/fs-eddy:516-521`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-eddy#L516-L521)
  `which eddy > /dev/null` → if `$status`, "ERROR: cannot find eddy" and
  `exit 1` (hard gate)

So the guard checks `eddy` while the default path invokes `eddy_cpu`. The two
names diverge across FSL versions.

### Expected Behaviour

The existence check should test the **same** binary the script will run —
i.e. `eddy$cpu` (the actual invoked name, `eddy_cpu` by default, `eddy`
under `--gpu`). If that binary is present, the script should proceed; if not,
it should report the precise missing name.

### Observed Behaviour

The check tests `eddy`; the default invocation is `eddy_cpu`. Concrete
failure modes:

1. **Modern FSL (6.0.4+)** typically installs `eddy_cpu` (CPU/OpenMP) and
   `eddy_cuda<ver>` (GPU) and **drops the generic `eddy` wrapper**. Here
   `which eddy` fails, so
   [`scripts/fs-eddy:516-521`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-eddy#L516-L521)
   aborts the whole script with "ERROR: cannot find eddy. Make sure FSL is
   installed" — even though the very binary it would have run (`eddy_cpu`)
   **is** installed. The user is blocked despite a working FSL.

2. **Older FSL** ships a generic `eddy` (and historically `eddy_openmp`)
   but **no** `eddy_cpu`. Here `which eddy` passes the gate, the script
   proceeds, and then the default invocation at line 267 tries to run
   `eddy_cpu`, which is not on `PATH` → "eddy_cpu: command not found" and the
   eddy step fails at
   [`scripts/fs-eddy:271-272`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-eddy#L271-L272).
   (This is the situation reproduced in the current environment: the FSL on
   `PATH` provides `eddy` but not `eddy_cpu`.)

In both cases the binary named in the guard differs from the binary actually
executed.

### Reproducer

```bash
# In the current environment, FSL on PATH provides `eddy` but not `eddy_cpu`:
which eddy        # -> /usr/pubsw/packages/fsl/current/bin/eddy   (gate passes)
which eddy_cpu    # -> not found                                  (default call would fail)

# So fs-eddy's `which eddy` check (line 516) succeeds, but its default
# invocation `eddy$cpu` == `eddy_cpu` (line 267) would fail to launch.
# Symmetrically, on FSL 6.0.4+ that ships eddy_cpu but no generic `eddy`,
# the line-516 gate aborts with "ERROR: cannot find eddy" before any work,
# even though eddy_cpu is present.
```

## Root Cause

The installation guard hard-codes the generic binary name `eddy`, while the
invocation derives the name dynamically as `eddy$cpu` (defaulting to
`eddy_cpu`). The two were not kept in sync, so the name the script *checks
for* is not the name it *runs*. FSL's eddy binaries have been renamed over
versions (generic `eddy` → `eddy_openmp` → `eddy_cpu` for CPU; `eddy_cuda`
for GPU), and `fs-eddy` accounts for this only in the invocation, not in the
guard.

## Impact

- **Portability / launch failures.** On a common modern FSL layout
  (`eddy_cpu` present, generic `eddy` absent), `fs-eddy` refuses to start at
  the `which eddy` gate, with a misleading "FSL is not installed" message,
  despite FSL and `eddy_cpu` being present. On an older layout the gate
  passes but the eddy step then fails on the missing `eddy_cpu`. The user-
  visible result is that the eddy-correction step does not run.
- **Loud, not silent.** Both modes produce an error and stop (gate `exit 1`
  or a failed `eddy_cpu` invocation with `if($status) exit 1`), so no wrong
  output is produced — the tool simply fails to launch eddy.
- **Scope.** This is low (2): `fs-eddy` is a standalone auxiliary script (not
  a default pipeline), and on the FSL build that exactly matches the
  hard-coded assumptions both names happen to exist. It is a portability
  defect that bites on mismatched FSL builds rather than a wrong-result bug.

## Recommended Fix

Check the binary the script will actually invoke. Compute the eddy binary
name once and use it in both the guard and the call:

```diff
-which eddy > /dev/null
+which eddy$cpu > /dev/null
 if($status) then
-  echo "ERROR: cannot find eddy. Make sure"
-  echo "       FSL is installed"
+  echo "ERROR: cannot find eddy$cpu. Make sure"
+  echo "       FSL (with the eddy$cpu binary) is installed"
   exit 1;
 endif
```

and likewise log the real name at line 73 (`which eddy$cpu | tee -a $LF`).
Because `$cpu` is already resolved from the command line by the time the
check runs (argument parsing precedes `check_params`), `eddy$cpu` correctly
expands to `eddy_cpu` (default/`--cpu`) or `eddy` (`--gpu`).

### Alternative Fixes Considered

A more robust variant probes a list of known eddy names and picks the first
present, e.g.:

```tcsh
set eddybin = ()
foreach e (eddy$cpu eddy_cpu eddy_openmp eddy)
  if (`which $e |& grep -v "not found"` != "") then
    set eddybin = $e
    break
  endif
end
if ($#eddybin == 0) then
  echo "ERROR: cannot find an FSL eddy binary (tried eddy$cpu eddy_cpu eddy_openmp eddy)"
  exit 1
endif
```

then invoke `$eddybin` at line 267. This tolerates all FSL eras at the cost
of more code; the minimal `which eddy$cpu` fix above already removes the
guard/call name mismatch.

## Workarounds (If Any)

Create a symlink so the checked/invoked names resolve, matching the install:
e.g. on modern FSL, `ln -s $FSLDIR/bin/eddy_cpu $FSLDIR/bin/eddy` (satisfies
the `which eddy` gate); on older FSL, `ln -s $FSLDIR/bin/eddy
$FSLDIR/bin/eddy_cpu` (satisfies the default invocation). Alternatively pass
`--gpu` only if a generic `eddy`/`eddy_cuda` is actually present.
