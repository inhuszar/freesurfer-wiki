# [severity-2] [bug-00209] fem_elastic — memory leaks in TSolver::comm_solution, TSolver::setup_load_sym and ZlibStringCompressor (no destructor; every VolumeMorph load/save leaks its compression buffer)

> [!bug] Synopsis
> Three leaks in the FEM core. (1) `TSolver::comm_solution()` allocates `new PetscScalar[3*nnodes]` and immediately overwrites the pointer with `VecGetArray`, leaking
> the allocation on every solve (every FEM step and every untangler crop solve). (2) `TSolver::setup_load_sym()` never frees its `indices`, `values` and `rhsValues` arrays.
> (3) `ZlibStringCompressor` has no destructor, so the buffer it grows to about 1–2× the uncompressed transform size is never released; each `VolumeMorph::load_new` / `save` leaks it.
> The leaks do not change results but inflate peak memory of [[surf2vol]], [[exportGcam]] and [[createMorph]]; the developers have suspected the compressor leak since 2018.

## Affected Artefacts

- **Tool(s):** [[surf2vol]] (solver and compressor), [[exportGcam]], [[createMorph]], [[applyMorph]] (compressor via `.tm3d` load/save)
- **Pipeline stage(s):** [[mri_cvs_register]] elastic step (surf2vol, then exportGcam)
- **FreeSurfer version(s):** confirmed in `8.2.0`; present since the 2008-03-14 import (`4b881dc775`)
- **Platforms:** all
- **Triggering configuration:** always-on. The solver leaks run once per `TSolver::solve()` (the CVS default `-fem_steps 17` runs steps 17 … 0, i.e. 18 solves,
  [`fem_elastic/fsurf2vol.cpp:476`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L476)) plus one `TDirectSolver::solve()` per untangler crop; the compressor leak occurs on every `.tm3d` load or save.

## Detailed Description

### (1) `comm_solution()` overwrites its own allocation

```cpp
TSolver<Cstr,n>::comm_solution()
{
  PetscErrorCode ierr;

  int no_eqs = m_pmesh->get_no_nodes() *n;

  PetscScalar *pdelta = new PetscScalar[no_eqs];
  ierr = VecGetArray(m_delta, &pdelta);
  CHKERRQ(ierr);
```

`VecGetArray` returns the vector's internal array through `&pdelta`, so the block from `new` is unreachable. The function is called by both `TSolver::solve()`
([`fem_elastic/solver.h:420`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/solver.h#L420)) and `TDirectSolver::solve()` ([`fem_elastic/solver.h:1315`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/solver.h#L1315)). The leak is `8 · 3 · nnodes` bytes per call (`PetscScalar` is `double` in this build).
For the CVS meshes (hundreds of thousands of nodes — node count not measured here) that is of the order of 10 MB per solve.

> [!note] Resident versus virtual
> The leaked array is never written to, and blocks of this size are served by `mmap`, so the pages are normally never touched: the leak shows up as virtual size, not necessarily as resident memory.

### (2) `setup_load_sym()` never frees its scratch arrays

```cpp
  int *indices = new int[ mrhs.size() ];
  double *values = new double[ mrhs.size() ];
```

and

```cpp
  PetscScalar* rhsValues = new PetscScalar[ mrhs.size()];
```

None of `indices`, `values` or `rhsValues` is released before `return 0;` at [`fem_elastic/solver.h:1138`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/solver.h#L1138) (compare the sibling `setup_load()`, which ends with `delete[] indices; delete[] values;`,
[`fem_elastic/solver.h:1017-1018`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/solver.h#L1017-L1018)). Sizes are the number of constrained degrees of freedom: small.

### (3) `ZlibStringCompressor` owns a buffer and has no destructor

```cpp
class ZlibStringCompressor
{
public:
  ZlibStringCompressor(unsigned long bufferSize=0);
  const string compress(const string& toCompress, int level);
  const string inflate(const string& compressed);
  unsigned long getBufferSize();
  void setDebugLevel(int level);
  int getDebugLevel();
  Bytef* setBufferSize(unsigned long size);
  unsigned int m_bufferAllocationMultiplier;
private:
  static void checkZlibResult(const int result,
                              const char* file,
                              const int line);
  long unsigned m_bufferSize;
  /*
    pointer to start of buffer
  */
  Bytef* m_buffer;
  static unsigned long findSizeInBytes(const string& s);
  static unsigned long findRequiredBufferSize
  (const unsigned long uncompressedSize);
  int m_debugLevel;
};
```

`compress()` and `inflate()` grow `m_buffer` through `setBufferSize()` ([`fem_elastic/ZlibStringCompressor.cpp:22-40`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/ZlibStringCompressor.cpp#L22-L40)),
`compress()` allocating `2 × (size + size/1000 + 12)` bytes ([`fem_elastic/ZlibStringCompressor.cpp:82-87`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/ZlibStringCompressor.cpp#L82-L87)); nothing ever releases the final buffer. The class is also copyable (implicit copy duplicates the pointer),
so adding a destructor requires making it non-copyable as well.

The in-tree comments show that the developers saw the symptom but not the cause:

- [`fem_elastic/morph.cpp:1223`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L1223) — `ZlibStringCompressor compressor; // may have a mem leak, so move outside of loop`
- [`fem_elastic/morph.cpp:1373`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L1373) — `ZlibStringCompressor compressor; // memory leak in compressor?`
- [`fem_elastic/morph.cpp:1403`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L1403) — `//ZlibStringCompressor compressor;// might be a memleak, so made function scope`
- Commit `febf7c3f07` (2018-08-31): "I moved the ZlibStringCompressor out of the inner loop in transform reading and writing routines because there appears to be a memory leak in it. When moved, createMorph only uses 12G vs 27G, similar savings for exportGCAM."
- Commit `9fefeefc69` (2018-12-11), touching `fsurf2vol.cpp`: "Added some notes and terminal output when trying to find the mem leak (still could not find it)". (`surf2vol` also prints `PrintMemUsage` every step, [`fem_elastic/fsurf2vol.cpp:479`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L479).)

The 2018 change moved the compressor out of the per-transform loop, which (by inference from the commit message) reduced the number of leaked buffers, but it did not remove the leak: each compressor instance still never frees its final buffer.

### Expected Behaviour

Every allocation is released; peak memory of `exportGcam` / `createMorph` / `surf2vol` is governed by the data they hold, not by discarded scratch buffers.

### Observed Behaviour

Memory grows with each solve and each morph (de)serialisation. Only (3) has a sizeable effect on resident memory: the buffer is written by zlib.

### Reproducer

For (3), the unmodified `ZlibStringCompressor.cpp` was compiled with `g++ -g -O0 -lz` together with a driver that, inside a block scope, creates a `ZlibStringCompressor`, compresses a
1,000,000-byte string (`std::string(1000000,'a')` → 4,384 bytes), inflates it back (1,000,000 bytes), and lets the object go out of scope. `valgrind --leak-check=full` reports
`2,002,024 bytes in 1 blocks are definitely lost`, allocated by `ZlibStringCompressor::setBufferSize` ([`ZlibStringCompressor.cpp:29`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/ZlibStringCompressor.cpp#L29)) called from `compress()` ([`ZlibStringCompressor.cpp:86`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/ZlibStringCompressor.cpp#L86)), i.e. exactly
`2 × (1,000,000 + 1,000 + 12)`.

> [!gap] Solver leaks (1) and (2) not run
> (1) and (2) are established by reading the code (a pointer assigned twice with no intervening `delete`; arrays with no matching `delete[]`). Running a PETSc-linked build under Valgrind
> to quantify them was not done, and the node count of a real CVS mesh was not measured.

## Root Cause

(1) A leftover allocation before switching to `VecGetArray` (the pointer is both the destination of `new` and of `VecGetArray`). (2) Missing `delete[]` calls that the older `setup_load()` has.
(3) A resource-owning class without destructor: `m_buffer` is allocated with `new Bytef[]` and only ever freed by the next `setBufferSize()` (which also uses the wrong `delete`, [[00208]]).

## Impact

- **Peak memory, not wrong results:** the compressor leak is of the order of the largest uncompressed transform times 1–2. For a 256³ delta field with three float frames plus a 1-byte mask
  (≈ 218 MB uncompressed, assumption: layout of `DeltaTransform3d::convert_to_delta`, [`fem_elastic/morph.cpp:604-653`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L604-L653)) that is roughly 220–440 MB per `compressor` object (estimate, not measured). The 2018 commit message reports a 27 G → 12 G drop for `createMorph` after reducing the number of instances.
- **Repetition:** one leaked buffer per `VolumeMorph::save` call (so one per FEM step with `surf2vol -dbg_output`, see [[00202]]) and per `.tm3d` load; the solver leaks repeat per FEM step and per untangler crop.
- **Severity 2 (low):** correct output; cost is memory/job-scheduling headroom in a pipeline that is already memory-hungry. A reviewer who weights `exportGcam`'s peak memory in the [[mri_cvs_register]] default path could argue for 3.

## Recommended Fix

```diff
--- a/fem_elastic/solver.h
+++ b/fem_elastic/solver.h
 TSolver<Cstr,n>::comm_solution()
 {
   PetscErrorCode ierr;

   int no_eqs = m_pmesh->get_no_nodes() *n;

-  PetscScalar *pdelta = new PetscScalar[no_eqs];
+  PetscScalar *pdelta = NULL;
   ierr = VecGetArray(m_delta, &pdelta);
   CHKERRQ(ierr);
@@ setup_load_sym()
   ierr = ISDestroy(is);
   CHKERRQ(ierr);

+  delete[] indices;
+  delete[] values;
+  delete[] rhsValues;
+
   return 0;
```

(`rhsValues` is not used after `VecSetValues` at [`fem_elastic/solver.h:1107-1108`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/solver.h#L1107-L1108); `indices` is copied by `ISCreateGeneral` in the PETSc API used here — verify against the PETSc version in use before freeing it before `ISDestroy`; the diff frees it after.)

```diff
--- a/fem_elastic/ZlibStringCompressor.h
+++ b/fem_elastic/ZlibStringCompressor.h
 public:
   ZlibStringCompressor(unsigned long bufferSize=0);
+  ~ZlibStringCompressor();
+  ZlibStringCompressor(const ZlibStringCompressor&) = delete;
+  ZlibStringCompressor& operator=(const ZlibStringCompressor&) = delete;
--- a/fem_elastic/ZlibStringCompressor.cpp
+++ b/fem_elastic/ZlibStringCompressor.cpp
+ZlibStringCompressor::~ZlibStringCompressor()
+{
+  delete[] m_buffer;
+}
```

A regression test is the Valgrind driver above (expect zero definitely-lost bytes); for the solver, a Valgrind run of a tiny `surf2vol` problem.

## Workarounds (If Any)

None for the leak itself. Memory pressure can be reduced only by running fewer simultaneous `exportGcam` / `createMorph` / `surf2vol` jobs per node, or by raising memory limits. Avoid `surf2vol -dbg_output` on large problems (one extra `save()` per step).

## Provenance and Discovery

- **Discovered:** 2026-10-19 by agent, during an audit of the `fem_elastic` core. The leak history (commits `febf7c3f07`, `9fefeefc69` and the three source comments) was found with read-only `git log`/`git show` on the source tree.
- **Evidence:** Derived from source analysis of `fem_elastic/solver.h`, `ZlibStringCompressor.*` and `morph.cpp` at `d932c45b79`; (3) confirmed by Valgrind on the unmodified compressor.
  `git log -L` on the allocation lines shows only the 2008-03-14 import commit (`4b881dc775`).
