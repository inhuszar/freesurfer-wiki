# [severity-3] [bug-00087] `GLMtestFFx` leaks intermediate matrices on every contrast iteration

> [!bug] Synopsis
> The fixed-effects test path
> ([`utils/fsglm.cpp:673-728`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/fsglm.cpp#L673-L728))
> declares `CiXtXXs` and `CiXtXXst` as
> per-iteration scratch matrices but allocates
> them with `NULL` as the destination on **every**
> pass through the contrast loop:
>
> ```cpp
> for (n = 0; n < glm->ncontrasts; n++) {
>   ...
>   CiXtXXs  = MatrixMultiplyD(glm->CiXtX[n], Xst, NULL);   /* :703 — fresh alloc */
>   CiXtXXst = MatrixTranspose(CiXtXXs, NULL);              /* :704 — fresh alloc */
>   glm->gCVM[n] = MatrixMultiplyD(CiXtXXs, CiXtXXst, glm->gCVM[n]);
>   ...
> }
>
> MatrixFree(&Xs);
> MatrixFree(&Xst);
> MatrixFree(&CiXtXXs);                                     /* :724 — frees only last iter */
> MatrixFree(&CiXtXXst);                                    /* :725 — frees only last iter */
> ```
>
> The single post-loop `MatrixFree` only releases
> the **most recent** allocation. Each previous
> iteration's matrix is leaked.

## Affected Artefacts

- **Tool:** [[mri_glmfit]] when invoked with
  fixed-effects flags
  (`--yffxvar`, `--ffxdof`, `--ffxdofdat`,
  see [`mri_glmfit/mri_glmfit.cpp:50-53`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_glmfit/mri_glmfit.cpp#L50-L53)).
- **Pipeline stage(s):** none in default
  `recon-all`. Reachable via `MRIglmTest`
  ([`utils/fmriutils.cpp:1253`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/fmriutils.cpp#L1253))
  per voxel and `MRIglmFitAndTest`
  ([`utils/fmriutils.cpp:1034`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/fmriutils.cpp#L1034)).
- **Triggering configuration:** flag-gated
  (`--yffxvar`); fires once per voxel × per
  contrast inside the GLM test loop.
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION` (commit `d932c45b79`).

## Detailed Description

```cpp
/* utils/fsglm.cpp:673-728 */
int GLMtestFFx(GLMMAT *glm)
{
  ...
  MATRIX *Xs = NULL, *Xst = NULL, *CiXtXXs = NULL, *CiXtXXst = NULL;
  ...
  Xs = MatrixAlloc(glm->X->rows, glm->X->cols, MATRIX_REAL);   /* :689 — outer alloc */
  ...
  Xst = MatrixTranspose(Xs, NULL);                              /* :694 — outer alloc */

  for (n = 0; n < glm->ncontrasts; n++) {
    ...
    CiXtXXs  = MatrixMultiplyD(glm->CiXtX[n], Xst, NULL);       /* :703 — INNER alloc */
    CiXtXXst = MatrixTranspose(CiXtXXs, NULL);                  /* :704 — INNER alloc */
    glm->gCVM[n] = MatrixMultiplyD(CiXtXXs, CiXtXXst, glm->gCVM[n]);
    ...
  }

  MatrixFree(&Xs);                                              /* OK — single allocation */
  MatrixFree(&Xst);                                             /* OK — single allocation */
  MatrixFree(&CiXtXXs);                                         /* :724 — leaks N-1 prior iters */
  MatrixFree(&CiXtXXst);                                        /* :725 — leaks N-1 prior iters */

  return (0);
}
```

`Xs` and `Xst` are allocated **outside** the loop
and so the post-loop free is correct for them.
`CiXtXXs` and `CiXtXXst` are allocated
**inside** the loop, with the destination
parameter set to `NULL` (which forces
`MatrixMultiplyD` and `MatrixTranspose` to
allocate fresh storage). The pointer variables
are then overwritten on the next iteration; the
previous iteration's memory has no remaining
reference and is leaked.

The fix is either:

1. Pass the existing pointer as the destination
   (`MatrixMultiplyD(glm->CiXtX[n], Xst, CiXtXXs)`),
   so `MatrixMultiplyD` reuses storage, **or**
2. Free `CiXtXXs` and `CiXtXXst` at the end of
   each iteration body.

Option 1 is the existing convention in
[`utils/fsglm.cpp`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/fsglm.cpp)
(see e.g. `glm->Xt`, `glm->XtX`, `glm->iXtX` —
all reused across calls).

### Quantitative impact

Per voxel call, with `ncontrasts == K`, the
function leaks `2 × (K − 1)` matrices. Each
matrix is `K × X->rows` (for `CiXtXXs`) or
`X->rows × K` (for its transpose); for a typical
fMRI design with `X->rows ≈ 200` and `K = 2`
that is roughly `2 × 200 × 8 = 3200` bytes per
voxel.

`MRIglmTest` is per-voxel: a 64×64×40 fMRI volume
yields ~164 K voxels × 3 KB ≈ 500 MB leaked per
`mri_glmfit --yffxvar` invocation with two
contrasts. With more contrasts the leak scales
linearly. The process exits after `mri_glmfit`
finishes, so the OS reclaims; but for tools
that wrap `mri_glmfit` in-process, or for
permutation/simulation harnesses, the leak
accumulates across runs.

## Root Cause

Inconsistent use of the
"`MatrixMultiplyD(A, B, dst)` reuses `dst`"
convention. `Xs` and `Xst` are correctly
allocated once outside the loop; the inner
`CiXtXXs`/`CiXtXXst` were probably written
with the "reuse" intent but the destination
argument was left at `NULL`, defeating the
optimisation and turning the slot into a
per-iteration fresh allocation.

## Impact

- **Memory:** linear in `(ncontrasts − 1) ×
  nvoxels`. Bounded by process exit; cumulative
  for in-process harnesses.
- **Output correctness:** unaffected.
- **Severity:** 3 — gated by `--yffxvar`; not
  default `recon-all`. Active leak with
  measurable cost on realistic inputs.

## Recommended Fix

```diff
--- a/utils/fsglm.cpp
+++ b/utils/fsglm.cpp
@@ -700,8 +700,8 @@ int GLMtestFFx(GLMMAT *glm)
     glm->gammat[n] = MatrixTranspose(glm->gamma[n], glm->gammat[n]);
 
-    CiXtXXs = MatrixMultiplyD(glm->CiXtX[n], Xst, NULL);
-    CiXtXXst = MatrixTranspose(CiXtXXs, NULL);
+    CiXtXXs  = MatrixMultiplyD(glm->CiXtX[n], Xst, CiXtXXs);
+    CiXtXXst = MatrixTranspose(CiXtXXs, CiXtXXst);
     glm->gCVM[n] = MatrixMultiplyD(CiXtXXs, CiXtXXst, glm->gCVM[n]);
```

The first iteration with `CiXtXXs == NULL`
allocates as before; subsequent iterations
reuse the storage if the contrast shape is
unchanged (which it is — `CiXtX[n]` has the
same column count as `glm->iXtX`'s rows for
every `n`).

If contrast shapes can vary across `n`, the
matching shape check inside `MatrixMultiplyD`
will already free + realloc as needed.

## Workarounds

For long-running harnesses, fork a child per
`mri_glmfit` invocation so the leak is
reclaimed at child exit.
