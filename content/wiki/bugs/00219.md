# [severity-3] [bug-00219] `applyMorph` — per-item `vol` interpolation is applied globally; last item wins; unknown strings ignored

> [!bug] Synopsis
> Each `vol <in> <out> <interp>` item carries its own interpolation keyword
> (`nearest`/`linear`), but `main()` copies the keyword into the **shared**
> `VolumeMorph::m_interpolationType` while it is still building the filter
> list. All filters run afterwards, so every volume is resampled with the
> keyword of the last recognised item. A command such as
> `vol seg.mgz a.mgz nearest vol t1.mgz b.mgz linear` therefore resamples
> the label volume trilinearly (inventing non-label values). Keywords other
> than `linear` and `nearest` are silently ignored (the previous or the
> default value stays in force). The per-filter member
> `VolumeFilter::m_interpolationType` exists but is never used.

## Affected Artefacts

- **Tool(s):** [[applyMorph]]
- **Pipeline stage(s):** _N/A_ (the only in-tree use, `applyMorph ... vol ... nearest` in `mri_cvs_register`, is commented out since 2024-03 and has one `vol` item per call)
- **FreeSurfer version(s):** confirmed in 8.2.0; the code dates from the original 2008 import (commit `4b881dc775f`)
- **Platforms:** all
- **Triggering configuration:** an `applyMorph` call with two or more `vol` items that request different interpolations, or with a `vol` interpolation keyword that is neither `linear` nor `nearest`.

## Detailed Description

`DataItem` has an `interpolation` string that the parser fills for `vol`
items from the third operand. In `main()`, the loop that creates one filter
object per item reads `cit->interpolation` and, if it is `"linear"` or
`"nearest"`, assigns `SAMPLE_TRILINEAR` or `SAMPLE_NEAREST` to
`pmorph->m_interpolationType`. `pmorph` is the single `VolumeMorph` shared by
all filters (it is also what `VolumeMorph::apply_transforms` consults when it
samples the input volume). The assignment therefore overwrites the previous
one on every iteration, and by the time the filters are executed (a second
loop) only the value written last remains. `VolumeFilter` has an
`m_interpolationType` member that was evidently meant to carry the
per-item value, but nothing ever assigns or reads it.

Items that are not volumes have an empty `interpolation` string and leave the
shared value alone, as do volume items with an unrecognised keyword: there is
no validation and no error. The constructor default is trilinear.

### Expected Behaviour

Each `vol` item is resampled with the interpolation named in its own third
operand. An unknown keyword is a command-line error.

### Observed Behaviour

The interpolation of the last `vol` item with a recognised keyword is used for
all volume items; unknown keywords are ignored without a message (rc 0).

### Reproducer

Synthetic: a 32^3 volume `ramp.mgz` with value `10 * x` along voxel axis 0, a
template `tmpl.mgz` (32^3), and a `.tm3d` holding an affine `+0.5` voxel
x-translation (`half.tm3d`, geometries stored). For a half-voxel shift
`nearest` rounds up (`out[x] = in[x+1]`) and `linear` gives the midpoint
(`out[x] = in[x] + 5`), so the two are easy to distinguish in the first
voxels. Output paths are absolute.

```bash
applyMorph --template tmpl.mgz --transform half.tm3d \
    vol ramp.mgz <W>/r_nn_alone.mgz nearest
applyMorph --template tmpl.mgz --transform half.tm3d \
    vol ramp.mgz <W>/r_lin_alone.mgz linear
# two items, different keywords, both orders
applyMorph --template tmpl.mgz --transform half.tm3d \
    vol ramp.mgz <W>/r_first_nn.mgz nearest   vol ramp.mgz <W>/r_second_lin.mgz linear
applyMorph --template tmpl.mgz --transform half.tm3d \
    vol ramp.mgz <W>/r_first_lin.mgz linear   vol ramp.mgz <W>/r_second_nn.mgz nearest
# unknown keyword: after a nearest item, and on its own
applyMorph --template tmpl.mgz --transform half.tm3d \
    vol ramp.mgz <W>/r_a.mgz nearest   vol ramp.mgz <W>/r_b.mgz cubic
applyMorph --template tmpl.mgz --transform half.tm3d \
    vol ramp.mgz <W>/r_c.mgz cubic
```

Values of output voxels `x = 0..4` along axis 0 (installed 8.2.0 binary, every
run exits 0):

| Output | `out[0..4]` | Interpolation actually used |
|--------|-------------|-----------------------------|
| `r_nn_alone` (nearest) | `10 20 30 40 50` | nearest, as requested |
| `r_lin_alone` (linear) | `5 15 25 35 45` | linear, as requested |
| `r_first_nn` (requested nearest) | `5 15 25 35 45` | **linear** (last item wins) |
| `r_second_lin` (requested linear) | `5 15 25 35 45` | linear |
| `r_first_lin` (requested linear) | `10 20 30 40 50` | **nearest** (last item wins) |
| `r_second_nn` (requested nearest) | `10 20 30 40 50` | nearest |
| `r_a`, `r_b` (nearest, then `cubic`) | `10 20 30 40 50` | nearest: the unknown keyword leaves the previous value |
| `r_c` (`cubic` alone) | `5 15 25 35 45` | trilinear default: keyword ignored, no error |

For a label volume the first case is the damaging one: a segmentation
requested with `nearest` is interpolated trilinearly if a later item asks for
`linear` (for integer-typed volumes `MRIsetVoxVal` then rounds the blended
value to the nearest integer, which can create labels that are absent from
the input).

## Root Cause

The interpolation choice is stored in the wrong object and at the wrong
time. It belongs to the filter (`VolumeFilter::m_interpolationType`, which is
declared but never written) and should be applied when that filter executes;
instead it is written to the shared morph during setup, where only the
last assignment survives. The comparison chain at
[`fem_elastic/fapplyMorph.cpp:249-252`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fapplyMorph.cpp#L249-L252) has no `else`, so any other string is dropped silently.

## Impact

- **Silent wrong resampling of volumes** in multi-item calls with different
  keywords (the class of usage the data-item grammar invites: several
  volumes of one subject in one call, for example a label volume with
  `nearest` and an intensity volume with `linear`). Label volumes can be
  blended, intensity volumes can be snapped to voxels.
- **Severity 3, not 2 or 4.** Single-`vol` invocations, and calls where all
  keywords agree, are unaffected, so the defect is gated behind a specific
  option combination (severity 3). It is not rated 4 because no default
  pipeline or in-tree script uses multi-item calls (`mri_cvs_register`'s
  `applyMorph` lines are commented out and replaced by `mri_vol2vol`).
- Unknown keywords (a typo such as `nearset`, or the natural `cubic`) do not
  fail: the user gets trilinear resampling without notice.

## Recommended Fix

Store the interpolation per filter, validate it at parse time, and install it
when the filter runs:

```diff
@@ in IoParams::parse, vol branch @@
       if ( ++cit == container.end() )
         throw " Incomplete data item";
       item.interpolation = *cit;
+      if ( item.interpolation != "linear" && item.interpolation != "nearest" )
+        throw " Unknown interpolation (expected linear or nearest)";
 
       items.push_back(item);
```

```diff
@@ in main(), filter construction @@
     case DataItem::volume :
       {
-        p = std::shared_ptr<AbstractFilter>(new VolumeFilter);
+        std::shared_ptr<VolumeFilter> pTmp(new VolumeFilter);
+        pTmp->m_interpolationType =
+          ( cit->interpolation == "nearest" ) ? SAMPLE_NEAREST : SAMPLE_TRILINEAR;
+        p = pTmp;
       }
       break;
@@
-    if ( cit->interpolation=="linear" )
-      pmorph->m_interpolationType = SAMPLE_TRILINEAR;
-    else if ( cit->interpolation=="nearest")
-      pmorph->m_interpolationType = SAMPLE_NEAREST;
-
     p->pmorph = pmorph;
```

```diff
@@ in VolumeFilter::Execute @@

```

A regression test is the two-item experiment above in both orders: each output
must equal the corresponding single-item run. (Setting the interpolation
inside `VolumeFilter::Execute` also makes the result independent of any
other item, since the morph's member is then written immediately before use.)

## Workarounds (If Any)

Use one interpolation keyword per `applyMorph` call (one call per distinct
keyword), exactly as the tool page advises, and spell the keyword exactly
`linear` or `nearest`.
