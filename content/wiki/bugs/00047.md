# [severity-3] [bug-00047] `MRIvol2VolR` — per-voxel matrix leaks plus an incomplete interp-code switch

> [!bug] Synopsis
> `MRIvol2VolR`
> ([`utils/mri2.cpp:1053-1180`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri2.cpp#L1053-L1180))
> resamples a 3-frame eigenvector or 9-frame tensor
> volume *and* re-orients each tensor / vector by a
> rotation `RRot`. Inside the per-voxel loop, every
> rotation step calls `MatrixMultiply(..., NULL)` and
> assigns the result to `RotVector` /
> `RotTensor` — leaking the previous matrix on every
> iteration. For a 256³ volume the leak is ~16 M
> matrices. The same function also has dead-store
> issues at construction
> ([`:1066-1069`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri2.cpp#L1066-L1069))
> where `RRotT` is allocated as a 3×3 identity and then
> immediately re-assigned to `MatrixTranspose(RRot,
> NULL)`, leaking the identity. Finally, the
> non-trilinear interp switch
> ([`:1126-1135`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri2.cpp#L1126-L1135))
> only enumerates `SAMPLE_NEAREST` and `SAMPLE_SINC`;
> `SAMPLE_CUBIC_BSPLINE` is not handled and leaves
> `valvect[f]` uninitialised.

## Affected Artefacts

- **Sole caller in-tree:**
  [`freeview/FSVolume.cpp:1895`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/freeview/FSVolume.cpp#L1895)
  for FreeView's tensor / eigvec rotation display.
- **Pipeline stage(s):** none in `recon-all`. The
  function is FreeView's reorient-on-resample helper.
- **Triggering configuration:** loading a 3- or
  9-frame tensor / DTI eigenvector volume in FreeView
  with a non-identity orientation transform.
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION`.

## Detailed Description

```cpp
RRotT     = MatrixIdentity(3, NULL);          // :1066 — leaked
Tensor    = MatrixIdentity(3, NULL);          // :1067
RotTensor = MatrixIdentity(3, NULL);          // :1068 — overwritten at :1158
RRotT     = MatrixTranspose(RRot, NULL);      // :1069 — leaks the identity from :1066
```

```cpp
for (ct = 0; ct < targ->width; ct++) {
  for (rt = 0; rt < targ->height; rt++) {
    for (st = 0; st < targ->depth; st++) {
      …
      if (nframes == 3) {
        RotVector = MatrixMultiply(RRot, Vector, NULL);    // :1145 — new alloc per voxel
      } else {                                             // nframes == 9
        RotTensor = MatrixMultiply(RRot,                   // :1158 — new alloc per voxel
                       MatrixMultiply(Tensor, RRotT, NULL),// inner alloc also leaked
                       NULL);
      }
    }
  }
}
```

`RotVector` was allocated at `:1071`; the first per-voxel
`MatrixMultiply` re-assigns it (leaking the original).
Every subsequent iteration leaks the *previous* result.
The 9-frame branch additionally leaks the result of
`MatrixMultiply(Tensor, RRotT, NULL)` because the result
is consumed by the outer multiply and then discarded
without a free.

The interp switch:

```cpp
if (InterpCode == SAMPLE_TRILINEAR)            // :1122 — handled before switch
  MRIsampleSeqVolume(src, fcs, frs, fss, valvect, 0, src->nframes - 1);
else {
  for (f = 0; f < src->nframes; f++) {
    switch (InterpCode) {
      case SAMPLE_NEAREST: ...                  // :1127
      case SAMPLE_SINC:    ...                  // :1130
    }
  }
}
```

There is no `default` case; if a caller passes
`SAMPLE_CUBIC` or `SAMPLE_CUBIC_BSPLINE`, the for-loop
runs without writing `valvect[f]` and the rotation
operates on uninitialised values.

## Root Cause

The per-voxel `MatrixMultiply(..., NULL)` calls were
written without re-using the pre-allocated
`RotVector` / `RotTensor` buffers. The non-rotating
sister `MRIvol2Vol` does not have this pattern. The
identity-matrix leaks at `:1066-1069` look like
copy-paste boilerplate that was never trimmed once
`MatrixTranspose` was inserted.

## Impact

- **FreeView memory pressure** when displaying tensor /
  DTI eigvec volumes with a non-identity rotation. For
  a 256³ × 9-frame tensor volume the per-voxel leak is
  two 3×3 matrices per iteration ≈ 16 M × 2 × ~150 B ≈
  4–5 GB. The leak is bounded by virtual-memory limits,
  not algorithmically.
- **Uninitialised reads** when an upstream caller asks
  for `SAMPLE_CUBIC_BSPLINE`. No in-tree caller does so;
  the defect is latent for the current FreeView use.
- **No effect on default `recon-all`** — `MRIvol2VolR`
  is not on any recon-all path.

## Workarounds

- For tensor / DTI display in FreeView, restart FreeView
  periodically when working with rotated tensor volumes
  on large grids.

- **Discovered:** 2026-04-30 by agent (audit pass over

  in the same shape and is leak-free; the rotation
  variant fails to apply the same pattern.
