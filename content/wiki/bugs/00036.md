# [severity-2] [bug-00036] MRIdilateSegmentation infinite loop for nDils == 0 (and any nDils < −1)

> [!bug] Synopsis
> `MRIdilateSegmentation` exposes three documented modes via
> the `nDils` parameter: `nDils > 0` (apply N dilations),
> `nDils == -1` (iterate until convergence), and an
> implicit-but-not-handled "no dilation" case (`nDils == 0`).
> The progressive-dilation loop is written
> `while (n != 1) { recurse; n--; }`. For `nDils == 0` the
> condition `0 != 1` is true, the loop recurses with `n = 1`,
> then on return `n--` makes `n = -1`, then `n != 1` is still
> true → loop runs forever. Same hang for any `nDils < -1`.
> Fires on `mri_convert --dil-seg 0` and on any future caller
> that uses `0` to mean "skip the dilation step".

  Also any in-tree caller that uses `MRIdilateSegmentation`

## Detailed Description

### Expected Behaviour

The function's docstring at
[`utils/mriset.cpp:1059-1064`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mriset.cpp#L1059-L1064)
documents `nDils > 0` and the special `nDils == -1` ("iterate
until convergence") modes. The natural reader expectation for
`nDils == 0` is "no dilation — return a copy of the input".
Negative values other than `-1` are not documented; the
behaviour should at minimum be deterministic (either error or
treated as zero).

### Observed Behaviour

The progressive-dilation outer loop at
[`utils/mriset.cpp:1107-1111`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mriset.cpp#L1107-L1111):

```cpp
// If nDils > 1, loop through progressive dilations
n = nDils;
while (n != 1) {
  out = MRIdilateSegmentation(seg2, out, 1, mask, maskframe, maskthresh, pnchanges);
  seg2 = MRIcopy(out, seg2);
  n--;
}
```

is written for `nDils >= 1` (the comment says `> 1`, but `n =
1` exits the loop and proceeds to a single in-line dilation
after — so the function does the right thing for `nDils == 1`
too).

For `nDils == 0`:

| Iteration | n at start | n != 1? | recurse → n at end |
|----------:|-----------:|:-------:|---------------------:|
|         1 |          0 |   yes   |                  −1 |
|         2 |         −1 |   yes   |                  −2 |
|         3 |         −2 |   yes   |                  −3 |
|       ... |      ...   |   ...   |              ...    |

`n` decreases without bound; `n != 1` is always true. The
recursive call with `nDils == 1` succeeds and applies one
dilation each time, so the program produces correct output but
never terminates and consumes unbounded memory.

For `nDils < -1` (e.g., `-2`): same structure. `n = -2 → -3 →
-4 → …`, never hits 1. The `nDils == -1` special path at
[`:1091`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mriset.cpp#L1091)
catches only the exact `-1` value, so the bug fires for any
other negative input.

### Reproducer

```bash
# "Zero dilation" is a natural way to express "skip dilation"
mri_convert --dil-seg 0 --dil-seg-mask brainmask.mgz aseg.mgz aseg_dilated.mgz
# Expected: copy aseg.mgz to aseg_dilated.mgz, no dilation.
# Observed: process hangs, slowly consuming memory as it
#           recurses one dilation at a time forever.
```

## Root Cause

The decrement-toward-1 idiom assumes `nDils > 0`. The
`nDils == 1` boundary is correct because the loop exits
without recursing. The `nDils == -1` case is handled
explicitly by the if at line 1091. But `nDils == 0` and
`nDils < -1` fall through to the buggy decrement loop.

## Impact

- **`mri_convert --dil-seg 0`**: hangs. The user intends "no
  dilation" (a natural reading) and gets an unbounded
  recursive loop.
- **`mri_convert --dil-seg -2`** (or any negative value other
  than `-1`): same hang.
- **External callers** of `MRIdilateSegmentation` from
  `libutils` are exposed to the same trap. Any wrapper that
  passes a user-controlled count with `0` as a "skip" sentinel
  hangs.
- **Latent for default [[wiki/pipelines/recon-all|recon-all]]** — `recon-all` does not
  invoke `mri_convert --dil-seg`. Fires only when the user
  explicitly chooses the dilation step with `nDils == 0` or
  any `nDils < -1`.

## Recommended Fix

```diff
   // If nDils == -1, this will loop through progressive dilations
   // until no changes are made.
   if (nDils == -1) { ... return (out); }

+  // nDils == 0 means "no dilation": copy and return early.
+  if (nDils <= 0) {
+    if (nDils < 0) {
+      printf("ERROR: MRIdilateSegmentation: invalid nDils = %d\n", nDils);
+      MRIfree(&seg2);
+      return (NULL);
+    }
+    *pnchanges = 0;
+    MRIfree(&seg2);
+    return (out);
+  }
+
   // If nDils > 1, loop through progressive dilations
   n = nDils;
-  while (n != 1) {
+  while (n > 1) {
     out = MRIdilateSegmentation(seg2, out, 1, mask, maskframe, maskthresh, pnchanges);
     seg2 = MRIcopy(out, seg2);
     n--;
   }
```

Two changes: a guarded early-return for `nDils <= 0` (with an
explicit error for the `< -1` case to surface user mistakes
that the current code silently hangs on), and a tighter loop
condition `n > 1` so any future regression that reintroduces
a negative `n` does not hang.

### Alternative Fixes Considered

- **Treat `nDils <= 0` as a no-op silently.** Less helpful for
  diagnosing user errors that pass negative values
  unintentionally; the explicit error message is preferred.
- **Range-check `--dil-seg N` at the CLI layer in
  `mri_convert`.** Belt-and-braces. Both fixes can coexist.

## Workarounds (If Any)

- For "no dilation": skip the `--dil-seg` flag entirely.
- For an explicit "no-op" with the rest of the
  `--dil-seg-mask` plumbing, pass `--dil-seg 1` and accept
  one trivial dilation (probably not what the user wanted, so
  this is not a real workaround).

## Confidence and Gaps

> [!gap] Memory growth before the user notices the hang
> Each loop iteration creates and reassigns `out` and `seg2`
> via `MRIcopy`. Whether the heap stays bounded depends on
> whether each iteration reuses the existing buffer (it does,
> per `MRIcopy`'s in/out semantics) or reallocates. In the
> bounded-heap case the user observes a hang with constant
> memory; in the realloc-per-iteration case the user
> additionally OOMs.
