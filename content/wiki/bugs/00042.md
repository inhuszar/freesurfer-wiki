# GTMrbv allocates the per-segment hit-counter inside the frame loop — `rbvsegmean` QA output is divided by zero on every frame

> [!bug] Synopsis
> `GTMrbv` is the region-based-voxelwise (RBV) PVC step run
> by `mri_gtmpvc --rbv`. It produces two main outputs: the
> per-voxel RBV-corrected PET volume (`gtm->rbv`, written
> downstream as `rbv.nii.gz`) *and* a QA volume
> `gtm->rbvsegmean` of size `nsegs × 1 × 1 × nframes`
> containing the mean RBV-corrected PET signal in each
> segment for each frame. The mean computation requires a
> per-segment hit count, stored in a `MATRIX *nhits`. The
> hit-count is allocated *inside* the per-frame loop (line
> 1321), and the increment is gated by `if (f == 0)
> nhits->rptr[…]++` (line 1336). On every frame iteration,
> the previous-frame's `nhits` matrix is leaked and a fresh
> all-zeros matrix takes its place. For frames `f > 0`,
> `nhits` is never incremented (since the gate is
> `f == 0`). After the frame loop ends, only the final
> frame's `nhits` (all zeros) survives. The
> normalisation pass at line 1366 then divides every
> `rbvsegmean` entry — every segment, every frame — by zero,
> producing `Inf` (for non-zero accumulated means) or `NaN`
> (for accumulated zeros) entries throughout the output.
> Sister function `GTMrbv0`
> ([`:1488`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/gtm.cpp#L1488))
> has the correct pattern: `nhits` allocated *once* before
> the voxel loop, incremented for every voxel of every
> segment, and used for division at the end.

## Detailed Description

### Expected Behaviour

`gtm->rbvsegmean` is the per-segment, per-frame mean of the
RBV-corrected PET signal — used as a QA summary alongside
the voxelwise output. The mean is `sum(val) / nhits` where
`val` is the RBV-corrected signal and `nhits` is the count
of voxels assigned to each segment. The reference
implementation `GTMrbv0` shows the intended pattern: `nhits`
is allocated *once*, incremented for every contributing
voxel (regardless of frame), and divided into the
accumulated sum at the end.

### Observed Behaviour

The buggy loop ([`utils/gtm.cpp:1287-1352`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/gtm.cpp#L1287-L1352)):

```cpp
for (f = 0; f < gtm->nframes; f++) {
  /* … per-frame setup, smoothing, sampling … */
  nhits = MatrixAlloc(gtm->beta->rows, 1, MATRIX_REAL);   /* (a) alloc INSIDE frame loop */
  for (c = 0; c < gtm->rbvseg->width; c++) {
    for (r = 0; r < gtm->rbvseg->height; r++) {
      for (s = 0; s < gtm->rbvseg->depth; s++) {
        /* … figure out segid → nthseg … */
        if (f == 0) nhits->rptr[nthseg + 1][1]++;            /* (b) increment ONLY when f==0 */

        /* … compute val = v * vhat0 / (vhat + FLT_EPSILON) … */
        v2 = MRIgetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f);
        MRIsetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f, v2 + val);  /* accumulate sum */
      }
    }
  }
}                                                            /* (c) end of frame loop */

/* track seg means for QA */
for (nthseg = 0; nthseg < gtm->nsegs; nthseg++) {
  for (f = 0; f < gtm->nframes; f++) {
    val = MRIgetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f)
          / nhits->rptr[nthseg + 1][1];                       /* (d) divide by 0 */
    MRIsetVoxVal(gtm->rbvsegmean, nthseg, 0, 0, f, val);
  }
}
MatrixFree(&nhits);                                          /* (e) frees the LAST-frame nhits */
```

Three independent failures cooperate:

**(a)** `nhits = MatrixAlloc(…)` is *inside* the frame
loop. Each iteration allocates a fresh zero-initialised
matrix and silently drops the previous pointer. Memory is
leaked at a rate of `nframes − 1` matrices per call (small,
but real).

**(b)** The increment `if (f == 0) nhits->rptr[…]++` only
fires on the very first frame. For `f == 0`, the freshly-
allocated matrix is populated with the per-segment counts;
for `f >= 1`, the freshly-allocated matrix is never
incremented and remains all zero.

**(c)** After the frame loop ends, `nhits` points at the
final frame's all-zero matrix (the `f = nframes − 1`
allocation, which was never incremented). All previous
populated `nhits` matrices have been leaked.

**(d)** The post-loop division pass at
[`:1366`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/gtm.cpp#L1366)
divides the accumulated `rbvsegmean[seg, 0, 0, frame]` by
`nhits[seg+1][1] = 0`. Every entry in `rbvsegmean` becomes
`±Inf` (for accumulated sums whose magnitude is greater
than `0`) or `NaN` (for sums of exactly zero — these can
arise for empty segments, but most real segments have
non-zero accumulated sums and produce `Inf`).

**(e)** `MatrixFree(&nhits)` frees the surviving matrix, so
no use-after-free occurs after this point. (The leaked
earlier matrices remain leaked.)

The corrupted `gtm->rbvsegmean` is then written to disk by
`mri_gtmpvc`
([`mri_gtmpvc.cpp:1177`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_gtmpvc/mri_gtmpvc.cpp#L1177))
as the user-facing QA output `rbvsegmean.nii.gz` (or
`.mgz`).

## Root Cause

The `GTMrbv` rewrite (which the inline comment at
[`:1202`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/gtm.cpp#L1202)
identifies as a re-write of `GTMrbv0`) reordered the loop
nesting from
*"voxel-outside / frame-inside"* (`GTMrbv0`'s pattern) to
*"frame-outside / voxel-inside"* (the new pattern needed by
the per-frame smoothing of `yhatseg`). The hit-counter
allocation and increment were moved into the new outer
loop, but the increment was kept gated by `if (f == 0)`
(presumably to avoid double-counting), without realising
that the allocation was now also inside the loop and would
overwrite the `f == 0` counts on subsequent frames.

## Impact

- **`mri_gtmpvc --rbv` QA output `rbvsegmean.nii.gz` is
  corrupted on every frame.** The user-visible symptom is
  an `Inf`/`NaN`-valued QA volume that breaks any
  downstream tool that reads it (e.g. `mri_segstats --seg
  rbvsegmean.nii.gz`).
- **The voxelwise `rbv.nii.gz` output is *unaffected*** —
  the per-voxel RBV equation is computed correctly at
  [`:1341`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/gtm.cpp#L1341)
  (`val = v * vhat0 / (vhat + FLT_EPSILON)`) and written
  voxel-by-voxel to `gtm->rbv` independent of `nhits`. So
  the *primary* RBV PVC output is correct; only the
  per-segment-mean *QA companion* is wrong.
- **Downstream consumers that use `rbvsegmean` as an
  intermediate** would propagate the corruption. A grep
  shows `rbvsegmean` is only consumed by `mri_gtmpvc`
  itself (writing it to disk) and by `GTMrbv` /
  `GTMrbv0` (computing it); no other in-tree code reads
  it.
- **Memory leak**: `nframes − 1` matrices of size
  `(nsegs × 1)` are leaked per call. For a typical 100-
  frame dynamic PET with ~250 segments, that's
  `99 × 250 × sizeof(float) ≈ 100 KB` leaked per call —
  small.

## Recommended Fix

Move the `nhits` allocation *out of* the frame loop, and
remove the `if (f == 0)` gate (the increment should fire on
every voxel-of-every-frame visit but counts the same total
because the inner work is per-(c,r,s)-per-frame; we want
*per-segment voxel count*, which is identical across
frames, so we can equivalently keep the `if (f == 0)` gate
and just move the alloc + free out — that matches
`GTMrbv0`'s logic of incrementing once per voxel).

Two equivalent fixes:

```diff
   if (Gdiag_no > 0) PrintMemUsage(stdout);
+  /* Allocate hit-counter ONCE before the frame loop so the
+     f==0 increments survive into the post-loop normalisation. */
+  nhits = MatrixAlloc(gtm->beta->rows, 1, MATRIX_REAL);
   for (f = 0; f < gtm->nframes; f++) {
     /* … per-frame setup, smoothing, sampling … */
-    nhits = MatrixAlloc(gtm->beta->rows, 1, MATRIX_REAL);
     for (c = 0; c < gtm->rbvseg->width; c++) {
       for (r = 0; r < gtm->rbvseg->height; r++) {
         for (s = 0; s < gtm->rbvseg->depth; s++) {
           /* … */
           if (f == 0) nhits->rptr[nthseg + 1][1]++;
           /* … */
         }
       }
     }
   }
```

Either keep the `if (f == 0)` gate (cleanest match to the
existing logic — counts each voxel exactly once) or drop
the gate and divide the accumulated sum by
`nframes * nhits` instead (equivalent up to the
multiply-divide). The minimum diff is the alloc-out-of-loop
hunk above.

### Alternative Fixes Considered

- **Drop the `if (f == 0)` gate and keep alloc inside the
  loop.** Each frame would correctly populate its own
  `nhits`; freeing inside the loop and reallocating at the
  next iteration would still leak unless we also add a
  `MatrixFree(&nhits)` before the next allocation.
  Functionally correct but has the leak; the recommended
  fix is cleaner.
- **Adopt `GTMrbv0`'s loop-order entirely.** Larger
  rewrite. The rewrite was presumably done for memory
  reasons (smoothing one frame at a time avoids holding
  `nframes` synthesised volumes in memory simultaneously).
  Reverting would undo that benefit.

## Workarounds (If Any)

- Ignore the `rbvsegmean.nii.gz` output and compute
  per-segment means directly from `rbv.nii.gz` (which is
  correct) using
  `mri_segstats --seg rbv.nii.gz --i seg-template.nii.gz`.
- For batch QA pipelines that ingest `rbvsegmean.nii.gz`
  directly, add a `mri_concat --max --thresh-binary 1e30`
  or similar pre-pass to mask out `Inf` entries before
  group analysis.

## Confidence and Gaps

> [!gap] Whether the leak is observable in long sessions
> The per-call leak is small (`(nframes − 1) ×
> (nsegs × 1) × sizeof(float)`), but `mri_gtmpvc` is run
> once per subject and exits, so the leak is reaped on
> process termination. No long-lived process is affected.

> [!gap] Whether older versions of `GTMrbv` had the bug
> The "rewrite of `GTMrbv0`" comment suggests the bug was
> introduced by the rewrite. `GTMrbv0` (still in the file
> as the older, slower path) is correct, but is no longer
> called from `mri_gtmpvc`.
