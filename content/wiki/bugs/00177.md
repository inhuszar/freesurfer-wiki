# [severity-2] [bug-00177] inflate_subject3 — invalid tcsh `$p1=$!` never captures the backgrounded PID, so `wait $p1` is a no-op

> [!bug] Synopsis
> `inflate_subject3` launches the left-hemisphere inflation in the
> background (`inflate_subject-lh $1 &`), then tries to record its
> process ID with the line `$p1=$!`. This is not valid tcsh assignment
> syntax: tcsh expands `$p1` (an undefined variable) instead of setting
> it, so the PID in `$!` is never stored. The intended parallel join at
> the end, `wait $p1`, therefore receives no PID and degenerates into a
> bare `wait` for **all** background jobs (or errors on the undefined
> variable, depending on shell state). The script still happens to work
> because the only background job is the lh inflation, but the explicit
> PID-tracking the author wrote is dead, and the line itself is an
> error under `tcsh -f`.

## Affected Artefacts

- **Tool(s):** [[inflate_subject3]], which fans out to
  [[inflate_subject-lh]] (backgrounded) and [[inflate_subject-rh]]
  (foreground).
- **Pipeline stage(s):** _N/A_ — `inflate_subject3` is a standalone
  manual re-inflation wrapper run after white-matter edits; it is not
  invoked by [[wiki/pipelines/recon-all|recon-all]].
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all — purely a tcsh syntax error.
- **Triggering configuration:** fires on every invocation; the line
  `$p1=$!` is reached unconditionally after the backgrounded lh job.

## Detailed Description

The script's intent is a simple two-way fan-out / fan-in: run the
left-hemisphere inflation in the background, run the right-hemisphere
inflation in the foreground, then block until the backgrounded left
job also finishes before returning. The author captures the
background PID into `p1` and joins on it with `wait $p1`.

In tcsh, a scalar is assigned with `set var = value`. The token
`$p1=$!` is parsed as a **variable substitution** of `$p1` followed by
the literal `=$!` — it is not an assignment. Because `p1` has never
been `set`, tcsh raises `p1: Undefined variable.` Even if `p1` were
somehow defined, the line would expand to its value and attempt to
execute the result as a command, not store the PID.

### Expected Behaviour

```tcsh
inflate_subject-lh $1 &
set p1 = $!          # record the background PID
inflate_subject-rh $1
wait $p1             # join specifically on the lh job
```

`$!` holds the PID of the most recently backgrounded job; storing it
in `p1` lets `wait $p1` block on exactly that job.

### Observed Behaviour

The line as written is `$p1=$!`. Under `tcsh -f` (the script's
shebang is `#!/bin/tcsh -f`):

- `p1` is undefined, so the substitution `$p1` triggers
  `p1: Undefined variable.`
- `p1` is therefore still undefined when execution reaches `wait $p1`
  on the next-but-one line, so that line **also** references an
  undefined variable.

The net effect is that the explicit PID capture/join the author coded
never operates. Since the script backgrounds only one job
([[inflate_subject-lh]]), a correct implementation and the broken one
converge in outcome **only** because a bare `wait` would also block on
that single job — but the code as written does not even reach a clean
bare `wait`; it references the undefined `$p1`.

### Reproducer

```bash
# Demonstrate the tcsh parse error in isolation:
tcsh -f -c 'sleep 1 & 
$p1=$!
echo "p1 is now: <$p1>"
wait $p1'
# → prints: p1: Undefined variable.
```

The first reference to `$p1` (on the `$p1=$!` line) aborts with
`p1: Undefined variable.` before the value is ever printed, confirming
the assignment never happened.

## Root Cause

Missing `set` keyword and spaces. tcsh requires `set p1 = $!` to assign
the special variable `$!` (last background PID) to a user variable.
Writing `$p1=$!` substitutes the (undefined) value of `p1` instead of
assigning to it — a common C-shell vs. POSIX-shell assignment-syntax
confusion. In POSIX `sh`/`bash`, `p1=$!` is correct; in tcsh it is not.

## Impact

- **Latent / cosmetic in practice.** The script backgrounds exactly one
  job, so even a fully correct PID join would block on that same job.
  The user-visible end result (both hemispheres inflated before the
  script returns) is unaffected as long as `inflate_subject-rh`
  (foreground) takes at least as long as nothing else needs joining.
- **Diagnostic noise.** Under `tcsh -f` the undefined-variable
  reference prints `p1: Undefined variable.` to stderr, which can alarm
  users reading the log even though it is harmless here.
- **Fragility if extended.** If anyone later adds a second background
  job before the `wait`, the intended "join on the lh job specifically"
  semantics are silently absent, and the script would not reliably wait
  for the correct child. The bug is latent technical debt rather than a
  present correctness failure, hence severity 2.

## Recommended Fix

Use proper tcsh assignment syntax:

```diff
 inflate_subject-lh $1 &
-$p1=$!
+set p1 = $!
 inflate_subject-rh $1
 wait $p1
```

After the change, `p1` holds the lh job's PID and `wait $p1` blocks on
exactly that job.

### Alternative Fixes Considered

Because there is only one background job, the two PID-handling lines
could be reduced to a bare `wait` after the foreground rh call:

```tcsh
inflate_subject-lh $1 &
inflate_subject-rh $1
wait
```

This is simpler but discards the author's apparent intent to track the
specific PID; the `set p1 = $!` fix preserves that intent and is
robust if more background jobs are added later.

## Workarounds (If Any)

None required: the script still inflates both hemispheres. Users who
want to suppress the `p1: Undefined variable.` message can apply the
one-line fix locally.
