# [severity-2] [bug-00185] fs-topup — --no-multi-frame sets a dead variable (DoMultiFrameMean); flag is a silent no-op and multi-frame inputs are still averaged

> [!bug] Synopsis
> `fs-topup`'s `--no-multi-frame` flag is documented to "do not do anything
> to multi-frame inputs (requires --p)". Its case body sets a variable
> `DoMultiFrameMean = 0` that is **never read anywhere else in the script**.
> The variable that actually controls multi-frame handling is `MultiFrame`
> (default 1 = compute mean), and `--no-multi-frame` never touches it. So the
> flag is a silent no-op: `MultiFrame` stays at 1, and multi-frame field-map
> inputs are still mean-averaged (`mri_concat --mean`) exactly as without the
> flag — the opposite of what the user asked for.

## Affected Artefacts

- **Tool(s):** [[fs-topup]] — FreeSurfer frontend to FSL `topup` for
  susceptibility-distortion field-map estimation.
- **Pipeline stage(s):** _N/A_ — `fs-topup` is a standalone script (also
  called internally by [[fs-eddy]]). Not part of [[wiki/pipelines/recon-all|recon-all]].
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all — pure shell argument-parsing logic.
- **Triggering configuration:** invoking `fs-topup ... --no-multi-frame`
  with multi-frame input volumes (`nframes > 1`). The flag is accepted by the
  parser but has no effect.

## Detailed Description

`fs-topup` lets the user choose how multi-frame field-map volumes are reduced
to a single frame before being passed to FSL `topup`. The control variable is
`MultiFrame`, initialised to 1
([`scripts/fs-topup:31`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-topup#L31)),
where `1` = compute the mean across frames and `2` = take the first frame.
Three flags are meant to set it:

| Flag | Intended effect | Sets |
|------|-----------------|------|
| `--multi-frame-mean` | average frames | `MultiFrame = 1` ✓ |
| `--multi-frame-first` | take first frame | `MultiFrame = 2` ✓ |
| `--no-multi-frame` | leave frames untouched (needs `--p`) | should set `MultiFrame = 0` ✗ |

The per-volume reduction is gated by
[`scripts/fs-topup:140`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-topup#L140):
`if($nf > 1 && $MultiFrame) then` ... and then dispatches on `MultiFrame`
(1 → `mri_concat --mean`, 2 → `mri_convert --frame 0`). For
`--no-multi-frame` to mean "do nothing", `MultiFrame` must be **0** so that
this guard is false and the `else` branch (which keeps the volume as-is,
requiring a `--p` parameter file for the multi-frame data) is taken.

### Expected Behaviour

`--no-multi-frame` should set `MultiFrame = 0`. With `MultiFrame == 0`, the
guard `$nf > 1 && $MultiFrame` is false, so the volume is passed through
untouched and the script relies on the user-supplied `--p` acquisition
parameter file (as the help text says, "requires --p").

### Observed Behaviour

The case body sets an unrelated, never-read variable:

```tcsh
case "--no-multi-frame":
  set DoMultiFrameMean = 0
  breaksw
```

`DoMultiFrameMean` is assigned here and **nowhere else**; no `if`, no test,
no command ever reads it (verified by grepping the whole script — the only
occurrence is this assignment). Meanwhile `MultiFrame` retains its default
value `1`. Consequently:

- The guard `$nf > 1 && $MultiFrame` is **true** for multi-frame input.
- The script runs `mri_concat $v --mean --o $vmn`
  ([`scripts/fs-topup:144`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-topup#L144)),
  i.e. it averages the frames — exactly the behaviour `--no-multi-frame` was
  supposed to suppress.

The flag is therefore a silent no-op. The installed `fs-topup` accepts
`--no-multi-frame` without complaint (the parser reaches it and continues),
so the user gets no indication that the option did nothing.

### Reproducer

```bash
# The flag is accepted (parser does not reject it) but changes nothing:
timeout 20 /usr/local/freesurfer/8.2.0/bin/fs-topup --no-multi-frame
#   -> "ERROR: must spec outdir"   (parser ran past --no-multi-frame fine)
#
# With a real multi-frame field-map pair, compare:
#   fs-topup --v1 ap.nii.gz --v2 pa.nii.gz --o out1                  # averages frames
#   fs-topup --v1 ap.nii.gz --v2 pa.nii.gz --o out2 --no-multi-frame --p params.txt
# out1 and out2 are identical for the multi-frame reduction step: both run
# `mri_concat --mean`, because MultiFrame stays 1 in both cases.
```

## Code Reference (Unambiguous)

- **File:** `scripts/fs-topup`
- **Function:** argument parser (`--no-multi-frame` case) and the
  multi-frame reduction guard
- **Lines:** defect at `439–441`; default/dispatch context at `31` and
  `140–145`
- **Commit:** `d932c45`

```tcsh
    case "--multi-frame-mean":
      set MultiFrame = 1
      breaksw
    case "--multi-frame-first":
      set MultiFrame = 2
      breaksw
    case "--no-multi-frame":
      set DoMultiFrameMean = 0      # ← dead variable; should be: set MultiFrame = 0
      breaksw
```

The control variable and its only consumer:

```tcsh
set MultiFrame = 1 # 1=compute mean, 2=take first frame   (line 31)
...
  if($nf > 1 && $MultiFrame) then                          # line 140
    ...
      if($MultiFrame == 1) set cmd = (mri_concat  $v --mean --o $vmn)
      if($MultiFrame == 2) set cmd = (mri_convert $v --frame 0  $vmn)
```

`DoMultiFrameMean` appears **only** at
[`scripts/fs-topup:440`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-topup#L440)
— it is never tested or used.

## Root Cause

Wrong variable name in the `--no-multi-frame` case body. The author wrote
`set DoMultiFrameMean = 0` but the dispatch logic keys off `MultiFrame`, not
`DoMultiFrameMean`. Because `MultiFrame` is never reset to 0, the
"do nothing to multi-frame inputs" intent is lost and the default
mean-averaging (`MultiFrame = 1`) prevails. The mismatch is invisible at
parse time (assigning to a fresh, unused variable is legal in tcsh).

## Impact

- **Option silently a no-op.** Users who pass `--no-multi-frame` (typically
  alongside `--p` to supply their own acquisition parameters) still get their
  multi-frame field-map data mean-averaged. The distortion field passed to
  FSL `topup` is computed from averaged frames rather than the raw
  multi-frame volume the user intended to preserve.
- **Silent.** No error or warning; the flag is accepted and ignored.
- **Scope.** This is low (2): it is an opt-in diagnostic/advanced flag, the
  default behaviour (mean-averaging) is reasonable, and most users never use
  `--no-multi-frame`. It does not crash or corrupt the main topup output for
  the common case; it just makes one rarely-used option ineffective.

## Recommended Fix

Set the variable that the dispatch logic actually reads:

```diff
     case "--no-multi-frame":
-      set DoMultiFrameMean = 0
+      set MultiFrame = 0
       breaksw
```

With `MultiFrame = 0`, the guard at
[`scripts/fs-topup:140`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-topup#L140)
is false for multi-frame inputs, the volume is passed through untouched, and
the existing `else` branch enforces the "requires `--p`" contract
(it errors at
[`scripts/fs-topup:152-154`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fs-topup#L152-L154)
if multi-frame data is given without `--p`).

### Alternative Fixes Considered

None needed — the one-token rename to `MultiFrame` makes the flag behave as
documented and reuses the already-correct guard/else logic.

## Workarounds (If Any)

To genuinely keep multi-frame field-map data untouched, a user can
pre-reduce the data themselves (or not) and supply single-frame inputs plus a
`--p` parameter file, avoiding the multi-frame branch. There is no working
flag that does this today.
