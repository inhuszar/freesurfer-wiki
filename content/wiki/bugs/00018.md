# MRIcubicSampleVolume — divides by nvals instead of 8; SAMPLE_CUBIC returns ~1/8 of the correct intensity

> [!bug] Synopsis
> `MRIcubicSampleVolume` in `utils/mri.cpp` is the primitive behind
> `SAMPLE_CUBIC` interpolation — reachable from every user-facing
> tool that offers `--resample_type cubic` (notably
> `mri_convert`). It builds a 4×4×4 stencil of neighbour voxels,
> multiplies each by a separable cubic kernel supplied by
> `MRIcubicCoeff`, sums them, and divides by the number of
> stencil points actually summed (`nvals`). The kernel is
> 2× a Catmull-Rom basis, so its per-axis coefficients sum to 2
> and the 3D product sum is 8; a constant signal `c` therefore
> accumulates `val = 8·c`, and the final `*pval = val / nvals`
> returns `c / 8` for an interior voxel (where `nvals = 64`)
> instead of the expected `c`. The two sibling routines in the
> same file — `MRIcubicSampleVolumeFrame` and `MRIgradCubicInterp`
> — both divide by `8.0` and give the correct answer, which
> confirms the intent and the bug's shape.

## Affected Artefacts

## Detailed Description

`MRIcubicCoeff` returns the four basis-function values `f(0), f(1),
f(2), f(3)` of a separable cubic kernel. Summing the four:

```
f(0) = ((2 - x) · x - 1) · x       = -x³ + 2x² - x
f(1) = (3x - 5) · x · x + 2        = 3x³ - 5x² + 2
f(2) = ((4 - 3x) · x + 1) · x      = -3x³ + 4x² + x
f(3) = (x - 1) · x · x              = x³ - x²

f(0) + f(1) + f(2) + f(3) = 0·x³ + 0·x² + 0·x + 2 = 2
```

So the per-axis kernel satisfies `Σ f(i) = 2` for all x in `[0, 1]`
— it's 2× a normalised Catmull-Rom / Keys cubic basis. In 3D the
separable kernel's sum is `2 × 2 × 2 = 8`.

For a separable interpolation kernel, the correct output for a
constant signal `c` is `c` itself:

$$
\mathrm{out} = \sum_{i,j,k} c \cdot f_x(i) \, f_y(j) \, f_z(k)
       = c \cdot \Big(\sum f_x\Big)\Big(\sum f_y\Big)\Big(\sum f_z\Big)
       = 8\,c
$$

so the accumulated sum needs to be divided by **8** to recover
`c`. Both sibling routines in the same translation unit do
exactly that:

- `MRIcubicSampleVolumeFrame`
  ([`utils/mri.cpp:10568`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L10568)):
  `*pval = val / 8.;`
- `MRIgradCubicInterp`
  ([`utils/mri.cpp:10457–10458`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L10457-L10458)):
  `grad->rptr[1][wrtdim+1] /= 8.0;`

`MRIcubicSampleVolume` divides by `nvals` — the count of stencil
points actually summed — instead:

- [`utils/mri.cpp:10361`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L10361):
  `*pval = val / nvals;`

For an interior voxel `nvals == 64` (the full 4×4×4 stencil), so
the output is `val / 64 = 8·c / 64 = c / 8`.

### Expected Behaviour

For a constant-intensity input, cubic interpolation should return
that constant everywhere non-integer coordinates are sampled.
More generally, the interpolated output should reproduce the
underlying voxel values at integer positions and smoothly
interpolate between them.

### Observed Behaviour

At any non-integer coordinate inside the volume, the returned
value is approximately `1/8` of the correct cubic interpolate:

- Full-stencil interior voxel (`nvals = 64`): output is `val/64`,
  i.e., `c/8` for constant signal.
- Face-boundary voxel (`nvals = 48`): output is `val/48`, i.e.,
  `8c·(partial_sum) / 48`, where the partial sum's exact value
  depends on the fractional position — a position-dependent
  non-linear error.
- Edge-boundary voxel (`nvals = 36`): similar, with a different
  position-dependent scaling.
- Corner voxel (`nvals = 27`): worst case; for `x = y = z = 0.5`
  the partial kernel sum cubes to ~9.59 so the output is
  `c · 9.59 / 27 ≈ 0.36 c` instead of `c`.

The per-voxel error therefore varies with the fractional
position AND with whether the stencil fits inside the volume, so
a cubic-sampled volume is not just uniformly scaled down —
it carries position-dependent distortion on top of the
dominant ×1/8 scale error.

```cpp
int MRIcubicSampleVolume(const MRI *mri, double x, double y, double z, double *pval)
{
  /* ... early-return for integer coords, out-of-bounds check,
         stencil loading into vv[4][4][4] ... */

  val = 0;

  nvals = 0 ;                                                   // ← counts stencil points
  for (iz = MAX(0, 1 - iz_low); iz < MIN(4, depth + 1 - iz_low); iz++) {
    fz = MRIcubicCoeff(zz, iz);
    for (iy = MAX(0, 1 - iy_low); iy < MIN(4, height + 1 - iy_low); iy++) {
      fy = MRIcubicCoeff(yy, iy);
      for (ix = MAX(0, 1 - ix_low); ix < MIN(4, width + 1 - ix_low); ix++) {
        fx = MRIcubicCoeff(xx, ix);
        val += (double)(vv[ix][iy][iz] * fx * fy * fz);
        nvals++ ;
      }
    }
  }
  *pval = val / nvals;                                          // ← should be val / 8.0

  return (NO_ERROR);
}
```

The three routines share the same `MRIcubicCoeff` kernel. Two of
the three know that the kernel product sums to 8; one of the
three doesn't.

## Root Cause

`MRIcubicCoeff`'s formulas emit a kernel whose per-axis values
sum to `2`, so the separable 3D product sums to `8`. The
companion routines divide by `8.0` to normalise. The author of
`MRIcubicSampleVolume` (or a later edit) misread the compensation
as "average over the stencil points actually touched" and used
`nvals` — the count of iterations — as the divisor. For an
interior voxel that makes the output 8× too small; near
boundaries the partial kernel sum also departs from 8 so the
error becomes position-dependent.

## Impact

- **`mri_convert --resample_type cubic`**: user-facing. Output
  volumes have interior intensities roughly 1/8 of the input,
  with additional position-dependent distortion at the image
  edges.
- **`MRIsampleVolumeType(..., SAMPLE_CUBIC)`**: every caller that
  routes through this enum hits `MRIcubicSampleVolume` via
  [`utils/mri.cpp:9383`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L9383).
- **`surfgrad.cpp` BBR**: when the user sets
  `bbrpar->interp == SAMPLE_CUBIC`, the boundary-based
  registration cost uses incorrectly-scaled inside / outside
  intensities, biasing the surface placement.
- **Standard [[recon-all]]**: unaffected. Recon-all's active
  sampling paths use `SAMPLE_TRILINEAR`; `SAMPLE_CUBIC` is an
  opt-in.

## Recommended Fix

Replace the `nvals` divisor with the correct constant `8.0`, and
drop the now-unused `nvals` counter:

```diff
   val = 0;
-
-  nvals = 0 ;
   for (iz = MAX(0, 1 - iz_low); iz < MIN(4, depth + 1 - iz_low); iz++) {
     fz = MRIcubicCoeff(zz, iz);
     for (iy = MAX(0, 1 - iy_low); iy < MIN(4, height + 1 - iy_low); iy++) {
       fy = MRIcubicCoeff(yy, iy);
       for (ix = MAX(0, 1 - ix_low); ix < MIN(4, width + 1 - ix_low); ix++) {
         fx = MRIcubicCoeff(xx, ix);
         val += (double)(vv[ix][iy][iz] * fx * fy * fz);
-        nvals++ ;
       }
     }
   }
-  *pval = val / nvals;
+  *pval = val / 8.0;
```

Note that `vv[ix][iy][iz]` for the out-of-stencil cells remains
zero because of the `double vv[4][4][4]` stack declaration in a
function that doesn't zero it — interior voxels always load all
64 entries, but boundary voxels leave some cells unloaded. The
existing boundary-limited accumulation loop skips those cells,
so the sum is already correctly restricted; dividing by `8.0`
with a partial stencil reproduces the zero-padded interpolation
that matches the `MRIgradCubicInterp` semantics. If matching
`MRIcubicSampleVolumeFrame`'s "iterate full 0..3 over
possibly-uninitialised `vv`" behaviour is preferred, see the
related concern below.

### Alternative Fixes Considered

1. Renormalise the `MRIcubicCoeff` kernel itself to sum to 1 (so
   the 3D product sums to 1) and drop the `/ 8.0` from all three
   routines. This makes the kernel a standard Keys / Catmull-Rom
   interpolant and removes the silent scale factor. Lower risk
   of future drift but touches all three call sites.
2. Initialise `vv[4][4][4] = {{{0}}}` explicitly at the top of
   the stencil-loading block so that the "iterate full 0..3"
   pattern used in `MRIcubicSampleVolumeFrame` doesn't read
   uninitialised stack (a separate bug documented in a gap
   below). `MRIcubicSampleVolume`'s bounds-limited iteration
   avoids that concern, so this alternative mainly helps the
   sibling routine.

## Workarounds (If Any)

For users who need cubic interpolation today, route through
`MRIcubicSampleVolumeFrame` directly (passing `frame = 0`) —
that routine divides by `8.0` and produces the correct scale.
Alternatively, use `SAMPLE_CUBIC_BSPLINE` via `mri_convert`,
which routes through the `mriBSpline.cpp` implementation and
does not share this kernel.

## Confidence and Gaps

> [!gap] Boundary behaviour under the fix
> Replacing `/ nvals` with `/ 8.0` is algebraically correct for
> interior voxels. For boundary voxels where the stencil is
> partial, the sum is the partial kernel sum, and dividing by
> `8.0` does not reproduce the same boundary behaviour as a
> zero-padded full-stencil evaluation — it produces a
> different, kernel-consistent edge roll-off. Whichever semantics
> the author originally wanted, this patch makes the scale
> match the two sibling routines exactly.

> [!gap] MRIcubicSampleVolumeFrame uninitialised vv
> The sibling `MRIcubicSampleVolumeFrame`
> ([`:10463–10571`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L10463-L10571))
> loads its stencil with the same boundary-limited loop as
> `MRIcubicSampleVolume` but then accumulates over the full
> 4×4×4, reading uninitialised cells of `vv[4][4][4]` at
> boundary voxels. That is a separate defect worth its own bug
> report; fixing it would require either zeroing `vv` on stack
> or bounds-limiting the accumulation loop.
