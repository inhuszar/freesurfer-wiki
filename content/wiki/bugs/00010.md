# [severity-2] [bug-00010] MRIremove1dStructures — broken do-while condition defeats max_iter safeguard

> [!bug] Synopsis
> `MRIremove1dStructures` in `mri_segment/mri_segment.cpp` is meant to
> iterate until either the segmentation converges (no more voxels get
> removed in a pass) or a safety cap `max_iter` is reached. Its
> do-while condition `while (nvox > 0 || ++niter > max_iter);` mis-wires
> the two exits: `++niter` only runs when `nvox == 0`, and the
> condition only becomes false (i.e., the loop only exits) when
> `nvox == 0` *and* the incremented `niter` is not greater than
> `max_iter`. The max-iteration cap is therefore dead code — `niter`
> never climbs above 1 under ordinary use. If the iterative removal
> ever oscillates so that `nvox > 0` persists indefinitely, nothing
> inside this function stops it.

- **Pipeline stage(s):** `autorecon2` — `mri_segment` is invoked by

- **FreeSurfer version(s):** confirmed in `8.2.0` at commit

- **Platforms:** all — purely control flow.
- **Triggering configuration:** the broken condition fires on every
  invocation; the user-visible consequence only manifests on inputs
  where the inner removal does not monotonically converge to
  `nvox == 0`, which is unusual for the intended
  remove-1d-structures algorithm but is the exact scenario the
  `max_iter` safeguard exists to catch.

## Detailed Description

`MRIremove1dStructures` scans the volume repeatedly: each pass
counts, for every voxel above `WM_MIN_VAL`, how many of its six
face-neighbours are also above `WM_MIN_VAL`. Voxels with fewer
than `thresh` such neighbours are zeroed, and the pass is repeated
until nothing changes (or the safety cap trips). The docstring
explicitly says "until the maximum number of iters is reached or
nothing changes."

The implementation's `while` condition tries to express both exits
in a single expression, but the left/right operands are miswired.

### Expected Behaviour

Two exit conditions:

- **Convergence:** the inner pass finds nothing to remove
  (`nvox == 0`). Exit.
- **Safety cap:** `niter` reaches `max_iter`. Exit.

Canonical C idiom: `while (nvox > 0 && niter++ < max_iter);` (loop
while there is progress *and* we have not hit the cap).

### Observed Behaviour

The actual condition is
`while (nvox > 0 || ++niter > max_iter);`. Breaking it down:

- When `nvox > 0` the left operand is already true, the OR
  short-circuits, and `++niter` **is not evaluated**. `niter`
  therefore stays at `0` for every non-zero-nvox pass.
- When `nvox == 0` the right operand is evaluated: `++niter`
  increments from `0` to `1`, then compares `1 > max_iter`
  (`max_iter` is at least 1000 by default). The comparison is
  false, the condition is false, and the loop exits — with
  `niter == 1` regardless of how many non-convergent passes
  preceded it.

Two concrete consequences:

1. The `max_iter` safeguard never fires under any realistic input.
   `niter` can only become `1` (on exit after the first
   `nvox == 0` pass). If the inner pass keeps removing voxels
   forever (`nvox > 0` persists), nothing in this function stops
   the loop.
2. The `printf` diagnostic at
   [`mri_segment/mri_segment.cpp:1060`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_segment/mri_segment.cpp#L1060)
   always reports `"... in 1 iterations"` regardless of how many
   passes were actually run, because `niter` is only incremented
   on the final (convergent) pass. The reported iteration count
   is not trustworthy.

In normal use — where each pass only removes a subset of the
remaining sparse voxels, so the set of voxels-to-remove shrinks
monotonically — the outer loop converges naturally and the defect
has no user-visible effect beyond the mis-reported iteration count.
On pathological inputs where removing one voxel can cause a
previously-valid neighbour to now violate the `thresh` rule in an
oscillating way, the safeguard that was supposed to catch this
stall is absent.

## Root Cause

Operator mix-up between the two intended exit conditions.
The canonical "loop while there is progress and we have not hit
the cap" pattern is `while (nvox > 0 && niter++ < max_iter)`. The
existing code converts that into `while (nvox > 0 || ++niter >
max_iter)`, which flips both the connective (`&&` → `||`) and the
comparison (`<` → `>`). The two flips partially cancel — the
loop still terminates on convergence — but the safety cap no
longer works, and the iteration counter cannot reflect the
actual number of passes run.

## Impact

- **Safety cap dead.** If any input ever causes
  `MRIremove1dStructures` to enter a non-converging regime, the
  function loops without bound. The `max_iter` parameter is
  silently ignored.
- **Iteration count misreported.** The closing `printf` always
  prints `"in 1 iterations"`, obscuring the real amount of work
  done and making it harder for users to diagnose slow segmentation
  runs.
- **No user-visible output corruption in normal runs.** The
  natural termination on `nvox == 0` still happens and still
  produces the same final segmentation; the diagnostic message is
  the only wrong artefact for well-behaved inputs.

## Recommended Fix

Swap the operator and connective so the condition matches the
docstring intent:

```diff
-  while (nvox > 0 || ++niter > max_iter) ;
+  while (nvox > 0 && ++niter < max_iter) ;
```

After the change:

- `nvox > 0 && ++niter < max_iter` is true only when there is
  progress *and* we still have iteration budget. Both exits are
  active.
- `niter` increments on every pass, so the reported iteration
  count is accurate.
- When `nvox == 0`, the condition short-circuits at the left and
  exits without consuming an iteration.

### Alternative Fixes Considered

Equivalent with a post-increment at the end of the loop body:

```c
niter = total = 0 ;
do {
  nvox = 0 ;
  /* ... */
  total += nvox ;
  niter++ ;
} while (nvox > 0 && niter < max_iter) ;
```

Slightly clearer about when `niter` advances; no functional
difference.

## Workarounds (If Any)

None needed for normal recon-all subjects: the natural
convergence masks the defect. Users who want an accurate
iteration count for diagnostic purposes should patch locally.
