# [severity-2] [bug-00155] long_create_orig — FOV>256 guard pipes through `tee -a $LF` but $LF is never set, so the branch dies on an undefined variable instead of printing the -cw256 advice

> [!bug] Synopsis
> `long_create_orig` guards against a field-of-view larger than 256 mm:
> when `FOV > 256` it prints an error telling the user to re-run with
> `-cw256`, then exits 1. Every line of that error message is piped
> through `|& tee -a $LF`, but `$LF` is never `set` anywhere in the
> script (which runs under `#!/bin/tcsh -f`). When the guard fires, the
> first `tee -a $LF` reference therefore aborts with
> `LF: Undefined variable.` — so the user sees a cryptic tcsh error
> instead of the intended `FOV=... > 256 / Include the flag -cw256`
> advice. The script still exits non-zero, but the diagnostic the guard
> exists to deliver is lost.

## Affected Artefacts

- **Tool(s):** [[long_create_orig]] (longitudinal stream helper that
  builds `orig.mgz` for a timepoint from the base template).
- **Pipeline stage(s):** the FOV>256 sanity guard, reached after the
  conformed `orig` volume is created for a longitudinal timepoint.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all — `tcsh -f` undefined-variable semantics.
- **Triggering configuration:** any input whose field of view exceeds
  256 mm — exactly the condition the guard is meant to catch. The bug
  cannot occur for FOV ≤ 256 because the branch is not entered.

## Detailed Description

The guard reads:

```tcsh
set FOV=`mri_info ${origvol} | grep fov: | awk '{print $2}'`
set FOV_gt_256=`echo "${FOV} > 256" | bc`
if ($FOV_gt_256) then
  echo "\n****************************************" |& tee -a $LF
  echo "ERROR! FOV=${FOV} > 256" |& tee -a $LF
  echo "Include the flag -cw256 with recon-all!" |& tee -a $LF
  echo "Inspect orig.mgz to ensure the head is fully visible." |& tee -a $LF
  echo "****************************************\n" |& tee -a $LF
  exit 1;
endif
```

`$LF` (the "log file" variable used by many FreeSurfer scripts) is
referenced only in these five lines. It is never `set` in
`long_create_orig`, and the script uses `#!/bin/tcsh -f`, so it neither
sources a startup file that might define `LF` nor inherits one by the
script's own convention. In a non-interactive `tcsh -f` script, expanding
an undefined variable is a **fatal** error: the first
`echo ... |& tee -a $LF` raises `LF: Undefined variable.` and the script
terminates immediately, before printing any of the advice and before the
explicit `exit 1`.

The block was, per the in-file comment, "copied from recon-all", where
`$LF` is a defined log-file path. The copy dropped the variable's
definition.

### Expected Behaviour

On FOV>256, the script prints the four-line advice (most importantly
`Include the flag -cw256 with recon-all!` and
`Inspect orig.mgz to ensure the head is fully visible.`) and exits 1, so
the user knows how to fix the run.

### Observed Behaviour

On FOV>256, the script prints `LF: Undefined variable.` and exits — none
of the advice lines appear. The user gets no guidance about `-cw256`.

### Reproducer

```bash
# Demonstrate tcsh -f undefined-variable behaviour in a taken branch:
cat > /tmp/lf.csh <<'EOF'
#!/bin/tcsh -f
set FOV_gt_256 = 1
if ($FOV_gt_256) then
  echo "ERROR! FOV=300 > 256" |& tee -a $LF
  echo "Include the flag -cw256 with recon-all!" |& tee -a $LF
  exit 1
endif
EOF
tcsh -f /tmp/lf.csh
#   -> LF: Undefined variable.   (advice never printed; exit 1)

# Same with LF defined prints the advice correctly:
tcsh -f -c 'set LF=/tmp/o.log; echo "Include the flag -cw256 with recon-all!" |& tee -a $LF'
#   -> Include the flag -cw256 with recon-all!
```

Executed: the undefined-`LF` form aborts with `LF: Undefined variable.`
and prints none of the advice; the defined-`LF` form prints it.

## Root Cause

The guard block was copied from `recon-all` (per the in-file comment
"copied from recon all") together with its `|& tee -a $LF` logging, but
`long_create_orig` never defines an `LF` log-file variable. Under
`tcsh -f`, dereferencing the undefined `$LF` aborts the branch on its
first line.

## Impact

- **The FOV>256 diagnostic is replaced by a cryptic error.** Users whose
  data trip the guard (the intended audience for the message) lose the
  actionable `-cw256` advice and instead see `LF: Undefined variable.`,
  making the failure harder to diagnose.
- The script still terminates non-zero, so a FOV>256 timepoint does not
  proceed silently — the longitudinal run halts as intended, just without
  the explanation. No wrong scientific output is produced.
- Rated **low (2)**: the path is gated behind the FOV>256 edge case and
  affects only a diagnostic message, not computed output. It is not on
  the default `recon-all` chain.

## Recommended Fix

The minimal, self-contained fix is to write the advice to stderr/stdout
without `$LF` (the guard does not otherwise have a log handle):

```diff
   if ($FOV_gt_256) then
-    echo "\n****************************************" |& tee -a $LF
-    echo "ERROR! FOV=${FOV} > 256" |& tee -a $LF
-    echo "Include the flag -cw256 with recon-all!" |& tee -a $LF
-    echo "Inspect orig.mgz to ensure the head is fully visible." |& tee -a $LF
-    echo "****************************************\n" |& tee -a $LF
+    echo "\n****************************************"
+    echo "ERROR! FOV=${FOV} > 256"
+    echo "Include the flag -cw256 with recon-all!"
+    echo "Inspect orig.mgz to ensure the head is fully visible."
+    echo "****************************************\n"
     exit 1;
   endif
```

### Alternative Fixes Considered

If a log file is desired, define `LF` near the top of the script
(e.g. `set LF = $longsubjdir/scripts/long_create_orig.log` once
`$longsubjdir` exists) and keep the `|& tee -a $LF` form. This adds a
real log artefact but requires choosing a valid, writable path; the
stdout-only fix above is simpler and removes the crash without
introducing a new file dependency.

## Workarounds (If Any)

No clean user-side workaround: the variable is undefined inside the
script's own code path. Exporting `LF` into the environment before
calling the script would not help, because `tcsh -f` does not import it
as a shell variable for `$LF` unless it is exported and the script reads
`$?LF`/`$LF` against the environment — and the script never `set`s it.
Editing the script locally (per the fix above) is the practical remedy.
