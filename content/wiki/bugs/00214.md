# [severity-3] [bug-00214] `applyMorph` — `point_list` inverts the shared morph in place, persisting to later items

> [!bug] Synopsis
> All filters of one `applyMorph` call share a single `VolumeMorph`.
> `PointListProbeFilter::Execute` calls `this->pmorph->invert()`, which
> inverts every transform of that shared object in place, and never inverts
> it back. Consequently the result depends on item order: the second
> `point_list` in a call is mapped with the **forward** morph (the double
> inversion restores it), and any `vol` or `surf` item executed after a
> point list, as well as `--dbg_coords`, uses the **inverted** morph. The
> inversion used to be conditional on the `tract_point_list` keyword; the
> condition is commented out, so `point_list` and `tract_point_list` are now
> identical and the global flag is dead.

## Affected Artefacts

- **Tool(s):** [[applyMorph]]
- **Pipeline stage(s):** _N/A_ (no in-tree caller; the `applyMorph` calls in `mri_cvs_register` are commented out)
- **FreeSurfer version(s):** confirmed in 8.2.0; the unconditional call was introduced by commit `10c9d3b92e5` (2018-01-10, "Fixed a bug so that now morph (tm3d) can be applied to point lists")
- **Platforms:** all
- **Triggering configuration:** an `applyMorph` invocation with a `point_list` or `tract_point_list` item that is **not the last** item, or with two or more point-list items, or with `--dbg_coords` together with a point-list item.

## Detailed Description

`main()` builds one `VolumeMorph` (`pmorph`), loads the transform file into
it, and gives the same `shared_ptr` to every filter object. The filters then
run in command-line order.

`PointListProbeFilter::Execute` needs the inverse map (points are given in
moving-space voxel coordinates and returned in fixed-space coordinates), so
it calls `pmorph->invert()` at its start. `VolumeMorph::invert()` operates
on the object it is called on: each transform's `invert()` is applied in
place and the transform list is reversed. Nothing undoes this at the end of
`Execute`, and nothing copies the morph first.

Before commit `10c9d3b92e5` the call was `if (tractPointList)
this->pmorph->invert();`, where `tractPointList` is a global set by the
`tract_point_list` keyword. The 2018 commit comments the condition out so
that plain `point_list` also inverts, which makes the two keywords
equivalent and leaves `tractPointList` set but never read.

### Expected Behaviour

Each item operates on the morph as loaded: `vol`, `surf`, `sprobe`,
`snormals` use the forward map, and every point-list item uses its inverse,
independent of the other items and of their order. `--dbg_coords`, which the
help describes only as "Debugging coordinates", should report the image under
the morph as loaded (or at least a documented one).

### Observed Behaviour

Item order changes the results, silently:

- the first `point_list` is inverted, the second one is not (two inversions
  cancel for transforms with an exact inverse), the third is inverted again,
  and so on;
- a `vol` item placed after a point list is resampled with the inverse
  morph (the direction of the resampling flips);
- `--dbg_coords` (evaluated after all items) reports the image under the
  inverted morph after a single point-list item (observed); by the same
  logic it reports the forward image after an even number of point-list
  items (not run).

### Reproducer

Synthetic: a 32^3 template volume, a ramp volume `ramp.mgz` with value
`10 * x` along voxel axis 0, and a hand-built `.tm3d` holding one affine
transform that is a pure `+3` voxel x-translation (`shift3.tm3d`, geometries
stored). `pts.txt` contains the single line `10 20 30`. All output paths are
absolute.

```bash
# (1) two point lists in one call
applyMorph --template tmpl.mgz --transform shift3.tm3d \
    point_list pts.txt <W>/p1.txt x  point_list pts.txt <W>/p2.txt x
cat <W>/p1.txt <W>/p2.txt        # observed: "7 20 30" then "13 20 30"

# (2) three point lists
applyMorph ... point_list pts.txt <W>/p3.txt x  point_list pts.txt <W>/p4.txt x \
               point_list pts.txt <W>/p5.txt x
# observed: 7 20 30 ; 13 20 30 ; 7 20 30      (tract_point_list behaves the same)

# (3) vol item before / after a point list
applyMorph ... vol ramp.mgz <W>/v_alone.mgz nearest --dbg_coords 10 20 30
applyMorph ... vol ramp.mgz <W>/v_before.mgz nearest point_list pts.txt <W>/q.txt x
applyMorph ... point_list pts.txt <W>/q2.txt x vol ramp.mgz <W>/v_after.mgz nearest \
               --dbg_coords 10 20 30
```

Observed (installed 8.2.0 binary, all exit 0). The `+3` translation maps
fixed index `p` to moving index `p + 3`; the correct volume output is
`out[x] = in[x + 3]`, the correct inverse of `(10,20,30)` is `(7,20,30)`:

| Run | Result |
|-----|--------|
| `v_alone`, `out[10..13]` | `130 140 150 160` (= `in[13..16]`, forward) |
| `v_before` (vol first, point list after) | identical to `v_alone` |
| `v_after` (point list first, vol after) | `70 80 90 100` (= `in[7..10]`, i.e. the **inverse** direction) |
| `--dbg_coords 10 20 30` in `v_alone` | `13 20 30` (forward) |
| `--dbg_coords 10 20 30` in `v_after` | `7 20 30` (inverted) |
| first / second / third `point_list` | `7 20 30` / `13 20 30` / `7 20 30` |

## Root Cause

Shared mutable state: `invert()` mutates the `VolumeMorph` that all
filters reference through one `std::shared_ptr`, and
`PointListProbeFilter::Execute` neither works on a private copy nor restores
the morph. The 2018 change that made `point_list` always invert (so that
`.tm3d` morphs can be applied to point lists) removed the only condition
under which the persistence was limited to point-list users.

## Impact

- **Silent, order-dependent wrong output.** Pipelines that put a
  `point_list` before a `vol`/`surf` item resample or move data in the wrong
  direction; two point lists in one call differ by the full transform. No
  warning is printed.
- **Severity 3, not 2 or 4.** It fires only for an opt-in item keyword in
  specific orderings (gated), and the default single-item usage is correct;
  it is not rated 4 because no pipeline calls `applyMorph` with point lists
  and the call has a trivial workaround (one item kind per invocation).
- **Interaction with [[00213]]:** for morphs containing a displacement-field
  (`field`) transform the inversion itself is defective, so the first point
  list is already wrong; because frame 0 is negated twice by two inversions,
  the double inversion restores the field exactly, and the persistence
  pattern is the same as for affine morphs.
- `--dbg_coords` is a debugging aid; its reported image changes with the
  presence of a point-list item.

## Recommended Fix

Make the point-list filter leave the shared morph as it found it (invert,
compute, invert back), including on the exception path:

```diff
 void
 PointListProbeFilter::Execute()
 {
   std::ifstream ifs( this->strInput.c_str() );
   if ( !ifs ) throw " Failed to open input file while applying PointListProbeFilter ";
 
   std::vector<Coords3d> outputImages;
   Coords3d pt, img; 
 
-  //if (tractPointList) 
-  this->pmorph->invert();
+  // work with the inverse, but restore the shared morph before returning
+  this->pmorph->invert();
+  struct Restore {
+    gmp::VolumeMorph* m;
+    ~Restore() { try { m->invert(); } catch (...) {} }
+  } restore = { this->pmorph.get() };
```

(`VolumeMorph` cannot simply be copy-constructed to obtain a private
copy: it owns a raw `mriCache` pointer that its destructor frees.) A
regression test is experiment (1)/(3) above: with a pure translation the
outputs must not depend on item order.

### Alternative Fixes Considered

Load the morph a second time (`pmorph->load(strTransform, zlibBuffer)`) for
the point-list filter, so that the shared object is never modified; costlier
for large FEM morphs, but immune to any transform whose `invert()` is not an exact involution
(whether the FEM-mesh inversion is one was not checked). Restoring the pre-2018 guard `if (tractPointList)` is **not**
recommended: the 2018 commit message states that plain point lists were
meant to be inverted.

## Workarounds (If Any)

Run `point_list`/`tract_point_list` in a separate `applyMorph` invocation
from `vol`/`surf` items and `--dbg_coords`, with at most one point-list item
per call, or place a single point-list item last.

## Confidence and Gaps

> [!gap] Intent of the 2018 change
> The commit message says plain point lists should be inverted. Whether the
> author also intended persistence across items is not stated; no test or
> comment suggests it, and the `tractPointList` flag being left behind
> suggests an oversight. The pre-2018 behaviour (invert only for
> `tract_point_list`) is not reproducible with 8.2.0.
