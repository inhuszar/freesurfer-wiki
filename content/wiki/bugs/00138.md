# [severity-3] [bug-00138] `mri_cnr -slope` corrupts the linear-regression design matrix — `d=0` sample is silently lost, one row becomes an all-zero `[0, 0]` design pair

> [!bug] Synopsis
> ```cpp
> /* mri_cnr/mri_cnr.cpp:369-421 (abridged) */
> MRIScomputeSlope(MRIS *mris, MRI *mri, double dist_in, double dist_out,
>                  double step_in, double step_out, MATRIX *m_linfit)
> {
>   ...
>   nsamples = 1 + (int)(dist_in / step_in) + (int)(dist_out / step_out);
>   m_X = MatrixAlloc(2, nsamples, MATRIX_REAL);   /* calloc-zeroed */
>   m_Y = MatrixAlloc(1, nsamples, MATRIX_REAL);
>   ...
>   for (vno = 0; vno < mris->nvertices; vno++) {
>     ...
>     /* (1) inward samples — n goes 0..N1-1, writes at columns 1..N1 */
>     for (n = 0, d = -dist_in; d < 0.0; d += step_in, n++)
>     {
>       ...
>       MRIsampleVolumeType(mri, xv, yv, zv, &val, interp);
>       *MATRIX_RELT(m_Y, 1, n+1) = val;
>       *MATRIX_RELT(m_X, 1, n+1) = d;

>     for (d = step_out; d <= dist_out; d += step_out, n++)
>     {
>       ...

>       *MATRIX_RELT(m_X, 1, n+1) = d;

>     MatrixMultiply(m_Y, m_pinv, m_P);
>     ...
>   }

> ```
>
> Trace with `dist_in = 2, step_in = 1, dist_out = 2, step_out = 1` (so `N1 = N2 = 2`, `nsamples = 5`):
>
> | col | what should be there | what actually is | reason |
> |---|---|---|---|
> | 1 | inward `d=-2` | inward `d=-2` ✓ | loop (1), `n=0` |
> | 2 | inward `d=-1` | inward `d=-1` ✓ | loop (1), `n=1` |
> | 3 | at-surface `d=0` | **`[m_X=0, m_Y=0, intercept=0]`** (calloc) | step (2) wrote to col 4 instead |
> | 4 | outward `d=1` | outward `d=1` ✓ — but only because step (3) iter 1 overwrote the `d=0` sample that (2) had written here | step (2) bug then step (3) overwrite |
> | 5 | outward `d=2` | outward `d=2` ✓ | loop (3), `n=4` |
>
> Two consequences per vertex:
>
> 1. **The `d=0` intensity is silently lost** — the on-surface value (the most informative point for the intercept) is written, then immediately overwritten by outward sample 1.
> 2. **Column `N1+1` becomes a degenerate `[0, 0]` design row** (the intercept column should be `1`, but `MatrixAlloc` left it at `0`). The least-squares fit `m_P = m_Y · pinv(m_X)` is computed over `nsamples` points but one of them is the all-zero pseudo-data `(0 = slope·0 + 0·offset)`, biasing the slope/offset estimate.
>
> Both the slope and the offset that `mri_cnr -slope <name>` writes as `<hemi>.<name>.slope.mgz` / `<hemi>.<name>.offset.mgz` are therefore wrong on every vertex.

## Detailed Description

### What the index arithmetic should do

The matrices are sized `nsamples = 1 + N1 + N2` (with `N1 = floor(dist_in/step_in)` and `N2 = floor(dist_out/step_out)`). The intended 1-based column layout is:

| col | what | when written |
|---|---|---|
| `1 .. N1`         | inward samples `d = −dist_in, …, −step_in` | loop (1), `n = 0..N1−1`, writes column `n+1` |
| `N1+1`            | at-surface sample `d = 0`                   | step (2) |
| `N1+2 .. N1+N2+1` | outward samples `d = step_out, …, dist_out` | loop (3), `n = N1+1..N1+N2`, writes column `n+1` |

For this scheme to work, after loop (1) the counter `n` is `N1`, step (2) writes column `N1+1`, then `n` becomes `N1+1` *after* step (2) so that loop (3) starts writing at column `N1+2`.

### What the code does instead

The `n++ ;` is placed **before** the step-(2) write:

```cpp
n++;                              // n: N1 → N1+1
... MRIsampleVolumeType ...
*MATRIX_RELT(m_Y, 1, n+1) = val;  // writes column n+1 = N1+2  ← off by one
*MATRIX_RELT(m_X, 1, n+1) = 0.0;
*MATRIX_RELT(m_X, 2, n+1) = 1;
```

So `(d=0, val)` lands in column `N1+2`. Loop (3) then enters with `n = N1+1` and immediately writes column `n+1 = N1+2` again, overwriting step (2)'s `(0, val)` with `(step_out, val_outward1)`.

Column `N1+1`, meanwhile, is never touched. The `MatrixAlloc(2, nsamples, MATRIX_REAL)` left it at `0.0` in both rows — including the intercept row, which should be `1` for every regression sample. So the pseudo-inverse sees an extra row equivalent to `0 = slope · 0 + 0 · offset`, i.e. the all-zero design pair `[0, 0]`.

### Effect on the linear fit

The least-squares fit:

$$\hat{p} = (X^T X)^{-1} X^T y$$

with one row of `X` reduced to `[d=0, intercept=0]` and the corresponding `y = 0`. That row contributes nothing to either column's normal-equation sum (the column with `d` gets `0 · 0 = 0`, the intercept column gets `0 · 0 = 0` and `0 · 1 = 0`), but it *displaces* the at-surface sample. So:

- The slope is fit over `N1 + N2` real samples plus one zero-row "ghost".
- The on-surface intensity that should anchor the intercept is missing.

The slope estimate is biased toward zero (the missing on-surface sample is usually the most extreme value relative to the fit line), and the intercept estimate is biased low (since the most informative anchor at `d=0` is gone).

For typical mri_cnr usage with `dist_in = dist_out = 2 mm`, `step_in = step_out = 0.5 mm` (the defaults), `N1 = N2 = 4` so each vertex has 9 samples in principle but only 8 valid + 1 zero-ghost. Bias is small per-vertex but systematic across the surface.

### Why this is severity 3

- **Documented CLI option** (`mri_cnr -slope <name>`) produces silently-wrong `.slope.mgz` and `.offset.mgz` outputs that downstream analyses use as if they were correctly fit slopes/offsets.
- **Not on the default `recon-all` path** — opt-in QA option.
- **No crash, no error** — output looks plausible (correct shape, plausible magnitude) but is biased on every vertex.
- **Conceptually a clear off-by-one in design-matrix index assignment**, not a subtle numerical issue.
- Below severity 4 because the bias is small per-vertex (one missing sample out of `1 + N1 + N2 ≈ 9–13`) and the output isn't used in primary `recon-all` deliverables.

## Root Cause

A counter-management slip. The developer wanted `n` to advance over the at-surface column so loop (3) starts writing at column `N1+2`. They added `n++ ;` to bump it. But because the subsequent `MATRIX_RELT(m_Y, 1, n+1)` already adds `+1` (treating `n` as 0-based, matching loop (1)), the bump made the at-surface write target `N1+2` instead of `N1+1`. Loop (3) then starts at `n = N1+1` and its first `n+1 = N1+2` collides with step (2)'s write.

The fix is either:
1. Drop the `n++ ;`, write `(d=0)` at `n+1 = N1+1`, then add `n++ ;` *after* step (2).
2. Keep the `n++ ;`, but write `(d=0)` at index `n` (without `+1`).

Both produce the same correct layout (`1..N1` inward, `N1+1` at-surface, `N1+2..N1+N2+1` outward).

## Impact

- **`mri_cnr -slope <name>`:** silently writes biased slope and offset overlays. Downstream QA / analysis pipelines that read these files (e.g. cortical thickness vs. intensity gradient checks) get systematically wrong values on every vertex.
- **`mri_cnr` without `-slope`:** unaffected. The CNR computation in `compute_volume_cnr` does not call `MRIScomputeSlope`.
- **`recon-all`:** unaffected (the `-slope` option is not invoked by `recon-all`).
- **Severity 3** — silent wrong output on a documented opt-in CLI flag; affects QA outputs but not the primary surface placement / segmentation pipeline.

One-line move: shift the `n++ ;` from before the at-surface write to after it. After the fix:

- After loop (1): `n = N1`.
- At-surface block writes column `n+1 = N1+1` ✓.
- Then `n++` → `n = N1+1`.
- Loop (3) iter 1: writes column `n+1 = N1+2` ✓ (no overwrite).

## Workarounds

For users who need correct slope/offset estimates from `mri_cnr -slope`, post-process the on-surface intensity manually:

```python
# vno-by-vno: read the white-surface intensity samples at d = -dist_in, ..., -step_in,
# 0, step_out, ..., dist_out, then fit slope/offset with a clean design matrix.
```

A clean Python reimplementation takes ~20 lines using `nibabel.freesurfer.io.read_geometry` for the white surface and `scipy.ndimage.map_coordinates` (or any tri-linear sampler) on the intensity volume.

## Provenance and Discovery

- **Discovered:** 2026-05-21 by agent (audit of intensity-vs-distance regression code in surface QA tools).
- **Evidence:**
  - The inward loop at `:386-394` uses `n` as a 0-based counter and writes column `n+1` (1-based matrix indexing). After loop completion, `n == N1`.
  - The `n++ ;` at `:395` makes `n == N1+1` *before* the at-surface write.
  - The at-surface write at `:399-401` then targets column `n+1 == N1+2`.
  - Column `N1+1` is never written; `MatrixAlloc` leaves it at `0.0` (including the intercept row, which should be `1.0`).
  - The outward loop at `:403` enters with `n == N1+1` and writes column `n+1 == N1+2` on its first iteration, overwriting the at-surface sample.
  - Total samples in matrix: `nsamples = 1 + N1 + N2`. Indices `1..N1` (inward), `N1+1` (zero-ghost), `N1+2..nsamples` (outward, with first one being the displaced at-surface). All matrix accesses are in-bounds; the defect is entirely in the value pattern.
