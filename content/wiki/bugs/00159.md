# [severity-3] [bug-00159] pointset2label — integer voxel macro used to write float/short/long volumes; deposits invalid bytes

> [!bug] Synopsis
> `pointset2label` paints the spline-sampled path value into the output
> volume through `set_voxel_value()`, which switches on the volume data
> type but uses the **integer** voxel macro `MRIIseq_vox` (an `int *`
> cast) for the `MRI_LONG`, `MRI_FLOAT`, `MRI_SHORT`, and `MRI_USHRT`
> cases. Only `MRI_UCHAR` (via `MRIseq_vox`) and `MRI_INT` (via
> `MRIIseq_vox`) are written through a correctly-typed macro. When the
> input/output volume is a float, short, ushort, or long volume, each
> painted voxel writes a 4-byte `int` over a cell of a different size and
> interpretation, corrupting that voxel (and, for `short`/`ushort`,
> overrunning into the neighbouring 2 bytes). Separately, the sampled
> spline points are written with no field-of-view bounds checking, so a
> path point outside the volume indexes out of bounds.

## Affected Artefacts

- **Tool(s):** [[pointset2label]]
- **Pipeline stage(s):** _N/A_ — a standalone freeview-adjacent helper
  that burns a way-point pointset/path into a label volume; not invoked
  by [[wiki/pipelines/recon-all|recon-all]].
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`;
  earliest known: _unknown_.
- **Platforms:** all — type-confusion in the write macro and a missing
  bounds guard.
- **Triggering configuration:**
  - **Type bug:** run without `-clear` on an input volume whose type is
    `float`, `short`, `ushort`, or `long` (`pointset2label wp.label
    float_vol.mgz 3 out.mgz`). With `-clear` the output is freshly
    allocated as `MRI_INT` and the `MRI_INT` arm is correct, so the type
    bug is dodged.
  - **Bounds bug:** any pointset whose splined path leaves the volume
    field of view (e.g. way-points near or beyond the volume edge).

## Detailed Description

### Type confusion in `set_voxel_value()`

`set_voxel_value()` rounds the world-derived voxel coordinate to integers
and then dispatches on `mri->type`. The intent is to store `val` using the
voxel accessor matching the volume's element type. FreeSurfer provides one
macro per type in `include/mri.h`:

- `MRIseq_vox`  — `BUFTYPE *` (unsigned char)
- `MRISseq_vox` — `short *`
- `MRIFseq_vox` — `float *`
- `MRIIseq_vox` — `int *`
- `MRILseq_vox` — `long32 *`

The function uses `MRIseq_vox` for `MRI_UCHAR` (correct) and `MRIIseq_vox`
for `MRI_INT` (correct), but then uses `MRIIseq_vox` — the `int *` macro —
for `MRI_LONG`, `MRI_FLOAT`, `MRI_SHORT`, and `MRI_USHRT` as well. Each of
those writes reinterprets the voxel's storage as a 4-byte `int`:

- **`MRI_FLOAT`:** the integer bit pattern of `(int)val` is written into a
  `float` cell; reading it back as a float yields a tiny denormalised or
  near-zero value (e.g. label 3 → the float for raw bits `0x00000003`),
  not `3.0`. The painted path is effectively invisible / corrupt.
- **`MRI_SHORT` / `MRI_USHRT`:** a 4-byte `int` is written where the cell
  is 2 bytes, overrunning into the adjacent voxel's 2 bytes — both the
  target voxel and its neighbour are corrupted.
- **`MRI_LONG`:** `long32` is 4 bytes on these platforms so the size
  happens to match, but the access still goes through the wrong-typed
  macro; it is correct only by coincidence of equal width and is fragile.

### Missing field-of-view bounds check

After `MRIworldToVoxel`, the code calls `set_voxel_value()` on `(x0,y0,z0)`,
`(x1,y1,z1)`, and the midpoint without verifying the voxel lies inside the
volume. `set_voxel_value()` itself does no range check before indexing the
data buffer. A spline point that maps outside `[0,width) × [0,height) ×
[0,depth)` therefore performs an out-of-bounds write.

### Expected Behaviour

For any output type, painting value `val` into voxel `(x,y,z)` should store
`val` cast to that type using the matching accessor (`MRIFseq_vox` for
float, `MRISseq_vox` for short/ushort, `MRILseq_vox` for long), and only
when `(x,y,z)` lies inside the volume. The simplest robust implementation
is `MRIsetVoxVal(mri, x, y, z, 0, val)`, which dispatches on type
internally and rounds/clamps appropriately, guarded by an index-in-volume
test.

### Observed Behaviour

Painting into a float/short/ushort volume deposits the raw `int` bit
pattern of the label value, corrupting the path voxels (and, for
short/ushort, their neighbours). Painting near a volume boundary can write
outside the allocated buffer.

### Reproducer

> [!gap] Reproducer not executed end-to-end
> Type bug:
>
> 1. Create or convert a volume to float
>    (`mri_convert -odt float T1.mgz T1f.mgz`).
> 2. `pointset2label wp.label T1f.mgz 3 out.mgz` (no `-clear`, so the
>    output keeps the float type).
> 3. Inspect `out.mgz` along the path: the painted voxels read as
>    ~`4.2e-45` (the float for int bits `0x00000003`), not `3.0`.
>
> Bounds bug: supply a `wp.label` whose splined path exits the volume FOV
> and observe the out-of-bounds write (e.g. under a sanitizer build).

void set_voxel_value(MRI* mri, double dx, double dy, double dz, double val)

## Root Cause

The non-`int` arms of the `switch` were written (or copy-pasted) using the
integer macro `MRIIseq_vox` rather than the type-specific accessor for
each branch. The `(int)val` cast compounds the float case by discarding
the fractional part before the bit-pattern is even mis-stored. The
`MRI_SHORT`/`MRI_USHRT` arms additionally write 4 bytes through a 2-byte
cell. The painting loop omits the `MRIindexNotInVolume()` guard that
FreeSurfer code conventionally places before a direct voxel write.

## Impact

- Writing a label path into a `float`, `short`, or `ushort` output volume
  produces a corrupt result: the path is either invisible (float reads
  back as ~0) or scribbles wrong values across the path and adjacent
  voxels (short/ushort). The corruption is **silent** — `MRIwrite`
  succeeds and no warning is emitted.
- The bug is **gated by the output volume's data type**: the common
  usage with `-clear` allocates an `MRI_INT` output and hits the correct
  arm, and a plain `MRI_INT`/`MRI_UCHAR` input is also fine. It only
  misfires when the user paints into a non-int input volume without
  `-clear`. This flag/type gating fixes the severity at **3 (medium)**:
  wrong output behind a specific input profile, not on the default
  `-clear`/integer path, and the tool is standalone (no pipeline reach).
- The missing bounds check is a latent out-of-bounds write that fires
  only for paths leaving the FOV; on its own it would be low severity,
  but it shares this page as a second defect in the same write routine.

## Recommended Fix

Use the type-correct accessors (or, more robustly, `MRIsetVoxVal`, which
dispatches internally), and guard the write with an in-volume check:

```diff
 void set_voxel_value(MRI* mri, double dx, double dy, double dz, double val)
 {
   int x = rint(dx), y = rint(dy), z = rint(dz);
-  switch ( mri->type )
-  {
-  case MRI_UCHAR:
-    MRIseq_vox( mri, x, y, z, 0 ) = (unsigned char)val;
-    break;
-  case MRI_INT:
-    MRIIseq_vox( mri, x, y, z, 0 ) = (int)val;
-    break;
-  case MRI_LONG:
-    MRIIseq_vox( mri, x, y, z, 0 ) = (int)val;
-    break;
-  case MRI_FLOAT:
-    MRIIseq_vox( mri, x, y, z, 0 ) = (int)val;
-    break;
-  case MRI_SHORT:
-  case MRI_USHRT:
-    MRIIseq_vox( mri, x, y, z, 0 ) = (int)val;
-    break;
-  default:
-    break;
-  }
+  if (MRIindexNotInVolume(mri, x, y, z))   /* FOV bounds check */
+    return;
+  MRIsetVoxVal(mri, x, y, z, 0, (float)val);   /* dispatches on mri->type */
 }
```

If a hand-rolled `switch` is preferred, replace the bodies with
`MRILseq_vox(...) = (long32)val;` (long), `MRIFseq_vox(...) = (float)val;`
(float), and `MRISseq_vox(...) = (short)val;` (short/ushort), keeping the
existing correct `MRI_UCHAR`/`MRI_INT` arms, and still add the
`MRIindexNotInVolume` guard.

### Alternative Fixes Considered

Force the output to `MRI_INT` regardless of input type (mirroring the
`-clear` path) so only the already-correct `int` arm is ever used. This
sidesteps the type bug but changes the output type the user asked for, so
fixing the accessors is preferable.

## Workarounds (If Any)

Always run with `-clear` (which allocates an `MRI_INT` output), or
pre-convert the input to `MRI_INT`/`MRI_UCHAR`
(`mri_convert -odt int ...`) before painting. Keep way-points well inside
the volume to avoid the unguarded out-of-bounds write.

> [!gap] long32 width coincidence
> On the supported 64-bit Linux/macOS targets `long32` and `int` are both
> 4 bytes, so the `MRI_LONG` arm is *currently* size-correct by accident;

> portability. The float and short/ushort arms are unambiguously wrong on
> all targets. A runtime reproducer on a float volume was not executed.
