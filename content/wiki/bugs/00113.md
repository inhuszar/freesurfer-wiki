# [severity-2] [bug-00113] `PathAlloc` and `PathCreateFromLabel` test the wrong variable in their null-checks; allocation failures produce silent NULL-deref on callers

> [!bug] Synopsis
> Two functions in `utils/path.cpp`
> consistently misplace their post-
> `calloc` null-check, testing a variable
> that's already known to be non-NULL
> instead of the freshly-allocated one.
>
> ```cpp
> /* utils/path.cpp:296-328 — PathAlloc */
> PATH *PathAlloc(int n_points, const char *name)
> {
>   PATH *path;
>
>   if (n_points < 0) return NULL;
>
>   path = (PATH *)malloc(sizeof(PATH));
>   if (NULL == path) {
>     printf("ERROR: Couldn't allocate path.\n");
>     return NULL;
>   }
>
>   path->n_points = n_points;
>   ...
>   path->points = (PATH_POINT *)calloc(n_points, sizeof(PATH_POINT));
>   if (NULL == path) {                          /* :321 — bug */
>     printf("ERROR: Couldn't allocate %d points in path.\n", n_points);
>     free(path);
>     return NULL;
>   }
>
>   return path;
> }
> ```
>
> The check at `:321` tests `path`, which
> the earlier check at `:304` already
> verified to be non-NULL. So:
>
> 1. If `calloc(n_points, sizeof(PATH_POINT))`
>    succeeds → `path->points` is valid →
>    `path` is non-NULL → check is false →
>    skip cleanup → return `path` (correct).
> 2. If `calloc` returns NULL →
>    `path->points = NULL`, but `path`
>    itself is still non-NULL → check is
>    false → skip cleanup → return `path`
>    with a NULL `points` field.
>
> Callers immediately access
> `path->points[i].x = ...` and
> dereference NULL.
>
> The intended check is
> `if (NULL == path->points)`.
>
> A second instance:
>
> ```cpp
> /* utils/path.cpp:424-450 — PathCreateFromLabel */
> int PathCreateFromLabel(LABEL *label, PATH **path)
> {
>   PATH *new_path = NULL;
>   ...
>   if (NULL == path) ErrorReturn(...);     /* :431 — validates `path` arg */
>
>   new_path = PathAlloc(label->n_points, NULL);
>   if (NULL == path)                       /* :435 — bug: should be new_path */
>     ErrorReturn(...);
>
>   for (pno = 0; pno < label->n_points; pno++) {
>     new_path->points[pno].x = ...;        /* segfault if PathAlloc returned NULL */
>   }
>   ...
> }
> ```
>
> At `:431`, `path` (the `PATH **`
> output parameter) is verified non-NULL.
> At `:435`, the same `path` is checked
> again — it can't have changed in the
> meantime. The check is dead code.
> When `PathAlloc` returns NULL,
> `new_path == NULL`, but the dead check
> doesn't fire, and the loop at `:439-444`
> dereferences NULL.

## Detailed Description

### What the code does on allocation failure

For `PathAlloc(n_points)`:

1. `path = malloc(sizeof(PATH))` — small,
   essentially never fails on modern
   Linux.
2. `path->n_points = n_points;`
   `path->name` set.
3. `path->points = calloc(n_points, ...)` —
   could fail for huge `n_points` or under
   memory pressure.
4. `if (NULL == path)` — never true (path
   is non-NULL from step 1).
5. Return `path` regardless of whether
   `path->points` was set.

So on `calloc` failure:
- Return value: non-NULL `path`.
- `path->points`: NULL.
- Caller pattern: e.g.
  `path->points[i].x = some_value` →
  segfault.

### Caller behaviour

`mri_path2label`'s typical pattern
([`:559`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_path2label/mri_path2label.cpp#L559)):

```cpp
paths[path_index] = PathAlloc(path_size, NULL);
/* no NULL check */
/* immediately writes paths[path_index]->points[i] */
```

There's no NULL check at the call site
either, so the segfault is the only
failure indication.

### `PathCreateFromLabel` bug variant

Same pattern, different reason for the
check being dead:

- `path` is the OUTPUT parameter
  (`PATH **`).
- It's validated non-NULL at
  `:431`.
- It can't change between `:431` and
  `:435`.
- The retry of the same check at
  `:435` is therefore meaningless dead
  code.
- The intended check on `new_path` (the
  `PATH *` returned by `PathAlloc`) is
  missing.

### Why the bug went undetected

Both functions allocate small numbers
of bytes for typical FreeSurfer surface
paths (a few hundred to thousand
points), and modern Linux's overcommit
practically never returns NULL from
`calloc` for such sizes. Memory failure
is the only path that exercises the
buggy null-check, and the path is
extremely rare in practice.

## Root Cause

Copy-paste of the variable name `path`
from the earlier (correct) check on the
struct allocation, without updating it
to refer to the field being allocated
(`path->points`) or the local
(`new_path`).

The sister function
`PathConvertToLabel` (allocates a label
from a path) at
[`:404-406`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/path.cpp#L404-L406)
uses the correct pattern
(`if (NULL == new_label)`) — confirming
that the author understood the intended
idiom and just transcribed it wrong in
the two affected functions.

## Impact

- **In practice:** modern Linux's
  overcommit means `calloc` rarely
  returns NULL, so the bug almost never
  manifests in real workflows.
- **When it manifests:** silent NULL
  dereference / segfault rather than
  graceful error.
- **Severity:** 2 — clear correctness
  bug, but very low practical impact
  outside memory-constrained
  environments.

## Workarounds

For users running into segfaults under
memory pressure: increase available
memory or split paths into smaller
chunks. There is no flag-level
workaround.

- **Evidence:**
  - `path` at line 321 is guaranteed

  - `path->points` is the freshly-

  - In `PathCreateFromLabel`, `path`

    `:431`.
