# [severity-3] [bug-00112] `ByteSwap2`/`ByteSwap4`/`ByteSwap8` swap only a fraction of the requested items

> [!bug] Synopsis
> All three byte-swap routines have the
> same loop-bound bug:
>
> ```cpp
> /* utils/machine.cpp:240-253 — ByteSwap2 */
> int ByteSwap2(void *buf2, long int nitems)
> {
>   char *cbuf, ctmp;
>   long int n;
>
>   cbuf = (char *)buf2;
>   for (n = 0; n < nitems; n += 2) {       /* :246 — bound is nitems, step is 2 */
>     ctmp = *cbuf;
>     *cbuf = *(cbuf + 1);
>     *(cbuf + 1) = ctmp;
>     cbuf += 2;
>   }
>   return (0);
> }
> ```
>
> The function comment says
> *"nitems is the number of 2-byte items
> in buf2"* — so the loop should iterate
> `nitems` times (each iteration swaps one
> 2-byte item and advances `cbuf` by 2).
> Instead the loop counter advances by 2
> per iteration AND the bound is `nitems`,
> so only `nitems / 2` iterations run.
>
> `ByteSwap4`
> ([`:259-280`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/machine.cpp#L259-L280))
> uses `n += 4` and bound `nitems` →
> swaps `nitems / 4` items.
>
> `ByteSwap8`
> ([`:286-317`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/machine.cpp#L286-L317))
> uses `n += 8` and bound `nitems` →
> swaps `nitems / 8` items.
>
> Concrete trace, `ByteSwap2(buf, 4)`
> (4 short items, 8 bytes):
>
> | iter | `n` | action                     | items processed |
> |------|-----|----------------------------|-----------------|
> | 1    | 0   | swap bytes 0,1 (item 0)    | 1               |
> | 2    | 2   | swap bytes 2,3 (item 1)    | 2               |
> | exit | 4   | `4 < 4` false              | —               |
>
> Items 2 and 3 (bytes 4–7) are **not**
> swapped.

## Affected Artefacts

- **Tool:** [[mri_probe_ima]] — reads
  Siemens IMA files for diagnostic
  display. Calls
  `imaReadPixelData(ifi, NULL)`

- **Pipeline stage(s):** none in default
  `recon-all`. IMA reading is a niche
  format-conversion path.
- **Triggering configuration:** running
  on a little-endian (x86) host AND
  reading an IMA file with multi-item
  byte-array data. The IMA convention
  (per `imautils.cpp:74-75` comment) is
  Sun big-endian, so x86 hosts always
  trigger the swap.
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION` (commit
  `d932c45b79`).

## Detailed Description

### Latent for nitems = 1

`imaLoadVal`
([`utils/imautils.cpp:45-82`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/imautils.cpp#L45-L82))
reads single header values with
`nitems = 1` (most dictionary entries are
one int / short / double / long). With
`nitems = 1`:

- ByteSwap2: `n = 0; 0 < 1` → swap once,
  then `n = 2; 2 < 1` → exit. **One item
  swapped, correct.**
- ByteSwap4: `n = 0; 0 < 1` → swap once,
  exit. **Correct.**
- ByteSwap8: `n = 0; 0 < 1` → swap once,
  exit. **Correct.**

So all single-value header reads work
correctly — the bug never trips for
`nitems = 1`.

### Manifest for nitems > 1

`imaReadPixelData`
([`utils/imautils.cpp:582-623`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/imautils.cpp#L582-L623))
calls
`ByteSwapBuf(PixelData, npixels, sizeof(short))`
where `npixels` is the number of pixels in
the IMA image (typically 256² = 65536 or
512² = 262144).

| `npixels` | items expected swapped | items actually swapped | items unswapped |
|-----------|------------------------|------------------------|-----------------|
| 65536     | 65536                  | 32768                  | 32768           |
| 262144    | 262144                 | 131072                 | 131072          |

The "unswapped" pixels live at the
**second half** of the image array. After
the call, the first half of pixels are
correctly little-endian; the second half
are still big-endian (i.e. their bytes
are reversed relative to what x86
expects). Displaying the image:

- Top half (or left half, depending on
  storage order): correct intensities.
- Bottom half: bytes reversed → e.g. a
  pixel storing the value 1234
  (`0x04D2`) gets read as 0xD204 = 53764
  on x86. Saturated noise pattern.

### Why the bug went undetected

The dominant in-tree caller pattern is
`nitems = 1` (header reads), which is
correct by accident. The pixel-data path
has a single caller (`mri_probe_ima`) and
is rarely exercised — most users convert
IMA via `mri_convert`, which uses the
DICOM reader path
(`utils/DICOMRead.cpp`), not the legacy
imautils path.

### The fix

For each of the three functions, the
correct loop is to iterate `nitems`
times, with `cbuf` advancing by the item
size. Either:

```cpp
for (n = 0; n < nitems; n++) {
  /* swap bytes at cbuf */
  cbuf += /* item size */;
}
```

or equivalently extend the loop bound to
`nitems * itemSize`:

```cpp
for (n = 0; n < nitems * 2; n += 2) {  /* ByteSwap2 */
  /* swap */
  cbuf += 2;
}
```

The first form is clearer and avoids the
multiplication.

## Root Cause

Confused loop semantics: the author
treated `n` as a byte counter (advancing
by `itemSize` each iteration) but bounded
the loop by `nitems` (which is in items,
not bytes). Either bound or step is
inconsistent with the variable name.

The bug evades simple integration testing
because the most common caller path
(`nitems = 1`) is correct by coincidence.

## Impact

- **`mri_probe_ima --pixel-data`:** the
  second half of pixel intensities are
  read with bytes reversed, producing a
  visually-corrupted half-image.
- **Header-only reads:** unaffected (all
  use `nitems = 1`).
- **Default `recon-all`:** unaffected
  (does not call IMA pixel readers; uses
  DICOM path).
- **Severity:** 3 — niche tool, niche
  format, but real and silent
  data-corruption bug when triggered.

## Recommended Fix

```diff
--- a/utils/machine.cpp
+++ b/utils/machine.cpp
@@ -243,7 +243,7 @@ int ByteSwap2(void *buf2, long int nitems)
   long int n;

   cbuf = (char *)buf2;
-  for (n = 0; n < nitems; n += 2) {
+  for (n = 0; n < nitems; n++) {
     ctmp = *cbuf;
     *cbuf = *(cbuf + 1);
     *(cbuf + 1) = ctmp;
     cbuf += 2;
   }
@@ -262,7 +262,7 @@ int ByteSwap4(void *buf4, long int nitems)
   long int n;

   cbuf = (char *)buf4;
-  for (n = 0; n < nitems; n += 4) {
+  for (n = 0; n < nitems; n++) {
     ctmp = *cbuf;
     ...
     cbuf += 4;
   }
@@ -289,7 +289,7 @@ int ByteSwap8(void *buf8, long int nitems)
   long int n;

   cbuf = (char *)buf8;
-  for (n = 0; n < nitems; n += 8) {
+  for (n = 0; n < nitems; n++) {
     ctmp = *cbuf;
     ...
     cbuf += 8;
   }
```

The fix is identical for all three: change
the increment from `n += itemSize` to
`n++`. The bound `n < nitems` then
correctly iterates `nitems` times.

## Workarounds

For users who need correct IMA pixel
reads on x86: apply the fix and rebuild,
or convert IMA files via `mri_convert`
(which routes through the DICOM reader
that doesn't share this bug).

## Provenance and Discovery

- **Discovered:** 2026-05-10 by agent
  (audit of small utility files in
  `utils/`).
- **Evidence:**
  - `cbuf` advances by `itemSize` per
    iteration (e.g. `cbuf += 2;` in
    ByteSwap2 at
    [`:250`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/machine.cpp#L250)),
    so each iteration processes one
    item's worth of bytes.
  - Loop counter `n` also advances by
    `itemSize` (`n += 2`).
  - Loop bound is `nitems` (not
    `nitems * itemSize`).
  - Therefore total iterations =
    `nitems / itemSize`, not `nitems`.
  - Concrete trace with `nitems = 4`
    confirms only 2 items swapped (out
    of 4 expected).
  - `swapShort` / `swapFloat` etc.
    (single-value siblings) are
    unaffected and correct.

## Verification Checklist

- [x] Loop step `n += itemSize` covers
      one item per iteration.
- [x] Loop bound `n < nitems`
      terminates after `nitems / itemSize`
      iterations.
- [x] `cbuf` advances by `itemSize` per
      iteration (correct pace).
- [x] Single-item callers
      (`imaLoadVal nitems=1`) work by
      coincidence.
- [x] Multi-item callers
      (`imaReadPixelData
      npixels=65536+`) manifest the
      bug.
- [x] Function comments at `:235-238`
      etc. clearly state nitems is the
      ITEM count, not the BYTE count.
