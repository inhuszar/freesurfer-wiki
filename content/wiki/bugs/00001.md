# gcaComputeSampleConditionalDensity — missing 1/2 factor in Mahalanobis exponent

> [!bug] Synopsis
> The sample-variant conditional-density helper in `utils/gca.cpp` evaluates
> the multivariate Gaussian density with `exp(-d)` instead of
> `exp(-d/2)`, where `d` is the squared Mahalanobis distance. The density
> is therefore inconsistent with its own log counterpart
> (`gcaComputeSampleConditionalLogDensity`, which correctly uses `0.5 * d`)
> and with the node-level helper `GCAcomputeConditionalDensity`. The defect
> reaches user-visible output via `GCAtransformAndWriteSamplePvals`, which
> writes the `<base>NNN_pvals.mgz` diagnostic volume from
> `mri_em_register`; posterior probabilities written into that volume are
> over-confident (far too close to 0 or 1) whenever a sample sits more
> than one sigma from its class mean.

- **Tool(s):** [[mri_em_register]] (via `GCAtransformAndWriteSamplePvals`)
- **Pipeline stage(s):** `autorecon1` / EM-register step in [[recon-all]];

- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45b79`;

- **Triggering configuration:** any invocation of `mri_em_register` that
  causes the sample-pvals volume to be written (the calls are at
  [`mri_em_register/mri_em_register.cpp:831`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_em_register/mri_em_register.cpp#L831), `:934`, `:1361`, `:1528` —

  default `recon-all` invocations.

## Detailed Description

`gcaComputeSampleConditionalDensity` is used to evaluate the Gaussian
density of an intensity vector under a single `GCA_SAMPLE`'s mean and
covariance, and to combine those densities with per-label priors into a
posterior. The density formula it implements omits the `1/2` factor in
the exponent of the multivariate Gaussian, producing a density that is
squared relative to the correct Gaussian (up to constants).

### Expected Behaviour

For a multivariate Gaussian with mean `μ`, covariance `Σ`, and
Mahalanobis distance `d² = (x − μ)ᵀ Σ⁻¹ (x − μ)`:

$$
f(x) = \frac{1}{(2\pi)^{k/2}\,\sqrt{\det \Sigma}}\,
       \exp\!\left(-\tfrac{1}{2}\,d^{2}\right).
$$

The companion helpers confirm this:

- `GCAcomputeConditionalDensity` ([`utils/gca.cpp:12255`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gca.cpp#L12255)):
  `p = (1.0 / (pow(2*M_PI, ninputs/2.0) * sqrt(det))) * exp(-0.5 * dist);` ✓
- `gcaComputeSampleConditionalLogDensity` ([`utils/gca.cpp:13084`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gca.cpp#L13084)):
  `log_p = -log(sqrt(det)) - .5 * GCAsampleMahDist(...);` ✓

### Observed Behaviour

`gcaComputeSampleConditionalDensity` ([`utils/gca.cpp:13206`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gca.cpp#L13206)) uses
`exp(-dist)` — no `0.5` multiplier. Exponentiating the companion log
density therefore does **not** reproduce this function's output; the two
disagree by a factor of `exp(-dist/2)`. Because `dist` is the squared
Mahalanobis distance (returned unscaled by `GCAsampleMahDist`), the bug
turns the Gaussian into its own square (up to normalisation), which is
effectively a Gaussian with half the variance. Posteriors formed by
normalising these densities over labels are therefore far more peaked
than intended.

```cpp
static double gcaComputeSampleConditionalDensity(GCA_SAMPLE *gcas, float *vals, int ninputs, int label)

  double p, dist;

  {
    dist = GCAsampleMahDist(gcas, vals, ninputs);
    p = 1 / sqrt(sample_covariance_determinant(gcas, ninputs)) * exp(-dist);
  }
  return (p);
}
```

```cpp
double GCAcomputeConditionalDensity(GC1D *gc, float *vals, int ninputs, int label)
{
  double p, dist;

/* compute 1-d Mahalanobis distance */
  {
    dist = GCAmahDist(gc, vals, ninputs);
    p = (1.0 / (pow(2 * M_PI, ninputs / 2.0) * sqrt(covariance_determinant(gc, ninputs)))) * exp(-0.5 * dist);
  }
  return (p);
}
```

## Root Cause

The `0.5` coefficient on the Mahalanobis quadratic was omitted when the
sample-density helper was written (or was removed at some point and not
corrected). `GCAsampleMahDist` unambiguously returns the squared
Mahalanobis distance — the one-input branch at [`utils/gca.cpp:13169`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gca.cpp#L13169)
computes `v*v / covars[0]`, matching the definition of `d²` — so the
exponent in the density formula must be `−d²/2`, not `−d²`.

## Impact

- Affects the `<basename>NNN_pvals.mgz` diagnostic volume produced by
  `mri_em_register` when its sample-write code paths run (they are gated
  behind debug/flag options: `transformed_sample_fname`,
  `write_samples`, `write_fsamples_dir`, and the `norm_fname` path with
  the surrounding `#if 0` disabled).
- Because the identical formula is used in the numerator and the
  summed-denominator in `GCAtransformAndWriteSamplePvals` (lines 5707
  and 5711), the missing factor does **not** cancel: per-label densities
  are raised to a higher effective power, and posteriors saturate much
  faster than the true Gaussian model predicts. Visualising the pvals
  volume therefore under-represents ambiguity between labels and can
  mislead a user inspecting atlas fit quality.
- The core EM registration transform is not affected: the optimisation
  objective goes through `local_GCAcomputeLogSampleProbability` (which
  uses the log-density helper, and is correct). The single call to
  `GCAnormalizedLogSampleProbability` in [`mri_em_register.cpp:947`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_em_register/mri_em_register.cpp#L947) is
  inside `#if 0`, so its separate issues do not reach users today.

## Recommended Fix

Insert the missing `0.5` factor so the function matches
`GCAcomputeConditionalDensity` and the log-density companion:

```diff
 static double gcaComputeSampleConditionalDensity(GCA_SAMPLE *gcas, float *vals, int ninputs, int label)
 {
   double p, dist;

 /* compute 1-d Mahalanobis distance */
   {
     dist = GCAsampleMahDist(gcas, vals, ninputs);
-    p = 1 / sqrt(sample_covariance_determinant(gcas, ninputs)) * exp(-dist);
+    p = 1 / sqrt(sample_covariance_determinant(gcas, ninputs)) * exp(-0.5 * dist);
   }
   return (p);
 }
```

Optionally, add the `(2π)^(-k/2)` normalisation factor for parity with
`GCAcomputeConditionalDensity`; this is not required for correctness of
the posterior computation in `GCAtransformAndWriteSamplePvals` (it
cancels in the ratio), but it would make the two helpers return the
same density value for the same inputs.

### Alternative Fixes Considered

Rewriting the helper in terms of
`gcaComputeSampleConditionalLogDensity` (i.e., `p = exp(log_p)`) would
guarantee the two helpers stay in sync and prevent future divergence.
Trade-off: slightly slower due to the round-trip through `log`/`exp`.

## Workarounds (If Any)

None in the running tool. Users inspecting `*_pvals.mgz` should treat
extreme values (0 or 1) with caution, or recompute posteriors externally
from the means/covariances stored in the atlas using the correct
Gaussian formula.
