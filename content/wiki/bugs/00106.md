# [severity-3] [bug-00106] `MRIvoxelDirection` first loop under-fills the gradient buffers near the upper boundary

> [!bug] Synopsis
> `MRIvoxelDirection`
> ([`utils/mrivoxel.cpp:316-384`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrivoxel.cpp#L316-L384))
> populates per-voxel gradient buffers
> (`dx_win`, `dy_win`, `dz_win`) for a
> `wsize × wsize × wsize` neighbourhood, then
> walks the buffers a second time to combine
> them with the centre voxel's gradient.
>
> The two loops disagree on bounds:
>
> ```cpp
> /* upper bounds clamped, lower bounds NOT */
> zmax = MIN(depth  - 1, z0 + whalf);
> ymax = MIN(height - 1, y0 + whalf);
> xmax = MIN(width  - 1, x0 + whalf);
>
> /* first loop — fills pdx/pdy/pdz */
> for (z = z0 - whalf; z <= zmax; z++) {
>   for (y = y0 - whalf; y <= ymax; y++) {
>     for (x = x0 - whalf; x <= xmax; x++) {
>       *pdx++ = MRIvoxelDx(mri, x, y, z);
>       ...
>     }
>   }
> }
>
> /* second loop — reads pdx/pdy/pdz UNCLAMPED */
> for (z = -whalf; z <= whalf; z++) {
>   for (y = -whalf; y <= whalf; y++) {
>     for (x = -whalf; x <= whalf; x++) {
>       dx = *pdx++;
>       ...
>     }
>   }
> }
> ```
>
> When the query voxel is near the **upper**
> volume boundary, `zmax`, `ymax`, or `xmax`
> is clamped below `z0+whalf`, and the first
> loop iterates fewer than `2*whalf+1` times
> on those axes — but the second loop always
> iterates the full count and reads beyond
> the initialised portion of the buffers.
>
> The commented-out `memset` block at
> [`:334-338`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrivoxel.cpp#L334-L338)
> (`#if 0` …) was the abandoned mitigation;
> currently the unfilled slots hold whatever
> uninitialised stack memory was at those
> addresses.

## Affected Artefacts

- **Tool:** [[mri_segment]] — single in-tree
  caller at
  [`mri_segment/mri_segment.cpp:737`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_segment/mri_segment.cpp#L737)
  invokes the function per voxel during
  intensity-based segmentation.
- **Pipeline stage(s):** default `recon-all`
  (auto-recon2, white-matter segmentation
  step).
- **Triggering configuration:** any voxel
  whose `(x, y, z)` is within `whalf` of the
  upper boundary on any axis. With the
  `mri_segment` default `wsize == 3`,
  `whalf == 1`, so this is the last slice
  / row / column on each axis.
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION` (commit `d932c45b79`).

## Detailed Description

### Asymmetric clamping

`zmax` is clamped to `MIN(depth-1,
z0+whalf)`. The lower bound is not similarly
clamped:

| voxel position             | first-loop iterations on z | second-loop iterations on z |
|----------------------------|----------------------------|------------------------------|
| interior (`z0+whalf < depth`) | `2*whalf+1`              | `2*whalf+1` ✓                |
| near lower edge (`z0-whalf < 0`) | `2*whalf+1` (with negative `z` clamped inside `MRIvoxelDx` via `zi[]`) | `2*whalf+1` ✓ |
| near upper edge (`z0+whalf >= depth`) | `depth-1 - (z0-whalf) + 1 < 2*whalf+1` | `2*whalf+1` ✗ |

For the upper-edge case, the first loop
under-fills the buffer; the second loop reads
past the filled portion. Multiplied across
three axes, the under-filled count grows
quickly: a corner-of-volume voxel with
`whalf=1` populates `2 × 2 × 2 = 8` slots
out of `3 × 3 × 3 = 27` and the other 19
reads are from uninitialised stack memory.

### Numerical effect

`dx_win[]`, `dy_win[]`, `dz_win[]` are local
`float` arrays of length
`MAX_WINDOW^3 = 343`. Local stack arrays are
not zero-initialised in C; their initial
contents reflect whatever was on the stack
from previous function calls.

The second loop reads `dx`, `dy`, `dz` and
combines them via

```cpp
dir += (x * odx + y * ody + z * odz) * (dx * odx + dy * ody + dz * odz);
```

So `dir` accumulates a product of
(stack-garbage) × (gradient-of-centre),
contaminating the final return value
proportionally to the number of unfilled
slots.

For the mri_segment caller, edge voxels in
the head/foot/lateral planes get a randomly
biased `dir` value, which then influences
the segmentation classification near the
volume boundary.

## Root Cause

Mismatched clamping conventions between the
two loops — the first loop's bounds were
written defensively (clamp upper to in-range)
but the second loop assumes the caller's
local notion of `[-whalf, whalf]` always
fills the buffer. The author's commented-out
memset at `:334-338` shows they noticed the
issue but rolled it back (probably for
performance) rather than committing to a
proper fix.

## Impact

- **Default `mri_segment` runs:** edge
  voxels (last `whalf` slices / rows / cols
  per axis) have their `dir` value
  contaminated by stack memory. With the
  default `wsize=3` (`whalf=1`), this is the
  last 1-voxel-thick boundary band.
- **Determinism:** the contamination is
  whatever the calling stack contains, so
  results may differ across runs / build
  configurations / compilers.
- **Severity:** 3 — default `recon-all` path
  with a small but reachable boundary effect;
  not single-frame-output-corrupting because
  the affected voxels are sparse, but
  non-deterministic.

## Recommended Fix

Either clamp the first loop's lower bounds
symmetrically OR enable the commented-out
zero initialisation OR clamp the second
loop's bounds to match the first.

The cleanest is symmetric initialisation:

```diff
--- a/utils/mrivoxel.cpp
+++ b/utils/mrivoxel.cpp
@@ -333,11 +333,9 @@ float MRIvoxelDirection(MRI *mri, int x0, int y0, int z0, int wsize)
   /* should do something smarter than this about border conditions */
-  #if 0
   memset(dx_win, 0, MAX_LEN*sizeof(float)) ;
   memset(dy_win, 0, MAX_LEN*sizeof(float)) ;
   memset(dz_win, 0, MAX_LEN*sizeof(float)) ;
-  #endif
```

This zeros the buffers so the under-filled
slots contribute 0 to the second loop's
accumulator — deterministic, no-op for
interior voxels, and bounded for edge
voxels.

A more thorough fix also clamps the lower
bounds of the first loop and writes to
specific indices (rather than via
`*pdx++`), so the second loop can clamp its
range too.

## Workarounds

For users who want deterministic output near
volume boundaries, run `mri_segment` with
extra padding (e.g. `mri_convert --pad`
before, then crop after).
