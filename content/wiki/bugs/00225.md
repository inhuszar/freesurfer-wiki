# [severity-1] [bug-00225] surf2vol — TMeshCrop::PopulateNodes never deduplicates node ids: new-solver crops carry about 20x orphan nodes and equations

> [!bug] Synopsis
> `TMeshCrop::PopulateNodes` appends the node ids of every element of a cluster to a vector without removing duplicates, and `TMeshCrop::Crop` creates one new node per entry. Each interior node is
> therefore created once per element that touches it (about 20 times in a typical tetrahedral mesh), and all but the last copy are orphans that no element references. The result is a local FEM problem with roughly 20 times
> more nodes, vectors and matrix rows than necessary. The effect is memory and time only; it appears only in the new topology solver (`surf2vol` without `-topology_old`), not in the [[mri_cvs_register]] path.

## Affected Artefacts

- **Tool(s):** [[surf2vol]] without `-topology_old`
- **Pipeline stage(s):** _N/A_ — [[mri_cvs_register]] passes `-topology_old` and so never builds a `TMeshCrop`
- **FreeSurfer version(s):** confirmed in `8.2.0`; present since the surf2vol import, 2008-04-18 (`9761aeb9b6`)
- **Platforms:** all
- **Triggering configuration:** every cluster cropped by `TopologySolver::DoLocalSmoothing()` (new solver) in a FEM step that has inverted elements.

## Detailed Description

`Crop()` first collects the nodes of the cluster's elements, then creates one node of the cropped mesh for each collected entry ([`fem_elastic/pbCluster_mesh_crop.cpp:311-316`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/pbCluster_mesh_crop.cpp#L311-L316),
[`fem_elastic/pbCluster_mesh_crop.cpp:335-354`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/pbCluster_mesh_crop.cpp#L335-L354)):

```cpp
  {
    unsigned int index = 0;
    for (typename IndexContainerType::const_iterator cit
         = vnodes.begin();
         cit != vnodes.end();
         ++cit, ++index )
    {
      m_pmesh->get_node( *cit, &pnodeIn );
      if ( !pnodeIn )
        throw " TMeshCrop - NULL node while cropping ";
      pnodeOut = Cstr::node(index,
                            pnodeIn->coords(),
                            pnodeIn->delta(),
                            pnodeIn->is_active() );
      outMesh->add_node(pnodeOut);

      internalMap[ *cit ] = index;
      o_nodeMap[ index ] = *cit;
    } // next cit, index
  }
```

The collector pushes every node of every element (four per tetrahedron) into the output iterator with no `set` / `unique` step:

```cpp
template<class Cstr, int n>
void
TMeshCrop<Cstr,n>::PopulateNodes( const IndexContainerType& velts,
                                  IndexContainerII ii_nodes
                                )
{
  for ( typename IndexContainerType::const_iterator cit
        = velts.begin();
        cit != velts.end();
        ++cit )
  {
    NodeType* pnode = NULL;
    const ElementType* cpelt
    = m_pmesh->get_elt(*cit);

    for (unsigned int ui(0), nnodes(cpelt->no_nodes());
         ui < nnodes; ++ui)
    {
      cpelt->get_node(ui, &pnode);
      if ( !pnode )
        throw " TMeshCrop::PopulateNodes - NULL node ";
      ii_nodes = pnode->get_id();
    }
  }

}
```

Each entry becomes a separate new node (`index` increments per entry), but `internalMap[ *cit ] = index` keeps only the **last** index for a repeated original id. Elements are wired through `internalMap`
([`fem_elastic/pbCluster_mesh_crop.cpp:377-381`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/pbCluster_mesh_crop.cpp#L377-L381)), so only the last copy of each node belongs to any element; the earlier copies are orphans that have `nodeMap` entries but no elements. The boundary list is deduplicated
([`fem_elastic/pbCluster_mesh_crop.cpp:323-327`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/pbCluster_mesh_crop.cpp#L323-L327), after `PopulateBoundaryNodes` has walked all duplicates, [`fem_elastic/pbCluster_mesh_crop.cpp:454-469`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/pbCluster_mesh_crop.cpp#L454-L469)), but the node list is not. The older untangler's crop (`TPbMeshCrop`) collects nodes in a `std::set` (`allNodes`, [`fem_elastic/pbmesh_crop.h:105-118`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/pbmesh_crop.h#L105-L118)) and has no such duplication.

Magnitude: a cropped patch of `E` tetrahedra produces `4E` nodes but only `U` distinct ones. In the 300-point Delaunay mesh used as a harness for the FEM core (6,896 nodes, 37,545 tetrahedra) the whole-mesh ratio is `4 × 37,545 / 6,896 ≈ 21.8`. Patches have a lower ratio because
boundary nodes are shared by fewer elements, so "about 20×" is an estimate for the patch interior, not a measurement of an actual `DoLocalSmoothing` crop.

### Expected Behaviour

The cropped mesh contains exactly one node per distinct original node of the cluster.

### Observed Behaviour

The cropped mesh contains one node per node-element incidence. The orphan nodes get zero rows in the stiffness matrix (no element contributes to them), and each adds three degrees of freedom to the vectors and the matrix.
The write-back loop ([`fem_elastic/pbCluster_mesh_crop.cpp:280-289`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/pbCluster_mesh_crop.cpp#L280-L289)) visits all cropped nodes in index order, so for a repeated id the last copy, the one the elements use, is written last and wins; hence the results are not corrupted by the duplicates.

### Reproducer

> [!gap] Reproducer not yet constructed
> The duplication is evident from the code. A harness that builds a cluster, calls `Crop`, and counts nodes was not written, and the numerical consequences of the zero rows in the direct solve were not examined (by reading, the right-hand side and initial guess are zero at orphans, so they stay at zero).

## Root Cause

`PopulateNodes` writes to a `back_insert_iterator` over a `std::vector` and the caller assumes the result is a set of unique ids. The vector is never sorted or uniqued, in contrast with `origBoundaryNodes`, which is, a few lines earlier.

## Impact

- **Memory and time only:** each crop allocates and assembles a local FEM problem about an order of magnitude larger than needed; `PopulateBoundaryNodes` also loops over all duplicated entries. No effect on the displacement field is expected.
- **Severity 1 (trivial):** a performance/memory inefficiency, numerically hidden by construction, in a code path that the shipped pipeline never uses (and that has a separate correctness defect, [[00222]]). Scored 1 rather than 2 because there is no incorrect output and no in-tree script reaches the path.

## Recommended Fix

Deduplicate right after `PopulateNodes` (sorted order is the same as the `std::set` order the old crop uses):

```diff
--- a/fem_elastic/pbCluster_mesh_crop.cpp
+++ b/fem_elastic/pbCluster_mesh_crop.cpp
   this->PopulateNodes( i_vidxElements,
                        std::back_inserter(vnodes)
                      );
+  std::sort( vnodes.begin(), vnodes.end() );
+  vnodes.erase( std::unique( vnodes.begin(), vnodes.end() ), vnodes.end() );
```

`PopulateBoundaryNodes` requires only that `velts` (the element indices) is sorted, which it already is. Test: crop a small mesh and assert `outMesh->get_no_nodes()` equals the number of distinct node ids.

## Workarounds (If Any)

Use `-topology_old` (the default of [[mri_cvs_register]]).
