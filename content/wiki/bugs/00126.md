# [severity-3] [bug-00126] `MRISwriteIntoVolume` NULL-input alloc returns wrong-shaped MRI, causing the indexing branch to fail and the function to leak + return NULL

> [!bug] Synopsis
> ```cpp
> /* utils/mrisurf_io.cpp:412-470 */
> MRI *MRISwriteIntoVolume(MRI_SURFACE *mris, MRI *mri, int which)
> {
>   int vno;
>   VERTEX *v;
>   float val = 0;
>
>   if (mri == NULL) {
>     mri = MRIalloc(1, 1, mris->nvertices, MRI_FLOAT);  /* :419 — bug */
>   }
>
>   for (vno = 0; vno < mris->nvertices; vno++) {
>     v = &mris->vertices[vno];
>     if (v->ripflag) continue;
>     switch (which) { ... val = v->dx / dy / dz / val / curv / annotation / area ... }
>     if (mri->width == mris->nvertices)
>       MRIsetVoxVal(mri, vno, 0, 0, 0, val);                /* :455 */
>     else if (mri->nframes == mris->nvertices)
>       MRIsetVoxVal(mri, 0, 0, 0, vno, val);                /* :457 */
>     else {
>       ErrorReturn(NULL,
>                   (ERROR_BADPARM,
>                    "MRISwriteIntoVolume: nvertices %d doesn't match ..."));
>     }
>   }
>   return (mri);
> }
> ```
>
> When `mri == NULL`, the function
> allocates a `width=1`,
> `height=1`, `depth=nvertices`,
> `nframes=1` MRI. The
> per-vertex writeback then
> checks `mri->width ==
> nvertices` (1 vs nvertices →
> **false**) and
> `mri->nframes == nvertices`
> (1 vs nvertices → **false**),
> and falls into the
> `ErrorReturn(NULL, …)` path
> on the very first vertex.
>
> The just-allocated `mri` is
> leaked (no
> `MRIfree(&mri)` before
> `return`), and the function
> returns NULL.
>
> Sister function
> `MRISreadFromVolume` at
> `:478-526` requires
> `mris->nvertices ==
> mri->width` (it indexes
> as `MRIgetVoxVal(mri, vno,
> 0, 0, 0)`), so the
> indexing convention is
> "vertex index lives in the
> width dimension." The
> alloc at `:419` is what
> diverged.

## Detailed Description

### Step-by-step on the
defective path

1. Caller (e.g.
   `mrisurf_integrate.cpp:569`)
   calls
   `mri = MRISwriteIntoVolume(mris, NULL, VERTEX_DX);`
2. Inside, `mri ==
   NULL`, so [`:418-420`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_io.cpp#L418-L420):
   ```c
   mri = MRIalloc(1, 1, mris->nvertices, MRI_FLOAT);
   ```
   `MRIalloc(width, height,
   depth, type)` returns
   `width=1, height=1,
   depth=nvertices,
   nframes=1`.
3. Loop enters, `vno=0`,
   skips ripflag check (or
   not), computes `val`.
4. Check [`:454`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_io.cpp#L454):
   `mri->width ==
   mris->nvertices` →
   `1 == nvertices` → false.
5. Check [`:456`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_io.cpp#L456):
   `mri->nframes ==
   mris->nvertices` →
   `1 == nvertices` → false.
6. Fall to [`:459-466`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_io.cpp#L459-L466)
   `ErrorReturn(NULL, ...)`.
   Macro prints
   `"MRISwriteIntoVolume:
   nvertices N doesn't match
   with in MRI 1 x 1 x N x
   1"` and returns NULL.
7. Memory leak: the MRI
   allocated at step 2 is
   never freed.
8. Caller now has `mri ==
   NULL`. Next line
   ([`:570`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_integrate.cpp#L570)):
   `MRIwrite(mri, fname);`
   — passes NULL.
   `MRIwrite` typically
   dereferences `mri->type`,
   `mri->width`, etc., so
   this segfaults (or
   crashes with a NULL
   deref).

### Sister function
agrees on shape

`MRISreadFromVolume`
([`:478-526`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_io.cpp#L478-L526))
enforces `mris->nvertices
== mri->width` at the
top (line 484) and reads
via
`MRIgetVoxVal(mri, vno,
0, 0, 0)`. So the
indexing-by-width
convention is the
authoritative one;
`MRISwriteIntoVolume`'s
`else if (mri->nframes ==
nvertices)` branch is a
secondary accommodation
that happens to be
incompatible with both
the NULL alloc and the
read sister function.

### What the correct
alloc would be

```c
mri = MRIalloc(mris->nvertices, 1, 1, MRI_FLOAT);
```

or equivalently:

```c
mri = MRIallocSequence(mris->nvertices, 1, 1, MRI_FLOAT, 1);
```

This matches the working
caller pattern at
[`mri_extract_fcd_features.cpp:483`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_extract_fcd_features/mri_extract_fcd_features.cpp#L483)
and the sister `Read`
function's expected
input shape.

### Why this is severity 3
(not 4)

- Reachable, silent
  (well, it does emit an
  `ErrorPrintf`), and
  causes a crash on the
  diagnostic write path.
- BUT: only fires in
  opt-in diagnostic mode
  (`Gdiag & DIAG_WRITE`
  +
  `DIAG_VERBOSE_ON` +
  `write_iterations > 0`).
- A user running
  production
  `mris_register` /
  `mris_make_surfaces`
  without verbose debug
  flags is unaffected.
- Developers running
  with full diagnostics
  get an immediate
  crash, which is
  recoverable.

## Root Cause

The alloc shape inside
the NULL-input fallback
diverged from the
indexing convention
used elsewhere in the
function (and in the
sister read function).
The argument order of
`MRIalloc(width, height,
depth, type)` puts
`nvertices` in the
`depth` slot at `:419`,
but the inner loop
expects it in the
`width` (or `nframes`)
slot.

## Impact

- **Production runs**:
  unaffected
  (diagnostic flags
  not set).
- **Developer debug
  runs**
  (`-v -w` for
  `mris_register`,
  `mris_make_surfaces`,
  etc., **with**
  `DIAG_WRITE` and
  `DIAG_VERBOSE_ON`):
  immediate crash /
  NULL deref when the
  surface-integration
  inner loop tries to
  write
  `dist_dx0000.mgz`,
  `dx0000.mgz`, etc.
- **MGM / FCD feature
  extraction
  pipeline**: unaffected
  (caller pre-allocates
  the correctly-shaped
  mri).

## Recommended Fix

```diff
--- a/utils/mrisurf_io.cpp
+++ b/utils/mrisurf_io.cpp
@@ -416,7 +416,7 @@ MRI *MRISwriteIntoVolume(MRI_SURFACE *mris, MRI *mri, int which)
   float val = 0;

   if (mri == NULL) {
-    mri = MRIalloc(1, 1, mris->nvertices, MRI_FLOAT);
+    mri = MRIalloc(mris->nvertices, 1, 1, MRI_FLOAT);
   }
```

Allocates `width=nvertices,
height=1, depth=1`, which
matches the indexing
convention at `:454-455`,
matches the sister
`MRISreadFromVolume`
function's expected
input shape, and matches
the production caller at
`mri_extract_fcd_features.cpp:483`.

## Workarounds

For users running the
affected diagnostic
paths: pre-allocate the
mri before the call.
E.g., in a custom
script, allocate
`MRIallocSequence(mris->nvertices,
1, 1, MRI_FLOAT, 1)`
and pass it in.

For the typical user:
the bug doesn't fire
in production runs, so
no workaround needed.
