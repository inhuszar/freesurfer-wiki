# [severity-2] [bug-00208] fem_elastic — SmallMatrix::inplace_transpose and ZlibStringCompressor::setBufferSize release new[] arrays with scalar delete (and leave m_buffer dangling after bad_alloc)

> [!bug] Synopsis
> Two classes in `fem_elastic` allocate arrays with `new T[n]` and release them with scalar `delete`:
> `SmallMatrix::inplace_transpose()` (`delete m_pdata;`) and `ZlibStringCompressor::setBufferSize()` (`delete m_buffer;`). This is undefined behaviour that is
> benign with glibc's allocator but is flagged by Valgrind/ASan, and the compressor additionally leaves `m_buffer` dangling when the following `new[]` throws.
> `inplace_transpose()` runs once per active point constraint per FEM step in `surf2vol`, i.e. on the default [[mri_cvs_register]] path.

## Affected Artefacts

- **Tool(s):** [[surf2vol]] (`SmallMatrix`, `ZlibStringCompressor`), [[exportGcam]], [[createMorph]], [[applyMorph]] (`ZlibStringCompressor` through `VolumeMorph::load` / `save`)
- **Pipeline stage(s):** the elastic-registration step of [[mri_cvs_register]] (surf2vol + exportGcam) executes both sites
- **FreeSurfer version(s):** confirmed in `8.2.0`; present since the 2008-03-14 import (`4b881dc775`)
- **Platforms:** all (the allocator decides whether the UB is visible; glibc `free()` does not distinguish `new` from `new[]`)
- **Triggering configuration:** always-on for `inplace_transpose()` (every active MFC constraint); for `setBufferSize()` whenever a buffer already exists and is
  being replaced (the `inflate()` loop doubles the buffer on `Z_BUF_ERROR`; `compress()` re-sizes when the next block is larger than the current buffer).

## Detailed Description

`SmallMatrix` stores its elements in a heap array created with `new double[rows*cols]` (constructors at
[`fem_elastic/small_matrix.cpp:20`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/small_matrix.cpp#L20), [`fem_elastic/small_matrix.cpp:57`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/small_matrix.cpp#L57), [`fem_elastic/small_matrix.cpp:88`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/small_matrix.cpp#L88), and the destructor, `identity()` and `clone()` correctly use `delete[]`,
[`fem_elastic/small_matrix.cpp:47`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/small_matrix.cpp#L47), [`fem_elastic/small_matrix.cpp:53`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/small_matrix.cpp#L53), [`fem_elastic/small_matrix.cpp:83`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/small_matrix.cpp#L83)). `inplace_transpose()` is the one place that uses scalar `delete`:

```cpp
void
SmallMatrix::inplace_transpose()
{
  double *pdata = new double[m_rows*m_cols];

  for (int i=0; i<m_rows; ++i)
    for (int j=0; j<m_cols; ++j)
      pdata[ j*m_rows + i ] = (*this)(i,j);

  delete m_pdata;
  m_pdata = pdata;

  int ibuf = m_rows;

  m_rows = m_cols;
  m_cols = ibuf;
}
```

`ZlibStringCompressor::setBufferSize()` has the same pattern, plus an exception-safety problem: the old buffer is freed first, `m_buffer` is not reset, and if
`new Bytef[size]` throws `std::bad_alloc` the function throws a `const char*` with `m_buffer` still pointing at the freed block:

```cpp
Bytef* ZlibStringCompressor::setBufferSize(const unsigned long size)
{
  delete m_buffer;
  if (getDebugLevel()>0) std::cout << "Deleted buffer" << std::endl;
  m_bufferSize=0;
  try
  {
    m_buffer = new Bytef[size];
  }
  catch (std::bad_alloc&)
  {
    std::cerr << " requested buffer size = " << size << std::endl;
    throw " ZlibStringCompressor::setBufferSize - Caught std::bad_alloc";
    //ZlibException("Caught std::bad_alloc", __FILE__, __LINE__);
  }
  if (getDebugLevel()>0) std::cout << "Set buffer size to " << size  << std::endl;
  m_bufferSize=size;
  return m_buffer;
}
```

### Expected Behaviour

Memory obtained from `new[]` is released with `delete[]` (C++ [expr.delete]); a freed pointer member is reset so a later call cannot free it again.

### Observed Behaviour

Per the C++ standard the scalar `delete` of an array allocation is undefined behaviour. With glibc the block is simply `free()`d, so output is unaffected, which is why
nobody has noticed. Memory checkers report it, and the sized-deallocation form emitted by the compiler passes the wrong size (`sizeof(double)` rather than the
array size), which would matter with an allocator that uses the size argument. After a `bad_alloc` in `setBufferSize()` the next call frees the stale pointer a
second time.

### Reproducer

Both source files were compiled unmodified (`g++ -g -O0`, with `-lz`) together with a ten-line driver that (a) constructs `SmallMatrix m(3,12)` and calls
`m.inplace_transpose()`, and (b) constructs a `ZlibStringCompressor` and calls `setBufferSize(100)` then `setBufferSize(200)`. Valgrind 3.22 Memcheck reports, for each
driver, `Mismatched free() / delete / delete []`:

- (a) at `SmallMatrix::inplace_transpose()` [`small_matrix.cpp:164`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/small_matrix.cpp#L164), "0 bytes inside a block of size 288 alloc'd" by `new[]` in the `SmallMatrix(int,int)` constructor ([`small_matrix.cpp:20`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/small_matrix.cpp#L20)), plus
  `Mismatched new/delete size value: 8`;
- (b) at `ZlibStringCompressor::setBufferSize()` [`ZlibStringCompressor.cpp:24`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/ZlibStringCompressor.cpp#L24), block of size 100 allocated by `new[]` at [`ZlibStringCompressor.cpp:29`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/ZlibStringCompressor.cpp#L29), plus
  `Mismatched new/delete size value: 1`.

(AddressSanitizer could not be used on the analysis host: `libasan.so.5` is missing. Valgrind's mismatch check reports the same class of error.) No `bad_alloc` was provoked;
that part is from reading the code.

## Root Cause

Copy-paste of `delete` where `delete[]` is required, in code imported in 2008 and never exercised under a memory checker. `SmallMatrix` is used only by `fem_elastic` (`grep` of the tree shows no other users).
The compressor's `setBufferSize()` frees before allocating and never nulls the pointer.

## Impact

- **Output unaffected in practice:** on glibc the scalar `delete` of a trivially-destructible `new[]` block is an ordinary `free()`.
- **Diagnostics noise and portability risk:** every Valgrind/ASan run of `surf2vol` reports it (obscuring real errors such as [[00209]]'s leaks); allocators that honour the
  sized-delete argument (`operator delete(void*, size_t)` with `sizeof(double)`) could corrupt their bookkeeping.
- **Severity 2 (low):** reached on the default CVS path, but with no observable wrong output under the shipped allocator, which is why it is scored as latent rather than 3 or 4.

## Recommended Fix

```diff
--- a/fem_elastic/small_matrix.cpp
+++ b/fem_elastic/small_matrix.cpp
   for (int i=0; i<m_rows; ++i)
     for (int j=0; j<m_cols; ++j)
       pdata[ j*m_rows + i ] = (*this)(i,j);

-  delete m_pdata;
+  delete[] m_pdata;
   m_pdata = pdata;
--- a/fem_elastic/ZlibStringCompressor.cpp
+++ b/fem_elastic/ZlibStringCompressor.cpp
 Bytef* ZlibStringCompressor::setBufferSize(const unsigned long size)
 {
-  delete m_buffer;
+  delete[] m_buffer;
+  m_buffer = 0;
   if (getDebugLevel()>0) std::cout << "Deleted buffer" << std::endl;
   m_bufferSize=0;
```

Better: replace the raw buffer with `std::vector<Bytef>` (also fixes the missing destructor, see [[00209]]) and `SmallMatrix` storage with `std::vector<double>`. Verify with Valgrind (`--leak-check=full`) and a unit test that calls `inplace_transpose()` and grows a compressor buffer twice.

## Workarounds (If Any)

None needed for correct results. To silence the reports when running under a memory checker, suppress `alloc-dealloc-mismatch` (`ASAN_OPTIONS=alloc_dealloc_mismatch=0`).
