# [severity-3] [bug-00091] `MRIglmFitAndTest` drops the sign of `sig` when `p` underflows to 0

> [!bug] Synopsis
> The signed-significance output in
> `MRIglmFitAndTest`
> ([`utils/fmriutils.cpp:1053-1058`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/fmriutils.cpp#L1053-L1058))
> handles the `p == 0` underflow case
> separately from the `p > 0` case, but the
> sign correction lives only in the latter
> branch:
>
> ```cpp
> if (glm->p[n] == 0)
>   MRIsetVoxVal(mriglm->sig[n], c, r, s, 0, 10e10);   /* :1053 — unsigned cap */
> else {
>   double sig = -log10(glm->p[n]);
>   if (glm->C[n]->rows == 1)
>     sig *= SIGN(glm->gamma[n]->rptr[1][1]);          /* :1056 — sign correction */
>   MRIsetVoxVal(mriglm->sig[n], c, r, s, 0, sig);
> }
> ```
>
> A voxel whose effect is **negative** but
> highly significant — significant enough that
> the F-distribution CDF tail underflows to
> exactly `0.0` — gets `+1e11` written to
> `sig` instead of `-1e11`. The output column
> in `sig.{nii,mgh,mgz}` reports the
> most-extreme negative voxels with the
> opposite sign.

## Detailed Description

The signed-sig convention in FreeSurfer is:
for a one-row contrast (t-test), the
"significance" column equals
`-log10(p) * SIGN(gamma)`. Positive sig means
positive effect; negative sig means negative
effect.

```cpp
/* utils/fmriutils.cpp:1045-1061 */
for (n = 0; n < glm->ncontrasts; n++) {
  ...
  MRIsetVoxVal(mriglm->p[n], c, r, s, 0, glm->p[n]);
  ...
  if (glm->p[n] == 0)
    MRIsetVoxVal(mriglm->sig[n], c, r, s, 0, 10e10);   /* :1053 — UNSIGNED cap */
  else {
    double sig = -log10(glm->p[n]);
    if (glm->C[n]->rows == 1)
      sig *= SIGN(glm->gamma[n]->rptr[1][1]);          /* :1056 — sign for the else case only */
    MRIsetVoxVal(mriglm->sig[n], c, r, s, 0, sig);
  }
}
```

The truth table for a one-row contrast voxel:

| `gamma`     | `p == 0` | `sig` written | expected |
|-------------|----------|----------------|----------|
| `+ε`        | no       | `+(-log10(p))` | `+(-log10(p))` |
| `−ε`        | no       | `−(-log10(p))` | `−(-log10(p))` |
| `+ε`        | **yes**  | **`+1e11`**    | `+1e11`        |
| `−ε`        | **yes**  | **`+1e11`**    | `−1e11` (BUG) |

For p > 0, the formula is correct; the bug
fires only on the underflow boundary.

### Underflow regime

IEEE-754 double's smallest positive normal is
~`2.225e-308`; with denormals, ~`5e-324`. The
F-distribution's right-tail probability
underflows around `F` values that depend on
`DOFNum` and `DOFDen` but, for a one-row
contrast (t² distribution) with `DOFDen` of a
few hundred, are reached for `t ≳ 38` or so
(equivalent to `-log10(p) ≳ 308`). This is
within the dynamic range of high-SNR fMRI
group analyses (e.g., motor task contrasts
across subjects can yield such effective t's
at the most-active voxels) and of permutation-
based extreme-value distributions.

### Output consequence

The map `sig.{nii,mgh,mgz}` is what users
threshold and visualise. A symmetric
threshold (`abs(sig) > T`) at `T < 1e11` will
include the affected voxels but display them
on the *positive* side regardless of their
true effect direction. Conversely, a one-
sided negative-effect threshold
(`sig < −T`) will **miss** the most-significant
negative voxels.

## Root Cause

Defensive separation of the `p == 0` case
from the general `p > 0` formula, written
without considering the sign-correction step.
The cap value `10e10` (= `1e11`) was likely
copied from the unsigned-sig convention
without recognising that the surrounding
contract had been extended to the signed
form.

The companion path
[`MRIlog10(mriglm->p[n], NULL, sig, 1)`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_glmfit/mri_glmfit.cpp#L1865)
used when `--no-sig-double` is set computes
`sig` via a different code path (per-voxel
`MRIlog10` with sign applied later); whether
that path also has an underflow handling bug
is out of scope for this report.

## Impact

- **Default `mri_glmfit` permutation/sim and
  `mri_dualperm`:** when any voxel's p-value
  hits exactly `0.0` and `gamma < 0`, the
  signed `sig` map flips that voxel's sign.
- **Display / thresholding:** affected voxels
  appear on the wrong side of the colour
  scale; one-sided thresholds miss them.
- **Effect on summary stats / cluster
  reports:** a cluster of strongly-negative
  effect at the most extreme voxels could be
  mis-classified as positive in cluster
  reports that respect the signed sig map.
- **Severity:** 3 — auxiliary tool's default
  path; bug fires on a narrow numerical
  regime (p underflows to exactly 0), but
  affects the most-significant voxels —
  precisely the ones a user is most likely to
  scrutinise.

## Recommended Fix

```diff
--- a/utils/fmriutils.cpp
+++ b/utils/fmriutils.cpp
@@ -1050,11 +1050,15 @@
           MRIsetVoxVal(mriglm->p[n], c, r, s, 0, glm->p[n]);

             MRIsetVoxVal(mriglm->pcc[n], c, r, s, 0, glm->pcc[n]);
-	  if(glm->p[n] == 0)  MRIsetVoxVal(mriglm->sig[n], c, r, s, 0, 10e10);
-	  else {
-	    double sig = -log10(glm->p[n]);
-	    if(glm->C[n]->rows == 1) sig *= SIGN(glm->gamma[n]->rptr[1][1]);
-	    MRIsetVoxVal(mriglm->sig[n], c, r, s, 0, sig);
-	  }
+          {
+            double sig;
+            if (glm->p[n] == 0)
+              sig = 10e10;                                     /* cap */
+            else
+              sig = -log10(glm->p[n]);
+            if (glm->C[n]->rows == 1)
+              sig *= SIGN(glm->gamma[n]->rptr[1][1]);          /* sign for both branches */
+            MRIsetVoxVal(mriglm->sig[n], c, r, s, 0, sig);
+          }
```

The fix factors the sign correction out of
the `else` branch so it applies uniformly to
both the cap and the computed value.

## Workarounds

For one-sided negative-effect analyses, opt
into the legacy path with `--no-sig-double`
(uses `MRIlog10` instead of the per-voxel
double-precision sig writer). For symmetric
threshold-based displays, post-process
`sig.{nii,mgh,mgz}` by re-deriving it from
`gamma` and `p` directly:

```bash
fscalc gamma.mgh sign , p.mgh log10 \-, mul --o sig_signed.mgh
```

(or equivalent in any voxel calculator).

    (`1e11` vs `-log10(p)`) but disagree on
    sign handling.
