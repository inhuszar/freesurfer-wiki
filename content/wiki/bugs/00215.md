# [severity-3] [bug-00215] `createMorph` — `gcam` input: `GCAMrasToVox()` runs unconditionally on voxel-type GCAMs (type guard compiled out in 2023), so every `.m3z` yields a garbage delta field

> [!bug] Synopsis
> The `gcam` branch of [[createMorph]] calls `GCAMrasToVox(gcam, mriBuf)` on every GCAM it reads ([`fem_elastic/fcreateMorph.cpp:156`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L156)). Until 2023 that function first converted a `GCAM_VOX` GCAM back to RAS, so the call was a harmless round trip for voxel-type input. Commit `0a3a8c2d16` (2023-06-29) compiled that guard out ([`utils/gcamorph.cpp:11191-11195`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcamorph.cpp#L11191-L11195)), so voxel-type node positions are now pushed through the image's RAS-to-voxel matrix a second time. All three shipped `.m3z` files that were examined are `GCAM_VOX`, and `mri_nl_align` writes its GCAM without converting it to RAS, so the resulting delta field is wrong for essentially every real input: an identity warp gives displacements of up to about 20 voxels. The only in-tree caller, the legacy CVS branch of [[trac-preproc]], is affected.

## Affected Artefacts

- **Tool(s):** [[createMorph]] (`--in gcam`); the wrong `.tm3d` then propagates into [[exportGcam]] and [[applyMorph]].
- **Pipeline stage(s):** TRACULA inter-subject registration with `xspace == cvs`, legacy branch only (first-generation `mri_cvs_register` outputs present, `final_CVSmorph_to<template>.tm3d` absent): [`scripts/trac-preproc:1760-1768`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/trac-preproc#L1760-L1768), followed by `exportGcam` ([`scripts/trac-preproc:1776-1782`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/trac-preproc#L1776-L1782)) whose `.m3z` is later used by `mri_vol2vol --m3z` ([`scripts/trac-preproc:1970`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/trac-preproc#L1970)). See [[trac-preproc]] and [[wiki/pipelines/trac-all|trac-all]].
- **FreeSurfer version(s):** confirmed in `8.2.0`; introduced 2023-06-29 (commit `0a3a8c2d16`, Yujing Huang, "comment out unnecessary GCAM_RAS/GCAM_VOX conversions"). Earlier releases kept the round trip and therefore did not show the symptom.
- **Platforms:** all
- **Triggering configuration:** `createMorph ... --in gcam <file>.m3z` with any GCAM whose `type` is `GCAM_VOX` (the default; see below). Always on for such input; no flag gates it.

## Detailed Description

`createMorph --in gcam F` is meant to turn a GCAM (`.m3z`) into a dense delta field (`field|` record of the `.tm3d`): for each node index `g`, `delta[g] = node(g) - g`, both in voxel units of the GCAM's *image* volume ([`fem_elastic/fcreateMorph.cpp:370-413`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L370-L413)). `CopyGcamToDeltaField` therefore requires the node coordinates `(x, y, z)` to be **voxel** coordinates. To make sure of that, `main` calls `GCAMrasToVox()` on the freshly read GCAM, on a throw-away `MRI` carrying the GCAM's own image geometry ([`fem_elastic/fcreateMorph.cpp:148-157`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L148-L157)).

`GCAMrasToVox()` multiplies every node's `(x,y,z)` and `(origx,origy,origz)` by the image RAS-to-voxel matrix and then sets `gcam->type = GCAM_VOX` ([`utils/gcamorph.cpp:11184-11261`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcamorph.cpp#L11184-L11261)). It is only correct when the input is `GCAM_RAS`. Before 2023 the function protected itself: if the GCAM was already `GCAM_VOX` it first called `GCAMvoxToRas()`, so the net effect on a voxel GCAM was the identity. That block is now `#if 0`.

Which type do real `.m3z` files have? The type is stored in the `TAG_GCAMORPH_TYPE` tag ([`utils/gcamorph.cpp:1279`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcamorph.cpp#L1279)); files lacking the tag take the allocator default `GCAM_VOX` ([`utils/gcamorph.cpp:1331`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcamorph.cpp#L1331)). `mri_nl_align` writes its GCAM without converting to RAS (the `GCAMvoxToRas` call is commented out, [`mri_hires_register/mri_nl_align.cpp:675-677`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_hires_register/mri_nl_align.cpp#L675-L677)), and `mri_warp_convert` builds voxel-type GCAMs ([`utils/warpfield.cpp:445`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/warpfield.cpp#L445)). In this investigation the type tag was decoded from `cvs_avg35/mri/transforms/talairach.m3z`, `cvs_avg35_inMNI152/mri/transforms/talairach.m3z`, `average/mni_icbm152_nlin_asym_09c/samseg.t1/template.m3z` and a synthetic identity warp: all four are `GCAM_VOX`. No `GCAM_RAS` `.m3z` was found.

Every other in-tree caller guards the call with `if (gcam->type == GCAM_RAS)` ([`utils/mriio.cpp:661`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mriio.cpp#L661), [`utils/warpfield.cpp:141-145`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/warpfield.cpp#L141-L145), [`utils/gcamorph.cpp:16403-16405`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcamorph.cpp#L16403-L16405)); `createMorph` is the one that does not, and it relied on the removed round trip. The same 2023 commit also disabled an identical guard in `GCAMinitVolGeom` ([`utils/gcamorph.cpp:1385-1389`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcamorph.cpp#L1385-L1389)).

Two further defects in the same branch are recorded here because they change the same field:

1. The validity mask is allocated and filled with ones ([`fem_elastic/fcreateMorph.cpp:298-310`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L298-L310)) and never cleared for invalid nodes; `CopyGcamToDeltaField` then returns it ([`fem_elastic/fcreateMorph.cpp:476-481`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L476-L481)), but the caller's `set_mask` is commented out ([`fem_elastic/fcreateMorph.cpp:176-181`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L176-L181)). Out-of-extent and `GCAM_POSITION_INVALID` nodes therefore get zero displacement (identity) instead of "invalid".
2. `gcam->spacing` is never consulted: the loops use node indices directly as voxel offsets ([`fem_elastic/fcreateMorph.cpp:353-372`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L353-L372)), so a down-sampled GCAM (for example `spacing = 2` as in the shipped `talairach.m3z`) is read as if it were at voxel spacing.

### Expected Behaviour

A zero-displacement (identity) `.m3z` must give an all-zero delta field, and a GCAM that shifts every node by `+2` voxels in x must give `(2, 0, 0)` everywhere (up to the border). Chaining the result with `applyMorph` on the template image must reproduce the template.

### Observed Behaviour

The delta field equals `R2V·g − g`, where `R2V` is the image RAS-to-voxel matrix, i.e. the identity warp is mapped as if voxel indices were RAS millimetres. The error is silent: no warning is printed, the exit status is 0, and `createMorph` prints the (correct-looking) atlas and image geometry.

### Reproducer

Experiments run with the installed 8.2.0 binaries on synthetic data (a 32x32x32, 8 mm template with the LIA-like orientation `x_r=-1, y_s=-1, z_a=1`, centre (0,0,0), random intensities in `tmpl.mgz`):

```bash
# 1. zero displacement field in source-voxel space -> identity .m3z
#    (zero_vox.mgz: 32^3 float, 3 frames of zeros, same geometry as tmpl.mgz)
mri_warp_convert --invox zero_vox.mgz --outfswarp ident.m3z -g tmpl.mgz

# 2. wrap it
createMorph --out id.tm3d --template tmpl.mgz --subject tmpl.mgz --in gcam ident.m3z

# 3. resample the template through it (must reproduce tmpl.mgz)
applyMorph --template tmpl.mgz --transform id.tm3d vol tmpl.mgz id_applied.mgz linear
```

Observed:

- The `field|` record of `id.tm3d` (decoded with a short Python script following the layout in [[createMorph]]) holds `(4.75, 4.75, 7.25)` voxels at index (10,10,10), `(-18.875, -18.875, -11.125)` at (31,31,31), and a maximum absolute value of 19.875; 99.997 % of voxels are non-zero. The only zero is node (0,0,0), which `GCAMread` flags `GCAM_POSITION_INVALID` because all its coordinates are zero. These values equal `R2V·g − g` exactly: with `R2V = [[-1/8,0,0,16],[0,0,-1/8,16],[0,1/8,0,16]]` and `g = (10,10,10)`, `R2V·g − g = (4.75, 4.75, 7.25)`.
- With a GCAM that shifts every node by +2 voxels in x (`shift2_vox.mgz` through the same `mri_warp_convert` call) the delta at (10,10,10) is `(4.5, 4.75, 7.25)`, again exactly `R2V·(g+(2,0,0)) − g`, instead of `(2, 0, 0)`.
- `applyMorph` through `id.tm3d` reproduced the template at only 1 of 32768 voxels (fraction 3e-5).
- Control: `createMorph --in volume zero_vox.mgz` (a zero `volume` field, which does not pass through `GCAMrasToVox`) followed by the same `applyMorph` call reproduced the template at 100 % of voxels, so the corruption originates in the `gcam` branch and not in the tm3d/applyMorph chain.
- Type tag: `GCAMwrite` stores `TAG_GCAMORPH_TYPE`; decoding it from the synthetic `ident.m3z`, from `cvs_avg35/mri/transforms/talairach.m3z`, from `cvs_avg35_inMNI152/mri/transforms/talairach.m3z` and from `average/mni_icbm152_nlin_asym_09c/samseg.t1/template.m3z` gave `2` (`GCAM_VOX`) in all four.

## Root Cause

`GCAMrasToVox()` is a *conversion* routine, not an idempotent "make sure the nodes are in voxel space" routine. Its former `if (gcam->type == GCAM_VOX) GCAMvoxToRas(gcam);` prelude made it safe to call on voxel GCAMs; commit `0a3a8c2d16` removed that prelude ("unnecessary conversions"), and `createMorph`, which still calls the function unconditionally and relied on the round trip, was not given a type guard. The call sequence for a voxel-type GCAM is now `x_vox → R2V·x_vox`, i.e. a voxel coordinate is treated as a RAS coordinate.

The structural fix is at the call site: only convert when the GCAM really is in RAS, exactly like `MRIread` for `.m3z` ([`utils/mriio.cpp:661`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mriio.cpp#L661)) and `Warpfield::convert()` do.

The mask defect has an independent cause: the mask is initialised to 1 ("fill the mask with true values to start with") and the commented-out `ucZero` ([`fem_elastic/fcreateMorph.cpp:304`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L304)) is never assigned, so even if the caller attached it, it would mark every voxel valid.

## Impact

- **Silent wrong output.** `createMorph --in gcam` produces a `.tm3d` whose `field|` record is wrong at essentially every voxel, with no diagnostic. `applyMorph` and `exportGcam` consume it without complaint.
- **TRACULA.** In the legacy branch of `trac-preproc` (xspace `cvs`; `nlalign-afteraseg-norm.m3z` present but `final_CVSmorph_to<template>.tm3d` missing) the wrong `.tm3d` is converted by `exportGcam` into `final_CVSmorph_to<template>.m3z`, which `trac-preproc` then uses to map ROIs and masks into the CVS template ([`scripts/trac-preproc:1970`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/trac-preproc#L1970)). The inter-subject (CVS) space of the TRACULA outputs in that branch is therefore wrong. Whether any user data is actually processed through this legacy branch with 8.2.0 was not established.
- **Manual users** composing `.m3z` files with `createMorph` for [[applyMorph]]/[[exportGcam]] get wrong morphs.
- **Why severity 3 and not 5.** By the schema's reach criterion a defect in [[wiki/pipelines/trac-all|trac-all]] is a pipeline defect (severity 5). The defective call is, however, reachable only in the legacy branch of one inter-subject space (`xspace == cvs`, first-generation CVS outputs present, final morph absent); the default and the other spaces never call `createMorph`. Gated behind a specific configuration, the schema places it at 3 (the lower of the two tiers it straddles).
- **No `createMorph` option avoids it.** The wrong values are produced before any option is consulted (see Workarounds for ways around the `gcam` keyword).

## Recommended Fix

Convert only when the GCAM is in RAS and attach a correct mask:

```diff
--- a/fem_elastic/fcreateMorph.cpp
+++ b/fem_elastic/fcreateMorph.cpp
@@ main(), gcam branch
       useVolGeomToMRI( &gcam->image, mriBuf );
-      GCAMrasToVox(gcam, mriBuf );
+      if (gcam->type == GCAM_RAS)
+        GCAMrasToVox(gcam, mriBuf );
       MRIfree( &mriBuf );
@@
-        //MRI* mask =
-        CopyGcamToDeltaField(gcam, mri);
+        MRI* mask = CopyGcamToDeltaField(gcam, mri);

         pvol->set_field(mri);
-        //pvol->set_mask(mask);
+        if (mask) pvol->set_mask(mask);
         pmorph->m_transforms.push_back( pvol );
```

and in `CopyGcamToDeltaField` start the mask at zero and set it only for filled voxels:

```diff
-        MRIvox(mask, x,y,z) = ucOne;
+        MRIvox(mask, x,y,z) = ucZero;
 ...
         MRIsetVoxVal(mask, img_x, img_y, img_z, 0, ucOne );
```

(with `unsigned char ucZero(0)` re-enabled and the `if ( !maskCounter )` early return at [`fem_elastic/fcreateMorph.cpp:476-480`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L476-L480) removed, since the mask is now informative). Attaching the mask changes behaviour for voxels outside the GCAM extent (invalid instead of identity) and needs validation against the consumers.

Accompanying tests: (1) an identity `.m3z` must give an all-zero field (apart from the invalid node at the origin); (2) a +2-voxel shifted `.m3z` must give `(2,0,0)` in the interior; (3) `createMorph` + `applyMorph` of an identity `.m3z` must reproduce the template; (4) a `GCAM_RAS`-typed `.m3z` must give the same field as the equivalent `GCAM_VOX` one. Honouring `gcam->spacing` is a separate enhancement.

### Alternative Fixes Considered

- Restore the `GCAM_VOX -> GCAMvoxToRas` prelude inside `GCAMrasToVox`. This repairs `createMorph` but reverses an intentional 2023 change that other callers (for example `mri_nl_align`, `mri_hires_register`, `GCAMinitVolGeom`) may rely on; the call-site guard is safer.
- Replace the whole branch by `GCAMsampleMorph`-based resampling (the commented-out block at [`fem_elastic/fcreateMorph.cpp:455-474`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L455-L474)); this would also handle spacing and arbitrary atlas/template grids, at the cost of a behaviour change that needs validation.

## Workarounds (If Any)

For TRACULA, avoid the legacy branch: it is taken only when `final_CVSmorph_to<template>.m3z` is absent ([`scripts/trac-preproc:1721`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/trac-preproc#L1721)), so supplying that file (for example from a second-generation `mri_cvs_register` run, whose `combined_to<template>_elreg_afteraseg-norm.m3z` the script symlinks to that name, [`scripts/trac-preproc:1722-1730`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/trac-preproc#L1722-L1730)) or choosing another inter-subject space bypasses `createMorph`. These routes were read from the script and not run. For manual use, build chains from `volume`, `affine` and `morph` items only (a `volume` item does not pass through `GCAMrasToVox`, see the control above), or combine `.m3z` files with [[mri_concatenate_gcam]] instead of `createMorph`. The only `gcam` input this branch converts correctly is a `GCAM_RAS` GCAM, and none was found.
