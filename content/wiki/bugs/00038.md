# mrisDivideEdge does not interpolate whitex/whitey/whitez (duplicate x/y/z block)

> [!bug] Synopsis
> `mrisDivideEdge` creates a new vertex at the midpoint of an
> existing edge and propagates per-vertex coordinate fields to
> the new vertex by averaging the two endpoints. The body
> writes 21 averages across seven coordinate triples
> (`x/y/z`, `tx/ty/tz`, `infx/y/z`, `pialx/y/z`, `cx/y/z`,
> `odx/y/z`, `origx/y/z` — plus `val`). The third triple from
> the bottom (`utils/mrisurf_defect.cpp:56-58`) is a verbatim
> duplicate of the first triple at `:38-40`: it sets
> `vnew->x`, `vnew->y`, `vnew->z` again instead of a different
> coordinate field. By position and by surrounding pattern
> (the only major coordinate triple notably absent from the
> list is `whitex/whitey/whitez`), the duplicate block was
> intended to be `whitex/whitey/whitez`. Consequence: every
> vertex added by `MRISdivideLongEdges` /
> `MRISdivideEdges` / `mrisDivideEdge` carries `whitex =
> whitey = whitez = 0` (calloc-zeroed at allocation) instead
> of the midpoint of the two endpoints' white-surface
> positions. Fires in [[mris_make_surfaces]] (and therefore
> default [[recon-all]]) where `MRISdivideLongEdges` is
> called at
> [`mris_make_surfaces.cpp:875`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mris_make_surfaces/mris_make_surfaces.cpp#L875)
> and
> [`mris_make_surfaces.cpp:1164`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mris_make_surfaces/mris_make_surfaces.cpp#L1164),
> after
> `MRISsaveVertexPositions(mris, WHITE_VERTICES)` at
> [`:870`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mris_make_surfaces/mris_make_surfaces.cpp#L870)
> has populated the white-coordinate fields.

## Detailed Description

### Expected Behaviour

`mrisDivideEdge` is the geometric counterpart of
`mrisDivideEdgeTopologically`: the latter splits the topology
at the new vertex, and the former assigns coordinates and
auxiliary fields to that new vertex by averaging the two
endpoints. The natural reader expectation — and the pattern
observable in every other averaged field — is that the new
vertex should sit at the midpoint of the edge in *every*
coordinate space the surface tracks (current,
original/orig, inflated, pial, white, canonical, target, etc.).
A new vertex with `whitex = 0` is at the volumetric origin
(typically a corner of the volume), which is nonsensical as a
"midpoint of a surface edge".

### Observed Behaviour

The body of `mrisDivideEdge`
([`utils/mrisurf_defect.cpp:30-68`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_defect.cpp#L30-L68)):

```cpp
vnew->x = (v1->x + v2->x) / 2;        /* :38 */
vnew->y = (v1->y + v2->y) / 2;
vnew->z = (v1->z + v2->z) / 2;
vnew->tx = (v1->tx + v2->tx) / 2;
vnew->ty = (v1->ty + v2->ty) / 2;
vnew->tz = (v1->tz + v2->tz) / 2;

vnew->infx = (v1->infx + v2->infx) / 2;
vnew->infy = (v1->infy + v2->infy) / 2;
vnew->infz = (v1->infz + v2->infz) / 2;

vnew->pialx = (v1->pialx + v2->pialx) / 2;
vnew->pialy = (v1->pialy + v2->pialy) / 2;
vnew->pialz = (v1->pialz + v2->pialz) / 2;

vnew->cx = (v1->cx + v2->cx) / 2;
vnew->cy = (v1->cy + v2->cy) / 2;
vnew->cz = (v1->cz + v2->cz) / 2;
vnew->x = (v1->x + v2->x) / 2;        /* :56 — DUPLICATE OF :38 */
vnew->y = (v1->y + v2->y) / 2;        /* :57 — DUPLICATE OF :39 */
vnew->z = (v1->z + v2->z) / 2;        /* :58 — DUPLICATE OF :40 */
vnew->odx = (v1->odx + v2->odx) / 2;
vnew->ody = (v1->ody + v2->ody) / 2;
vnew->odz = (v1->odz + v2->odz) / 2;
vnew->val = (v1->val + v2->val) / 2;
```

Lines 56-58 set the same three fields as lines 38-40. The
write is therefore redundant, and whatever the author
*intended* the second block to set is silently never written.
The new vertex's `whitex/whitey/whitez` retains its
calloc-zeroed value of `(0, 0, 0)`.

The fact that the duplicate is exactly `x/y/z` (the *first*
of the seven-or-eight coordinate triples in this function)
is the smoking gun: copy-paste-and-forget-to-rename. The
slot is positioned between `cx/y/z` (canonical) and
`odx/y/z` (last delta). The only commonly-tracked surface
coordinate that is *not* present elsewhere in the function
is `whitex/whitey/whitez`. (The other possibilities — `t2x`,
`targx`, `fx`, `l4x` — are either not interpolated by sister
"divide" / "subdivide" functions in the file, or are not
populated at the call sites that exercise this path.)

### Reproducer

```bash
# Default recon-all path.
recon-all -s SUBJ -i T1.nii.gz -all
# Or just the affected stage:
mris_make_surfaces \
   -orig_white orig \
   -orig_pial orig \
   -aseg aseg.presurf \
   SUBJ lh

# A new vertex added by MRISdivideLongEdges during white surface
# placement will have whitex == whitey == whitez == 0.
# Diagnostic at the point of failure:
#   the *thickness* at any such vertex (computed as
#   sqrt((x-whitex)² + (y-whitey)² + (z-whitez)²)) becomes
#   the magnitude of the vertex's current position vector
#   from the volumetric origin (~ 60-100 mm for typical
#   subject space), instead of the true cortical thickness
#   (~1.5-3 mm).
```

  vnew->ty = (v1->ty + v2->ty) / 2;

  vnew->infy = (v1->infy + v2->infy) / 2;

## Root Cause

Copy-paste error: the original `x/y/z` block at the top of
the function was duplicated and the field names were not
renamed to `whitex/whitey/whitez`. The two blocks are
character-for-character identical apart from indentation, so
no syntactic warning fires.

## Impact

- **`mris_make_surfaces` thickness and pial placement.** New
  vertices added by `MRISdivideLongEdges` carry
  `(whitex,whitey,whitez) = (0,0,0)`. Any code reading those
  fields for a new vertex sees the volumetric origin
  (typically a corner of the volume bbox, far outside the
  brain). Concretely affected sites include:
    - thickness vector
      [`utils/mrisurf_mri.cpp:8324`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_mri.cpp#L8324)
      — `nx = v->x - v->whitex` etc.
    - white-surface anchor
      [`utils/mrisurf_mri.cpp:8346,8350,8420`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_mri.cpp#L8346)
      — `xs = v->whitex + d*nx`
    - duplicate-vertex test
      [`utils/mrisurf_vals.cpp:1539`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_vals.cpp#L1539)
      — `FZERO(v->whitex - v->pialx) && …` (will spuriously
      report large displacement at new vertices).
    - integration tmp-coords seed
      [`utils/mrisurf_integrate.cpp:2242-2244`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisurf_integrate.cpp#L2242-L2244)
      — `v->tx = v->whitex; v->ty = v->whitey; v->tz =
      v->whitez;` — seeds the placement integration with the
      origin instead of the surface midpoint.
    - flat-mapping resampling
      [`utils/mrisutils.cpp:2053-2055`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mrisutils.cpp#L2053-L2055)
      — `MRISsampleFace(…, v0->whitex, v1->whitex, v2->whitex)`.
- **Magnitude per-vertex.** Thickness for a new vertex
  becomes the magnitude of its position vector from the
  volumetric origin, typically 60-100 mm for cortex (vs the
  true cortical thickness of 1-4 mm). When propagated through
  surface averaging, this can pull cortical-thickness
  statistics outwards by a small but non-trivial amount in
  any region where `MRISdivideLongEdges` actually adds
  vertices.
- **Latent in [[mris_fix_topology]]**:
  [`mris_fix_topology.cpp:290`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mris_fix_topology/mris_fix_topology.cpp#L290)
  also calls `MRISdivideLongEdges` after topology correction,
  but `whitex/whitey/whitez` has not been populated at that
  stage of the pipeline (white surface comes later, in
  `mris_make_surfaces`). The bug is harmless there only
  because the field is already zero on both endpoints.

## Recommended Fix

```diff
   vnew->cx = (v1->cx + v2->cx) / 2;
   vnew->cy = (v1->cy + v2->cy) / 2;
   vnew->cz = (v1->cz + v2->cz) / 2;
-  vnew->x = (v1->x + v2->x) / 2;
-  vnew->y = (v1->y + v2->y) / 2;
-  vnew->z = (v1->z + v2->z) / 2;
+  vnew->whitex = (v1->whitex + v2->whitex) / 2;
+  vnew->whitey = (v1->whitey + v2->whitey) / 2;
+  vnew->whitez = (v1->whitez + v2->whitez) / 2;
   vnew->odx = (v1->odx + v2->odx) / 2;
   vnew->ody = (v1->ody + v2->ody) / 2;
   vnew->odz = (v1->odz + v2->odz) / 2;
   vnew->val = (v1->val + v2->val) / 2;
```

### Alternative Fixes Considered

- **Delete the duplicate block entirely.** Restores correct
  semantics for `x/y/z` (the first block already set them)
  but leaves `whitex/whitey/whitez` uninitialised — same
  observable as today. Not a fix, just a cleanup.
- **Move the `whitex/whitey/whitez` assignment into a helper
  that interpolates *all* coordinate triples** (similar to a
  `MRISinterpolateNewVertex(mris, vnew, v1, v2, 0.5)` function).
  Better long-term factoring; the same bug-by-omission could
  recur in the next `divideEdge`-shaped function (e.g.,
  `mrisDivideFace`'s post-step interpolation, if any).
- **Also interpolate `t2x/y/z`, `targx/y/z`,
  `nx/ny/nz`, `wnx/wny/wnz`, `pnx/pny/pnz`, `onx/ony/onz`,
  `fx/fy/fz`, `l4x/y/z`.** These are all currently *not*
  interpolated. For most callers they are recomputed
  downstream (normals via `MRIScomputeMetricProperties`,
  targets via `MRIScomputeBorderValues`), so omission is
  intentional. Adding them changes behaviour at callers that
  do not recompute, which carries regression risk. The
  minimal fix is the one-block change above.

## Workarounds (If Any)

- Disable subdivision by passing `-noaddmesh` (or equivalent)
  to `mris_make_surfaces` if available. Observed flag
  spelling varies between sister tools; check
  `mris_make_surfaces -u` for the local build's flag name.
- Force the input surface to already be fine enough that no
  edge exceeds the threshold sweep — i.e., pre-subdivide
  with a tool that does not exhibit this defect (no clean
  in-tree alternative; `MRISdivideEdges` shares
  `mrisDivideEdge` and is also affected).
