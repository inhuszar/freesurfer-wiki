# [severity-3] [bug-00134] `MRIvol2VolTLKernel` allocates a full-size 8-frame MRI and never uses or frees it; ~500 MB leak per call on typical brain volumes

> [!bug] Synopsis
> ```cpp
> /* utils/mri2.cpp:1233-1291 */
> MRI *MRIvol2VolTLKernel(MRI *src, MRI *targ, MATRIX *Vt2s)
> {
>   ...
>   MRI *kernel;
>
>   kernel = MRIallocSequence(targ->width, targ->height, targ->depth, MRI_FLOAT, 8);  /* :1243 — alloc */
>   if (kernel == NULL) return (NULL);
>   MRIcopyHeader(targ, kernel);                                                       /* :1245 — last use of `kernel` */
>
>   ...
>   for (ct = 0; ct < targ->width; ct++) {
>     for (rt = 0; rt < targ->height; rt++) {
>       for (st = 0; st < targ->depth; st++) {
>         ...
>         kvect = MRItrilinKernel(src, fcs, frs, fss, kvect);
>         for (f = 0; f < 8; f++)
>           MRIsetVoxVal(targ, ct, rt, st, f, kvect[f]);   /* :1276 — write to TARG, not kernel */
>       }
>     }
>   }
>
>   free(kvect);
>   if (FreeMats) { ...MatrixFree... }
>
>   return (0);                                            /* :1290 — returns NULL */
> }
> ```
>
> Three related defects:
>
> 1. **Unused local
>    allocation
>    leaked at
>    `:1243`:**
>    `kernel`
>    holds a freshly
>    allocated
>    `targ->width *
>    targ->height *
>    targ->depth * 8 *
>    sizeof(float)`
>    buffer. The
>    only operations
>    on `kernel`
>    after alloc are
>    a NULL check
>    (`:1244`) and a
>    header copy
>    (`:1245`). The
>    buffer is never
>    written, never
>    returned, never
>    freed.
>
> 2. **Output written
>    to wrong buffer
>    at `:1276`:**
>    The computed
>    `kvect[]` is
>    written to
>    `targ` (the
>    input "target"
>    arg, which the
>    caller passes
>    as the output
>    buffer). This
>    is what the
>    caller expects,
>    but the
>    function's local
>    `kernel` was
>    presumably the
>    intended output
>    based on the
>    name.
>
> 3. **NULL return
>    at `:1290`:**
>    Function
>    signature
>    declares
>    `MRI *` but
>    returns `(0)`,
>    not the
>    computed
>    `kernel` or
>    `targ`. The
>    caller at
>    `mri_vol2vol.cpp:972`
>    doesn't capture
>    the return value
>    (it allocates
>    `out` itself
>    via
>    `MRIcloneBySpace`),
>    so the NULL
>    return isn't
>    observed —
>    but the
>    contract is
>    broken.

## Detailed Description

### Memory-leak
quantification

For a 256³
target volume:

```
leak = 256 * 256 * 256 * 8 * sizeof(float)
     = 16,777,216 * 32
     ≈ 537 MB
```

For a 128³ target:

```
leak = 128 * 128 * 128 * 8 * 4
     ≈ 67 MB
```

Each invocation of
`mri_vol2vol
--kernel` leaks
this much memory.

The leak is
per-call: the
function does not
free `kernel`
before returning,
and the caller has
no handle to it
(the function
returns NULL, and
the caller doesn't
capture the return
value anyway).

### What the
function should
have been

Two equally valid
ways to fix:

```diff
@@ -1240,7 +1240,7 @@ MRI *MRIvol2VolTLKernel(MRI *src, MRI *targ, MATRIX *Vt2s)
   MATRIX *V2Rsrc = NULL, *invV2Rsrc = NULL, *V2Rtarg = NULL;
   int FreeMats = 0;
-  MRI *kernel;
-
-  kernel = MRIallocSequence(targ->width, targ->height, targ->depth, MRI_FLOAT, 8);
-  if (kernel == NULL) return (NULL);
-  MRIcopyHeader(targ, kernel);
+  /* No local kernel buffer — write directly to targ which is the caller's
+   * pre-allocated 8-frame output buffer. */
```

OR write to
`kernel` and
return it:

```diff
   for (st = 0; st < targ->depth; st++) {
     ...
     for (f = 0; f < 8; f++)
-      MRIsetVoxVal(targ, ct, rt, st, f, kvect[f]);
+      MRIsetVoxVal(kernel, ct, rt, st, f, kvect[f]);
   }
 ...
-  return (0);
+  return (kernel);
```

The current code
mixes both
conventions — it
allocates `kernel`
(as if it would
be the output)
but then writes
to `targ` (which
is the caller's
buffer).

### Why this is
severity 3

- **Reproducible
  ~500 MB leak**
  per
  `mri_vol2vol
  --kernel`
  invocation on a
  typical
  conformed brain
  volume.
- **Silent**:
  tool reports
  success; user
  must inspect
  RSS in `top`
  to see the
  leak.
- **Reachable**:
  documented
  `--kernel`
  flag.
- **Functionally
  correct**: the
  output `out`
  buffer does
  contain the
  correct kernel
  values; only
  the
  redundant
  `kernel`
  allocation
  leaks.
- **Below severity
  4**: data is
  not corrupted;
  long-lived
  pipeline
  scripts that
  call
  `--kernel`
  many times
  could leak GB
  of memory and
  eventually OOM,
  but a single
  call leaks
  ~500 MB which
  is recovered
  at process
  exit.

## Root Cause

Likely a
refactoring
defect. An
earlier version
of the function
probably:
- allocated
  `kernel` as
  the output,
- wrote to
  `kernel`,
- returned
  `kernel`.

A refactor
changed the
calling
convention so
the caller
pre-allocates
the output and
passes it as
`targ`. The
writes were
correctly
redirected to
`targ` (line
1276), but the
unused
`kernel`
allocation and
the `return
(0)` were left
in place.

  leak grows
