# [severity-2] [bug-00218] `DeltaTransform3d` — `doOutput` writes `nframes` frames but `doInput` always reads 3; a non-3-frame field makes `createMorph` write a `.tm3d` record that the reader mis-parses

> [!bug] Synopsis
> The `field|` record of a `.tm3d` stores `width, height, depth`, then the field floats, then a mask flag; the number of frames is not stored. The writer loops over `m_field->nframes`, the reader allocates exactly 3 frames. [[createMorph]]'s `volume` keyword accepts any volume that `MRIread` can open without checking its frame count, so a 1-, 2- or 4+-frame volume produces a record of the wrong size. On reload the reader runs past the end of the record (fewer than 3 frames) or silently ignores the extra frames (more than 3), and the mask flag that follows the floats is read from the wrong offset. Reachable only through a malformed `volume` input, hence severity 2.

## Affected Artefacts

- **Tool(s):** [[createMorph]] (writer; `volume` keyword), [[applyMorph]] and [[exportGcam]] (readers, through `VolumeMorph::load`).
- **Pipeline stage(s):** _N/A_ — no in-tree script passes a `volume` item to `createMorph`; [[surf2vol]] always builds 3-frame fields ([`fem_elastic/morph.cpp:611-615`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L611-L615)).
- **FreeSurfer version(s):** confirmed in `8.2.0`; present in the original 2008 import (commit `4b881dc775`, 2008-03-14).
- **Platforms:** all
- **Triggering configuration:** `createMorph --in volume F` where `F` has a frame count other than 3.

## Detailed Description

`DeltaTransform3d::doOutput()` writes the three dimensions, then every frame of `m_field` (`for un < m_field->nframes`), then the mask flag and mask ([`fem_elastic/morph.cpp:494-525`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L494-L525)). `DeltaTransform3d::doInput()` reads the same three dimensions, then allocates `MRIallocSequence(width, height, depth, MRI_FLOAT, 3)` and reads `m_field->nframes` (that is, 3) frames, then the mask flag ([`fem_elastic/morph.cpp:445-492`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L445-L492)). The frame count is neither written nor read, so the two sides agree only when `nframes == 3`.

`createMorph`'s `volume` branch hands the `MRIread` result straight to `set_field()` without looking at `nframes` ([`fem_elastic/fcreateMorph.cpp:123-137`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fcreateMorph.cpp#L123-L137)), and the `.tm3d` is written at the end of the run without being read back, so nothing detects the mismatch. [[createMorph]]'s tool page documents "exactly 3 frames" as a requirement, but the program does not enforce it.

Consequences when the file is read back:

- **`nframes < 3`.** The reader consumes `3·W·H·D` floats but the record holds only `nframes·W·H·D` floats plus one flag byte. The frames after the data, and the mask flag, are read past the end of the record's `std::istringstream`. `TRead<T>` does not check the stream state and returns the contents of an uninitialised heap cell ([`fem_elastic/streamIoMisc.h:23-32`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/streamIoMisc.h#L23-L32)), so the missing frames, and the mask flag, are indeterminate values.
- **`nframes > 3`.** The writer emits all frames; the reader stops after frame 2. The extra frames are not read, and the bytes that follow (the remaining frames) are interpreted as the mask flag and mask: a non-zero byte in the flag position would be taken as "has mask", so the field would be masked with arbitrary data.

### Expected Behaviour

`createMorph --in volume F` should reject a volume whose frame count is not 3 (the only layout the reader supports), or the record should carry its frame count.

### Observed Behaviour

`createMorph` exits 0 and writes a `.tm3d` whose `field|` record has a payload that is `nframes · W·H·D·4 + 1` bytes long instead of `3 · W·H·D·4 + 1`. `applyMorph` loads such a file without any message. In the experiments below the indeterminate values happened to be zero in every run, so the damage was masked by luck; the behaviour is nevertheless undefined.

### Reproducer

Synthetic 32x32x32, 8 mm volumes with nframes = 1, 2, 3, 4 (`nfN.mgz`, frame 0 filled with 2.0, the other frames with 0), all on the grid of `tmpl.mgz` (random intensities, same geometry):

```bash
for nf in 1 2 4; do
  createMorph --out nf$nf.tm3d --template tmpl.mgz --subject tmpl.mgz --in volume nf$nf.mgz
  applyMorph  --template tmpl.mgz --transform nf$nf.tm3d vol tmpl.mgz nf${nf}_applied.mgz linear
done
```

Observed (the `field|` record was decoded after zlib inflation: header, then `int32 w,h,d`, then payload):

| frames in the volume | bytes after the three dimensions | = x (W·H·D·4 = 131072) | correct size for the reader |
|---|---|---|---|
| 1 | 131073 | 1 | 393217 |
| 2 | 262145 | 2 | 393217 |
| 3 | 393217 | 3 | 393217 (consistent) |
| 4 | 524289 | 4 | 393217 |

`createMorph` and `applyMorph` exited 0 in all cases and printed no warning. The reloaded 1-, 2- and 4-frame morphs gave `applyMorph` outputs equal to the expected "shift of 2 voxels along the first axis" at 100 % of the voxels (for the 1- and 4-frame cases, because the unread/missing frames were zero); a 2-frame variant with frame 1 equal to 1.0 gave the expected x+2, y+1 shift, i.e. the third (z) frame, read past the end of the record, came back as 0. Three repeated `applyMorph` runs for each variant produced identical output. A 4-frame variant with frame 3 equal to 7.0 was loaded as if that frame did not exist. So in practice the first three frames survive and the rest is dropped or zero-filled, and the lack of any diagnostic remains the defect.

## Root Cause

The on-disk format has no frame-count field and the class has no invariant check. The reader hard-codes 3 frames (the format's de-facto contract), the writer trusts whatever frame count the in-memory `MRI` has, and the only producer that does not construct the `MRI` itself (`createMorph volume`) performs no check. `TRead` reports no error and hands back uninitialised memory when the stream is exhausted.

## Impact

- **Reach.** Only a hand-supplied `volume` input with the wrong frame count. The shipped TRACULA use of `createMorph` and the CVS pipeline ([[surf2vol]]) always produce 3-frame fields. Latent under typical usage: severity 2.
- **Effect when reached.** The frame data after the third are dropped, and missing frames read as indeterminate (observed zero). In the worst case the mask flag is read from garbage bytes. No diagnostic is issued by `createMorph` or by the readers.
- **No regression:** present since the 2008 import.

## Recommended Fix

Reject the input where it enters, and make the writer refuse to produce an inconsistent record:

```diff
--- a/fem_elastic/fcreateMorph.cpp
+++ b/fem_elastic/fcreateMorph.cpp
@@ "volume" branch
       if ( !field )
       {
         std::cerr << " failed to read field "  << std::endl;
         exit(1);
       }
+      if ( field->nframes != 3 )
+      {
+        std::cerr << " volume field must have exactly 3 frames (dx,dy,dz), got "
+                  << field->nframes << std::endl;
+        exit(1);
+      }
       pvol->set_field(field);
--- a/fem_elastic/morph.cpp
+++ b/fem_elastic/morph.cpp
@@ DeltaTransform3d::doOutput
   if ( !m_field )
     throw "DeltaTransform3d save - NULL data";
+  if ( m_field->nframes != 3 )
+    throw "DeltaTransform3d save - field must have 3 frames";
```

A format-level alternative is to add a frame count to the record, but that changes the `.tm3d` layout read by released tools. Tests: `createMorph --in volume` with 1-, 2- and 4-frame volumes must exit non-zero and write no file; a 3-frame volume must round-trip through `applyMorph` unchanged. Optionally, `TRead` should check `is.good()` and throw on a short read.

## Workarounds (If Any)

Make sure the input to `createMorph --in volume` has exactly 3 frames (`mri_convert` or `mri_concat` can assemble them) before calling it.
