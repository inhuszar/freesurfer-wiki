# [severity-2] [bug-00084] `freadInt` silently returns uninitialised stack data on read failure

> [!bug] Synopsis
> `freadInt`
> ([`utils/fio.cpp:182-193`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/fio.cpp#L182-L193))
> attempts to detect read failure with
>
> ```cpp
> int freadInt(FILE *fp)
> {
>   int i, err;
>   if ((err = fread(&i, sizeof(int), 1, fp)) < 0 && Gdiag_no >= 0) {
>       ErrorPrintf(ERROR_BADFILE, "freadInt: fread failed %d", err);
>   }
> #if (BYTE_ORDER == LITTLE_ENDIAN)
>   i = swapInt(i);
> #endif
>   return (i);
> }
> ```
>
> Two defects in three lines:
>
> 1. **`fread(...) < 0`** is unreachable. `fread`
>    returns a `size_t` count of items
>    successfully read; failure is signalled by
>    `0`, never by a negative value. The
>    "ERROR_BADFILE" branch never fires, and the
>    function's only failure mode is to silently
>    `swapInt` and return whatever junk happened
>    to be on the stack at `i`.
> 2. **`Gdiag_no`** is the diagnostic vertex
>    index (the global that drives the `if (vno
>    == Gdiag_no) DiagBreak();` pattern), not a
>    verbosity flag. Even on a corrected
>    `< 1` / `!= 1` comparison, `Gdiag_no >= 0`
>    is at best meaningless as a gate (its
>    sentinel default is `-1`, but other callers
>    set it to a real vertex number for unrelated
>    debugging).
>
> Sister functions in the same file
> (`freadLong` `:198`, `freadShort` `:211`,
> `freadDouble` `:178`) all use the correct
> `!= 1` check.

## Affected Artefacts

- **Tool:** `freadInt` is a low-level helper used
  by 19 source files in v$FREESURFER_VERSION
  (volume-format readers, surface readers,
  GCA / GCAM / wfile readers, etc.). Any caller
  that depends on the function reporting a read
  failure receives, instead, a stack-uninitialised
  integer.
- **Pipeline stage(s):** none in default
  `recon-all` *as a wrong-output bug* — the
  upstream callers all `fopen` the file before
  reading, so EOF on a well-formed input is rare.
  But for truncated or corrupt files the failure
  is silent.
- **Triggering configuration:** truncated or
  corrupt binary file fed to any tool that uses
  `freadInt`.
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION` (commit `d932c45b79`).

## Detailed Description

```cpp
/* utils/fio.cpp:182-193 */
int freadInt(FILE *fp)
{
  int i, err;
  if ((err = fread(&i, sizeof(int), 1, fp)) < 0 && Gdiag_no >= 0) {  /* :186 — dead check */
      ErrorPrintf(ERROR_BADFILE, "freadInt: fread failed %d", err);
  }
#if (BYTE_ORDER == LITTLE_ENDIAN)
  i = swapInt(i);
#endif
  return (i);
}
```

Compare:

```cpp
/* utils/fio.cpp:194-205 — freadLong, correct */
long long freadLong(FILE *fp)
{
  long long i;
  if (fread(&i, sizeof(long long), 1, fp) != 1) {
    ErrorPrintf(ERROR_BADFILE, "freadLong: fread failed");
  }
  ...
}
```

When `fread` returns 0 (EOF or read error), `i`
inside `freadInt` is never written; the function
swaps and returns indeterminate stack data,
which downstream code consumes as an integer
(typically a header field — version, frame
count, dimension, label). Subsequent allocations
sized by that integer can produce wild values.

Per ISO C: reading an indeterminate `int` is not
strict undefined behaviour (no trap
representation), but the value is unspecified
and the function's contract — that the return
is the integer at the file's current position —
is violated.

## Root Cause

Likely a typo on initial authoring (the `< 0`
sentinel is the convention for `read(2)` and
some POSIX I/O calls — but **not** `fread(3)`,
which returns an unsigned count). The
`Gdiag_no >= 0` clause was probably intended as
"diagnostics enabled," confusing the diagnostic-
vertex global with the verbosity flag (`Gdiag &
DIAG_SHOW`).

## Impact

- **Silent failure on truncated input:**
  callers reading binary headers or counts
  receive an uninitialised value; subsequent
  `calloc(<bogus>, ...)` either fails (caught
  elsewhere) or silently allocates a wildly
  wrong size, with read-past-EOF, garbled
  output, or `OOM`.
- **No effect on well-formed inputs:** for the
  default `recon-all` flow with intact files
  the bug never fires.
- **Severity:** 2 (latent under typical
  conditions; affects only error-handling
  paths).

Matches the convention used by the three sister
functions in the same file. If the caller needs
to distinguish EOF, expose an `Ex` variant (cf.
`freadIntEx` at
[`:249`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/fio.cpp#L249))
— which already exists and uses `fread`'s real
return value.

## Workarounds

Callers that need to distinguish EOF from a
legitimate `0` value should call `freadIntEx`
([`utils/fio.cpp:249-256`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/fio.cpp#L249-L256))
instead of `freadInt`.
