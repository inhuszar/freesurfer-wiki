# [severity-2] [bug-00174] fvcompare — --pial loads the WHITE surface (copy-paste error: surflist = (white))

> [!bug] Synopsis
> `fvcompare`'s `--pial` flag is meant to display only the pial surfaces
> (`?h.pial`) in freeview. Its case handler instead sets
> `surflist = (white)` — an exact copy of the `--white` handler — so
> `--pial` loads the **white** surfaces and never loads the pial surfaces
> at all. A user who asks `fvcompare --pial ...` to inspect the pial
> boundary is shown the gray/white boundary instead, with no indication
> that the wrong surface was loaded.

## Affected Artefacts

- **Tool(s):** [[fvcompare]] — the `--pial` option
  ([`scripts/fvcompare:376-378`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fvcompare#L376-L378)).
- **Pipeline stage(s):** _N/A_ — `fvcompare` is an interactive
  visual-comparison wrapper around [[wiki/tools/freeview|freeview]]; it is
  not invoked by [[wiki/pipelines/recon-all|recon-all]].
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all — the defect is in the tcsh argument parser; it
  affects every platform that can run freeview.
- **Triggering configuration:** `fvcompare --s <subj> --pial` (or any
  invocation that passes `--pial`). Always reproducible.

## Detailed Description

`fvcompare` builds a freeview command line that overlays surfaces from
two (or more) subjects. The `surflist` variable holds the list of
surface basenames to load; the default is `(white pial)`
([`scripts/fvcompare:18`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fvcompare#L18)).
Several flags narrow this list:

- `--white` → `surflist = (white)` (white only)
- `--orig`  → `surflist = (orig orig.nofix)`
- `--pial`  → **should** be `surflist = (pial)` (pial only)

The `--pial` handler is a verbatim copy of the `--white` handler:

```tcsh
    case "--white":
      set surflist = (white)
      breaksw

    case "--pial":
      set surflist = (white)
      breaksw
```

So `--pial` produces exactly the same surface list as `--white`. The
later loop that emits `--surface` arguments iterates over `surflist` and
constructs paths `$subject/surf/$hemi.$surf`
([`scripts/fvcompare:161-162`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fvcompare#L161-L162)),
so every emitted surface is `?h.white`. The pial surface is never
referenced.

### Expected Behaviour

`fvcompare --pial` should load only the pial surfaces — the help text
says: `--white : only show white surfaces`, and by symmetry `--pial`
should "only show pial surfaces". Freeview should display `?h.pial`.

### Observed Behaviour

`fvcompare --pial` loads `?h.white`. The generated freeview `--surface`
arguments name `surf/lh.white` / `surf/rh.white` (and even label them
`name=s1-lh.white-yellow`), with no `?h.pial` surface anywhere. The pial
boundary the user asked to inspect is absent; the white boundary is shown
instead.

### Reproducer

```bash
# bert ships with both lh.white and lh.pial.
fvcompare --s bert --pial --no-seg --lh
# fvcompare echoes its freeview command; the surface args read:
#   --surface .../bert/surf/lh.white:edgecolor=yellow:name=s1-lh.white-yellow
#   --surface .../bert/surf/lh.white:edgecolor=green:name=s2-lh.white-green
# i.e. lh.white, NOT lh.pial.
#
# For contrast, the default (no surf flag) DOES load both white and pial:
fvcompare --s bert --no-seg --lh
#   --surface .../surf/lh.white...   AND   --surface .../surf/lh.pial...
```

Executed with a stub `freeview`/`fsvglrun` on `PATH` (to capture the
command without opening a GUI) against the installed
`/usr/local/freesurfer/8.2.0/bin/fvcompare`. The `--pial` run emitted only
`lh.white` surface arguments; the default run emitted both `lh.white` and
`lh.pial`, confirming the pial path works and is reachable when `--pial`
does not clobber `surflist`.

```tcsh
      set cue = "$name-$hemi.$surf-$surfcolor[$nth]"
      set surfarg = "$subject/surf/$hemi.$surf":"edgecolor=$surfcolor[$nth]":"name=$cue"
```

## Root Cause

Copy-paste error. The `--pial` case was duplicated from the `--white`
case and the `white` token was never changed to `pial`. The two handlers
are byte-for-byte identical apart from the case label, so `--pial` and
`--white` are functionally the same flag.

## Impact

- **Wrong surface shown when the flag is used; latent otherwise.** The
  bug only fires when the user explicitly passes `--pial`. The default
  invocation (no surface flag) still loads both white and pial correctly,
  so the most common `fvcompare` use is unaffected.
- **Silent.** No error or warning is emitted; the freeview window simply
  shows the white boundary under labels that may say "white" (the `name=`
  field reflects the actual surface, `lh.white`), so an attentive user
  could notice. But a user who trusts the `--pial` flag to do what it
  says will draw conclusions about the pial surface from the white
  surface — e.g. mis-judging pial accuracy, CSF inclusion, or surface
  edits.
- This is a QA/visualisation helper, not a pipeline producing files, and
  the broken behaviour is gated behind a specific flag — hence severity 2.

## Recommended Fix

Set the pial surface in the `--pial` handler:

```diff
     case "--pial":
-      set surflist = (white)
+      set surflist = (pial)
       breaksw
```

After the change, `fvcompare --pial` loads `?h.pial` only, mirroring
`--white`'s "white only" behaviour and matching the implied
`--pial : only show pial surfaces` semantics.

### Alternative Fixes Considered

None needed — the one-token change is unambiguous and self-contained.

## Workarounds (If Any)

Use the explicit `--surf pial` flag instead of `--pial`:

```bash
fvcompare --s bert --surf pial
```

`--surf` sets `surflist` directly from its argument
([`scripts/fvcompare:380-383`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/fvcompare#L380-L383)),
so `--surf pial` correctly loads only the pial surfaces. Alternatively,
omit the flag entirely to load both white and pial (the default).
