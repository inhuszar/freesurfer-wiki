# [severity-3] [bug-00101] `GTMrefTAC` reads past `beta` when a refid is missing from `segidlist`

> [!bug] Synopsis
> `GTMrefTAC`
> ([`utils/gtm.cpp:2424-2478`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/gtm.cpp#L2424-L2478))
> averages the `gtm->beta` rows whose seg IDs
> appear in the user-supplied
> `gtm->km_refids[]` array to build the
> reference time-activity curve. The lookup
> uses a search-and-break pattern, but the
> post-loop accumulator runs **regardless** of
> whether the search found a match:
>
> ```cpp
> /* utils/gtm.cpp:2436-2447 — DoKMRef block */
> for (f = 0; f < gtm->yvol->nframes; f++) {
>   sum = 0;
>   for (n = 0; n < gtm->n_km_refids; n++) {
>     for (nthseg = 0; nthseg < gtm->nsegs; nthseg++) {
>       segid = gtm->segidlist[nthseg];
>       if (segid == gtm->km_refids[n]) break;
>     }
>     /* :2443 — runs whether matched or not */
>     sum += gtm->beta->rptr[nthseg + 1][f + 1];
>   }
>   gtm->km_reftac->rptr[f + 1][1] = sum / gtm->n_km_refids;
>   ...
> }
> ```
>
> If `km_refids[n]` is not in `segidlist`, the
> inner loop completes naturally and `nthseg ==
> gtm->nsegs`. The accumulator then reads
> `gtm->beta->rptr[nsegs + 1][f + 1]` — one
> row past the end of `beta` (allocated as
> `MatrixAlloc(nsegs, nframes, ...)` with valid
> 1-indexed rows `1..nsegs`).
>
> The OOB-read value is summed into `sum`, the
> mean is divided by `n_km_refids` (which
> already counts the missing refid as if it
> were valid), and the result is written to
> `km.ref.tac.dat`. The same pattern repeats
> in the `DoKMHB` block at `:2456-2466` for
> `km_hbids`.

## Affected Artefacts

- **Tool:** [[mri_gtmpvc]] when invoked with
  `--km-ref <ids>` or `--km-hb <ids>`
  ([`mri_gtmpvc/mri_gtmpvc.cpp:1561-1568`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_gtmpvc/mri_gtmpvc.cpp#L1561-L1568)).
- **Pipeline stage(s):** none in default
  `recon-all`.
- **Triggering configuration:** the user
  supplies a refid that is not present in the
  GTM segmentation (e.g. a typo in the seg-id
  number, or a refid that was replaced by the
  GTM seg-replacement list).
- **FreeSurfer version(s):** confirmed in
  `$FREESURFER_VERSION` (commit `d932c45b79`).

## Detailed Description

```cpp
/* utils/gtm.cpp:2436-2447 — DoKMRef block */
for (f = 0; f < gtm->yvol->nframes; f++) {
  sum = 0;
  for (n = 0; n < gtm->n_km_refids; n++) {
    for (nthseg = 0; nthseg < gtm->nsegs; nthseg++) {
      segid = gtm->segidlist[nthseg];
      if (segid == gtm->km_refids[n]) break;
    }
    sum += gtm->beta->rptr[nthseg + 1][f + 1];
  }
  gtm->km_reftac->rptr[f + 1][1] = sum / gtm->n_km_refids;
  fprintf(fp, "%20.15lf\n", sum / gtm->n_km_refids);
}
```

Three correctness issues compound:

1. **Out-of-bounds read.** When the inner
   `for (nthseg ...)` loop completes without
   `break`, `nthseg == gtm->nsegs`. `beta` has
   1-indexed rows `1..nsegs`; reading
   `rptr[nsegs + 1]` is OOB. With matrix.cpp's
   contiguous-data layout, the read lands one
   row past the allocated buffer in
   `data` — reading whatever happens to live
   in heap memory afterwards.

2. **Spurious average.** The OOB-read value
   contributes to `sum` and is divided by
   `n_km_refids` (the user-supplied count,
   which still includes the missing refid as
   a valid contributor). The reference TAC
   for that frame is therefore biased by an
   unspecified amount.

3. **Silent failure.** The user gets a
   `km.ref.tac.dat` file with no warning that
   their refid was unmatched; downstream
   pharmacokinetic modelling consumes the
   bogus TAC.

The matching-`break` semantic means: when a
match exists, `nthseg` retains the matched
index and `beta->rptr[nthseg + 1][...]`
correctly reads the matching row. Only the
no-match path is broken.

The `DoKMHB` block at `:2456-2466` repeats the
same pattern for `km_hbids` — same defect.

## Root Cause

Search-and-break pattern without a "found"
flag. The inner `for` loop's exit condition
(`nthseg == nsegs`) is indistinguishable from
the post-`break` state at the call site —
both leave `nthseg` at a value, just one is
in-range and the other is out-of-range.
Sister code in the same file (`GTMmgRefTAC`)
uses the correct `found` flag idiom, showing
the author knew the right pattern in another
context.

## Impact

- **Silent corruption of `km.ref.tac.dat` /
  `km.hb.tac.dat`:** when a user-supplied
  `km_refids[n]` is missing from
  `segidlist`, the corresponding seg's
  contribution is replaced by an
  unspecified heap value. The reference TAC
  is then averaged with the bogus row
  included, biasing every PK-model
  computation that uses the TAC.
- **No diagnostic.** The user has no signal
  that their refid was unrecognised.
- **Severity:** 3 — flag-gated; requires the
  user to supply an unmatched refid (a
  configuration error). When triggered, the
  output is silently wrong and downstream
  PK-modelling results are biased.

## Recommended Fix

```diff
--- a/utils/gtm.cpp
+++ b/utils/gtm.cpp
@@ -2436,11 +2436,17 @@ int GTMrefTAC(GTM *gtm)
     for (f = 0; f < gtm->yvol->nframes; f++) {
       sum = 0;
+      int nfound = 0;
       for (n = 0; n < gtm->n_km_refids; n++) {
+        int found = 0;
         for (nthseg = 0; nthseg < gtm->nsegs; nthseg++) {
           segid = gtm->segidlist[nthseg];
-          if (segid == gtm->km_refids[n]) break;
+          if (segid == gtm->km_refids[n]) { found = 1; break; }
         }
+        if (!found) {
+          fprintf(stderr, "WARNING: km refid %d not in segidlist\n", gtm->km_refids[n]);
+          continue;
+        }
         sum += gtm->beta->rptr[nthseg + 1][f + 1];
+        nfound++;
       }
-      gtm->km_reftac->rptr[f + 1][1] = sum / gtm->n_km_refids;
-      fprintf(fp, "%20.15lf\n", sum / gtm->n_km_refids);
+      gtm->km_reftac->rptr[f + 1][1] = (nfound > 0) ? sum / nfound : 0;
+      fprintf(fp, "%20.15lf\n", gtm->km_reftac->rptr[f + 1][1]);
     }
```

The same pattern should be applied to the
`DoKMHB` block at `:2456-2466`. The mirror
implementation in `GTMmgRefTAC`
(`:1758-1769`) shows the convention.

## Workarounds

Verify that every id in the `--km-ref` and
`--km-hb` lists appears in the GTM
segmentation before running `mri_gtmpvc`.
Cross-check with the `gtmseg` log output.
