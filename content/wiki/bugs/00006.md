# [severity-2] [bug-00006] MRIdistanceTransform — anisotropic voxels produce non-Euclidean mm distances

> [!bug] Synopsis
> `MRIdistanceTransform` in `utils/mri.cpp` returns an Euclidean
> distance in millimetres only when the input volume is isotropic
> (`xsize == ysize == zsize`). Two independent assumptions fail on
> anisotropic inputs: (i) the underlying fast-marching Eikonal
> solver uses a unit grid spacing in all three axes, so its output
> treats each voxel as a unit cube regardless of the physical
> spacing; and (ii) the wrapper rescales the result by
> `mri_src->xsize` only, which is correct (by coincidence) for
> isotropic data but ignores the y- and z-spacings entirely. On
> anisotropic inputs both errors compound, giving distances that are
> neither voxel-count nor true millimetres.

## Affected Artefacts

- **Tool(s):** [[mri_distance_transform]] (CLI wrapper) and any tool
  that calls `MRIdistanceTransform` — notably
  [[mri_ca_register]] via [`gcamorph.cpp:887`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcamorph.cpp#L887), [`gcamorph.cpp:14476`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcamorph.cpp#L14476),
  and [`gcamorph.cpp:14478`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcamorph.cpp#L14478) (label-morph SSE and demons on distance
  transforms); `mri_extract_fcd_features` via [`utils/fcd.cpp:319`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/fcd.cpp#L319);
  [`utils/gcaboundary.cpp:1105`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/gcaboundary.cpp#L1105); [`utils/class_array.cpp:173`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/class_array.cpp#L173).
- **Pipeline stage(s):** The defect is latent in the standard
  [[wiki/pipelines/recon-all|recon-all]] flow because recon-all conforms its inputs to
  1 mm isotropic before running atlas registration and surface
  deformation. Non-conformed inputs, `mri_ca_register` used outside
  recon-all, and any tool that feeds a native (anisotropic) volume
  into `MRIdistanceTransform` hit the defect directly.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit
  `d932c45b79`.
- **Platforms:** all.
- **Triggering configuration:** any volume with non-equal voxel
  spacings on the three axes (for example, 1×1×3 mm clinical T1w).

## Detailed Description

`MRIdistanceTransform` is a thin wrapper around `MRIextractDistanceMap`
(in `utils/mri_fastmarching.cpp`), which dispatches to the templated
`FastMarching<sign>` class in `include/fastmarching.h`. The wrapper
applies a post-hoc rescaling:

```cpp
mri_dist = MRIextractDistanceMap(mri_src, mri_dist, label, max_dist, mode, mri_mask);
mri_dist->outside_val = max_dist;
MRIscalarMul(mri_dist, mri_dist, mri_src->xsize);
```

Two separate issues prevent this from producing a correct Euclidean
distance field in millimetres when the input is anisotropic.

### 1. The Eikonal solver assumes an isotropic unit grid

The per-voxel update in `FastMarching<sign>::_UpdateValue` solves the
discretised Eikonal equation

$$
\left(\frac{T-A}{h_x}\right)^{2} + \left(\frac{T-B}{h_y}\right)^{2} + \left(\frac{T-C}{h_z}\right)^{2} = \frac{1}{F^{2}}
$$

with $h_x = h_y = h_z = 1$ and $F = 1$. The quadratic coefficients in
the implementation are

```cpp
float a = 3;
float b = -(A+B+C);
float c = A*A + B*B + C*C - 1;  // ← "- 1" bakes h² = 1 into the solver
```

There is no `xsize`/`ysize`/`zsize` anywhere in the update; the
spacings are never read.

### 2. The wrapper converts voxels → mm using the x-spacing only

After the solver returns, the wrapper multiplies the entire volume by
`mri_src->xsize`. Even if the solver had produced a correct
voxel-count distance, this scale is correct in all three axes only
when `xsize == ysize == zsize`. For anisotropic inputs, the mm
distance along y or z is under- or over-reported by the ratio
`ysize/xsize` or `zsize/xsize`.

### Expected Behaviour

`MRIdistanceTransform(src, dst, label, max, mode, mask)` should
return, at each voxel, the Euclidean distance in millimetres from
that voxel to the nearest voxel carrying `label` (with sign encoding
inside/outside when `mode == DTRANS_MODE_SIGNED`).

### Observed Behaviour

For an isotropic volume (the common case) the result is correct up
to the accuracy of the fast-marching solver.

For an anisotropic volume with spacings $(h_x, h_y, h_z)$:

- The solver produces a scalar $T$ at each voxel that satisfies a
  unit-grid Eikonal equation, so $T$ is a voxel-count distance.
- The wrapper returns $T \cdot h_x$. Along the x axis this equals the
  true mm distance. Along the y axis the true mm distance is
  $T \cdot h_y$, and the returned value is off by a factor of
  $h_x / h_y$.

As an illustrative example, a $256 \times 256 \times 60$ volume with
spacings $(1, 1, 3)$ mm will have the label-to-voxel distance along
the z axis reported as $\tfrac{1}{3}$ of its true mm value.

### Reproducer

> [!gap] Reproducer not yet constructed

> 2. Call `MRIdistanceTransform(src, NULL, 1, 100, DTRANS_MODE_UNSIGNED, NULL)`;
>    confirm that the distance at `(10, 0, 0)`, `(0, 10, 0)` and

> 3. Rebuild the same volume with spacings `(1, 1, 3) mm`, seed the

```cpp
MRI *MRIdistanceTransform(MRI *mri_src, MRI *mri_dist, int label, float max_dist, int mode, MRI *mri_mask)
{
  const int width = mri_src->width;
  const int height = mri_src->height;
  const int depth = mri_src->depth;

  if (mri_dist == NULL) {
    mri_dist = MRIalloc(width, height, depth, MRI_FLOAT);
    MRIcopyHeader(mri_src, mri_dist);
  }
  else
    MRIclear(mri_dist);

  // these are the modes in fastmarching...
  const int outside = 1;
  const int both_signed = 3;
  const int both_unsigned = 4;

  if (mode == DTRANS_MODE_SIGNED) {
    mode = both_signed;
  }
  else if (mode == DTRANS_MODE_UNSIGNED) {
    mode = both_unsigned;
  }
  else if (mode == DTRANS_MODE_OUTSIDE) {
    mode = outside;
  }

  if (mri_src->type != MRI_FLOAT) {
    MRI *mri_tmp = MRIchangeType(mri_src, MRI_FLOAT, 0, 1, 1);
    mri_dist = MRIextractDistanceMap(mri_tmp, mri_dist, label, max_dist, mode, mri_mask);
    MRIfree(&mri_tmp);
  }
  else
    mri_dist = MRIextractDistanceMap(mri_src, mri_dist, label, max_dist, mode, mri_mask);

  mri_dist->outside_val = max_dist;
  MRIscalarMul(mri_dist, mri_dist, mri_src->xsize);  // ← uses xsize only
  return mri_dist;
}
```

  float c = A*A + B*B + C*C - 1;     // ← unit spacing in all axes

There are no `xsize` / `ysize` / `zsize` reads anywhere in the
`FastMarching` class; the spacings are not available to the solver.

## Root Cause

Two design choices compound:

1. `FastMarching::_UpdateValue` was written for an isotropic unit
   grid. The `h²` term in the discretised Eikonal equation is
   hard-coded to `1`, and the solver does not have access to the
   source volume's voxel spacings.
2. The `MRIdistanceTransform` wrapper applies a single-scalar rescale
   by `mri_src->xsize` to convert voxel units to millimetres. This
   rescale collapses three independent spacings into one, and is
   correct only when `xsize == ysize == zsize`.

For isotropic volumes both shortcuts happen to cancel out, so the
defect was masked by FreeSurfer's habit of conforming inputs to
1 mm isotropic before anything reaches this code.

## Impact

- **`mri_distance_transform` CLI.** Users who invoke the tool on an
  anisotropic volume (the tool accepts arbitrary input) get a
  distance field that is neither voxel-count nor true millimetres;
  along the axis matching `mri_src->xsize` the values are correct,
  but along the other two axes they are scaled by
  `xsize / ysize` or `xsize / zsize`.
- **`mri_ca_register` (label-morph mode, demons on distance maps).**
  When invoked with anisotropic source and target volumes the SSE in
  `MRIlabelMorphSSE` compares two biased distance fields. If the two
  fields share the same anisotropy the bias largely cancels in the
  ratio; when spacings differ between source and atlas, the
  comparison is systematically distorted along the under-reported
  axes, which biases the warp.
- **FCD feature extraction, `gcaboundary`, `class_array`.** All
  consume the signed distance transform and assume mm units;
  downstream thresholds expressed in mm are miscalibrated on
  anisotropic inputs.
- Standard [[wiki/pipelines/recon-all|recon-all]] runs conform to 1 mm isotropic early on, so
  the defect does not reach the cortical-surface pipeline.

## Recommended Fix

Two complementary patches are needed.

**Short-term (wrapper):** Refuse or loudly warn on anisotropic input
so the silent corruption cannot happen unnoticed:

```diff
+  if (!(FEQUAL(mri_src->xsize, mri_src->ysize) &&
+        FEQUAL(mri_src->ysize, mri_src->zsize))) {
+    ErrorReturn(NULL, (ERROR_UNSUPPORTED,
+      "MRIdistanceTransform: anisotropic voxel spacing "
+      "(%g, %g, %g) is not supported; conform the input first.",
+      mri_src->xsize, mri_src->ysize, mri_src->zsize));
+  }
   mri_dist->outside_val = max_dist;
   MRIscalarMul(mri_dist, mri_dist, mri_src->xsize);
```

**Proper fix (solver):** Propagate the spacings into the Eikonal
update. Store $h_x, h_y, h_z$ in the `FastMarching` template and
rewrite the quadratic:

$$
\sum_i \frac{(T-X_i)^2}{h_i^{2}} = 1
\quad\Rightarrow\quad
\left(\sum_i \tfrac{1}{h_i^2}\right) T^{2}
- 2\left(\sum_i \tfrac{X_i}{h_i^2}\right) T
+ \left(\sum_i \tfrac{X_i^{2}}{h_i^{2}}\right) = 1.
$$

Substitute the three coefficients (and the two-axis and one-axis
degenerate cases) into the existing `a`, `b`, `c` computation, and
remove the `MRIscalarMul(...,  mri_src->xsize)` post-scale from the
wrapper — the solver will already emit distances in mm.

### Alternative Fixes Considered

Rescale voxel coordinates to isotropic before running the solver
(e.g., pad and resample to the smallest spacing, then reverse). This
is equivalent in effect to fixing the solver but allocates a larger
intermediate volume and adds interpolation error at label boundaries.

## Workarounds (If Any)

Conform the input to an isotropic grid (`mri_convert --conform`,
`--conform-min`, or `mri_convert -vs Xmm Xmm Xmm`) before calling
`MRIdistanceTransform`. This is already the default behaviour inside
[[wiki/pipelines/recon-all|recon-all]].

> [!gap] Fast-marching degenerate cases
> The proper fix needs care in the "one-axis only" and "two-axes
> only" fall-back paths (lines 360–380 of the solver), which choose
> between quadratics with fewer terms. Each of those reduced
> quadratics needs its own anisotropic variant; a developer with a
> reference fast-marching implementation should translate the
> Sethian/Tsitsiklis discretisation carefully rather than patching
> by analogy.
