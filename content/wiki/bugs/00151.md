# [severity-2] [bug-00151] tcsh `setenv VAR = value` is invalid — `-sd`/`--sd` (and `FS_CHECK_OS`) handlers abort with "Too many arguments" instead of setting the variable

> [!bug] Synopsis
> Seven FreeSurfer tcsh scripts set an environment variable with the
> syntax `setenv VAR = value` (with spaces around `=`). The `tcsh`
> `setenv` builtin does **not** accept an `=`: the assignment is written
> `setenv VAR value`. With three whitespace-separated tokens
> (`VAR`, `=`, `value`) `setenv` aborts the current statement with
> `setenv: Too many arguments.`, the variable is **not** set, and — because
> the failing `setenv` is the last thing the option handler does — the
> option's argument is silently dropped and option parsing stops there.
> In six scripts this breaks the `-sd`/`--sd` handler
> (`setenv SUBJECTS_DIR = $argv[1]`), so passing `-sd <dir>` on the command
> line is non-functional. In `fs-check-os` the same defect
> (`setenv FS_CHECK_OS = 1`) leaves `FS_CHECK_OS` undefined, so the very
> next line `if(! $FS_CHECK_OS)` dies with `FS_CHECK_OS: Undefined variable.`

## Affected Artefacts

- **Tool(s):** [[longmc]], [[rca-base-init]], [[conf2hires]],
  [[defect2seg]], [[train-gcs-atlas]], [[fsfirst.fsl]] (all six in the
  `-sd`/`--sd` handler), and [[fs-check-os]] (in the post-parse
  `FS_CHECK_OS` default block).
- **Pipeline stage(s):** _N/A_ — none of these scripts is on the default
  [[wiki/pipelines/recon-all|recon-all]] chain; they are standalone helpers
  / longitudinal sub-steps invoked individually.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all — pure `tcsh` builtin semantics. All seven scripts
  use `#!/bin/tcsh -f`.
- **Triggering configuration:**
  - For the `-sd` sites: pass `-sd <dir>` (or `--sd <dir>` where the
    script accepts the double-dash spelling) on the command line.
  - For `fs-check-os`: any invocation that reaches the post-parse block
    while `FS_CHECK_OS` is unset — i.e. a normal run that does **not**
    pass `--check` / `--no-check` (those set `FS_CHECK_OS` in the parse
    loop) and does not exit early via `--get`. `FS_CHECK_OS` is never set
    anywhere else in the source tree, so it is unset by default.

## Detailed Description

In `tcsh`, the `setenv` builtin takes the form `setenv name value`
(or `setenv name` to set it empty). Unlike `set`, it uses **no** `=`.
Writing `setenv VAR = value` passes three arguments to the builtin
(`VAR`, `=`, `value`); `setenv` accepts at most two, so it raises
`setenv: Too many arguments.` and performs no assignment.

This error is non-fatal at the statement level (a later statement on a
new line still runs), but it has two compounding consequences in the
affected handlers:

1. The intended variable is never assigned. For the `-sd` handlers,
   `SUBJECTS_DIR` keeps whatever value it already had; the path the user
   typed after `-sd` is lost.
2. The failing `setenv` is the **last** statement before `shift` /
   `breaksw` on the same logical line (`setenv SUBJECTS_DIR = $argv[1]; shift;`).
   When the builtin errors, the remainder of that line does not execute
   and the surrounding parse loop does not continue past the error — so
   the option's argument is not even consumed cleanly.

For `fs-check-os` the failure is sharper. The buggy line lives in a
guard that only runs when `FS_CHECK_OS` is unset:

```tcsh
if($?FS_CHECK_OS == 0) then
  setenv FS_CHECK_OS = 1
endif
if(! $FS_CHECK_OS) then
  ...
```

After `setenv FS_CHECK_OS = 1` fails, `FS_CHECK_OS` is still undefined,
so the immediately-following `if(! $FS_CHECK_OS)` references an undefined
variable, which **is** fatal in a non-interactive `tcsh -f` script:
`FS_CHECK_OS: Undefined variable.` and the script exits non-zero.

Note that the *same scripts* contain correctly-written `setenv` lines
elsewhere — e.g. `fs-check-os` writes `setenv FS_CHECK_OS 1` (no `=`) in
its `--check` case and `setenv SUBJECTS_DIR $argv[1]` (no `=`) in its
own `--sd` case — which confirms the `= ` form in the affected lines is
an editing slip, not an intended idiom.

### Expected Behaviour

- `-sd <dir>` / `--sd <dir>` sets `SUBJECTS_DIR` to `<dir>` for the
  remainder of the run, exactly as the equivalent handlers in
  [[wiki/pipelines/recon-all|recon-all]] and other FreeSurfer scripts do.
- `fs-check-os`, when `FS_CHECK_OS` is unset, defaults it to `1` and
  proceeds to perform the OS check.

### Observed Behaviour

- `setenv: Too many arguments.` is printed to stderr at the handler.
- The target variable is not modified.
- For the `-sd` sites, the user-supplied subjects directory is silently
  ignored (parsing stops at the broken handler).
- For `fs-check-os`, the script additionally aborts on the next line with
  `FS_CHECK_OS: Undefined variable.`

### Reproducer

```bash
# 1. -sd handler is non-functional (installed binaries):
env -u SUBJECTS_DIR /usr/local/freesurfer/8.2.0/bin/defect2seg --sd /tmp
#   -> setenv: Too many arguments.    (and --sd /tmp is dropped)
env -u SUBJECTS_DIR /usr/local/freesurfer/8.2.0/bin/rca-base-init -sd /tmp
env -u SUBJECTS_DIR /usr/local/freesurfer/8.2.0/bin/longmc        -sd /tmp
env -u SUBJECTS_DIR /usr/local/freesurfer/8.2.0/bin/conf2hires    --sd /tmp
env -u SUBJECTS_DIR /usr/local/freesurfer/8.2.0/bin/train-gcs-atlas --sd /tmp
env -u SUBJECTS_DIR /usr/local/freesurfer/8.2.0/bin/fsfirst.fsl   --sd /tmp

# 2. fs-check-os reaches the buggy default block (no --check), FS_CHECK_OS unset:
env -u FS_CHECK_OS /usr/local/freesurfer/8.2.0/bin/fs-check-os --sd /tmp
#   -> setenv: Too many arguments.   (then dies; exit 1)

# Minimal first-principles demonstration of the builtin semantics:
tcsh -f -c 'setenv FOO = bar; echo "[$FOO]"'
#   -> setenv: Too many arguments.   (FOO stays unset)
tcsh -f -c 'setenv FOO bar; echo "[$FOO]"'
#   -> [bar]                         (correct form)
```

All `-sd` reproducers above were executed against the installed 8.2.0
binaries and emit `setenv: Too many arguments.`; the `fs-check-os`
reproducer was executed and additionally aborts.

## Root Cause

A `set`-vs-`setenv` syntax confusion. The `tcsh` `set` builtin uses
`set name = value` (with `=`), but `setenv` uses `setenv name value`
(no `=`). The author wrote the `set`-style `=` in a `setenv` statement.
Because the resulting three-token call exceeds `setenv`'s two-argument
maximum, the builtin errors and assigns nothing.

## Impact

- **`-sd` / `--sd` is non-functional in six scripts.** Users who set the
  subjects directory via the command-line flag instead of the
  `SUBJECTS_DIR` environment variable do not get the directory they
  asked for; the run proceeds against the inherited / default
  `SUBJECTS_DIR` (or fails later when the expected paths are absent). The
  error is printed but easy to miss in a long log.
- **`fs-check-os` aborts** on its default path when `FS_CHECK_OS` is
  unset (the normal case — the variable is set nowhere else in the
  tree), failing with `FS_CHECK_OS: Undefined variable.` rather than
  performing the OS check.
- **Latency / severity.** Rated **low (2)**: in routine use the subjects
  directory is supplied through the `SUBJECTS_DIR` environment variable
  (or `-s <subject>` against an already-exported `SUBJECTS_DIR`), so the
  broken `-sd` flag is rarely the path that bites. None of these scripts
  is part of the default `recon-all` pipeline. The defect is real and
  always-on whenever the affected flag is used, but does not silently
  corrupt scientific output — it either drops the flag (loud-ish) or
  aborts the helper.

## Recommended Fix

Remove the `= ` in every affected `setenv` (six `-sd` sites identical,
plus the `fs-check-os` default block):

```diff
-      setenv SUBJECTS_DIR = $argv[1]; shift;
+      setenv SUBJECTS_DIR $argv[1]; shift;
```

```diff
 if($?FS_CHECK_OS == 0) then
-  setenv FS_CHECK_OS = 1
+  setenv FS_CHECK_OS 1
 endif
```

After the change, `setenv` receives exactly two arguments and assigns
correctly. A repository-wide grep for the same anti-pattern is advisable
to catch any further sites:

```bash
grep -rnE 'setenv[[:space:]]+[A-Za-z_][A-Za-z0-9_]*[[:space:]]+=' scripts/
```

### Alternative Fixes Considered

None preferable. The two-argument `setenv name value` form is the
canonical fix and matches the correctly-written `setenv` lines already
present in the same files.

## Workarounds (If Any)

- For the `-sd` sites: do **not** rely on `-sd`/`--sd`; instead
  `setenv SUBJECTS_DIR <dir>` in the shell before invoking the script
  (or `export SUBJECTS_DIR=<dir>` from a POSIX shell).
- For `fs-check-os`: pre-set `setenv FS_CHECK_OS 1` (or pass `--check`,
  which sets it correctly in the parse loop) before/within invocation to
  skip the broken default block.

## Confidence and Gaps

> [!gap] tcsh-version sensitivity of the exact error text
> The "Too many arguments" diagnostic and the non-assignment were
> reproduced under `tcsh 6.20.00`. Some `tcsh` builds tolerate a glued
> `setenv VAR =value` (assigning the literal `=value`) or `setenv VAR =`
> (assigning the literal `=`); the spaced three-token form
> `setenv VAR = value` used here errors on every `tcsh` we are aware of
> and never assigns the intended value. The fix is correct regardless of
> which degenerate behaviour a given `tcsh` exhibits.
