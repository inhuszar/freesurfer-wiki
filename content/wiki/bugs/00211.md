# [severity-3] [bug-00211] `applyMorph` — the `sprobe` data item always runs as `snormals`

> [!bug] Synopsis
> In [[applyMorph]], the command-line parser advances its iterator past the
> `sprobe`/`snormals` keyword *before* testing `*cit == "sprobe"`, so the
> test is applied to the template-surface file name. Unless that file is
> literally named `sprobe`, the item is typed `snormals` and
> `SurfaceNormalsProbeFilter` runs. The per-vertex Euclidean distance
> written by `SurfaceProbeFilter::Execute` can therefore not be requested
> from the command line: `sprobe` silently produces the normal-component
> residual `|n . (T(t) - s)|` instead of the distance `||T(t) - s||`
> (observed: byte-identical output files for the two keywords).

## Affected Artefacts

- **Tool(s):** [[applyMorph]]
- **Pipeline stage(s):** _N/A_ (no in-tree script calls `applyMorph` with `sprobe`; the only in-tree references to `applyMorph` are commented-out lines in `mri_cvs_register`)
- **FreeSurfer version(s):** confirmed in 8.2.0; the lines date from the original 2008 import of `fapplyMorph.cpp` (commit `4b881dc775f`)
- **Platforms:** all
- **Triggering configuration:** any `applyMorph ... sprobe <template surf> <subject surf> <out>` item. Always on for that keyword; the `snormals` keyword and the `vol`/`surf`/point-list items are unaffected.

## Detailed Description

`IoParams::parse` turns the positional `inputs` list into `DataItem`
records. For the surface-probe items the intended logic is: look at the
keyword (`sprobe` or `snormals`), choose `DataItem::sprobe` or
`DataItem::snormals` accordingly, then read the three operands
`<template surf> <subject surf> <out>`. `main()` then maps the item type
to a filter object: `DataItem::sprobe` creates a `SurfaceProbeFilter`,
`DataItem::snormals` a `SurfaceNormalsProbeFilter` (which is a subclass
overriding `Execute`).

The parser, however, executes `++cit` (to reach the first operand) **before**
the keyword comparison, so `*cit` is already the first operand, the template
surface path. The comparison is `path == "sprobe"`, which is false for
every realistic input; the `else` branch assigns `DataItem::snormals`.

### Expected Behaviour

`sprobe` should instantiate `SurfaceProbeFilter`, which writes for every
vertex `i` the Euclidean distance between the image of the template vertex
under the morph and the corresponding subject vertex, in voxel units
(`-0.1` when the image is invalid); `snormals` should write the absolute
normal component of the same displacement.

### Observed Behaviour

Both keywords run `SurfaceNormalsProbeFilter`. The `SurfaceProbeFilter::Execute`
distance loop is dead code from the command line. No error or warning is
printed; the output has the right shape (one scalar per vertex), so the
substitution is easy to miss. The scalar written for `sprobe` is
numerically a different quantity (the absolute projection of the residual
onto the subject surface normal, which is zero wherever the residual is
tangential), not a distance.

### Reproducer

Synthetic data only: a 32^3 template volume, a hand-built `.tm3d` morph
holding one affine transform that is a pure `+3` voxel x-translation
(`shift3.tm3d`, with valid fixed and moving geometries stored), the
`bert` subject's `lh.white` (135 546 vertices) as the template surface, and a
copy of it shifted by `+2 mm` in RAS y as the "subject" surface
(`lh.white.shift`). With the voxel geometry stored in the morph that is
`+3` voxels in x and `-2` voxels in z between corresponding vertices, so the
true Euclidean distance is `sqrt(3^2 + 2^2) = 3.6056` at every vertex.

```bash
# <W> = an absolute scratch directory. Always give an absolute output path
# whose basename already starts with lh./rh. (MRISwriteCurvature otherwise
# writes next to the input surface and inserts the hemisphere prefix).
applyMorph --template tmpl.mgz --transform shift3.tm3d \
    sprobe   lh.white lh.white.shift <W>/out/lh.sprobe.curv
applyMorph --template tmpl.mgz --transform shift3.tm3d \
    snormals lh.white lh.white.shift <W>/out/lh.snormals.curv
cmp <W>/out/lh.sprobe.curv <W>/out/lh.snormals.curv && echo IDENTICAL

# Control: a surface file whose name is literally "sprobe", used from the
# current directory, makes the parser take the sprobe branch.
cp lh.white sprobe
applyMorph --template ../tmpl.mgz --transform ../shift3.tm3d \
    sprobe sprobe ../lh.white.shift <W>/out/lh.sprobe_ctrl.curv
```

Observed with the installed 8.2.0 binary (all three runs exit 0):

| Run | Per-vertex values (135 546 vertices) |
|-----|--------------------------------------|
| `sprobe lh.white lh.white.shift ...` | min 5.4e-05, max 3.6055, mean 1.912 |
| `snormals lh.white lh.white.shift ...` | identical: `cmp` reports no difference |
| `sprobe sprobe lh.white.shift ...` (file named `sprobe`) | min 3.605549, max 3.605553, mean 3.605552, i.e. the expected constant `sqrt(13)` |

The control proves that `SurfaceProbeFilter::Execute` works and that only
the keyword test is at fault; the distance can be obtained today only by
naming the template surface file `sprobe` and running from its directory.

## Root Cause

`*cit` is evaluated after the `if ( ++cit == container.end() )` guard at
[`fem_elastic/fapplyMorph.cpp:354-355`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fapplyMorph.cpp#L354-L355). At that point the iterator points to the first operand
(the template surface path), not to the keyword that selected this branch
at [`fem_elastic/fapplyMorph.cpp:351-352`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fapplyMorph.cpp#L351-L352). The keyword is never saved before the iterator is moved, so
the comparison at [`fem_elastic/fapplyMorph.cpp:358`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fapplyMorph.cpp#L358) is `strInput == "sprobe"`. Compare the
`vol`, `surf` and point-list branches, which assign the item type directly
because each has its own `else if` keyword test.

## Impact

- **Wrong quantity, silently.** A user who asks for the distance between
  morphed template vertices and subject vertices gets the absolute normal
  component of the residual instead. The two agree only where the residual
  is purely along the surface normal; for a tangential residual the
  written value is 0 even though the vertices are far apart. Any
  registration-accuracy map derived with `sprobe` is affected.
- **Severity 3, not 2 or 4.** The defect is confined to an opt-in data-item
  keyword (specific mode, default `vol`/`surf` paths unaffected), which is
  the severity-3 criterion. It is not scored 4 because no pipeline or
  in-tree script reaches it, and `snormals` (the quantity actually
  produced) is a documented, intended output. It is not scored 2 because
  the primary output file of the requested mode is wrong, not a diagnostic.
- **Interaction.** Once fixed, the `sprobe` path becomes reachable and
  inherits the NULL-dereference on morphs without valid geometry
  ([[00220]]); that crash already exists today for `snormals`.

## Recommended Fix

Remember the keyword before advancing the iterator:

```diff
     else if ( *cit == "sprobe" ||
               *cit == "snormals" )
     {
+      const bool isProbe = ( *cit == "sprobe" );
+
       if ( ++cit == container.end() )
         throw " Incomplete data item";
 
       DataItem item;
-      if ( *cit == "sprobe" )
-        item.m_type = DataItem::sprobe;
-      else
-        item.m_type = DataItem::snormals;
+      item.m_type = isProbe ? DataItem::sprobe : DataItem::snormals;
       item.strInput = *cit;
```

A regression test should run `sprobe` and `snormals` on the same inputs
with a known pure translation and assert that the two outputs differ and
that `sprobe` equals the translation length at every vertex. Note that the
fix changes the output of existing `sprobe` invocations (they will start to
produce true distances); the tool page and `applyMorph.help.xml` (which
documents none of the item keywords) should be updated in the same change.

## Workarounds (If Any)

Use `snormals` for the normal-component residual. To obtain the Euclidean
distance today, either compute it outside `applyMorph` from the morphed
surface (`surf` item) and the subject surface, or give the template surface
file the literal name `sprobe` in the current directory (observed to
select the distance filter).
