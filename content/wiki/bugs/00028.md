# MRImakeDensityMap retains the `max_count = label_means[...]` bug that was fixed in the sister function

> [!bug] Synopsis
> The partial-volume calculation in `MRImakeDensityMap`
> (`utils/mri.cpp:14641-14644`) tracks `max_count` — the largest
> neighbour count — but assigns the neighbour's mean intensity to
> the running maximum:
> `max_count = label_means[this_label]`. The sister function
> `MRIvoxelsInLabelWithPartialVolumeEffects` has the **same
> two-line block twice**, in both cases corrected to
> `max_count = label_counts[this_label]` with the original buggy
> line preserved as a `// bug` comment. The fix was not propagated
> to `MRImakeDensityMap`. As a result, the "best neighbour
> label" decision in `MRImakeDensityMap` compares neighbour
> counts against a running mean intensity — a meaningless
> apples-to-oranges comparison — and the partial-volume estimate
> for every border voxel is computed against the wrong neighbour
> label.

## Detailed Description

### Expected Behaviour

For each border voxel, the algorithm should iterate over all
labels seen in the local neighbourhood, identify the label with
the **largest count** that also satisfies an intensity
constraint, and use that label's mean to compute the
partial-volume mixing fraction. The running maximum should be a
count, not a mean intensity. The sister function
`MRIvoxelsInLabelWithPartialVolumeEffects` at
[`utils/mri.cpp:14485-14489`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L14485-L14489)
demonstrates the intended idiom:

```cpp
if ((label_counts[this_label] > max_count) && ((label_means[this_label] - val) * (mean_label - val) < 0)) {
  // max_count = label_means[this_label] ; // bug
  max_count = label_counts[this_label];
  nbr_label = this_label;
}
```

The author left the buggy line as a comment and corrected it on
the next line.

### Observed Behaviour

`MRImakeDensityMap` at
[`utils/mri.cpp:14641-14644`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L14641-L14644)
still has the original buggy assignment without any correction:

```cpp
if ((label_counts[this_label] > max_count) && ((label_means[this_label] - val) * (mean_label - val) < 0)) {
  max_count = label_means[this_label];   /* ← bug: should be label_counts[this_label] */
  nbr_label = this_label;
}
```

After the first matching iteration, `max_count` holds a mean
intensity (e.g., ~80 for grey matter, ~110 for white matter on a
typical T1) instead of a voxel count. Subsequent iterations
compare `label_counts[this_label] > max_count` — testing whether
a count exceeds a previously-stored mean intensity — which has no
defensible interpretation. The chosen `nbr_label` becomes
effectively arbitrary: any label whose count happens to exceed
the running mean-intensity, in iteration order, wins the slot.

The downstream consequence is at
[`utils/mri.cpp:14649-14657`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mri.cpp#L14649-L14657):

```cpp
if (max_count > 0) /* compute partial volume pct */
{
  mean_nbr = label_means[nbr_label];
  pv = (val - mean_nbr) / (mean_label - mean_nbr);
  if (vox_label == label)
    volume = pv * vox_vol;
  else
    volume = vox_vol * (1 - pv);
  if (pv < 0 || pv > 1) DiagBreak();
}
```

`pv` is computed against the wrong neighbour, so the
partial-volume mixing fraction stored in `mri_dst` is the wrong
fraction of `vox_vol`. The output density map is biased by the
amount of intensity disagreement between the "wrongly chosen"
neighbour and the "correctly chosen" neighbour.

form on the line below. The same fix was not propagated.

## Root Cause

When the author identified and patched the bug pattern in
`MRIvoxelsInLabelWithPartialVolumeEffects`, the audit did not
extend to the structurally similar block in `MRImakeDensityMap`.
Both functions implement the same partial-volume calculation
with neighbour selection; both share the same
`label_counts[this_label] > max_count` guard followed by an
intent-violating assignment. The fix was applied to one
function and missed in the other.

## Impact

- **Latent in v$FREESURFER_VERSION default flows.**
  `MRImakeDensityMap` is reachable only through the attic tool
  `mri_make_density_map` (and from `GCAMextract_density_map`,
  which is itself called only by the same attic tool). The
  defect does not propagate into [[recon-all]] outputs.
- **Wrong density-map values when the function _is_ exercised.**
  Any user invoking the attic tool, or any external linker
  against `libutils` that calls `MRImakeDensityMap`, gets
  silently wrong partial-volume estimates at every border
  voxel that has multiple non-self labels in its 7-voxel
  window. The output is a `MRI_FLOAT` density map whose values
  diverge from a reference computation by a non-trivial fraction
  of `vox_vol`.
- **Silent.** No error, no warning. The function returns the
  density map without any diagnostic to indicate the wrong
  neighbour selection.

## Recommended Fix

```diff
   if ((label_counts[this_label] > max_count) && ((label_means[this_label] - val) * (mean_label - val) < 0)) {
-    max_count = label_means[this_label];
+    max_count = label_counts[this_label];
     nbr_label = this_label;
   }
```

This is a single-token correction. The patch matches the
documented fix in `MRIvoxelsInLabelWithPartialVolumeEffects`
exactly. Optionally also remove the no-longer-needed second
buggy-line comment from the sister function once both are
patched.

### Alternative Fixes Considered

- **Refactor both functions to share a helper.** The two blocks
  are duplicate logic; extracting a helper
  `pickPVNeighbourLabel(label_counts, label_means, val,
  mean_label, vox_label, max_labels)` would prevent future
  drift. Larger change; not necessary for the immediate
  correctness fix.

## Workarounds (If Any)

- Avoid `MRImakeDensityMap` until patched. There is no
  per-caller workaround that recovers the correct neighbour
  selection without a code change.

## Confidence and Gaps

> [!gap] Empirical magnitude
> The numerical magnitude of the resulting density-map error has
> not been measured. The fraction depends on (a) how often
> `label_counts > max_count` after the sentinel is corrupted
> (label-distribution dependent) and (b) how much
> `label_means[this_label]` differs across competing neighbour
> labels (intensity-distribution dependent). For a typical T1
> aseg, the divergence is unlikely to be small.

> [!gap] External users
> The function is exported from `libutils` and could be invoked
> by external tools or scripts not visible in this audit. Their
> exposure has not been catalogued.
