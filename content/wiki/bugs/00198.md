# [severity-3] [bug-00198] `surf2vol` — `update_sources()` discards the result of `std::remove_if`, so points mapped outside the mesh or into inverted elements are not removed (stale duplicates and uninitialised coordinates reach TetGen)

> [!bug] Synopsis
> After each FEM step `update_sources()` moves the mesher's surface points
> through the new mesh and is meant to delete the points whose image is
> invalid (outside the mesh, or in an element with inverted orientation).
> It calls `std::remove_if( points.begin(), points.end(), InvalidPointFilter() )`
> on a `std::list` and ignores the returned iterator, so nothing is erased:
> the list keeps its size, valid points are shifted forward over the invalid
> ones, and the tail keeps stale copies. Any invalid point among the last
> positions stays in the list with **uninitialised coordinates** (a default-constructed
> `TCoords` leaves its data unset) and the list is passed unfiltered to the
> next step's TetGen call. Reachable only when the mesher receives surface
> points, i.e. with `-use_pial_for_surf` (the default list is empty, see [[00197]]).

## Affected Artefacts

- **Tool(s):** [[surf2vol]]
- **Pipeline stage(s):** _N/A_ — [[mri_cvs_register]] never passes
  `-use_pial_for_surf`, so the list is empty and the function is a no-op there

  ([`fem_elastic/fsurf2vol.cpp:38`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L38)
  defines it as 1).

## Detailed Description

`main` creates one mesh per FEM step with `DelaunayMesh dmesh(srcPoints, ...)`,
a list of points that TetGen must respect. After solving the step it calls
`update_sources( srcPoints, pmesh )`
([`fem_elastic/fsurf2vol.cpp:515`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L515))
so that the next, finer mesh is built on the *displaced* surface. The function
maps every point with `pmesh->dir_img` and then tries to drop the invalid
ones:

```cpp
std::transform( points.begin(), points.end(), points.begin(), PointMorphWithMesh(pmesh) );
std::remove_if( points.begin(), points.end(), InvalidPointFilter() );
```

`TMesh::dir_img` returns a default-constructed `tCoords` whose status is set
to `cOutOfBounds` (no element at the point) or `cInvalid` (the element has an
orientation problem)
([`fem_elastic/mesh.h:1239-1255`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/mesh.h#L1239-L1255));
its coordinate array is **not initialised** by the default constructor
([`fem_elastic/coords.h:167-172`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/coords.h#L167-L172)).
Invalid points therefore have status != `cValid` and arbitrary coordinates.

`std::remove_if` does not erase: it moves the elements that do not satisfy the
predicate to the front and returns the new logical end. The result is thrown
away, so the container keeps its original length. Verified with a stand-alone
test against the real `coords.h` (list of six `TCoords`, elements 1 and 3
invalid, same call): the list afterwards has size 6 and contents
`0 2 4 5 | 4 5` — the invalid elements are gone from the front, but the tail
holds stale copies of the last valid elements. In general the last *k* positions
(k = number of invalid points) keep their old values: duplicates of valid
points, **or an invalid point with garbage coordinates if one was among them**.
The next `DelaunayMesh` writes the whole list into TetGen's point list without
any validity test
([`fem_elastic/fem_3d.cpp:804-810`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fem_3d.cpp#L804-L810)).

The update runs at
[`:515`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L515),
*before* the orientation check and the untangling
([`:519-566`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L519-L566)),
so points lying in the elements that the untangler is about to repair are
exactly the ones that come back invalid.

### Expected Behaviour

Points with an invalid image are removed from the list (the function name,
the filter class and the `remove_if` call all express that intent), so the next
mesh is built from valid points only.

### Observed Behaviour

Experiment with the installed 8.2.0 `surf2vol` on `cvs_avg35`: fixed =
`lh.white`, moving = `lh.white` rigidly translated by +3 mm in x, identity
cached affine, `-fem_steps 2 -fem_end_step 0 -elt_vol 10 -penalty_weight 1000
-topology_old -compress -pc_type jacobi -ksp_type preonly -use_pial_for_surf
-surf_subsample 1`:

- Step 2: `srcPoints size = 9101`, TetGen `Input points: 9109` (8 box corners +
  9101), then `orientation_pbs` / `solving topology problems`.
- Step 1: TetGen again reports `Input points: 9109` — the list did not shrink —
  and prints `Warning:  Point 9109 is identical with point 9108.` The two
  *last* points of the input are identical. That is the signature of exactly
  one invalid point shifted out of the sequence by `remove_if`, leaving the
  final element duplicated in the tail (the stand-alone test above shows the
  same pattern). It does not occur in step 2.

Here the leaked element was a harmless duplicate that TetGen merged. With
an invalid point in the last positions of the list (surface vertex order is
fixed, so which ones are last is data dependent) the mesher would receive
uninitialised coordinates; that case was not reproduced, and what TetGen does
with such input (ignore, abort, or produce a distorted mesh) was not tested.

## Root Cause

`std::remove_if` is a non-member algorithm: it reorders the range and returns
the new end iterator, and the container must be shrunk with
`container.erase(newEnd, container.end())` (or the member
`std::list::remove_if` used). The call discards the return value, so the
list is never shortened, and `DelaunayMesh` (which stores a reference to the
list and has no validity filter) consumes it in full.

## Impact

- **Gated:** dormant in the default [[mri_cvs_register]] path because the list
  is empty ([[00197]]); becomes live as soon as `-use_pial_for_surf` is used,
  or when [[00197]] is fixed.
- **Observed effect:** a duplicated vertex in the TetGen input (one warning);
  harmless in the experiment.
- **Possible effect, not reproduced:** uninitialised coordinates in the TetGen
  input if an invalid point sits in the last positions of the list; the
  resulting mesh (and therefore the deformation) could be distorted, or
  TetGen could fail. Invalid points are also silently kept in the
  surface-point list for all later steps, and a point that went invalid is
  never re-validated because its coordinates were overwritten by the
  `std::transform`.
- **Severity 3 (and not 2):** the defect is flag-gated (matches the schema's
  3), and the downstream effect of garbage coordinates on TetGen is
  unbounded. The experiment's observed consequence on its own
  (a merged duplicate) would argue for 2; the score of 3 reflects that the
  garbage-coordinate path exists and was not excluded.
- **Interaction:** `dir_img` invalidates points in inverted elements regardless
  of its `signalTopology` argument ([[00224]]), which is what makes invalid
  images common right after a step that produced folds.

## Recommended Fix

```diff
 static
 void
 update_sources(PointsListType& points,
                const CMesh3d* pmesh)
 {
   std::transform( points.begin(), points.end(),
                   points.begin(), PointMorphWithMesh(pmesh) );
-  std::remove_if( points.begin(), points.end(), InvalidPointFilter() );
+  points.remove_if( InvalidPointFilter() );
 }
```

`PointsListType` is a `std::list`, so the member `remove_if` erases the
matching nodes. A test should build a list with some invalid points and assert
`size()` shrinks accordingly. A further improvement is to keep a point at its
previous position instead of dropping it when its image is invalid (and to
call `update_sources` after the topology repair at `:519-566`), so that the
surface keeps its mesh vertices; the existing code expresses the intent to
drop invalid points, so the minimal fix above follows it.

## Workarounds (If Any)

Do not use `-use_pial_for_surf` (the default). Without it the point list is
empty and the function does nothing.
