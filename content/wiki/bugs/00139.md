# [severity-3] [bug-00139] `MRIparameterMapsToFlash` writes FLASH values via the `short`-only `MRISseq_vox` macro into a destination whose type was copied from `mri_src` — silently corrupts `MRI_FLOAT` inputs used by FLASH atlas training

> [!bug] Synopsis
> ```cpp
> /* utils/flash.cpp:90-115 */
> MRI *MRIparameterMapsToFlash(MRI *mri_src, MRI *mri_dst,
>                              double *TRs, double *TEs, double *FAs, int nflash)
> {
>   int x, y, z, n;
>   double T1, PD;
>   double val;
>
>   if (!mri_dst)
>     mri_dst = MRIallocSequence(mri_src->width, mri_src->height, mri_src->depth,
>                                mri_src->type,                /* :96 — inherits src type */
>                                nflash);
>
>   for (x = 0; x < mri_src->width; x++) {
>     for (y = 0; y < mri_src->height; y++) {
>       for (z = 0; z < mri_src->depth; z++) {
>         MRIsampleVolumeFrame(mri_src, x, y, z, 0, &val);  T1 = val;
>         MRIsampleVolumeFrame(mri_src, x, y, z, 1, &val);  PD = val;
>
>         for (n = 0; n < nflash; n++) {
>           val = FLASHforwardModel(T1, PD, TRs[n], FAs[n], TEs[n]);
>           MRISseq_vox(mri_dst, x, y, z, n) = (short)nint(val);   /* :108 — bug */
>         }
>       }
>     }
>   }
>   return (mri_dst);
> }
> ```
>
> `MRISseq_vox` is defined at [`include/mri.h:1485-1486`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/include/mri.h#L1485-L1486) as
> ```c
> #define MRISseq_vox(mri,x,y,z,n)  (((short*)mri->slices[z+(n)*mri->depth][y])[x])
> ```
> — i.e., it casts the row pointer to `short *` and writes `short` at index `x`. The macro is correct only when `mri->type == MRI_SHORT`.
>
> For the typical FLASH-atlas-training input, T1 and PD are produced by `mri_ms_fitparms` as `MRI_FLOAT` ([`mri_ms_fitparms.cpp:616-617`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_ms_fitparms/mri_ms_fitparms.cpp#L616-L617): `mri_T1 = MRIcloneDifferentType(mri_flash[0], MRI_FLOAT); mri_PD = MRIcloneDifferentType(mri_flash[0], MRI_FLOAT);`). So in `mri_ca_train --flash` / `mri_rf_train --flash`, `mri_src->type == MRI_FLOAT`, `MRIallocSequence` allocates `mri_dst` with `MRI_FLOAT`, and the `(short)nint(val)` write goes through a row whose actual storage is `float` (4 bytes per element):
>
> | x | row byte offset for `short` write | what's *supposed* to be there (float) |
> |---|---|---|
> | 0  | 0–1   | low 2 bytes of `float[0]` |
> | 1  | 2–3   | high 2 bytes of `float[0]` |
> | 2  | 4–5   | low 2 bytes of `float[1]` |
> | …  | …     | … |
> | k  | 2k, 2k+1 | overlaps `float[k/2]` |
>
> After writing `width` shorts (the inner loop runs `x = 0..width-1`), the row's **first `2·width` bytes** contain interleaved short data, and the **remaining `2·width` bytes** are untouched (zero from `calloc`). Reading the row back as `width` floats produces nonsensical values for the first `width/2` and zero for the rest — i.e., the FLASH-synthesised intensities the caller relies on are garbage.

## Detailed Description

### The type mismatch

`MRIallocSequence(W, H, D, type, N)` allocates a volume where each row is `W * sizeof(type)` bytes. The `slices[z+f*D][y]` pointer points to the start of that row. The cell at column `x` is at offset `x * sizeof(type)` and spans `sizeof(type)` bytes.

The macro `MRISseq_vox(mri, x, y, z, n)` is defined as `((short*)mri->slices[z+(n)*mri->depth][y])[x]` — it treats the row pointer as if it were a `short[]` and accesses index `x`. The byte offset of that access is `x * sizeof(short) = 2x`.

Three cases:

| `mri->type` | Bytes per element | Macro byte offset for column `x` | Result |
|---|---|---|---|
| `MRI_SHORT` (intended) | 2 | `2x` | Correct — matches the actual element layout. |
| `MRI_FLOAT` | 4 | `2x` | Writes 2 bytes into a 4-byte slot. Slots `0..width/2-1` get half-overwritten (in pairs of `short` writes); slots `width/2..width-1` stay at the `calloc` default of `0.0`. |
| `MRI_UCHAR` | 1 | `2x` | Writes 2 bytes into a 1-byte slot. Slot `x=2k` and `x=2k+1` both straddle byte offset `2k`, and the second-byte of each write overwrites the next element. |

The function unconditionally uses the `MRI_SHORT` layout regardless of `mri_dst->type`.

### Per-row byte-level trace for `MRI_FLOAT`

Consider a row of `W = 256` floats (1024 bytes total). The inner `n` loop writes one short value per `(x, n)` pair, but for a fixed `(y, z)` slice the writes traverse `x = 0..W-1` (the same row for a given `n`). After the inner-loop pass over `x = 0..255` finishes for one slice/frame, the row contains:

```
bytes  0   1   2   3   4   5   6   7  ...  510 511 512 513 ...  1022 1023
       <short[0]><short[1]><short[2]><short[3]>...<short[255]>  <not written>
       \---- float[0] ----/\---- float[1] ----/...\---- float[127.5]    \-- float[128..255] untouched (0.0)
```

So `float[0]` in the destination volume has its low 16 bits from `short[0]` and its high 16 bits from `short[1]` — interpreted as a 32-bit IEEE-754 float, the bit pattern is essentially noise. `float[1]`'s 4 bytes come from `short[2]`+`short[3]`, again noise. After `x = 127`, the floats `float[128..255]` are untouched and read back as `0.0` (from `MRIallocSequence` → `calloc`).

The downstream GCA training (`mri_ca_train`) then reads these floats expecting valid FLASH intensities and uses them in per-label Gaussian intensity priors — silently building the atlas on garbage data.

### Why the explicit `(short)nint(val)` cast hides the intent

Looking at the function in isolation, the `(short)nint(val)` cast at `:108` strongly suggests the author *intended* `mri_dst` to be `MRI_SHORT`. The defect is that the allocation at `:96` inherits `mri_src->type` instead of forcing `MRI_SHORT`, and the macro choice at `:108` never noticed the inconsistency. Either:

- The allocation was supposed to be `MRIallocSequence(..., MRI_SHORT, nflash);` (with the `(short)` cast being the explicit narrowing), or
- The macro was supposed to be `MRIsetVoxVal(mri_dst, x, y, z, n, val);` (so the destination type would be honoured).

The two callers (`mri_ca_train`, `mri_rf_train`) pass canonical `MRI_FLOAT` parameter maps from `mri_ms_fitparms`, so both paths exercise the bug.

### Why this is severity 3

- **Triggered by a documented training flag** (`mri_ca_train -map_to_flash`, `mri_rf_train -map_to_flash`).
- **Silent garbage output.** No crash, no warning, no diagnostic — the downstream GCA build proceeds with corrupted intensities and produces a `.gca` / `.rfa` file that is bit-for-bit "valid" but trained on noise.
- **Not on default `recon-all`.** End-users running stock `recon-all` against pre-built FreeSurfer atlases are unaffected, because the bug only fires *during atlas training*, not during atlas application.
- **Affects atlas-distribution workflows.** FreeSurfer developers (and outside groups) who build custom multi-spectral GCAs/RFAs from FLASH-derived T1/PD maps are exposed; the resulting atlas would silently mis-segment subcortical structures based on intensity priors derived from noise.
- **Below severity 4** because the bug is in opt-in training paths rather than the end-user-facing segmentation step.

## Root Cause

The allocation site at `:96` and the write site at `:108` were written under inconsistent assumptions:

- **`:96`** expected the destination to mirror the source's storage type (consistent with the FreeSurfer convention of "auto-allocate dst matching src if NULL").
- **`:108`** expected the destination to be `MRI_SHORT` (consistent with the explicit `(short)nint(val)` cast and the `MRISseq_vox` macro name).

Neither assumption is honoured by the other line. The bug surfaces only when the source's type happens not to be `MRI_SHORT` — which is the case for the only two production callers (both pass `MRI_FLOAT`).

The original FLASH paper, the `MRIparameterMapsToFlash` docstring at `utils/flash.cpp:67-71` (and the surrounding `mri_ms_fitparms` comments), and the GCA training pipeline as a whole conceptually treat FLASH intensities as 16-bit short values (anatomical MR intensity range), so the `MRISseq_vox` and `(short)` choices look intentional. Forgetting to force the allocation to `MRI_SHORT` is the bug.

## Impact

- **`mri_ca_train --flash` and `mri_rf_train --flash` workflows** training new GCA/RFA atlases from FLASH-derived T1/PD parameter maps: the per-vertex/per-voxel FLASH intensity samples that drive intensity-likelihood training are garbage. The resulting atlas's intensity Gaussians (means and covariances per anatomical label) are estimated from noise instead of actual FLASH intensities. Subsequent `mri_ca_label` / `mri_rf_label` calls against such an atlas will mis-segment subcortical structures wherever the atlas's intensity prior would otherwise have informed boundary placement.
- **`mri_ca_train` / `mri_rf_train` without `-map_to_flash`:** unaffected (the buggy function is gated behind the flag).
- **`recon-all` against the pre-built FreeSurfer atlases:** unaffected — the bug fires during atlas *training*, not during atlas *application*. Existing distributed atlases (which were either built before the bug was introduced, or built with `MRI_SHORT` inputs that happen to dodge the bug) are still usable.
- **Severity 3** — silent corruption of opt-in atlas-training output; downstream segmentation on those atlases would be wrong but the bug is not on any end-user-facing pipeline.

## Recommended Fix

Two equivalent fixes, choose one:

**Option A — make the destination match the macro's assumption:**

```diff
--- a/utils/flash.cpp
+++ b/utils/flash.cpp
@@ -93,7 +93,7 @@ MRI *MRIparameterMapsToFlash(MRI *mri_src, MRI *mri_dst, double *TRs, double *TEs, double *FAs, int nflash)
   double T1, PD;
   double val;

-  if (!mri_dst) mri_dst = MRIallocSequence(mri_src->width, mri_src->height, mri_src->depth, mri_src->type, nflash);
+  if (!mri_dst) mri_dst = MRIallocSequence(mri_src->width, mri_src->height, mri_src->depth, MRI_SHORT, nflash);

   for (x = 0; x < mri_src->width; x++) {
     for (y = 0; y < mri_src->height; y++) {
```

**Option B — make the write respect the destination's actual type:**

```diff
@@ -105,7 +105,7 @@ MRI *MRIparameterMapsToFlash(MRI *mri_src, MRI *mri_dst, double *TRs, double *TEs, double *FAs, int nflash)
         for (n = 0; n < nflash; n++) {
           val = FLASHforwardModel(T1, PD, TRs[n], FAs[n], TEs[n]);
-          MRISseq_vox(mri_dst, x, y, z, n) = (short)nint(val);
+          MRIsetVoxVal(mri_dst, x, y, z, n, val);

```

Option B is more permissive (the destination can be any numeric type) and avoids the `(short)nint(...)` truncation; Option A is closer to the apparent original intent and preserves the FLASH-as-short convention used elsewhere in `gca.cpp` (e.g., [`gca.cpp:11326`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/gca.cpp#L11326), [`:13436`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/gca.cpp#L13436)). Option A is the safer minimal fix.

## Workarounds

Until the function is fixed, anyone training FLASH-based GCA/RFA atlases should pre-convert the T1/PD parameter maps to `MRI_SHORT` before invoking `mri_ca_train --flash` / `mri_rf_train --flash`:

```sh
mri_convert --in_orientation LIA --no_scale 1 --odt short T1.float.mgz T1.short.mgz
mri_convert --in_orientation LIA --no_scale 1 --odt short PD.float.mgz PD.short.mgz
# Then pass these short volumes to mri_ca_train -map_to_flash ...
```

With `MRI_SHORT` inputs, `MRIparameterMapsToFlash` allocates `mri_dst` as `MRI_SHORT` and the `MRISseq_vox` write matches the actual storage layout — the bug is silently bypassed.
