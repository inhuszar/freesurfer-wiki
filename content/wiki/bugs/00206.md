# [severity-3] [bug-00206] fem_elastic — CMesh3d copy constructor shallow-copies the octree: double free in FemTransform3d::invert (applyMorph point_list / tract_point_list on a FEM-mesh morph)

> [!bug] Synopsis
> `CMesh3d`'s copy constructor builds its octree with `new OctreeType( *cmesh.m_poctree )`, but `toct::Octree` has a user-written destructor
> (`delete m_pnode;`) and no copy constructor, so the implicit copy shares the root node. `FemTransform3d::invert()` copies the mesh,
> calls `build_index_src()` on the copy (which deletes the shared root), and then drops the original mesh, whose destructor deletes the same
> root a second time. [[applyMorph]] hits this for every `point_list` / `tract_point_list` item when the morph contains a FEM-mesh
> transform (an uncompressed [[surf2vol]] result, or a [[createMorph]] `mesh` input). A standalone harness built from the unmodified
> sources dies with SIGSEGV (exit 139). The copy constructor also leaves `m_poctree` uninitialised when the source mesh has no octree.

## Affected Artefacts

- **Tool(s):** [[applyMorph]] (trigger), [[surf2vol]] and [[createMorph]] (produce the morph types that trigger it)
- **Pipeline stage(s):** _N/A_ — not on the [[mri_cvs_register]] path (that script passes `-compress`, so its morph contains delta-field, not mesh, transforms)
- **FreeSurfer version(s):** confirmed in `8.2.0`; present since the 2008-03-14 import (commit `4b881dc775`)
- **Platforms:** all (undefined behaviour; glibc usually aborts or segfaults)
- **Triggering configuration:** `applyMorph` with a `.tm3d` that contains a `FemTransform3d` and at least one `point_list` or
  `tract_point_list` data item. A FEM-mesh `.tm3d` comes from `surf2vol` **without** `-compress`, or from `createMorph` with a `mesh` input.

## Detailed Description

`FemTransform3d::invert()` needs an inverted copy of the FEM mesh, so it copies it through the `CMesh3d` copy constructor, inverts the copy's nodes,
rebuilds the spatial index and swaps the copy in as `m_sharedMesh`:

```cpp
void
FemTransform3d::invert()
{
  if ( m_pInitial )
    throw " FemTransform3d invert - non null initial";

  //std::cout << "FemTransform3d: invert" << std::endl;

  // ugly, but how else?
  std::shared_ptr<CMesh3d>
  pmesh( new CMesh3d(*dynamic_cast<CMesh3d*>(&*m_sharedMesh) ));
  pmesh->invert();
  pmesh->build_index_src();

  m_sharedMesh = pmesh;

}
```

The spatial index is a `toct::Octree<ElementProxy,3>` owned through a raw pointer. `CMesh3d`'s copy constructor ("Code Reference" below) "copies" it with the
octree's implicit copy constructor, which copies the `m_pnode` pointer member and nothing else, while `Octree` frees its root node in its destructor and declares no
copy operations (rule of three).

The sequence in `FemTransform3d::invert()` is therefore:

1. `new CMesh3d(*orig)` — `copy->m_poctree` is a distinct `Octree` object whose `m_pnode` is **the same root** as `orig->m_poctree->m_pnode`.
2. `pmesh->build_index_src()` — executes `delete m_poctree` on the copy ([`fem_elastic/fem_3d.cpp:653`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fem_3d.cpp#L653)),
   i.e. `~Octree` runs and `delete m_pnode` frees the whole shared tree.
3. `m_sharedMesh = pmesh` — the original mesh loses its last `shared_ptr` owner; `~CMesh3d` runs `delete m_poctree` on the original `Octree`,
   whose `~Octree` calls `delete m_pnode` on the already-freed root. This is the double free (a virtual destructor call on freed memory).

Two secondary defects in the same constructor:

- `m_poctree` is not in the member-initialiser list; when the source mesh has no octree (`cmesh.m_poctree == NULL`) the copy's `m_poctree` is left
  **uninitialised**, and both `build_index_src()` and `~CMesh3d` then `delete` an indeterminate pointer. (Not reachable from `applyMorph`, which
  builds the octree first via `initOctree`, but reachable for any other copy of an un-indexed mesh.)
- The shared tree's leaves hold `const ElementProxy*` that point into the **source** mesh's `m_vpEltBlock`, which the copy constructor does not copy
  (the copy's own `m_vpEltBlock` stays empty). Until `build_index_src()` is called on the copy, every lookup through the copied octree would return
  proxies owned by the source mesh.

### Expected Behaviour

Copying a `CMesh3d` yields an independent mesh. Inverting a FEM transform in `applyMorph` produces the inverse mesh, after which the `point_list`
filter maps its points and writes the output file.

### Observed Behaviour

The first `point_list` / `tract_point_list` item applied to a morph that contains a FEM-mesh transform corrupts the heap (double free of the octree
root) and the process is expected to abort or segfault at the point where the original mesh is released. The failure is loud (crash) but occurs
before the point list is written.

### Reproducer

> [!gap] End-to-end `applyMorph` run not performed
> The crash was demonstrated with two harnesses built from the unmodified sources, not with an installed `applyMorph` on a real FEM `.tm3d`.
> Producing such a file requires an uncompressed `surf2vol` run (large, slow), which was out of scope.

Harness 1 (octree only). A small program including the unmodified `fem_elastic/toctree.hpp` and `fem_elastic/coords.h` inserts 20,000 random boxes into an
`Octree<Box,3>` (box type derived from `TCubicRegion<3>`), checks 200,000 random point lookups against brute force (0 mismatches), then performs exactly the
three steps above: `O* copy = new O(*o); delete copy; delete o;`. Result: SIGSEGV, exit status 139. Run with `MALLOC_CHECK_=3` the process aborts with
`free(): invalid pointer`.

Harness 2 (real `CMesh3d`). A program compiled against the unmodified `fem_elastic/fem_3d.cpp`, `small_matrix.cpp` and the bundled tetgen sources builds a
`DelaunayMesh` from 300 random points in a 100³ box (6,896 nodes, 37,545 tetrahedra), calls `pm->build_index_src()`, then
`CMesh3d* cp = new CMesh3d(*pm); cp->build_index_src(); delete cp;` followed by `delete pm;` — the same sequence as `FemTransform3d::invert()` minus the
node inversion. Result: SIGSEGV, exit status 139, with and without `MALLOC_CHECK_=3`.

```bash
# Intended end-to-end reproducer (NOT run): a FEM-mesh morph + a point list
surf2vol <usual surface/volume options, but WITHOUT -compress> -out_mesh fem   # writes fem.tm3d
applyMorph --template fixed.mgz --transform fem.tm3d \
           point_list pts.txt pts_out.txt unused
```

## Root Cause

Violation of the rule of three in `toct::Octree`: it owns a raw `NodeType* m_pnode`, deletes it in its destructor, and is nevertheless copyable. `CMesh3d`'s copy
constructor then relies on that implicit copy. The same constructor also forgets to initialise `m_poctree` and ignores that the octree indexes
`ElementProxy` objects stored in the source mesh. The only in-tree caller of the copy constructor in compiled code is `FemTransform3d::invert()`
(the other, in `fsurf2vol.cpp`, sits inside the `USE_SURF_FORWARD_MORPH` block that is not compiled by default).

## Impact

- **Crash, not silent corruption:** `applyMorph` with a `point_list` / `tract_point_list` item on a FEM-mesh morph is expected to crash (heap corruption /
  SIGSEGV / glibc abort) at the first such item. No output is written for that item.
- **Gated by flags and input type:** the default [[mri_cvs_register]] path produces delta-field morphs (`-compress`), so it is unaffected. Delta-field morphs
  take a different `invert()` ([[00213]] documents a separate problem there), which is why there is no simple "convert first" workaround.
- **Severity 3 (medium):** crash gated behind a specific item type *and* a specific morph content, off the default pipeline path. Not 2, because the
  crash is deterministic once both conditions hold.
- **Not yet observable (secondary issue):** once the double free is fixed, `FemTransform3d::invert()` will go on to use a mesh whose bounding box is stale:
  `TMesh::invert()` ([`fem_elastic/mesh.h:1328-1346`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/mesh.h#L1328-L1346)) returns a bounding box that is initialised to `cmin = 10`, `cmax = -10` and that
  `FemTransform3d::invert()` discards, and neither `m_cmin` nor `m_cmax` of the copy is updated (they come from `clone()`, [`fem_elastic/mesh.h:558-559`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/mesh.h#L558-L559)),
  so `build_index_src()` sizes the octree root from the forward mesh's box.

> [!gap] Inverted-mesh bounding box
> Whether the stale `m_cmin` / `m_cmax` make `element_at_point()` on the inverted mesh miss points that lie outside the forward mesh's box is not
> established. It can only be tested after the double free is repaired.

## Recommended Fix

Make the copy independent of the source's octree (callers already rebuild the index with `build_index_src()`), initialise the pointer, and make the octree
non-copyable so the mistake cannot recur:

```diff
--- a/fem_elastic/fem_3d.cpp
+++ b/fem_elastic/fem_3d.cpp
 CMesh3d::CMesh3d(const CMesh3d& cmesh)
-    : TMesh3d(cmesh), m_maxNodes(cmesh.m_maxNodes)
+    : TMesh3d(cmesh), m_maxNodes(cmesh.m_maxNodes), m_poctree(NULL)
 {
-  if ( cmesh.m_poctree )
-  {
-    m_poctree = new OctreeType( *cmesh.m_poctree );
-  }
+  // The octree indexes ElementProxy objects that live in the source mesh and
+  // cannot be shared; the copy starts without an index (call build_index_src()).
 }
--- a/fem_elastic/toctree.hpp
+++ b/fem_elastic/toctree.hpp
   ~Octree()
   {
     delete m_pnode;
   }
+
+  Octree(const Octree&) = delete;
+  Octree& operator=(const Octree&) = delete;
```

`CMesh3d::operator=` is declared at [`fem_elastic/fem_3d.h:162`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fem_3d.h#L162) but not defined anywhere in the tree; define it consistently
(free the octree, copy through `TMesh3d::operator=`, reset `m_poctree`) or declare it deleted. A regression test is the harness above: copy, `build_index_src()` on
the copy, destroy original and copy — run under valgrind or ASan.

### Alternative Fixes Considered

Deep-copy the octree by rebuilding it inside the copy constructor (`if (cmesh.m_poctree) build_index_src();`). Correct, but `FemTransform3d::invert()` rebuilds immediately
afterwards, so the index would be built twice (slow on large meshes).

## Workarounds (If Any)

Avoid `point_list` / `tract_point_list` items with morphs that contain a FEM mesh. Other `applyMorph` item types do not call `VolumeMorph::invert()` (its only call
site is [`fem_elastic/fapplyMorph.cpp:682`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fapplyMorph.cpp#L682)). Compressing the morph (`surf2vol -compress`) avoids this bug but leads to the delta-field inversion problem in [[00213]].
