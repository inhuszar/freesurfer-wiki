# [severity-2] [bug-00061] `label.cpp` (and FreeView) — `lv->vno <= mris->nvertices` defensive check off by one

> [!bug] Synopsis
> Four sites in
> `utils/label.cpp` and one in `freeview/SurfaceLabel.cpp`
> use the same defensive idiom:
>
> ```cpp
> if (lv->vno >= 0 && lv->vno <= mris->nvertices) {
>   continue;     /* "vertex already assigned" */
> }
> ```
>
> The valid index range for `mris->vertices[]` is
> `0..nvertices-1`. The inclusive `<=` accepts
> `vno == nvertices` — one past the end. The
> consequence is benign in the immediate scope (the
> `continue` skips the entry), but the entry's
> `vno = nvertices` then propagates back to the LABEL
> struct unchanged. Any downstream code that
> dereferences `mris->vertices[lv->vno]` (without its
> own bounds check) reads OOB. The defect is also a
> symptom: an `lv->vno == nvertices` is not actually
> "assigned"; it is invalid sentinel data that the
> defensive check is silently rubber-stamping.

## Detailed Description

The five occurrences share the same shape:

```cpp
for (n = 0; n < area->n_points; n++) {
  lv = &area->lv[n];
  if (lv->vno >= 0 && lv->vno <= mris->nvertices) {       /* (!) <=  */
    continue;     /* vertex already assigned */
  }
  /* ... resolve lv->vno from coordinates ... */
}
```

The `continue` is correct *intent*: skip entries
whose `vno` already maps to a valid vertex. But the
range `0 <= vno <= nvertices` includes `nvertices`,
which is **not** a valid vertex index. With this
defective check:

- An `lv` with `vno = nvertices` (e.g., a sentinel for
  "unresolved" left over from a previous partial
  resolve) is treated as already-assigned and not
  re-resolved.
- The label is written / used downstream with
  `lv->vno = nvertices`. Any subsequent
  `mris->vertices[lv->vno]` dereference (e.g.,
  rendering, label-on-surface overlays, distance
  computations) reads one past the end of the vertex
  array.

Operationally, the most likely effect is reading the
adjacent allocation's first byte. On a typical
allocator that's allocator-padding zeros — silent. On
hardened systems it triggers a guard-page fault.

## Root Cause

`<=` is the natural form of "less than or equal to
size", but for indexing it should be `<`. The same
single-character mistake repeated across four sites
(plus a FreeView mirror) suggests copy-paste of an
incorrect template.

## Impact

- **Latent.** The defect only fires for entries with
  `vno == nvertices`, which is a sentinel value some
  upstream code may produce. In the common case,
  inputs have valid `vno` values or `vno < 0`
  (sentinel for "unresolved"); the bug is harmless.
- **When it fires:** the label entry is treated as
  already-assigned and propagates downstream. If the
  downstream code dereferences `mris->vertices[vno]`
  without its own bounds check, OOB read.

## Recommended Fix

Apply the same diff to all four sites:

```diff
-  if (lv->vno >= 0 && lv->vno <= mris->nvertices) {
+  if (lv->vno >= 0 && lv->vno <  mris->nvertices) {
```

A defensive sweep across `utils/label.cpp` and the
FreeView equivalent is recommended, since the same
pattern may exist in additional places (the agent
audit caught four `<=` sites; a `<` version is the
correct form everywhere).
