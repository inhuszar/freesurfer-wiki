# [severity-2] [bug-00109] `tukey_biweight` uses integer `abs()` on a `double` residual — sub-unit band above the cap is misclassified as inlier

> [!bug] Synopsis
> ```cpp
> /* utils/tukey.cpp:21-32 */
> double tukey_biweight(double residual, double C)
> {
>   if (abs(residual) > C) {                 /* :23 — abs(int) on a double */
>     return (C * C / 2);
>   } else {
>     double p = residual / C;
>     p *= p;
>     p = 1 - p;
>     p = p * p * p;
>     return (((C * C) / 2) * (1 - p));
>   }
> }
> ```
> The standard library has two `abs`-family
> functions:
> `int abs(int)` from `<stdlib.h>` (included
> at `:15`) and `double fabs(double)` from
> `<math.h>`. The expression `abs(residual)`
> resolves to the integer overload because
> `<cstdlib>`'s `abs(int)` is what the
> C-style include surfaces — silently
> truncating `residual` toward zero before
> the comparison.
>
> Concretely:
>
> | `residual` | `(int)residual` | `abs((int)residual)` | `> C = 4.685`? |
> |------------|-----------------|----------------------|----------------|
> | 4.5        | 4               | 4                    | no  ← correct  |
> | 4.7        | 4               | 4                    | no  ← **wrong** (true \|r\| > C) |
> | 4.99       | 4               | 4                    | no  ← **wrong** |
> | 5.0        | 5               | 5                    | yes ← correct  |
> | 6.3        | 6               | 6                    | yes ← correct  |
>
> So any residual whose magnitude lies in
> the half-open band `[C, ceil(C))` falls
> into the `else` branch and gets the
> polynomial loss instead of the saturated
> cap `C² / 2`.

- **FreeSurfer version(s):** confirmed in

## Detailed Description

### What `tukey_biweight` is supposed to compute

The Tukey biweight loss
`ρ(r; C)` is

- `(C²/2) · (1 - (1 - (r/C)²)³)` for
  `|r| ≤ C` (a smoothly increasing
  bowl)
- `C²/2`                            for
  `|r| > C` (a saturated cap)

The intent: large residuals saturate so
they don't dominate the fit (robust
regression).

### What the code actually computes

Because `abs(double)` resolves to
`int abs(int)` from `<stdlib.h>`, the
comparison silently truncates the
fractional part of `residual` toward
zero before testing against `C`.

Let `n = floor(|r|)` for `r ≥ 0` (or
`-floor(-r)` for `r < 0`). The condition
`abs((int)r) > C` is equivalent to
`n > C`, which is true only when
`|r| ≥ ceil(C) + (some tolerance for
the half-open boundary)`.

The mis-classification window:

- Outliers in `[C, ceil(C))` are routed
  through the else-branch.
- The else-branch evaluates
  `(C²/2) · (1 - (1 - (r/C)²)³)`.
- At `|r| = C` exactly, `(r/C)² = 1`,
  `p = 0`, result = `C²/2` — correct
  (smooth boundary).
- For `|r|` slightly above `C`,
  `(r/C)² > 1` so `1 - (r/C)² < 0`. Cubing
  preserves the sign, and
  `1 - (1 - (r/C)²)³ = 1 + ε³ > 1`.
- Therefore the polynomial overshoots:
  the loss is slightly **above** `C²/2`
  in the misclassification band.

### Numerical impact

For a typical Tukey biweight tuning of
`C = 4.685` (the conventional value for
95% Gaussian efficiency), the
misclassification band is
`[4.685, 5.0)` — width 0.315.
For `r = 4.99`, `(r/C)² ≈ 1.134`,
`(1 - 1.134)³ ≈ -0.0024`,
loss ≈ `(C²/2) · 1.0024` — about 0.24%
above the cap.

For `mri_ms_fitparms`, `tukey_thresh` is
computed dynamically as
`total_error / nvalues`
([`mri_ms_fitparms.cpp:2505`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_ms_fitparms/mri_ms_fitparms.cpp#L2505))
where `total_error` is the sum of
absolute differences. If the resulting
`C` happens to be 50 (a typical mid-pass
intensity-difference scale), the
misclassification band is `[50, 51)` of
width 1.0 — and any voxel pair whose
residual falls in that band gets a slight
loss inflation rather than the saturated
cap.

### Why the bug went undetected

The misclassification window has
sub-unit width relative to the cap, so
the SSE error introduced is small —
typically much less than 1% of the total.
This perturbs the optimization landscape
enough to slow convergence in pathological
cases, but doesn't change the qualitative
fit.

## Root Cause

`<stdlib.h>` provides `int abs(int)`. C++
also exposes `std::abs` overloads via
`<cstdlib>` and `<cmath>`, but a call to
the unqualified `abs(double)` from the C
include resolves to the integer overload
— the double argument is implicitly
truncated.

The author probably wrote `abs` as a
shorthand for "absolute value", not
appreciating that without `<cmath>` (or
without `using std::abs`) the only
in-scope `abs` is the integer one.

A modern C++ compiler with `-Wconversion`
or `-Wnarrowing` would catch this; the
FreeSurfer build does not enable those
warnings.

## Impact

- **`mri_ms_fitparms --tukey`:** a
  fraction of voxel-pair residuals (those
  in `[C, ceil(C))`) get an inflated loss
  rather than the saturated cap.
  Magnitude of error per residual is small
  (sub-1% of cap); cumulative effect on
  SSE is also small.
- **No effect on default `recon-all`:** Tukey
  is opt-in.
- **Severity:** 2 — flag-gated, narrow
  effect, real correctness bug.

## Recommended Fix

```diff
--- a/utils/tukey.cpp
+++ b/utils/tukey.cpp
@@ -20,7 +20,7 @@
 double tukey_biweight(double residual, double C)
 {
-  if (abs(residual) > C) {
+  if (fabs(residual) > C) {
     return (C * C / 2);
   } else {
     double p = residual / C;
```

`fabs` is the canonical floating-point
absolute-value function from `<math.h>`,
already included at `:16`.

A defensive build-time fix is to enable
`-Wabsolute-value` (gcc/clang) which
warns when `abs` is called on a non-int
argument:

```
warning: using integer absolute value
function 'abs' when argument is of
floating point type [-Wabsolute-value]
```

## Workarounds

For users who need correct Tukey behaviour
under `--tukey` now, the workaround is to
apply the one-character fix and rebuild.
