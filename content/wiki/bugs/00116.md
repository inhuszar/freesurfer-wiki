# [severity-2] [bug-00116] `readBrukerD3proc` reads `$IM_SIT` into `pz` instead of `pnframes`; nframes never set

> [!bug] Synopsis
> ```cpp
> /* utils/Bruker.cpp:309-327 */
> if (!strcmp(Parameter, "$IM_SIX"))      sscanf(Value, "%d", px);
> else if (!strcmp(Parameter, "$IM_SIY")) sscanf(Value, "%d", py);
> else if (!strcmp(Parameter, "$IM_SIZ")) sscanf(Value, "%d", pz);
> else if (!strcmp(Parameter, "$IM_SIT")) {
>   sscanf(Value, "%d", pz);                  /* :319 — bug: should be pnframes */
> }
> else if (!strcmp(Parameter, "$IM_SIT")) {   /* :321 — duplicate key, dead branch */
>   sscanf(Value, "%d", pnframes);
>   if (*pnframes > 1) {
>     fprintf(stderr, "ERROR: nframes %d but one is supported.\n", *pnframes);
>     return 0;
>   }
> }
> ```
>
> Two consecutive `else if` branches
> compare `Parameter` against the same
> string `"$IM_SIT"`. The first match
> always wins, so:
>
> - `$IM_SIT` reaches the first branch
>   and writes the value to `*pz`
>   (depth) — overwriting the depth
>   set by `$IM_SIZ`.
> - The second branch (which would
>   write to `*pnframes` and check
>   `>1`) is unreachable.
>
> Bruker `D3PROC` keys: `IM_SIX/Y/Z`
> are spatial X/Y/Z dimensions, and
> `IM_SIT` is the "T" (time) dimension.
> So the bug puts the **time** count
> into the **depth** slot, and the
> nframes slot stays uninitialised.

## Affected Artefacts

- **Tool:** [[mri_convert]] — when input
  is a Bruker scanner output directory,
  `MRIread` dispatches to `brukerRead`
  ([`utils/mriio.cpp:767`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/mriio.cpp#L767)).
- **Pipeline stage(s):** none in
  default `recon-all`. Bruker is a
  preclinical / animal-MRI format.
- **Triggering configuration:** any
  Bruker dataset with `$IM_SIT` set
  in `pdata/1/d3proc`. Most 3D-only
  anatomical scans don't have
  `$IM_SIT`, so the depth is set
  correctly by `$IM_SIZ` and the
  bug doesn't fire. For 4D dynamic
  / fMRI Bruker datasets, `$IM_SIT`
  is present and overwrites the
  depth.
- **FreeSurfer version(s):**
  confirmed in `$FREESURFER_VERSION`
  (commit `d932c45b79`).

## Detailed Description

### Concrete impact

For a 4D Bruker dataset with
spatial dims `(64, 64, 32)` and
30 time frames:

| key       | value | written to | result          |
|-----------|-------|------------|-----------------|
| $IM_SIX   | 64    | `*px`      | width  = 64 ✓   |
| $IM_SIY   | 64    | `*py`      | height = 64 ✓   |
| $IM_SIZ   | 32    | `*pz`      | depth  = 32 ✓ (initially) |
| $IM_SIT   | 30    | `*pz`      | depth  = 30 ✗ (overwritten!) |
| $IM_SIT   | (n/a) | (dead branch) | nframes = uninitialised |

Caller chain
([`Bruker.cpp:175-182`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/utils/Bruker.cpp#L175-L182)):

```cpp
readBrukerD3proc(d3procFile, &width, &height, &depth, &type, &nframes);
...
mri = MRIalloc(width, height, depth, type);
```

So `MRIalloc(64, 64, 30, type)` is
called instead of
`MRIalloc(64, 64, 32, type)`. The
allocated volume has 30 slices
instead of 32 — the last 2 slices
are missing from the volume.

`nframes` is also wrong (stays at
whatever the caller used to
initialise, often 1 or 0). The
`MRIalloc(..., type)` 4-arg overload
defaults nframes to 1, so the
volume has 1 frame. Reading
30 frames worth of data into a
1-frame volume causes either an
incomplete read or a buffer
overflow (depends on
`readBrukerVolume` semantics).

### Why the bug went undetected

Bruker is preclinical/animal MRI;
most users feed in 3D anatomical
data without `$IM_SIT` defined,
which leaves the bug dormant. The
file's primary in-tree caller is
`mri_convert` only for the rare
case of converting from a Bruker
acquisition.

### The dead second branch

The second `else if` block at
`:321-327`:

```cpp
else if (!strcmp(Parameter, "$IM_SIT")) {
  sscanf(Value, "%d", pnframes);
  if (*pnframes > 1) {
    fprintf(stderr, "ERROR: nframes %d but one is supported.\n", *pnframes);
    return 0;
  }
}
```

Note: this branch checks
`*pnframes > 1` and **errors out**.
So even if the dispatch were
fixed (via reaching this branch),
the function would refuse 4D
Bruker data with the message
"only one frame supported." The
intent appears to be: "store the
nframes count, but the rest of
the reader doesn't handle 4D, so
fail."

The fix should remove the dead
branch entirely and combine its
logic into the first `$IM_SIT`
branch — set `pnframes`, check
the `>1` condition, leave `pz`
alone.

## Root Cause

Copy-paste of the `$IM_SIZ` handler
to a new `$IM_SIT` handler — the
comparison string was updated but
the assignment (`sscanf(Value, "%d",
pz)`) was not. The author then
added a third `$IM_SIT` block to
handle nframes correctly, but
didn't remove the buggy second
block, leaving them both with the
same key.

Reviewer-friendly fix: a single
`$IM_SIT` branch that sets
`pnframes` and emits the
not-supported error if > 1.

## Impact

- **3D anatomical Bruker scans
  (no `$IM_SIT`):** bug dormant,
  data correct.
- **4D dynamic Bruker scans
  (with `$IM_SIT`):** depth
  overwritten with time count,
  nframes unset. MRI volume
  allocated with wrong shape.
- **Severity:** 2 — niche format,
  real correctness bug, primarily
  affects 4D Bruker users (rare).

## Recommended Fix

```diff
--- a/utils/Bruker.cpp
+++ b/utils/Bruker.cpp
@@ -315,11 +315,9 @@ int readBrukerD3proc(char *d3procFile, int *px, int *py, int *pz, int *ptype, in
   else if (!strcmp(Parameter, "$IM_SIZ"))
     sscanf(Value, "%d", pz);
-  else if (!strcmp(Parameter, "$IM_SIT")) {
-    sscanf(Value, "%d", pz);
-  }
   else if (!strcmp(Parameter, "$IM_SIT")) {
     sscanf(Value, "%d", pnframes);
     if (*pnframes > 1) {
       fprintf(stderr, "ERROR: nframes %d but one is supported.\n", *pnframes);
       return 0;
     }
   }
```

Removes the buggy first `$IM_SIT`
branch that overwrites `pz`. The
second branch then becomes
reachable and sets `pnframes`
correctly (with the existing `> 1`
diagnostic).

## Workarounds

For users converting 4D Bruker data:
preconvert outside FreeSurfer (e.g.,
via Bruker's own ParaVision tools
or a third-party Bruker reader) into
NIfTI/MGH first.

- **Discovered:** 2026-05-10 by agent
  (audit of dispatch / parameter-
  parsing patterns).
- **Evidence:**
  - Two consecutive `else if`
    branches at `:318` and `:321`
    compare `Parameter` against
    the identical string
    `"$IM_SIT"`.
  - The first branch's body uses
    `pz` (likely copy-pasted
    from the `$IM_SIZ` handler
    above).
  - The second branch's body uses
    `pnframes` (the intended
    target).
  - C semantics: in an
    if-else-if chain, the first
    matching branch wins; the
    second is unreachable.
  - Bruker docs (per file
    header comments): `IM_SIT`
    = T (time) dimension.
