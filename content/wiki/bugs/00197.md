# [severity-3] [bug-00197] `surf2vol` — `create_surf_container()` skips on `pial || !usePialForSurf`: the mesher receives no surface points by default, `-use_pial_for_surf` never admits a pial surface, and the debug-point code dereferences past the end of the empty list

> [!bug] Synopsis
> `create_surf_container()` collects the fixed-surface vertices that the
> tetrahedral mesher (TetGen) must respect, and its header comment says it "will
> only use the white surface, if available". The skip condition is
> `if ( cit->type == pial || !usePialForSurf ) continue;`. With the default
> `usePialForSurf = false` the second operand is true for **every** surface, so
> the container stays empty (`srcPoints size = 0`) and each FEM mesh is just
> the bounding box plus TetGen volume refinement. With `-use_pial_for_surf`
> only white surfaces pass; a pial surface is never used under either setting
> (the operator should be `&&`). The value of `-surf_subsample` is also ignored
> (the spacing is hard-coded to 3.5), and when the container is empty the
> debug code at the start of the FEM loop advances an iterator 100 times past
> the end of an empty `std::list` and dereferences it (undefined behaviour,
> observed as garbage in a debug printout).

## Affected Artefacts

- **Tool(s):** [[surf2vol]]; [[mri_cvs_register]] (default path, see below)
- **Pipeline stage(s):** [[mri_cvs_register]] step 2 (elastic registration),
  [`mri_cvs_register/mri_cvs_register:389-403`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_cvs_register/mri_cvs_register#L389-L403)
  — the call passes neither `-use_pial_for_surf` nor `-surf_subsample`, so
  every FEM step of every CVS run meshes an empty surface-point list.
  [[mri_cvs_register]] is reached from [[trac-all]] only for the CVS
  inter-subject space ([`scripts/trac-preproc:82-83`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/scripts/trac-preproc#L82-L83))
  and from [[post-recon-all]] only with `--cvs`.
- **FreeSurfer version(s):** confirmed in 8.2.0; unchanged since the 2008-04-18
  import (commit `9761aeb9b6`, `git log -L1022,1023:fem_elastic/fsurf2vol.cpp`
  lists only that commit).
- **Platforms:** all
- **Triggering configuration:** the condition is evaluated on every call. The
  empty container is the default (no `-use_pial_for_surf`); the "pial is never
  used" half needs `-use_pial_for_surf`; the ignored `-surf_subsample` value
  needs `-use_pial_for_surf -surf_subsample <x>`; the iterator misuse needs an
  `initPoints` list of at most 100 points (the default is 0 points).

## Detailed Description

The FEM mesh is built by `DelaunayMesh` from the 8 corners of the box
`[cmin, 256]³` plus the points of the list it is given
([`fem_elastic/fsurf2vol.cpp:490`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L490),
[`fem_elastic/fem_3d.cpp:781-810`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fem_3d.cpp#L781-L810)),
and TetGen is then run with a volume constraint (`pq1.414a<vol>`,
[`fem_elastic/fem_3d.cpp:848-852`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fem_3d.cpp#L848-L852)).
Points supplied by `create_surf_container` become vertices of the mesh, so
the tetrahedra conform to the fixed surfaces. `main` fills the list once
(`initPoints`), copies it into `srcPoints`, and after every step moves the
points through the new mesh (`update_sources`, see [[00198]]) so that the
next, finer mesh follows the deformed surface
([`fem_elastic/fsurf2vol.cpp:430-436`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L430-L436),
[`:515`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L515)).

The declaration documents the intent: "will only use the white surface, if
available", with `usePialForSurf` defaulting to `false`
([`fem_elastic/fsurf2vol.cpp:179-187`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L179-L187)).
The natural reading is: pial surfaces are skipped unless the flag asks for
them, i.e. `type == pial && !usePialForSurf`. The code instead has
`||` ([`fem_elastic/fsurf2vol.cpp:1022-1023`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L1022-L1023)),
so:

| `-use_pial_for_surf` | white surface (`type != pial`) | pial surface |
|---|---|---|
| off (default) | skipped (`!usePialForSurf` true) | skipped |
| on | **used** | skipped (`type == pial` true) |

The default configuration therefore feeds the mesher no surface points at all,
and the flag can never contribute a pial surface.

Secondary defects in the same function and its caller:

1. **`-surf_subsample <value>` is only tested for `> 0`.**
   `MRISsubsampleDist(mris, 3.5f)` hard-codes the spacing
   ([`fem_elastic/fsurf2vol.cpp:1028-1033`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L1028-L1033);
   option parsed at
   [`:1458-1461`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L1458-L1461)).
2. **Undefined behaviour on an empty `initPoints`.** `main` advances
   `initPoints.begin()` by 100 elements and dereferences the result to obtain
   a debug point
   ([`fem_elastic/fsurf2vol.cpp:457-464`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L457-L464)).
   With the default empty list the iterator is incremented past `end()`
   and dereferenced, so `dbgCoords` holds whatever memory follows the list
   header. The value is then used only in diagnostic printouts and
   in `ptransform->img(dbgCoords)`
   ([`:582-598`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fsurf2vol.cpp#L582-L598)),
   so no wrong result was observed, but the code can crash or misbehave with
   other memory contents; the same is true for any list with 1 to 100 points.

### Expected Behaviour

Without `-use_pial_for_surf` the white surface vertices (not flagged by
`-aparc`) are handed to the mesher; with it, the pial vertices are added too.
`-surf_subsample x` thins the surface to a spacing of `x` mm. A debug point is
only taken when the list has more than 100 entries.

### Observed Behaviour

Experiments with the installed 8.2.0 `surf2vol` on the `cvs_avg35`
subject (fixed = moving, identity cached affine):

- **Default (no flag), `lh.white` + `lh.pial`:** the log prints
  `creating container for the mesher` followed by `srcPoints size = 0`, and
  TetGen reports `Input points: 8` (the box corners only) at every step. The
  debug printout shows garbage:
  `dir img for computed transform = 1 1.28062e-320 7.25129e-316` (another run
  of the same command printed `... 6.07352e-316` as the last number, i.e. the
  value is not reproducible, as expected for uninitialised memory).
- **`-use_pial_for_surf`, `lh.white` + `lh.pial`:** `srcPoints size = 139336`.
  That is the vertex count of `lh.white` alone (`lh.pial` has the same count),
  so the pial surface contributed nothing.
- **`-use_pial_for_surf -surf_subsample <x>` (white only):** the log prints
  `create_surf_container - init size = 139336 subsampled = 9101` and
  `srcPoints size = 9101` for `x = 0.5`, `1` and `10` alike.

## Root Cause

The skip condition combines two predicates with the wrong connective. The
intended predicate is "this is a pial surface **and** pial was not requested";
`||` makes it "this is a pial surface **or** pial was not requested", which is
true for everything when the flag is off and for pial surfaces when it is on.
The `3.5f` literal is used instead of the `subsampleDist` argument that the
function receives, and `main` does not guard its `begin() + 100` debug-point
code against short lists. The code is identical to the 2008 import; nothing
in it or in the history indicates why.

## Impact

- **Default `mri_cvs_register` path.** Every FEM step meshes the box with no
  surface-conforming vertices: TetGen only has to satisfy the volume
  constraint (`-elt_vol_range 5.0,10.0`, shrinking over the 17 steps), so the
  tetrahedra are not adapted to the cortical surfaces and the BCs fall in
  arbitrary elements. In the
  `cvs_avg35` runs of the [[00200]] experiment (`-elt_vol 10`) the mesh had
  229 624 nodes and 1 411 467 elements. If the intended behaviour is
  "mesh on the white surface", the registration runs with a coarser
  representation of the cortex than designed. The effect on registration
  quality has not been measured.
- **With `-use_pial_for_surf`:** an option whose name promises pial
  points never delivers them; users who enable it get white-surface points only.
- **`-surf_subsample`:** any positive value gives 3.5 mm spacing
  (9101 of 139336 vertices on `cvs_avg35` `lh.white`).
- **Garbage debug point:** UB in the diagnostic path; no crash observed.
- **Why 3 and not higher:** by *reach* (every CVS run) the bug could be scored
  4–5, but its effect is on mesh quality and resolution, not demonstrably on
  correctness of the output; the "intended" behaviour is inferred from one
  comment (see the gap below); and the surface-free meshes are what the shipped CVS script
  has always produced, so the tuning of `-penalty_weight`/`-young`/`-fem_steps`
  was presumably made against them. Per the schema's tiebreaker the lower score is used.
- **Fixing changes CVS output substantially:** the white surfaces of both
  hemispheres add about 274 000 mesher points (139 336 + 134 980 for
  `cvs_avg35`; fewer if [[00195]] is fixed first), the meshes become much
  larger and the empirically tuned parameters will no longer be valid.
  Enabling the points also activates [[00198]] (the discarded `remove_if`
  result), which is dormant while the list is empty.

## Recommended Fix

```diff
-    if ( cit->type == pial || !usePialForSurf )
+    if ( cit->type == pial && !usePialForSurf )
       continue;
 ...
-      int markedVertices = MRISsubsampleDist(mris, 3.5f);
+      int markedVertices = MRISsubsampleDist(mris, subsampleDist);
```

and, in `main()`, guard the debug point:

```diff
-  tDblCoords dbgCoords, dbgImage;
-  {
-    PointsListType::const_iterator cit = initPoints.begin();
-    for ( unsigned int counter = 0;
-          counter < 100; ++counter) ++cit;
-    dbgCoords = *cit;
-    dbgImage = dbgCoords;
-  }
+  tDblCoords dbgCoords(0.0), dbgImage;
+  if ( initPoints.size() > 100 )
+  {
+    PointsListType::const_iterator cit = initPoints.begin();
+    std::advance( cit, 100 );
+    dbgCoords = *cit;
+  }
+  dbgImage = dbgCoords;
```

The iterator guard is independent of the other changes and safe to apply on
its own (the debug printouts then refer to a fixed dummy point).
The `&&` change must **not** be applied silently: it changes every CVS mesh
(see Impact); apply it behind a validation of the resulting warps and a
re-tuning of the script's parameters, or document that the default is meant
to be surface-free and rename/remove the flag instead.

### Alternative Fixes Considered

- **Make the default explicit instead of changing it:** keep the surface-free
  meshes, change the comment and the option text, and remove the dead
  parameters (`-use_pial_for_surf`, `-surf_subsample`). Preserves all existing
  CVS output; requires a developer decision.
- **Honour the flag literally:** `if ( cit->type == pial && !usePialForSurf )`
  as above, which is the reading supported by the header comment.

## Workarounds (If Any)

For the surface-free behaviour (the default) nothing is needed. To obtain
white-surface points in the mesh pass `-use_pial_for_surf` (white surfaces only
pass the condition; `-surf_subsample <x>` then thins to 3.5 mm whatever `x`).
The garbage debug point has no workaround; it does not affect the result.

## Confidence and Gaps

> [!gap] Intended semantics of `-use_pial_for_surf`
> Whether the authors meant "white by default, white + pial with the flag"
> (the reading adopted here) or "pial only when asked, otherwise nothing" is
> not stated anywhere in the code or in the tool's `-help` text. It is also
> unknown whether the default surface-free mesh was a deliberate simplification:
> the CVS script's tuning comments
> ([`mri_cvs_register/mri_cvs_register:374-387`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_cvs_register/mri_cvs_register#L374-L387))
> were written against whatever the program actually did. The `||` is certain;
> its classification as a defect rests on the header comment.

> [!gap] Effect on registration quality
> No comparison of CVS warps obtained with and without surface points in the
> mesh exists.
