# MRIresample SAMPLE_VOTE — labels > 255 clipped to 255 and vote count overflows UCHAR; aparc label volumes silently collapse

> [!bug] Synopsis
> `MRIresampleFill` in `utils/mri.cpp` implements a
> majority-vote resampling mode (`SAMPLE_VOTE`) that is
> user-exposed as `mri_convert --resample_type vote` and is the
> canonical FreeSurfer idiom for resampling categorical label
> volumes. The implementation allocates a 256-frame `MRI_UCHAR`
> histogram, with one frame per possible label, and votes by
> incrementing the frame indexed by the source voxel's label
> value. Before the increment it applies `if (val < 0) val = 0;
> else if (val > 255) val = 255;`, silently mapping **every**
> label ≥ 256 onto the same frame 255. Standard FreeSurfer
> cortical-parcellation labels live at 1001–1035 / 2001–2035
> (and wmparc labels at 3001+ / 4001+), so voting on an
> `aparc+aseg.mgz` or `wmparc.mgz` collapses every cortical
> parcel to the single label value 255 in the destination —
> a catastrophic silent corruption of label identity. The
> same UCHAR histogram also overflows at 256 votes per
> label-per-destination-voxel, so aggressive downsampling (e.g.
> 1024³ → 128³) additionally wraps the vote counts.

## Affected Artefacts

- **Tool(s):** [[mri_convert]] via `--resample_type vote`
  exposed at
  [`mri_convert/mri_convert.cpp:1174–1176`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_convert/mri_convert.cpp#L1174-L1176).
  Any other tool that links `libutils` and calls
  `MRIresample(…, SAMPLE_VOTE)` directly is affected
  identically.
- **Pipeline stage(s):** _N/A_ for default [[recon-all]].
  recon-all does not invoke `mri_convert --resample_type vote`
  in its standard flow. The defect bites downstream pipelines
  and group-analysis workflows that resample
  `aparc+aseg.mgz` / `wmparc.mgz` with `--resample_type vote`.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit
  `d932c45b79`.
- **Platforms:** all — purely arithmetic.
- **Triggering configuration:** `mri_convert --resample_type
  vote` on any volume that contains label values `>= 256`, or on
  any resampling where the source-to-destination ratio maps
  more than 255 source voxels onto a single destination voxel
  (downsample factor larger than ≈ 6× per axis for an isotropic
  conformed volume). The aparc and wmparc label volumes
  produced by recon-all fall squarely in the first class.

## Detailed Description

The `SAMPLE_VOTE` path iterates over every source voxel,
transforms its coordinate into destination space, and casts
one vote for its intensity value into a histogram:

```cpp
mri_votes = MRIallocSequence(template_vol->width, template_vol->height,
                             template_vol->depth, MRI_UCHAR, 256);
/* ... */
val = nint(MRIgetVoxVal(src, si, sj, sk, nframe));
if (val < 0)
  val = 0;
else if (val > 255)
  val = 255;                                              // ← labels ≥ 256 collapse here
count = MRIgetVoxVal(mri_votes, di, dj, dk, val);
MRIsetVoxVal(mri_votes, di, dj, dk, val, count + 1);     // ← count overflows UCHAR at 256
```

After all source voxels have voted, the destination label is
the argmax across the 256 histogram frames at each
destination voxel.

Two independent capacity problems compound:

1. **Label range.** The histogram has exactly 256 frames and
   uses the source label value directly as the frame index.
   Cortical parcellation labels
   ([[color-lut]]: `ctx-lh-bankssts = 1001`,
   `ctx-lh-insula = 1035`, `ctx-rh-bankssts = 2001`, etc.) are
   outside `[0, 255]`. The explicit clip on line 12179 silently
   maps all of them onto frame 255. Any wmparc label
   (`3001+ / 4001+`) collapses the same way, as do any custom
   labels in the thousands.
2. **Vote count depth.** Each histogram frame is `MRI_UCHAR`.
   The code reads the current count with `MRIgetVoxVal`,
   increments, and writes back with `MRIsetVoxVal`. When `count
   == 255`, the `count + 1 == 256` value saturates (or wraps,
   depending on the voxel-access macro's semantics) on the
   store. Downsampling from a higher-resolution source by a
   factor that maps more than 255 source voxels into one
   destination voxel per label overflows this counter and
   the argmax becomes unreliable.

### Expected Behaviour

The canonical label-resampling semantics of "majority vote"
should preserve label identity for every label in the source
volume, not just labels in `[0, 255]`. A vote bin should hold
the full count of source voxels that landed on the destination
voxel without saturating.

### Observed Behaviour

- Every label value ≥ 256 in the source volume gets silently
  re-labelled to 255 in the destination. For `aparc+aseg.mgz`,
  this turns every cortical parcel (30-plus distinct labels
  per hemisphere) into the single label 255 (`CC_Anterior` in
  the FreeSurfer palette), destroying the parcellation.
  Subcortical labels in `[0, 255]` are preserved.
- On aggressive downsampling, once more than 255 source voxels
  of a given label land on one destination voxel, the UCHAR
  counter saturates; the argmax reports whichever label
  happened to saturate first rather than the true majority.
- Neither the tool's stdout nor its return code carries any
  warning that truncation occurred.

- **Function:** `MRIresampleFill()`
- **Lines:** `12077–12206` (the vote branch); defects at

```cpp
MRI *MRIresampleFill(MRI *src, MRI *template_vol, int resample_type, float fill_val)
{
  /* ... header copy and matrix setup elided ... */

  if (resample_type == SAMPLE_VOTE) {
    MRI *mri_votes;
    int count;
    MATRIX *minv;

    printf("resampling using voting...\n");
    // iterate over source voxels and vote to create dest one
    mri_votes = MRIallocSequence(template_vol->width, template_vol->height,
                                 template_vol->depth, MRI_UCHAR, 256);     // ← 256 frames only
    minv = MRIgetResampleMatrix(template_vol, src);
    /* ... */
    for (nframe = 0; nframe < src->nframes; nframe++) {
      for (si = 0; si < src->width; si++) {
        for (sj = 0; sj < src->height; sj++) {
          for (sk = 0; sk < src->depth; sk++) {
            /* ... transform src (si, sj, sk) → dst (di, dj, dk) ... */

            val = nint(MRIgetVoxVal(src, si, sj, sk, nframe));
            if (val < 0)
              val = 0;
            else if (val > 255)
              val = 255;                                                    // ← label clip
            count = MRIgetVoxVal(mri_votes, di, dj, dk, val);
            MRIsetVoxVal(mri_votes, di, dj, dk, val, count + 1);           // ← UCHAR count
          }
        }
      }
    }
    /* ... argmax across 256 label frames ... */
  }
  /* ... */
}
```

The 256-frame UCHAR allocation declares both the label range
and the count depth in a single call; both defects follow from
that one size choice.

## Root Cause

The histogram was sized as "one UCHAR frame per label, 256
labels max" — an implicit assumption that label values fit in
a byte. That was reasonable for classic aseg / `MRI_UCHAR`
volumes, which occupy `[0, 255]`, but it does not extend to
aparc or wmparc volumes where label values span `1001–1035`,
`2001–2035`, and beyond. The explicit `if (val > 255) val = 255;`
treats the out-of-range case as a clamp rather than an error,
so the corruption is completely silent. The UCHAR depth of
each frame was presumably chosen for memory reasons but was
never documented or enforced.

## Impact

- `mri_convert --resample_type vote` on aparc+aseg or wmparc
  volumes collapses every cortical / wm parcel label to `255`,
  destroying the categorical content the user explicitly
  asked to preserve. There is no warning.
- `mri_convert --resample_type vote` on ordinary aseg
  volumes (labels 0–255) is robust for label identity, but
  still overflows the vote counter when downsampling ratios
  exceed ≈ 6× per axis — the argmax becomes undefined.
- Standard [[recon-all]] is unaffected because recon-all does
  not invoke `--resample_type vote`.
- Group-analysis pipelines that use `--resample_type vote` to
  move aparc/wmparc into common space (e.g., MNI template)
  silently produce wrong label maps.

## Recommended Fix

Replace the fixed-size UCHAR histogram with a structure that
handles the true label and count ranges. A minimal, backwards-
compatible patch:

```diff
-    mri_votes = MRIallocSequence(template_vol->width, template_vol->height,
-                                 template_vol->depth, MRI_UCHAR, 256);
+    // Determine the label range of src once, and allocate a histogram
+    // large enough to hold every label with a count field wide enough
+    // not to saturate on realistic downsample ratios.
+    float src_min, src_max;
+    MRIlimits(src, &src_min, &src_max);
+    int label_max = (int)ceil(src_max);
+    if (label_max < 255) label_max = 255;                     // keep aseg fast path
+    mri_votes = MRIallocSequence(template_vol->width,
+                                 template_vol->height,
+                                 template_vol->depth,
+                                 MRI_INT,                     // wider count type
+                                 label_max + 1);
     /* ... */
-    val = nint(MRIgetVoxVal(src, si, sj, sk, nframe));
-    if (val < 0)
-      val = 0;
-    else if (val > 255)
-      val = 255;
+    val = nint(MRIgetVoxVal(src, si, sj, sk, nframe));
+    if (val < 0 || val > label_max) continue;
```

This removes the silent clip and widens the counter. If memory
is a concern (256³ × `label_max+1` × 4 bytes can be large for
wmparc), an alternative is to use a sparse per-voxel label
map — a `std::unordered_map<int,int>` per destination voxel
— which costs more bookkeeping but only occupies space
proportional to the actually-present labels.

### Alternative Fixes Considered

Run the voting algorithm label-by-label (one pass per unique
source label) and keep only the current-winner label +
winning-count per destination voxel. Two destination-sized
scalars replace the 256-frame histogram, and the memory cost
does not scale with label range. Slightly slower (O(N_labels)
passes over the source volume) but scales to arbitrary label
IDs without allocation tuning.

## Workarounds (If Any)

Users who need label-preserving resampling of aparc / wmparc
volumes should avoid `--resample_type vote`. Alternatives:

- `mri_label2vol` — forward-projects labels through a
  transform and can handle arbitrary label IDs.
- `mri_convert --resample_type nearest` — preserves label
  identity exactly when the grids align; at grid mismatches it
  gives the nearest source voxel's label rather than the
  majority.
- A one-label-at-a-time vote via `mri_binarize` + `mri_convert
  --resample_type interp` + argmax externally.

## Confidence and Gaps

> [!gap] Memory-footprint of the naïve fix
> Widening the histogram to `(label_max+1)` frames of `MRI_INT`
> costs ≈ 1 GB for a 256³ output volume with a wmparc label
> range (`label_max ≈ 4035`). The alternative one-label-at-a-
> time vote scales better but requires a slightly more
> invasive restructuring. Choice between the two depends on
> the expected caller.

> [!gap] Count-overflow practical threshold
> The UCHAR saturation only fires when more than 255 source
> voxels of a given label land on one destination voxel.
> Typical recon-all-era downsampling (256³ → 128³) spreads
> only eight source voxels per destination voxel, so the
> counter does not overflow in that common case. It starts to
> matter for dataset-style very-high-resolution acquisitions
> (1024³+) or when voting from multiple subjects into a
> shared template.
