# [severity-4] [bug-00122] `MRIdownsampleN` scales output by `1/(Fc·Fr·Fs)` even when factors are <1, producing 8x-too-bright values for `--ds 0.5` upsampling

> [!bug] Synopsis
> ```cpp
> /* utils/mri.cpp:7787-7874 */
> MRI *MRIdownsampleN(MRI *src, MRI *dst, float Fc, float Fr, float Fs, int KeepType)
> {
>   int c0, r0, s0, c, r, s, f;
>   ...
>   width  = (int)ceil(src->width  / Fc);
>   ...
>
>   for (f = 0; f < dst->nframes; f++) {
>     for (c = 0; c < dst->width; c++) {
>       for (r = 0; r < dst->height; r++) {
>         for (s = 0; s < dst->depth; s++) {
>           val = 0;
>           for (c0 = Fc * c; c0 < Fc * (c + 1); c0++) {    /* :7861 */
>             for (r0 = Fr * r; r0 < Fr * (r + 1); r0++) {
>               for (s0 = Fs * s; s0 < Fs * (s + 1); s0++) {
>                 val += MRIgetVoxVal(src, c0, r0, s0, f);
>               }
>             }
>           }
>           MRIsetVoxVal(dst, c, r, s, f, val / (Fc * Fr * Fs));  /* :7868 — bug */
>         }
>       }
>     }
>   }
> }
> ```
>
> The function's design assumes
> `Fc·Fr·Fs ≥ 1` (downsampling).
> For `Fc = 2`, each output voxel
> accumulates `2 × 2 × 2 = 8` input
> values from the inner loops; the
> `/ (Fc·Fr·Fs) = / 8` correctly
> produces an average.
>
> For `Fc < 1` (upsampling),
> `Fc · (c + 1) - Fc · c = Fc < 1`,
> so each output voxel's inner loop
> runs **at most once** (often zero
> or one iteration). The accumulator
> `val` holds a single input voxel
> value. But the final divisor is
> still `Fc·Fr·Fs`, which for
> `Fc=Fr=Fs=0.5` equals `0.125`.
>
> So output = single_input_value /
> 0.125 = **8 × input value**.

## Affected Artefacts

- **Tool:** [[mri_convert]] — the
  `--ds <Fc> <Fr> <Fs>` flag
  (downsample, also overloaded for
  upsample when factors are < 1)
  routes through `MRIdownsampleN`
  at
  [`mri_convert.cpp:2964`](https://github.com/freesurfer/freesurfer/blob/v$FREESURFER_VERSION/mri_convert/mri_convert.cpp#L2964).
- **Pipeline stage(s):** none in
  default `recon-all`. Used by
  ad-hoc volume rescaling.
- **Triggering configuration:**
  any `mri_convert --ds <f>` where
  `f < 1` (i.e., the user wants to
  upsample). Most commonly seen
  with isotropic-half factors like
  `--ds 0.5` or anisotropic
  combinations like `--ds 0.5 0.5
  1.0`.
- **FreeSurfer version(s):**
  confirmed in `$FREESURFER_VERSION`
  (commit `d932c45b79`).

## Detailed Description

### Concrete example: `--ds 0.5`

Input: 256³ UCHAR volume with
intensities in [0, 255]. Run:
```
mri_convert --ds 0.5 in.mgz out.mgz
```

Expected: 512³ UCHAR volume with
the same intensities in [0, 255],
nearest-neighbour upsampled.

What happens:

| step | computation |
|------|-------------|
| width | `ceil(256 / 0.5)` = 512 ✓ |
| For each output voxel `(c, r, s)`: | |
| inner loop bounds | `c0 ∈ [int(0.5·c), int(0.5·(c+1)))` |
| For c=0: | `c0 ∈ [0, 0)` → empty, OR `c0=0` if int(0)=0 and int(0.5)>0 |
| For c=1: | `c0 = int(0.5) = 0` → `0 < 1.0` → 1 iteration with c0=0 |
| For c=2: | `c0 = int(1.0) = 1` → `1 < 1.5` → 1 iteration with c0=1 |
| For c=3: | `c0 = int(1.5) = 1` → `1 < 2.0` → 1 iteration with c0=1 |
| accumulated `val` | one src voxel value |
| output `val / (Fc·Fr·Fs)` | `val / 0.125 = 8·val` |

For UCHAR with input voxel = 100:
output voxel = 800 → saturated at
255. For typical brain volumes
with intensities in the 50-150
range, every output voxel
saturates.

For float volumes, the values are
just 8× what they should be —
preserved but mis-scaled.

### Why the 2025-07-23 fix didn't catch this

Commit
[`fb7d6e85ca`](https://github.com/freesurfer/freesurfer/commit/fb7d6e85ca)
("fix 'mri_convert --ds <>' core
dump when ds < 1") changed the
parameter types `Fc, Fr, Fs` from
`int` to `float` and changed the
output dimension computation from

```cpp
width = src->width / Fc;  // int division
```

to

```cpp
width = (int)ceil(src->width / Fc);  // float division, ceil
```

This fix made the function not
crash for `ds < 1`, but did not
touch the final scaling at
`:7868`. The author addressed the
"core dump" symptom but missed
the "wrong values" semantic.

### Why this is severity 4

- **`mri_convert --ds 0.5`
  silently produces wrong
  output:** users who upsample
  via this tool get an unusable
  volume.
- **Visible artifact:** for UCHAR
  inputs, the saturation is
  obvious (whole brain becomes a
  uniform white blob).
- **No warning:** the tool runs
  to completion with no
  indication that the output is
  wrong.
- **Real use case:** upsampling
  is a common pre-processing
  step for surface placement
  with high-resolution targets.

## Root Cause

`MRIdownsampleN` was written for
the downsample case where the
inner loop accumulates
`Fc·Fr·Fs ≥ 1` voxels per output.
The final division by
`Fc·Fr·Fs` is the count
normaliser for the average.

For upsampling, the inner loop
accumulates at most 1 voxel, but
the division is still by
`Fc·Fr·Fs < 1`, which multiplies
the value. The author of the
2025-07-23 fix made the
allocation work (no crash) but
did not update the divisor.

The correct scaling would be to
divide by the actual number of
accumulated voxels, not by
`Fc·Fr·Fs`. Or equivalently:
divide by `max(1, Fc·Fr·Fs)`
when factors are < 1.

## Impact

- **`mri_convert --ds <f>` with
  `f < 1`:** output values
  multiplied by `1 / (f^3)` for
  isotropic factors. For UCHAR
  inputs, saturated white.
- **Silent failure:** tool
  reports success.
- **Severity:** 4 — visible
  user-facing wrong output via a
  reachable command-line flag.

## Recommended Fix

```diff
--- a/utils/mri.cpp
+++ b/utils/mri.cpp
@@ -7858,6 +7858,7 @@ MRI *MRIdownsampleN(MRI *src, MRI *dst, float Fc, float Fr, float Fs, int KeepTy
       for (s = 0; s < dst->depth; s++) {
         val = 0;
+        int nacc = 0;
         for (c0 = Fc * c; c0 < Fc * (c + 1); c0++) {
           for (r0 = Fr * r; r0 < Fr * (r + 1); r0++) {
             for (s0 = Fs * s; s0 < Fs * (s + 1); s0++) {
               val += MRIgetVoxVal(src, c0, r0, s0, f);
+              nacc++;
             }
           }
         }
-        MRIsetVoxVal(dst, c, r, s, f, val / (Fc * Fr * Fs));
+        MRIsetVoxVal(dst, c, r, s, f, nacc > 0 ? val / nacc : 0);
       }
```

This divides by the **actual
number of source voxels
accumulated**, which equals
`Fc·Fr·Fs` for downsampling and
1 for upsampling.

## Workarounds

For users needing to upsample now:
use `mri_convert --vs <0.5> <0.5>
<0.5>` (resample to a specific
voxel size) instead of `--ds 0.5`.
The `--vs` path uses a different
function that handles upsampling
correctly.

## Provenance and Discovery

- **Discovered:** 2026-05-11 by
  agent (review of the recent
  `fb7d6e85ca` "fix core dump"
  commit which addressed the
  crash but missed the scaling).
- **Evidence:**
  - Final scale at `:7868`
    divides by `Fc·Fr·Fs`.
  - For `Fc=Fr=Fs=0.5`, divisor
    is `0.125`.
  - Inner loop runs at most 1
    iteration per output voxel
    when `Fc < 1`.
  - 8x scaling reproduces
    analytically.
  - The 2025-07-23 commit only
    fixed dim computation and
    type, not scaling.
