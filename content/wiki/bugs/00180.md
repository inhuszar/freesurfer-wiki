# [severity-2] [bug-00180] reregister_subject_mixed — `-norm mri/norm` writes the normalised output back over the `mri/norm` input, destructively re-normalising it in place

> [!bug] Synopsis
> `reregister_subject_mixed` re-runs the EM registration against the
> mixed GCA with a single `mri_em_register` call. In `mri_em_register`,
> the `-norm <file>` flag names an **output**: the tool writes a freshly
> normalised copy of the input volume to that path. The script passes
> `-norm $sdir/norm` while **also** giving `$sdir/norm` (i.e.
> `mri/norm`) as the positional **input** volume. So `mri_em_register`
> reads `mri/norm`, intensity-normalises it against the GCA, and writes
> the result back over `mri/norm` — destructively overwriting the input
> with a re-normalised version on every run. Re-running the script
> repeatedly normalises an already-normalised volume, compounding the
> intensity transform.

## Affected Artefacts

- **Tool(s):** [[reregister_subject_mixed]] (the wrapper) driving
  [[mri_em_register]] (which performs the in-place write).
- **Pipeline stage(s):** _N/A_ — `reregister_subject_mixed` is a manual
  re-registration utility against `$FREESURFER_HOME/average/mixed.gca`,
  not a stage of the default
  [[wiki/pipelines/recon-all|recon-all]] run.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit `d932c45`.
- **Platforms:** all.
- **Triggering configuration:** always — the single `mri_em_register`
  command in the script unconditionally passes the same `mri/norm` path
  as both the `-norm` output and the positional input.

## Detailed Description

The script's only real work is one command:

```tcsh
mri_em_register -fsamples $sdir/fsamples -norm $sdir/norm \
    $sdir/norm $GCA $sdir/transforms/$LTA
```

where `$sdir = $SUBJECTS_DIR/$s/mri`. Reading the `mri_em_register`
argument handling:

- The option scanner consumes leading `-…` flags first
  (`for ( ; argc > 1 && ISOPTION(*argv[1]) ; …)`), so `-fsamples …`
  and `-norm …` are stripped from the positional list.
- `-norm` sets `norm_fname = argv[2]` (the path after the flag) and
  prints *"intensity normalizing and writing to …"*.
- The remaining three positionals are the input volume(s), the GCA, and
  the output transform: `ninputs = argc - 3`, `in_fname = argv[1]`,
  `gca_fname = argv[ninputs+1]`, `out_fname = argv[ninputs+2]`.
- Late in registration, the tool computes
  `mri_norm = GCAnormalizeSamples(mri_in, …)` and writes it with
  `MRIwrite(mri_norm, norm_fname)` — i.e. it **writes** to the `-norm`
  path.

With the script's argument order, both `in_fname` and `norm_fname`
resolve to `$sdir/norm` (= `mri/norm`). The tool reads `mri/norm` as the
moving volume and writes the normalised volume back to `mri/norm`.

### Expected Behaviour

`-norm` is meant to emit the *normalised* volume to a **distinct**
output path (the conventional recon-all name is `mri/norm.mgz`, produced
from `mri/nu.mgz` etc.). The registration input and the normalised
output should not be the same file, so the input is preserved and the
normalised result is a separate artefact. Re-running the registration
should consume the same untouched input each time and be idempotent in
the input.

### Observed Behaviour

`mri_em_register` opens `mri/norm`, registers it to the mixed GCA,
normalises it via `GCAnormalizeSamples`, and overwrites `mri/norm` with
that normalised volume. The original `mri/norm` is gone after the run.
Because the script can be (and is intended to be) re-run, each
invocation normalises a volume that was already normalised by the
previous invocation, so the intensity transform is applied repeatedly
and the volume drifts further from the true input with every pass. The
overwrite is silent — the tool reports "writing normalized volume to
…/norm" as if to an output, with no indication that it is clobbering its
own input.

### Reproducer

> [!gap] Reproducer not executed
> A full run requires a subject with `mri/norm`, the mixed GCA, and the
> `talairach.lta` machinery, which were not exercised in this audit.
> The destructive in-place write is established by static reading of
> `mri_em_register`'s argument handling (input = `argv[1]` = `mri/norm`;
> `-norm` output = `mri/norm`) plus the `MRIwrite(mri_norm, norm_fname)`
> at the end of registration. A demonstration would:
>
> 1. `cp mri/norm.mgz mri/norm` and record a checksum of `mri/norm`.
> 2. Run `reregister_subject_mixed <subj>` once; re-checksum `mri/norm`
>    (it will differ — the file was overwritten).
> 3. Run it again; the checksum changes a second time, confirming the
>    transform is re-applied to the already-normalised volume.

## Root Cause

The wrapper reuses one path, `$sdir/norm`, for two roles that
`mri_em_register` keeps distinct: the moving **input** volume
(positional `argv[1]`) and the **output** of intensity normalisation
(`-norm`). Because `-norm` causes an unconditional `MRIwrite` back to
that path, the input is clobbered. The likely intent was either to read
the input from a different volume (e.g. `mri/nu` or `mri/orig`) and
write the normalised result to `mri/norm`, or to drop `-norm` entirely
if a normalised volume is not wanted from this re-registration step.

## Impact

- **Input volume destroyed / drifted.** Each run overwrites `mri/norm`
  with a freshly normalised version of itself. A single run loses the
  original `mri/norm`; repeated runs (the script is explicitly a
  *re*-register utility) compound the intensity normalisation, pushing
  the volume progressively away from a single correct normalisation.
- **Confined to a manual, legacy utility.** `reregister_subject_mixed`
  is not part of the default [[wiki/pipelines/recon-all|recon-all]]
  chain; it must be invoked deliberately and depends on the mixed GCA at
  `$FREESURFER_HOME/average/mixed.gca`. The blast radius is one
  subject's `mri/norm`, recoverable by re-running normalisation from
  `mri/nu`. That bounded, opt-in scope keeps this at severity 2 despite
  the destructive write.
- **Silent.** The tool prints the write as if to an output file; nothing
  flags that the input was overwritten, so a user may not notice the
  corruption until downstream intensity-dependent steps misbehave.

## Recommended Fix

Separate the input volume from the `-norm` output so the input is not
overwritten. The minimal change writes the normalised result to a
distinct file:

```diff
-mri_em_register -fsamples $sdir/fsamples -norm $sdir/norm $sdir/norm $GCA $sdir/transforms/$LTA
+mri_em_register -fsamples $sdir/fsamples -norm $sdir/norm.reg.mgz $sdir/norm $GCA $sdir/transforms/$LTA
```

(or read the input from a different source volume, e.g. `$sdir/nu.mgz`,
and write the normalised output to `$sdir/norm`). If a normalised volume
is not actually needed from this re-registration, drop the `-norm` flag
entirely and keep only `-fsamples`:

```diff
-mri_em_register -fsamples $sdir/fsamples -norm $sdir/norm $sdir/norm $GCA $sdir/transforms/$LTA
+mri_em_register -fsamples $sdir/fsamples $sdir/norm $GCA $sdir/transforms/$LTA
```

### Alternative Fixes Considered

- **Write to a temp then rename only if intended.** Preserves the
  original by routing the `-norm` output through a scratch path; only
  promote it to `mri/norm` if overwriting is genuinely desired. Heavier
  than simply choosing a distinct output name.
- Developer confirmation is needed on whether this step is *meant* to
  re-emit `mri/norm`; that determines which of the two diffs above is
  correct (see Gaps).

## Workarounds (If Any)

Back up `mri/norm` before running (`cp mri/norm mri/norm.bak`) and
restore it afterward, or edit the local copy of the script to give the
`-norm` output a distinct filename. Do not re-run the script repeatedly
against the same `mri/norm` without restoring the original between runs.

## Confidence and Gaps

> [!gap] Intended role of `mri/norm` in this step
> It is unambiguous from the code that the input is overwritten. What
> the audit cannot determine from the script alone is whether the author
> *wanted* this re-registration to regenerate `mri/norm` (in which case
> the input should come from a different volume) or merely to refresh
> the transform/fsamples (in which case `-norm` should be dropped).
> Either fix removes the destructive same-file aliasing; a developer
> should confirm which is intended.
