# [severity-3] [bug-00207] `fem core` — `Element3d::get_matrix` returns BᵀDB without the element-volume factor (the `dfactor *= dvol` line is commented out)

> [!bug] Synopsis
> The stiffness matrix of the linear tetrahedron used by [[surf2vol]]'s elastic
> FEM is, in standard theory, `K_e = V_e · BᵀDB`. `Element3d::get_matrix()`
> computes `BᵀDB` correctly but the lines that multiply by the element volume
> are commented out, so `K_e = BᵀDB`: the element stiffness scales as
> `1/h²` rather than `h`, small elements are over-weighted by `1/V_e` relative
> to large ones, and the solution depends on the meshing density. The
> omission is in the 2008 import and looks deliberate, so whether it is a
> defect or an intentional normalisation that the [[mri_cvs_register]]
> parameters were tuned around is a developer question.

## Affected Artefacts

- **Tool(s):** [[surf2vol]] (every stiffness assembly: `TSolver` for the main
  solve and `TDirectSolver` for the untangler's local solves); consumed through
  [[mri_cvs_register]].
- **Pipeline stage(s):** [[mri_cvs_register]] elastic stage — the
  `surf2vol … -fem_steps 17 -elt_vol_range 5.0,10.0 …` call at
  [`mri_cvs_register/mri_cvs_register:389-403`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_cvs_register/mri_cvs_register#L389-L403).
- **FreeSurfer version(s):** confirmed in 8.2.0; present since the 2008-03-14
  import of the `fem_elastic` sources (commit `4b881dc775f`), unchanged.
- **Platforms:** all
- **Triggering configuration:** always-on; every element of every mesh built
  by surf2vol passes through `Element3d::get_matrix()`
  ([`fem_elastic/solver.h:708`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/solver.h#L708)).

## Detailed Description

For a linear tetrahedron the strain–displacement matrix `B` is constant, so
the element stiffness is `K_e = V_e · BᵀDB` with `V_e` the element volume
(`|det(x₂−x₁, x₃−x₁, x₄−x₁)| / 6`). `Element3d::get_matrix()` builds `D` from
Young's modulus and Poisson ratio and the entries of `B` from the shape
function gradients `m_cb, m_cc, m_cd` (which are `∝ 1/h`), and assembles the
twelve-by-twelve matrix block by block. The volume factor that would complete
the formula is present in the source but commented out:

```cpp
  double dbuf;
  double dfactor = m_cpMaterial->get_E() /
                   (1+m_cpMaterial->get_nu()) /
                   (1 - 2* m_cpMaterial->get_nu()); // used in front of the elasticity matrix
  double dalpha =
    1- m_cpMaterial->get_nu(); // first 3 diagonal elements
  // of the elasticity matrix
  double dbeta =
    .5 * ( 1 - 2* m_cpMaterial->get_nu() ); // next 3 diagonal elements
  // of the elasticity matrix
  double dnu = m_cpMaterial->get_nu();

//  double dvol = abs( vol( m_vpNodes[0]->coords(),
  //   m_vpNodes[1]->coords(),
  //   m_vpNodes[2]->coords(),
  //   m_vpNodes[3]->coords() ) );
  //dfactor *= dvol;
```

and the assembled blocks use `dfactor` without it
([`fem_elastic/fem_3d.cpp:151-153`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/fem_3d.cpp#L151-L153) and the eight following entries). The result is `BᵀDB`, not `V·BᵀDB`.

### Expected Behaviour

`K_e` should be `V_e · BᵀDB` (units: stiffness ∝ length for a 3-D solid), so
that the assembled global matrix is the discretisation of the elastic energy
`½ ∫ εᵀDε dV`: doubling the size of a tetrahedron doubles its stiffness, and
all elements contribute to the energy in proportion to their volume.

### Observed Behaviour

The matrix omits `V_e`: each element's energy contribution is `½ εᵀDε`
regardless of its size.

- **Numerical check against theory.** For a generic tetrahedron
  (nodes `(0.3,0.1,−0.2) (2.1,0.4,0.3) (0.5,1.9,0.1) (0.2,0.6,2.4)`,
  `E = 1000`, `ν = 0.3`, `V = 1.35483`), the matrix returned by
  `get_matrix()` equals `BᵀDB` (with `B` rebuilt from the element's own
  shape-function gradients and the Lamé-parameter `D`) to
  `max|K − BᵀDB| = 1.7e-13` (largest matrix entry 462.4) and has the three
  rigid translations and rotations in its null space (residuals ≈ 1e-13).
  So the expression is exactly `BᵀDB`, correct apart from the missing `V`.
- **Scaling with element size.** For the tetrahedron
  `(0,0,0) (2,0,0) (0,2,0) (0,0,2)` `K(0,0) = 528.846`; the same tetrahedron
  at twice the size (`(0,0,0) (4,0,0) (0,4,0) (0,0,4)`) gives
  `K(0,0)` ratio `0.25` (∝ 1/h²). Standard FEM would give `2.0` (∝ h).
- **Spread of element volumes.** A toy `DelaunayMesh` (300 random points in
  `[20,80]³`, box `[0,100]³`, requested maximum volume 50, `E = 1000`,
  `ν = 0.3`) came out as 37,545 positively oriented tetrahedra with volumes
  from 0.259 to 88.1 (a ratio of about 340). With the omitted factor the
  smallest of these is over-weighted by that ratio relative to the largest.

### Reproducer

Element-level reproduction (confirmed): link the real `fem_elastic/fem_3d.cpp`,
`small_matrix.cpp`, tetgen and `utils/timer.cpp` against a small driver that
builds tetrahedra with `Constructor::node`/`Constructor::elt`
(`E = 1000`, `ν = 0.3`) and prints `get_matrix()`:

```
single tetrahedron (0,0,0) (2,0,0) (0,2,0) (0,0,2):   K(0,0) = 528.846   (src_volume = 6V = 8)
same tetrahedron at 2x size:                          K(0,0) ratio big/small = 0.25   (standard FEM: 2.0)
generic tetrahedron:                                  max|K - B^T D B| = 1.7053e-13  (max|Kref| = 462.436)
```

Re-building with the factor restored (see Recommended Fix) gives
`K(0,0) = 705.128 = 528.846 × 8/6` and the size ratio `2.0`, i.e. the
standard `V·BᵀDB`.

> [!gap] End-to-end effect on CVS output not measured
> No full `surf2vol`/`mri_cvs_register` run was made with the factor
> restored, so the change in the registration (and the re-tuning it would
> need) is unquantified.

## Root Cause

The multiplication by the element volume was written, then commented out in
the original 2008 import (`git blame` attributes lines 137-141 to commit
`4b881dc775f`, "source for createMorph and applyMorph"); no later commit
touched it. Everything else in `get_matrix()` is the textbook `BᵀDB`
expression. Note that the commented-out text itself is not a correct
restoration: `vol()` returns `6V`, so `dfactor *= dvol` would have scaled
the matrix by `6V`, not `V` (a uniform factor of 6 on top of the missing `V`),
which may be one reason the line was abandoned.

## Impact

- **Mechanism:** the elastic part of the system is `Σ BᵀDB` over elements
  while the penalty (MFC) terms added in
  `TSolver::add_elt_mfc_lhs` ([`fem_elastic/solver.h:769-783`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/solver.h#L769-L783)) are
  `w · NᵀN` — point constraints with no volume dependence. Relative to
  standard FEM the elastic stiffness of an element is multiplied by `1/V_e`
  (in voxel³, i.e. mm³ for 1 mm data): the stiffness of small elements near
  the surfaces is over-weighted relative to large interior ones (about 340×
  across the toy mesh above), and the ratio of elastic to penalty stiffness
  depends on the mesh density that `-elt_vol_range` selects. The solution is
  consequently mesh-dependent in a way a converged FEM discretisation would not
  be.
- **Interaction with [[00200]]:** with the CVS options `-ksp_type preonly
  -pc_type jacobi` each step applies one diagonal scaling `K_ii / (K_ii + w)`
  (analysed in [[00200]]); `K_ii` is exactly the quantity that lacks the
  volume factor, so under that analysis the per-node step size depends
  directly on the local element volumes.
- **Default path:** every [[mri_cvs_register]] run executes this code.
- **Why 3 and not 4 or 5:** by reach this would rank with the default-path
  defects ([[00195]], [[00199]]), but the omission is in a line that was
  deliberately commented out (`//dfactor *= dvol;`) and
  `mri_cvs_register` documents that its elastic options
  (`-penalty_weight 1000`, `-young 1000`, 17 steps, `-elt_vol_range 5.0,10.0`)
  were tuned empirically on the *ratio* of penalty weight to Young's modulus
  ([`mri_cvs_register/mri_cvs_register:372-387`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/mri_cvs_register/mri_cvs_register#L372-L387)). The shipped CVS results may
  therefore depend on the current normalisation, and "fixing" it without
  re-tuning could degrade rather than improve the registration. It is
  recorded as a medium-severity numerical defect with uncertain intent;
  confidence is correspondingly low.

## Recommended Fix

If the missing factor is unintended, restore it with the correct
normalisation (`vol()` is `6V`; `std::abs` resolves to the `double`
overload under g++ 8.5, as it already does for the existing `abs( vol(…) )`
calls in this file), then re-tune `-penalty_weight`/`-young` and re-validate
the CVS results:

```diff
--- a/fem_elastic/fem_3d.cpp
+++ b/fem_elastic/fem_3d.cpp
@@ Element3d::get_matrix() const
-//  double dvol = abs( vol( m_vpNodes[0]->coords(),
-  //   m_vpNodes[1]->coords(),
-  //   m_vpNodes[2]->coords(),
-  //   m_vpNodes[3]->coords() ) );
-  //dfactor *= dvol;
+  // K_e = V_e * B^T D B; vol() returns 6*V_e
+  double dvol = std::abs( vol( m_vpNodes[0]->coords(),
+                               m_vpNodes[1]->coords(),
+                               m_vpNodes[2]->coords(),
+                               m_vpNodes[3]->coords() ) ) / 6.0;
+  dfactor *= dvol;
```

(Built against the element-level reproducer: `K(0,0)` 705.128 and size
ratio 2.0.) A unit test should assert that scaling a tetrahedron by `s`
scales `get_matrix()` by `s` and that the result equals `V·BᵀDB` for a
generic tetrahedron.

### Alternative Fixes Considered

- Leave the matrix as is and document the normalisation as intentional
  (stiffness per unit volume), keeping the tuned CVS parameters valid. This
  is the zero-risk option for existing results.
- Restore the factor only for the untangler's local solves, where mesh
  density is not a registration parameter — would still change results.

## Workarounds (If Any)

None needed to avoid a crash; users who want a mesh-density-independent
behaviour can only keep `-elt_vol_range` fixed, which is what the shipped CVS
parameters do.

## Confidence and Gaps

> [!gap] Developer intent for the commented-out volume factor
> The `dfactor *= dvol` line was deliberately commented out in the original
> import. Was the factor dropped because the resulting system behaved better
> with the point-constraint penalty (an intentional normalisation that the
> empirically tuned `-penalty_weight 1000 -young 1000 -elt_vol_range
> 5.0,10.0` depend on), or is it an unfinished edit? The mathematics is
> unambiguous (the matrix is `BᵀDB`, not `V·BᵀDB`); whether that is a defect
> needs confirmation from the FEM-core authors before any change is made.
