# [severity-3] [bug-00212] `VolumeMorph::exportGcam` — with a bounding box, GCAM node positions are shifted by minus the box origin

> [!bug] Synopsis
> `VolumeMorph::exportGcam` fills each GCAM node with
> `cache + (lattice index)`, where the displacement cache holds
> `moving-voxel position - fixed-voxel index` for the **full** fixed grid.
> Without a bounding box the lattice index equals the fixed-voxel index and
> the result is the correct moving-voxel position. With
> `exportGcam --bbox_threshold N` the lattice is a cropped box whose origin
> is `(box.x, box.y, box.z)`, so the stored position is too small by exactly
> the box origin. The exported `.m3z` then maps every atlas voxel to the
> wrong moving voxel (observed: identity morph, box origin `(7, 9, 5)`: node
> `(0,0,0)` holds `(0,0,0)` instead of `(7,9,5)`).

## Affected Artefacts

- **Tool(s):** [[exportGcam]] (and any other caller of `VolumeMorph::exportGcam` that passes `useTemplateBoundingBox = true`; the only such caller in the tree is `exportGcam --bbox_threshold`)
- **Pipeline stage(s):** _N/A_. `mri_cvs_register` never passes `--bbox_threshold`, and `surf2vol -gcam` passes `FALSE`, so the CVS path is unaffected.
- **FreeSurfer version(s):** confirmed in 8.2.0; the loop dates from the original 2008 import (commit `4b881dc775f`)
- **Platforms:** all
- **Triggering configuration:** `exportGcam ... --bbox_threshold <N>` (the presence of the flag, not its value, switches the box on) with a fixed volume whose thresholded bounding box does not start at voxel `(0,0,0)`.

## Detailed Description

`exportGcam` builds one GCAM node per voxel of the fixed ("template")
volume, or per voxel of its padded bounding box when `--bbox_threshold` is
given. Each valid node stores, in `x,y,z` and `origx,origy,origz`, the
**moving-volume voxel position** onto which the corresponding atlas voxel is
mapped (a `GCAM_VOX` GCAM). The data come from the displacement cache that
`apply_transforms(..., cacheField=true)` fills for every voxel of the full
fixed grid: frames 0-2 hold `img - pt`, where `pt` is the position of the
fixed voxel in the morph's own fixed geometry and `img` the position of its
image in the moving volume; frame 3 is a validity flag.

The export loop iterates over the box with two sets of counters: the
lattice index `(x, y, z)` starting at 0, used to index `gcam->nodes`, and
the full-grid index `(xbox, ybox, zbox)` starting at the box origin, used to
read the cache. The node position is then assembled as the cached
displacement plus the **lattice** index. Since `cache = img - pt` and
`pt = (xbox, ybox, zbox)` when the template grid is the morph's fixed grid,
the stored value is `img - box_origin`, not `img`.

### Expected Behaviour

Node `(x, y, z)` of the cropped lattice corresponds to full-grid voxel
`(xbox, ybox, zbox)` and must store that voxel's image in the moving volume,
i.e. `cache + (xbox, ybox, zbox)` (identical to `cache + (x, y, z)` only when
the box origin is zero).

### Observed Behaviour

The atlas side of the GCAM is handled correctly: the atlas geometry is the
template cropped with `MRIextractRegion`, whose `c_ras` is shifted by the box
origin. The moving side is not: node positions are lower by `(box.x, box.y,
box.z)`. The resulting m3z silently resamples the wrong region of the moving
volume. The `exportGcam` run prints no warning.

### Reproducer

Synthetic data: a 32^3 fixed volume that is 100 inside the block
`[8:24, 10:22, 6:26]` (zero elsewhere), a 32^3 moving volume with distinct
values, and a hand-built `.tm3d` holding one `id` transform (identity morph,
valid fixed and moving geometries stored).

```bash
# no box: lattice == full grid
exportGcam --fixed fixed.mgz --moving moving.mgz --morph ident.tm3d \
           --out_gcam <W>/nobox.m3z
# box: threshold 0 -> bounding box of voxels > 0, padded by 1 voxel
exportGcam --fixed fixed.mgz --moving moving.mgz --morph ident.tm3d \
           --out_gcam <W>/box.m3z --bbox_threshold 0
```

The tool prints `box = 7 , 9 , 5 / 18 , 14 , 22` (origin and size) for the
second run. Reading the nodes back from the m3z (big-endian stream: header
`float version, int w, h, d, spacing, float exp_k`, then per node `float
origx,origy,origz,x,y,z` and `int xn,yn,zn`; see [[m3z-format]]):

| Run | Lattice | Node `(0,0,0)` | Node `(5,5,5)` | Node `(10,12,8)` |
|-----|---------|----------------|----------------|------------------|
| no box | 32 x 32 x 32 | `(0,0,0)` | `(5,5,5)` | `(10,12,8)` |
| `--bbox_threshold 0` | 18 x 14 x 22 | `(0,0,0)` — expected `(7,9,5)` | `(5,5,5)` — expected `(12,14,10)` | `(10,12,8)` — expected `(17,21,13)` |

Downstream effect, with the same inputs: crop the fixed volume to that box
(`[7:25, 9:23, 5:27]`, with the affine translated accordingly) and resample
the moving volume through the box m3z,

```bash
mri_vol2vol --mov moving.mgz --targ fixed_crop.mgz --m3z box.m3z \
            --noDefM3zPath --o box_out.mgz --interp nearest --no-save-reg
```

For an identity morph the output should equal `moving[7:25, 9:23, 5:27]`.
Observed: 0 % of the output voxels equal that sub-block, while 95.5 % equal
`moving[0:18, 0:14, 0:22]` (the corner at the origin); the remaining 4.5 %
were not examined.

A secondary manifestation of the same formula: when `--fixed` lies on a
grid that differs from the fixed geometry stored in the morph, `pt` (the
morph-geometry voxel) differs from the lattice index, and the node again
holds `cache + lattice index`, not `cache + pt`. Observed with an
identity morph and a `--fixed` volume whose `c_ras` was shifted by 3 mm
relative to the stored fixed geometry (no `--bbox_threshold`): the interior
nodes kept their own lattice index (node `(10,12,8)` held `(10,12,8)`), i.e.
the same values as in the unshifted run, although the fixed grid is now offset
by 3 voxels from the morph's fixed geometry, while the validity mask moved by
3 voxels (3072 invalid nodes). I did not determine which position the identity
morph should then yield, so this variant is recorded as an observation, not
as a confirmed second defect. `mri_cvs_register` passes the same volume to
`surf2vol` and `exportGcam`, so this variant does not arise there.

## Root Cause

The loop at [`fem_elastic/morph.cpp:1575-1577`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L1575-L1577) keeps two index triples in lock-step: `(x,y,z)` (lattice,
0-based, indexes `gcam->nodes`) and `(xbox,ybox,zbox)` (full grid, indexes
`mriCache`). The cache stores a *relative* quantity, `img - pt`, so turning
it back into an absolute moving-voxel position requires adding the same `pt`
that was subtracted in `apply_transforms`, which for the box case is
`(xbox,ybox,zbox)`. The code adds `+x`, `+y`, `+z` (lattice indices) instead
at [`fem_elastic/morph.cpp:1593-1595`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L1593-L1595). Without a box the two triples are equal, so the error is
invisible in the default and in the CVS usage, and the bug was never
exposed.

## Impact

- **Silent wrong output** for any GCAM exported with `--bbox_threshold`:
  the m3z is structurally valid but every node points `box.origin` voxels
  too low in the moving volume. Anything that applies or composes that
  m3z ([[mri_vol2vol]] `--m3z`, `mri_concatenate_gcam`, `mri_warp_convert`)
  inherits the shifted correspondence.
- **Severity 3, not 4 or 5.** The error occurs only behind an opt-in flag
  of one tool, which is the severity-3 criterion ("gated behind specific
  flag combinations"). The only in-tree caller ([[mri_cvs_register]]) never
  uses `--bbox_threshold` (nor does `surf2vol -gcam`), so no default
  pipeline path is affected, which rules out 4 and 5. The magnitude is
  large when it fires (a box-origin-sized shift), so it is not rated 2.
- **Companion issue:** `--bbox_threshold` also combines badly with `--test`
  and with empty boxes, see [[00221]].

## Recommended Fix

Add the full-grid index instead of the lattice index (the cache stores
`img - pt` with `pt` equal to the full-grid index when the template is the
morph's fixed grid):

```diff
-        pnode->x = pnode->origx = MRIgetVoxVal( mriCache, xbox,ybox,zbox, 0) +x;
-        pnode->y = pnode->origy = MRIgetVoxVal( mriCache, xbox,ybox,zbox, 1) +y;
-        pnode->z = pnode->origz = MRIgetVoxVal( mriCache, xbox,ybox,zbox, 2) +z;
+        pnode->x = pnode->origx = MRIgetVoxVal( mriCache, xbox,ybox,zbox, 0) +xbox;
+        pnode->y = pnode->origy = MRIgetVoxVal( mriCache, xbox,ybox,zbox, 1) +ybox;
+        pnode->z = pnode->origz = MRIgetVoxVal( mriCache, xbox,ybox,zbox, 2) +zbox;
```

A regression test is the identity-morph experiment above: with any box the
node at lattice `(i,j,k)` must hold `(i,j,k) + box_origin`.

### Alternative Fixes Considered

The `+xbox` form is exact only if the template grid coincides with the
morph's stored fixed geometry. The robust alternative is to make the cache
store the absolute moving-voxel position (frames 0-2 = `img`, set at
[`fem_elastic/morph.cpp:865-868`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L865-L868) without subtracting `pt`) and drop the `+x` terms in
`exportGcam`; that also removes the secondary `--fixed`-geometry mismatch
described above. The same `img - pt` convention is written by a second
routine, `VolumeMorph::convert_transforms`
([`fem_elastic/morph.cpp:1051-1057`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.cpp#L1051-L1057)),
and `VolumeMorph::cache()` exposes the cache publicly
([`fem_elastic/morph.h:362-365`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/fem_elastic/morph.h#L362-L365)),
so changing the stored convention would have to be applied to both writers; a
search of `*.cpp`/`*.h` in the tree found no caller of `cache()`.

## Workarounds (If Any)

Do not use `--bbox_threshold`; export the full grid (the default), which is
what `mri_cvs_register` does. If a box is needed, crop the moving side
consistently or post-correct the nodes by the box origin outside FreeSurfer.

## Confidence and Gaps

> [!gap] Intent of the cropped-lattice semantics
> The code gives no comment on whether node positions are meant to be
> relative to the cropped lattice or to the full grid. The atlas geometry
> is cropped with a shifted `c_ras`, and `mri_vol2vol` resamples as if the
> node position were an absolute moving-voxel index (the identity test above
> misplaces the output), so the absolute reading is the only one consistent
> with the rest of the tool; a developer should confirm. The effect on real
> (non-identity, FEM) morphs was not measured; the reproducer is synthetic.
