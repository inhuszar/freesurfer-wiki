# MRIcubicSampleVolumeFrame — boundary-limited stencil load but full-range accumulation reads uninitialised stack

> [!bug] Synopsis
> `MRIcubicSampleVolumeFrame` in `utils/mri.cpp` is the
> multi-frame companion of `MRIcubicSampleVolume` and is the
> primitive invoked by `MRIresample` when
> `resample_type == SAMPLE_CUBIC`. It declares an uninitialised
> `double vv[4][4][4]` on the stack, fills the stencil with a
> boundary-limited loop that only writes cells whose underlying
> voxel exists in the source volume, and then accumulates over
> the **full** `0..3` × `0..3` × `0..3` range. At any sampling
> point within one voxel of a face, edge, or corner of the
> source volume, one or more cells of `vv` are never written,
> and the accumulator reads garbage stack bytes through them.
> The resulting interpolated value at boundary voxels is
> non-deterministic: it depends on whatever happened to be on
> the stack before the function was called.

## Affected Artefacts

- **Tool(s):** every tool that routes through `MRIresample` with
  `resample_type == SAMPLE_CUBIC` — primarily [[mri_convert]]
  (via `--resample_type cubic`) and [[mri_vol2vol]] (via the
  same flag on a multi-frame input). The in-tree call site is
  at
  [`utils/mri.cpp:12240`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L12240).
- **Pipeline stage(s):** _N/A_ for default [[recon-all]]. The
  standard recon-all chain uses `SAMPLE_TRILINEAR`; this defect
  appears only on user-opted `SAMPLE_CUBIC` paths.
- **FreeSurfer version(s):** confirmed in `8.2.0` at commit
  `d932c45b79`.
- **Platforms:** all. The precise garbage value depends on the
  C compiler and on whatever frame left bytes on the stack
  before the call, so the numerical output is build- and
  invocation-dependent.
- **Triggering configuration:** any sample point within one
  voxel of the source-volume boundary (i.e., any of `ix_low,
  iy_low, iz_low` equal to `0` or to `width-1 / height-1 /
  depth-1`). The early-return at
  [`utils/mri.cpp:10470`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L10470)
  short-circuits exact-integer coordinates; any non-integer
  sample within a voxel of the wall hits the defect.

## Detailed Description

The function allocates a 4×4×4 neighbour stencil on the stack:

```cpp
double val, xx, yy, zz, fx, fy, fz, vv[4][4][4];
```

C/C++ do not zero-initialise local `double[4][4][4]`, so every
cell of `vv` starts with indeterminate bytes from whatever was
last on the stack.

The stencil-loading loop is boundary-limited — it skips cells
whose voxel is outside the volume:

```cpp
for (iz = MAX(0, 1 - iz_low); iz < MIN(4, depth + 1 - iz_low); iz++) {
  for (iy = MAX(0, 1 - iy_low); iy < MIN(4, height + 1 - iy_low); iy++) {
    for (ix = MAX(0, 1 - ix_low); ix < MIN(4, width + 1 - ix_low); ix++) {
      switch (mri->type) {
        case MRI_UCHAR:
          vv[ix][iy][iz] = (double)MRIseq_vox(mri, ix_low - 1 + ix, iy_low - 1 + iy, iz_low - 1 + iz, frame);
          break;
        /* ... other types ... */
      }
    }
  }
}
```

For an interior voxel the bounds resolve to `iz,iy,ix ∈ [0, 3]`
so all 64 cells are loaded. For a boundary voxel the bounds
tighten and some cells of `vv` remain unwritten.

The accumulation loop does **not** respect those bounds —
it iterates the full cube:

```cpp
val = 0;
for (iz = 0; iz <= 3; iz++) {
  fz = MRIcubicCoeff(zz, iz);
  for (iy = 0; iy <= 3; iy++) {
    fy = MRIcubicCoeff(yy, iy);
    for (ix = 0; ix <= 3; ix++) {
      fx = MRIcubicCoeff(xx, ix);
      val += (double)(vv[ix][iy][iz] * fx * fy * fz);     // ← reads unloaded cells
    }
  }
}
*pval = val / 8.;
```

For every cell that the loading loop skipped, `vv[ix][iy][iz]`
holds whatever garbage the previous stack frame left there.
Multiplying by the cubic kernel coefficients (finite) and
summing produces a finite but meaningless contribution — the
reported intensity at boundary voxels is non-deterministic.

### Expected Behaviour

At boundary voxels the function should either (a) initialise
unfilled cells of `vv` to a defined value — typically `0`, to
match the zero-padded border semantics implied by the
`MRIindexNotInVolume` check — or (b) restrict the accumulation
to the same bounds as the loading loop, exactly as the sibling
`MRIcubicSampleVolume` does.

### Observed Behaviour

At any sampling point within one voxel of the boundary, the
returned intensity is the correct inner part of the cubic
interpolation **plus** a non-deterministic contribution from
whatever garbage happens to live on the stack at the positions
of the unloaded cells. Under a debug build the garbage often
looks small and the defect is masked; under optimised builds,
under AddressSanitizer, or after the caller happens to leave
large doubles on the stack (for example, during a busy
resampling loop), the boundary intensities can vary widely
between runs.

The same code pattern in the sibling `MRIcubicSampleVolume`
(see [[00018]]) avoids this UB by matching the accumulation
bounds to the loading bounds.

## Root Cause

When the two routines diverged, the author tightened only the
load loop's bounds, leaving the accumulation loop iterating the
full `0..3`. The separable cubic kernel's zero-padded boundary
evaluation requires either (a) zero-fill the unwritten cells or
(b) skip them in the accumulation; neither was done. C's
non-initialising default for local arrays means the unwritten
cells surface the stack's prior contents.

## Impact

- Any `mri_convert` / `mri_vol2vol` run with `--resample_type
  cubic` produces non-deterministic intensities at the output
  volume's boundary face/edge/corner voxels. The deviation is
  bounded in magnitude by the four cubic coefficients (maxing
  out around `|f| · stack_garbage`) but its sign and scale are
  unpredictable.
- When the source and destination volumes are both large 256³
  conformed volumes, only the outer shell of voxels is
  affected — a thin layer that is typically masked out of
  downstream analysis. When the user crops the output, or when
  both volumes are small, the affected fraction grows.
- AddressSanitizer, MemorySanitizer, and Valgrind will report
  the defect as "use of uninitialised value". Under optimising
  compilers the behaviour is formally UB and may become more
  pathological over time as compilers exploit the UB.
- Standard [[recon-all]] is unaffected — its resampling paths
  use `SAMPLE_TRILINEAR`.

## Recommended Fix

Two equivalent corrections; pick one.

**A. Zero-initialise the stencil up-front** (preserves the
current zero-padded boundary semantics explicitly):

```diff
-  double val, xx, yy, zz, fx, fy, fz, vv[4][4][4];
+  double val, xx, yy, zz, fx, fy, fz, vv[4][4][4] = {{{0}}};
```

**B. Tighten the accumulation bounds to match the load**
(mirrors the sibling `MRIcubicSampleVolume`):

```diff
   val = 0;
-  for (iz = 0; iz <= 3; iz++) {
+  for (iz = MAX(0, 1 - iz_low); iz < MIN(4, depth + 1 - iz_low); iz++) {
     fz = MRIcubicCoeff(zz, iz);
-    for (iy = 0; iy <= 3; iy++) {
+    for (iy = MAX(0, 1 - iy_low); iy < MIN(4, height + 1 - iy_low); iy++) {
       fy = MRIcubicCoeff(yy, iy);
-      for (ix = 0; ix <= 3; ix++) {
+      for (ix = MAX(0, 1 - ix_low); ix < MIN(4, width + 1 - ix_low); ix++) {
         fx = MRIcubicCoeff(xx, ix);
         val += (double)(vv[ix][iy][iz] * fx * fy * fz);
       }
     }
   }
```

Both patches eliminate the uninitialised-read. (A) produces a
zero-padded boundary exactly as the name `MRIcubicSampleVolume`
implies, and matches the `MRIgradCubicInterp` gradient routine
at
[`utils/mri.cpp:10432–10438`](https://github.com/freesurfer/freesurfer/blob/v8.2.0/utils/mri.cpp#L10432-L10438)
which _also_ loads with boundary-limited bounds, iterates
full range for accumulation — meaning `MRIgradCubicInterp`
has the **same uninitialised-read defect** and should be
patched the same way; see the related gap below. (B) converges
the two sibling routines on identical boundary treatment and
is the minimal-semantic-change fix.

### Alternative Fixes Considered

Initialise only the cells that would be touched but not
loaded, immediately before the accumulate. Equivalent to (A)
in effect; marginally slower but still O(64) per call.

## Workarounds (If Any)

Pass `--resample_type trilin` or `--resample_type cubic_bspline`
until the fix lands. Both paths avoid `MRIcubicSampleVolumeFrame`.

> [!gap] Stack-contents variability
> The practical magnitude of the corruption at boundary voxels
> depends on whatever was previously on the stack. In tight
> resampling loops the same garbage tends to recur, which can
> produce visually coherent (and therefore hard-to-spot)
> distortions. A reproducer that forces known stack contents
> before the call (e.g., a manual caller that fills
> `double[1024]` with a sentinel) would sharpen the bite.
