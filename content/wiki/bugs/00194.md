# [severity-2] [bug-00194] `mri_ms_fitparms` — echo-averaging sets `register_mat` from the wrong volume index

> [!bug] Synopsis
> When [[mri_ms_fitparms]] is given multi-echo FLASH input (different TEs), it
> first averages the echoes within each (TR, flip-angle) group. For each
> averaged group it (re)computes the group's voxel→RAS transform with
> `mri_avg->register_mat = MRIgetVoxelToRasXform(mri_all_flash[nvolumes])`,
> where `nvolumes` is the **output group counter**, not the source volume
> index `i`. After the first group, `nvolumes < i`, so the averaged volume
> inherits an **earlier input volume's** geometry. This feeds the per-volume
> `vox2ras[j]`/`ras2vox[j]` used to sample each flip-angle volume into the
> common fit frame, so the fitted `T1.mgz`/`PD.mgz` are mis-sampled — **but
> only when the input flip-angle volumes actually have different header
> vox2ras**. For the standard co-prescribed multi-flip protocol (all
> acquisitions on an identical grid) every `MRIgetVoxelToRasXform` is the
> same matrix and the bug is silent. Hence latent under typical conditions.

## Affected Artefacts

- **Tool(s):** [[mri_ms_fitparms]]
- **Pipeline stage(s):** _N/A_ — standalone tool (multi-flip/echo FLASH T1/PD mapping)
- **FreeSurfer version(s):** confirmed in `$FREESURFER_VERSION`

  (`average_volumes_with_different_echo_times`, reached when no outside

  (`average_volumes_with_different_echo_times_and_set_Mreg`) carry the same

## Detailed Description

`mri_ms_fitparms` fits FLASH tissue parameters across multiple flip-angle
(and optionally multi-echo) acquisitions. Before fitting, when the input
contains multiple echoes (TEs differ), it averages the echoes that share a
(TR, flip-angle) using `PARAMETERS_MATCH`, producing one averaged volume per
flip-angle group. Each averaged volume needs a voxel→RAS transform
(`register_mat`) because the fit samples every flip-angle volume into a
common reference frame.

The averaged volume `mri_avg` is `MRIcopy`'d from source volume `i` (the first
member of the group). Its `register_mat` must therefore be **volume `i`'s**
voxel→RAS transform. The original, correct idiom for this is in `main()`:

```c
mri_flash[nvolumes]->register_mat = MRIgetVoxelToRasXform(mri_flash[nvolumes]);
```

— the field index and the source-volume index are the same. The averaging
loop copied this idiom into a context where `nvolumes` is the **output group
counter**, while the source volume is `i`. The two indices diverge after the
first group.

### Why `register_mat` ends up wrong (and why the assignment is load-bearing)

`MRIcopy(mri_all_flash[i], NULL)` does **not** propagate `register_mat` to a
freshly-allocated destination: `MRIcopyHeader`'s
`MatrixCopy(src->register_mat, dst->register_mat)` discards the return value,
so a NULL destination field stays NULL (this is the mechanism documented in
[[00016]]). Therefore the explicit `mri_avg->register_mat = …` line is the
**only** thing that sets the averaged volume's transform — and it uses the
wrong index.

For two flip angles (5°, 30°), each with two echoes, input order
`5e1, 5e2, 30e1, 30e2`:

- **Group 0 (5°):** `i = 0`, `nvolumes = 0` → `register_mat` from
  `mri_all_flash[0]` — correct by coincidence (indices equal).
- **Group 1 (30°):** `i = 2`, `nvolumes = 1` → `register_mat` from
  `mri_all_flash[1]` (the 5° second echo), **not** the 30° volume.

So the averaged 30° volume holds 30° data but carries the 5° scan's
voxel→RAS transform.

### Expected Behaviour

`mri_avg->register_mat = MRIgetVoxelToRasXform(mri_all_flash[i])` — the
averaged group's transform should be that of the source volume it was copied
from.

### Observed Behaviour

The averaged group's transform is taken from `mri_all_flash[nvolumes]`, an
earlier input volume. In the fit, `vox2ras[j] = MatrixCopy(mri_flash[j]->register_mat, NULL)`
and `ras2vox[j] = MatrixInverse(vox2ras[j], NULL)` are then built from this
transform and used to map each flip-angle volume into the common frame. If
the wrong transform differs from the correct one, volume `j` is sampled at the
wrong coordinates → mis-registered intensities enter the T1/PD grid-search →
wrong `T1.mgz`/`PD.mgz` (and `sse.mgz`, `flash*.mgz`).

If all input volumes share the same header vox2ras (the usual case), the
wrong index selects a geometrically identical transform and the output is
unaffected.

## Root Cause

The `main()` idiom `X[k]->register_mat = MRIgetVoxelToRasXform(X[k])` was
copy-pasted into the averaging loop, where the destination is `mri_avg`
(a copy of `mri_all_flash[i]`) but the literal index `nvolumes` was kept.
`nvolumes` counts output groups, not input volumes, so for every group after
the first it indexes an earlier, unrelated input volume. The `register_mat`
of the averaged group therefore describes the wrong volume's scanner
geometry. Combined with [[00016]] (`MRIcopy` does not carry `register_mat`
to fresh destinations), this assignment is the sole source of the field, so
the error is not masked by a correct copy.

## Impact

- **Latent in standard use.** Multi-flip(-echo) FLASH T1/PD mapping is
  normally acquired with one identical geometry prescription across flip
  angles, so every input volume has the same `MRIgetVoxelToRasXform`. The
  wrong index then selects an identical matrix and the fitted maps are
  unaffected. Patient motion between scans does **not** change the header
  geometry (it changes the data, not the prescribed voxel→RAS), so it does
  not expose the bug; motion is handled separately via `M_reg`.
- **Wrong output only on geometry-heterogeneous input.** If the flip-angle
  acquisitions were prescribed with different FOV/orientation, or one volume
  was resampled onto a different grid, the averaged group inherits the wrong
  vox2ras and that flip-angle volume is mis-sampled into the fit frame,
  silently biasing `T1.mgz`/`PD.mgz`.
- **Severity 2 justification.** The wrong value is *computed* on every
  multi-echo run, but it only *changes output* on inputs that ordinary
  callers do not exercise (differing per-volume header geometry). Per the
  schema this is "latent under typical conditions," i.e. severity 2 — not a
  flag-gated mode (it is not gated by a flag) and not a default-path wrong
  output (typical inputs are unaffected).

## Recommended Fix

Use the source index `i` (or `mri_avg` itself) at both sites:

```diff
-    mri_avg->register_mat = MRIgetVoxelToRasXform(mri_all_flash[nvolumes]);
+    mri_avg->register_mat = MRIgetVoxelToRasXform(mri_all_flash[i]);
```

(Equivalently `MRIgetVoxelToRasXform(mri_avg)`, since `mri_avg` is a copy of
`mri_all_flash[i]` and the averaging does not alter geometry.) Apply at both
`:2804` and `:2882`.

A regression test should build two flip-angle groups with deliberately
different header vox2ras and assert the averaged group's `register_mat`
equals the source group's, not an earlier group's.

## Workarounds (If Any)

Ensure all input FLASH volumes share an identical voxel→RAS header (same FOV
prescription / grid) — which is already the norm — so the wrong index selects
an identical transform. There is no flag to disable the echo-averaging
recompute.
